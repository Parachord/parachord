# Parachord - Claude Code Guide

The always-loaded guide: architecture, where to read before changing an area, the invariants that apply to every change, and how releases and contributor communication work. Subsystem detail is in `docs/architecture/` (index below).

## Architecture

**app.js is a GENERATED artifact** — esbuild bundles `src/renderer/app.js` (the source of truth, same content, classic IIFE script, no transforms: target esnext, no minify) into `app.js` + `app.js.map` (both gitignored). Built by `pretest`/`prestart`/`predev`/`prebuild` hooks (`node scripts/build-renderer.js`; dev watch: `npm run dev:renderer`). Never hand-edit root `app.js` — edit `src/renderer/app.js`. CLAUDE.md's `app.js L####` line refs refer to `src/renderer/app.js` (identical content). Source-marker tests read `src/renderer/app.js`; tests that read the generated `app.js` rely on `pretest` having built it. **The component split has begun (Track 2b):** the leaf UI atoms (Tooltip/FixedTooltip, ParachordWordmark, PlaybackProgress) live in `src/renderer/components/ui-atoms.js`, and the SERVICE_LOGO*/ResolverIcon badge kit in `src/renderer/components/brand-logos.js` (re-exported by ui-atoms; a brand's logo goes there, a UI glyph in `icons.js`), required by `src/renderer/app.js` (`const { ... } = require('./components/ui-atoms')`). `src/renderer/components/**` is in the ESLint **strict tier**. Extracted component modules use `React.useState`-style qualified hooks, never bare destructured ones — app.js's module-scope `const { useState, ... } = React` destructure masks bare hooks from lint in the legacy file, and in the esbuild bundle they resolve **by accident** (the `__commonJS` module wrappers close over the entry IIFE's scope, where app.js's destructure lives), so a bare hook is invisible until the module is required under plain Node/jest. `no-undef` caught FixedTooltip's bare `useState`/`useRef` on the move (hygiene, not a would-be crash — the bundle would have resolved it; `tests/renderer/component-render-smoke.test.js` renders every export under Node so the class is caught there regardless). Presentational components are props-driven; they must not grow app-state references — state-domain hooks are the later phase.

**ESM-only dependencies in a CommonJS main process.** `chokidar` (5), `electron-store` (12) and `music-metadata` (12) ship no CommonJS build. `main.js` and `local-files/` still `require()` them: Electron 44's Node (24.21) supports `require(esm)` for graphs without top-level await, and that is what runs in the app. Two consequences: `require('electron-store')` is the module namespace, so the class is `.default` (the bare require gave "Store is not a constructor"); and jest needs two things to follow — the `module-sync` export condition in `jest.config.js` (music-metadata publishes only `import`/`module-sync`, so without it the package is "not found") and `--experimental-vm-modules` on the Node that runs jest (the `test` scripts pass it), which jest's own require(esm) requires on Node 24.9+. The test workflow runs Node 24 for that reason; the build workflow stays on 22 because electron-builder never loads these. Don't "fix" a future ESM-only bump by adding a Babel transform for node_modules; this path is the supported one. `dotenv` 17+ logs an "injecting env" tip on `config()`, so every call passes `{ quiet: true }`. (2026-10-18, parachord deps PR.)

No JSX — uses `React.createElement()` exclusively. Styling via Tailwind CSS classes + inline styles with CSS variables (`var(--accent-primary)`, `var(--card-bg)`, etc.).

Main component: `const Parachord = () => { ... }` (L4951), rendered via `ReactDOM.createRoot`.

## After you change how a feature works, update its docs

**A material change to how a feature works updates its documentation in the same PR.** Before calling the change done, search the docs for the feature and correct anything it makes untrue or incomplete:

- the area's file in `docs/architecture/`, from the table above;
- `docs/features/`;
- `docs/protocol-schema.md`, which is public and read by people building integrations;
- `README.md`;
- this file, if a rule or invariant here changes.

Then say in the PR which docs you changed, or that none needed changing. A doc that still describes the old behavior is worse than none, because the next person or agent works from it.

A bug fix that only restores documented behavior needs no doc change. `docs/plans/` holds historical records, so leave those as written. Release notes are separate (see Releasing).

## Invariants that apply everywhere

One line each; the linked doc has the reasons and the incidents behind them.

- **Use what exists before writing something new.** Before writing a component, hook, helper or module, look for one that already does the job: `src/renderer/components/` (the "comes from" list under Renderer patterns), `src/renderer/lib/`, `src/renderer/hooks/`, `sync-engine/`, `main-process/`. If one almost fits, extend it (a prop, a variant, an option) rather than writing a second copy; write a new one only when nothing fits, and then make it the shared one. Say in the PR which existing pieces you used, or why none fit. Most of the design-audit and #1451 work was undoing copies that started as "just this once". (UI specifics: "Design system: don't let it drift" below.)
- **Route by the plugin registry, never by service name.** "Given a provider URL or entity, do X" goes through `resolver-loader.js` (`findResolverForUrl`, `getUrlType`, `lookupPlaylist`, ...), so a new service is a `.axe` drop-in. Check a capability exists before using it. ([plugins.md](docs/architecture/plugins.md))
- **Every plug-in's settings are one layout, built from shared parts.** The plug-in settings dialog draws every plug-in with the same components: `pluginSwitchState` (`lib/plugin-switch.js`) in a `SettingRow` for on/off, `AccountRow` for signing in and out, `Disclosure` for Advanced, `SettingRow` and the field set for settings, and the plug-in's manifest for its text and capabilities. In one order: on/off, then the account, then the keys it signs in with (a client ID and secret: open, not under Advanced, until they're saved; `Disclosure`'s `alwaysOpen`), then what needs the sign-in (library sync, scrobbling, loves, startup), then other settings, Advanced last; flat rows divided by lines, never a grey card with its own heading (Library Sync said "Sign in above" over an account drawn below it, 2026-11-17). The top switch reads "Enable X". A capability gets its own switch, a nested `SettingRow` under it with a small switch, only when someone might want it off while the rest stays on, and turning it off leaves the rest working: Play from, Use metadata from, Use recommendations from (#1505), and the existing Scrobble to, Library sync and Push loves. What needs a sign-in sits under Enable too, as `NestedSettings` (Last.fm's and ListenBrainz's Scrobbling: the sign-in, its switch and loved tracks), so Enable can be on while signed out and its line claims only what works without the sign-in. Search never gets one (it is what Enable means, and playing needs it), and neither does a plug-in's only job (Wikipedia's artist info is its Enable). Each such choice is a saved list of ids that the code paths filter by, never a new per-service branch. A plug-in that draws its own panel (`renderSettings`, Plex) builds it only from `ctx.components`, the same shared parts ([plugins.md](docs/architecture/plugins.md)). Never a section for one named plug-in, a hand-built account header, Connect button or accordion, or a second on/off control: a new need goes into the shared part, so every plug-in gets it. A plug-in's manifest text follows the UI copy rules (`tests/plugins/manifest-copy.test.js`), and `tests/renderer/plugin-settings-consistency.test.js` ratchets what's left of the old per-plug-in sections down to 0. ([plugin settings audit](docs/plans/2026-11-17-plugin-settings-audit.md), #1498)
- **Source selection is validate, then sort.** A result must match artist AND title to reach `MIN_CONFIDENCE_THRESHOLD` (0.6); every resolution path drops sub-floor results before they touch `track.sources`, and a path that plays a named track picks with `pickTrackMatch` (`sync-providers/track-match.js`), never the first search result. `sync-providers/confidence-scoring.js` is canonical and must stay byte-equivalent with the Kotlin copies. ([playback.md](docs/architecture/playback.md))
- **No resolver holds a row.** Every `resolve()` runs under `RESOLVE_BUDGET_MS` (`resolver-limiter.js`), and a resolver whose service refused or failed throws, never returns `[]`/`null`: an empty answer is cached as a miss. ([playback.md](docs/architecture/playback.md) "No resolver holds a row")
- **Cross-cutting metadata lives on the source record.** Read ISRC through `window.pickTrackIsrc(track)`; read stream quality through `window.pickStreamQuality(track, playingResolverId)`, keyed on the resolver actually playing. ([playback.md](docs/architecture/playback.md))
- **One album-art pipeline.** Every cover comes from `getAlbumArt` (or `getTrackArt`); no surface-specific shortcuts, never cache a URL that was not requested, and a cover that fails to load is reported through `window.reportBrokenAlbumArt` rather than only hidden. ([album-art.md](docs/architecture/album-art.md))
- **Playlist saves keep every sync field.** Build save payloads by spreading the whole playlist (`window.buildPlaylistSavePayload`), never by listing fields. Create remote playlists only through `sync:create-playlist`, always passing `localPlaylistId`. The push loops' `syncedFrom` guard is provider-scoped. ([sync.md](docs/architecture/sync.md))
- **Every persisted key must be in `ALLOWED_STORE_KEYS`** (`main-process/ipc/store.js`), or the write is silently refused. `local_playlists`, `sync_playlist_state` and every `cache_*` key live in their own files under `userData/store/`. Only the 5-minute timer reliably persists most big caches; the track-sources cache also saves soon after resolutions, so every write to `trackSourcesCache` calls `markTrackSourcesDirty()` first. ([state-persistence.md](docs/architecture/state-persistence.md))
- **Regenerate `package-lock.json` only with the npm that ships with `build.yml`'s Node** (Node 22 today, so `npx npm@10.9.9 install --package-lock-only --ignore-scripts`, then `npx npm@10.9.9 ci --dry-run`; check the version again when `build.yml`'s Node changes). A lock regenerated with npm 11+ is restructured in a way npm 10 rejects, and every Build platform then fails at `npm ci` with "`npm ci` can only install packages when your package.json and package-lock.json are in sync" followed by `Missing: <package>@<version> from lock file` lines. The jest job runs Node 24 (npm 11), which accepts such a lock, so only the four Build jobs catch it.
- **`plugins-src/` is the plugin source of truth.** Never hand-edit `plugins/*.axe` or the generated fallback module (`src/renderer/lib/fallback-resolvers.generated.js`) — all gitignored; bump `manifest.version` when a plugin changes, or marketplace clients never re-download it. `build-axes.js` also syncs the one TRACKED writer output left (the `marketplace-manifest.json` versions), and a PR must commit it; a check that runs after a hook ran the writer cannot catch a missing commit. ([plugins.md](docs/architecture/plugins.md))
- **A plugin that needs a newer app declares `manifest.minAppVersion`** (per platform: `desktop`, `android`, `ios`), and until apps older than the field are rare it still detects the host feature and falls back. ([plugins.md](docs/architecture/plugins.md))
- **`src/renderer/app.js` is the renderer source**; root `app.js` is generated (see Architecture).
- **The local-files scanner must never read an unreadable folder as "everything deleted"**: keep the three guards in `scanner.scanFolder`. ([local-files.md](docs/architecture/local-files.md))
- **Every URL fetched on behalf of a deep link goes through the SSRF guard**, and play commands tear down spinoff/listen-along and clear the queue before starting. ([protocol.md](docs/architecture/protocol.md))
- **A DJ tool needs its registry entry, its `executeDjTool` case, and its context method**, or it is advertised but unimplemented. ([ai-chat.md](docs/architecture/ai-chat.md))
- **The renderer never talks to Discord**; the main process owns the socket, and only https art without credential-shaped query parameters is sent. ([now-playing.md](docs/architecture/now-playing.md))
- **Redirect URIs use the bound auth-server port**, never a hard-coded 8888. ([platform.md](docs/architecture/platform.md))
- **Widevine playback is shared infrastructure, never per-resolver engine code.** New stream services implement the plugin-mediated pair (#1356 M4) on the widevine bridge's plugin path (`main-process/widevine-bridge.js`) — `getPlaybackManifest(track, config)` + `relayLicense(challengeB64, context)` implemented in the `.axe` itself, with the host opening the licence session under the same gates via `widevine:open-session`; a supplier may drop key groups it was refused from its own manifests — the engine never sees the group label; quality stays GLOBAL and codec-neutral — tiers are bandwidth corridors (saver ≤100k / standard ≤200k / high ≤500k / max = no ceiling) over the full playable roster; adaptive caps at the corridor ceiling and always RESETS restrictions on any tier switch (Shaka treats an empty restrictions object as a merge no-op). `manifest.enableAudioGroups` stays false and `preferredAudioCodecs` stays empty everywhere: Shaka's ABR candidate set is ONE AdaptationSet — with group ids (Amazon's sets are family-pure) the set is a single family and adaptive at Max can never reach FLAC (#1243); a codec list collapses the roster at parse and confines the criteria forever (the vendor collapses the manifest / confines ABR via it). A manual selection narrows the choice criteria to the selected family — only `applyConfig`'s re-anchor repairs it. Never per-resolver quality vocabularies. Spatial/Atmos is one global opt-in (`playback_spatial`) — E-AC-3 JOC only, probe-gated, picked within the spatial rungs and always locked (standard/saver ceilings win over the spatial preference); AC-4/MPEG-H have no Chromium decoder on any build and stay excluded (the vendor collapses the manifest / confines ABR via it). Leaving an Amazon track stops/unloads the engine, never only pauses. ([amazon-music.md](docs/architecture/amazon-music.md), [plugins.md](docs/architecture/plugins.md))
- **A resolver the account's plan can't play stays active but leaves playback.** Amazon Prime and a signed-out Apple Music today, any such plan tomorrow: one map (`src/renderer/lib/playback-limits.js`) blocks it, and everything about playing (selection, source icons, the priority numbers) reads `playbackResolvers`, never `activeResolvers`, while search, album search, artist photos and links keep asking active resolvers. A plugin refuses such a play with `reason: 'plan-ineligible'`, never a plain `false`. The user's own "Play from X" switched off (`playback_off_resolvers`, #1505) joins the same list (`notPlayingResolverIds`), so a plug-in kept for search, covers and links reads exactly like a plan-blocked one. ([playback.md](docs/architecture/playback.md) "Playback limits", [plugins.md](docs/architecture/plugins.md))

## Renderer patterns

Summary; the full text, with the incidents behind each rule, is in [renderer-patterns.md](docs/architecture/renderer-patterns.md).

- **Track ids come from `trackSlug` / `slug`** (`src/renderer/lib/track-slug.js`). An ASCII-only strip collapses every non-Latin track on a release to one id. Collection ids (`generateTrackId` / `generateAlbumId` / `generateArtistId`) come from one formula in `sync-engine/collection-id.js`, shared with the sync providers; never a copy of it ("Collection ids" in [sync.md](docs/architecture/sync.md), #1401).
- **Every setState is a full-app render; coalesce bursts.** Per-item writes during a scroll go through `window.createCoalescedUpdater` (`queueTrackSources`, the art writers); hover prefetch waits for a 250ms dwell (`hoverDwell` in `lib/hover-dwell.js`, or a shared card's `onHoverPrefetch`); header collapse goes through `window.headerCollapseDecision`; derived lists built from big state are component-scope `useMemo`s.
- **A click changes the view before its MusicBrainz lookup**, and only what the user asked for takes the foreground lane: speculative prefetches, covers (`getAlbumArt` defaults to background), bios, photos and refreshes use the background lane (`mbBackground: true`), because every MusicBrainz request starts at most once per 1.1s (two in flight, one always kept for the foreground).
- **Pages are `React.memo`'d modules fed stable props** (Collection, Home, Playlists, playlist view (and its loading state, `PlaylistViewLoading`), artist page, Search, Fresh Drops, Recommendations, Concerts, Pop of the Tops, Critical Darlings, History, a friend's history, Settings; every page and panel is its own module now, #1451, and a test that reads a page's markup reads `tests/helpers/renderer-source.js`'s `appWithPages()`). Plain functions go through `useStableHandlers`; `tests/renderer/page-memo.test.js` fails on an unstable prop; a module must load under plain Node (`globalThis`, not `window`, at module scope).
- **Extracted modules use `React.useState`-style qualified hooks**, never bare destructured ones.
- **In the resolver queues, a play click goes first, track resolution next, covers last** (`config.__lane` → `laneRunOptions`; see "Resolver queue lanes" in [playback.md](docs/architecture/playback.md)).
- **Use refs in async callbacks** (`volumeRef`, `isPlayingRef`, `currentTrackRef`, ...) to avoid stale closures.
- **`showToast(message, type, action, options)`**: `options.persistent`, `options.duration` (ms), and `action: { label, onClick }`.
- **Page heroes come from `PageHero`** (`src/renderer/components/page-hero.js`): the coloured banner at the top of Collection, Playlists, History (and a friend's), Recommendations, Pop of the Tops, Fresh Drops, Critical Darlings and Concerts. 320px, collapsing to an 80px bar; the page's gradient and pattern come from `PAGE_COLORS` (`hero`, `pattern`, `patternOpacity`); the title is written in words (CSS draws the capitals). A page passes what goes under the title (`expanded`) and after it in the bar (`collapsedContent`). The artist page's photo hero and the playlist view's blurred cover are different designs.
- **Art hover actions come from `ArtOverlay`** (`src/renderer/components/card-art.js`, shown by `useReveal` on hover or keyboard focus): Add to playlist, Play, Add to queue over a cover, on every card and on the album and playlist pages' covers. **Release-type colours come from `lib/release-types.js`**: the album page's badge, the cards' on-art badge and the type filter chips.
- **A plug-in's account comes from `AccountRow`; an Advanced section from `Disclosure`** (`src/renderer/components/account-row.js`, `disclosure.js`): "<Service> account" with a status line and one button, "Sign in" in the service's colour (text colour by `readableTextOn`) or "Sign out"; and the one open-and-close section (a text `Button` with a turning chevron, `aria-expanded`, over a grey panel; the caller owns `open`). The plug-in dialog had six sign-in designs and five hand-built accordions (#1498).
- **A plug-in's extra settings sections come from `plugin-extras.js`** (`src/renderer/components/plugin-extras.js`): `ServiceAccount`, `ClientKeys`, `UsernameAccount`, `AdvancedKeys`, `LibrarySync`, `StartupRow`, `InstallCallout`, `WatchFolders`, each chosen by a capability or manifest field (the list is [plugins.md](docs/architecture/plugins.md) "Settings"), never by the plug-in's id; an account the app signs in to itself reaches the dialog as `hostAccounts[pluginId]` from app.js. A new need is a manifest field and a section here, never a branch on an id (#1498).
- **A plug-in's on/off switch comes from `pluginSwitchState`** (`src/renderer/lib/plugin-switch.js`): the one control that turns a plug-in on in its settings dialog, in a `SettingRow`. It keeps what "on" means for each kind of plug-in (music: the active list; AI and concerts: a key, disabled with "Add your … first" until there is one; no-key AI: `enabled: true`; the rest: enabled or set up). The footer is Remove + Done and never enables anything (#1498).
- **A Settings section comes from `SettingsSection`** (`src/renderer/components/settings-cards.js`): the card, the small-capitals heading and an optional line under it. Every section of Settings › General uses it (there was a copy per section, and Playback Quality had drifted to a grey card).
- **Section titles come from `SectionHeader`** (`src/renderer/components/section-header.js`, Home's style): a heading over a row or grid of content never carries its own font or link styles. Heroes, dialog titles and the small uppercase group labels are different elements.
- **Track rows come from `TrackRow`** (`src/renderer/components/track-lists.js`): every page list (History, a friend's history, Recommendations, Charts, the playlist page, Collection, Search, an album's tracklist) renders it, never its own copy of the row; extra columns go in `cells`. Its source column is `TrackSources` / `SourceIconButton`. A local file's Local Files icon is one more source, ordered by the user's source order like the rest.
- **Source icons come from `visibleSources`** (`src/renderer/lib/visible-sources.js`): a row's service icons, order and dimming are one rule (real sources, `playbackResolvers` only, `resolverOrder`), never a per-list copy.
- **Track lengths come from `trackDurationLabel`** (`src/renderer/lib/track-duration.js`): the track's own duration, else its best source's (same merge as `visibleSources`), else a blank cell, never "0:00".
- **A page's filter box and sticky bar come from `FilterBox` / `StickyBar`** (`src/renderer/components/filter-box.js`): the search icon that opens into "Filter…" (focused on open; an empty box closes on blur; ✕ or Escape empties and closes it), and the strip that stays at the top of a page's scroll area (`variant` 'filter' or 'header'). Twelve pages had their own copy of the box and eight their own bar.
- **Filter buttons come from `FilterChips`** (`src/renderer/components/filter-chips.js`, Home's source filter style): a row of pick-one chips never carries its own pill classes. An action chip (a search suggestion, an active location, with an optional ✕) is its `Chip`, never a hand-built pill; its ✕ is a button beside the chip's, never inside it.
- **A playlist link's "keep it updated or snapshot" question comes from `PlaylistUpdateDialog` / `UpdateModeChoice`** (`src/renderer/components/playlist-update-dialog.js`, on `Modal` and `RadioGroup`): every way of importing a playlist from a link asks it the same way. What each mode does: "Link imports" in [sync.md](docs/architecture/sync.md).
- **Status pills come from `Badge`** (`src/renderer/components/badge.js`): Hosted, AI, Shared and a playlist's sync services; a service's pill takes its plugin's `color`, never a palette class or emoji.
- **Playlist cards come from `PlaylistCard`** (`src/renderer/components/playlist-card.js`): Home, the Playlists page, Search and Recommendations (service and weekly playlists). The art is the playlist's own cover over the mosaic of its tracks' covers (`allPlaylistCovers[id]`), or the playlist glyph; a saved playlist's actions are `playlistCardActions(playlist)` in app.js. Search's copy showed only a music note.
- **Album cards come from `AlbumCard`** (`src/renderer/components/album-card.js`, art parts in `card-art.js`): every album grid (Home, Collection, Search, Fresh Drops, Pop of the Tops, Recommendations, History's and a friend's top albums) is this inset card; its overlay actions come from app.js's `albumCardActions({ title, artist, id, getTracks })`, and its hover prefetch dwell is the card's own. ## Design system: don't let it drift

The 2026-11-13 design audit ([docs/plans/2026-11-13-design-audit.md](docs/plans/2026-11-13-design-audit.md)) found the drift that per-page styling produces:
- 7 primary-button colours, 16 text-input recipes, 6 dialog-title sizes, 5 empty-state templates, 152 hex colours
- dark-mode gaps
- about 130 clickable `div`s a keyboard can't reach
- one concept under five names

Each rule below exists because the audit found its absence. Read the audit's area section before restyling an area.

- **Reuse before you build** (the first invariant above, applied to UI). Before writing any UI element, look in `src/renderer/components/` for a shared one and use it. Existing shared ones include `Button`, `Modal`, `Menu`, `SectionHeader`, `FilterChips` / `Chip`, `OptionTile`, `ListRow`, `NavItem`, `PageHero`, the field set (`fields.js`), `EmptyState` / `ErrorState`, `Tooltip`, the card family and the skeletons. The Renderer patterns list above names each one's job.
  - If you'd otherwise write a second copy of something that already exists elsewhere (a button, dialog shell, menu, empty or error state, input, switch, spinner, icon), first extract it into a shared component under `src/renderer/components/`, then point both places at it. That's how `SectionHeader` (#1370) and `FilterChips` (#1371) were made.
  - Never restyle a shared component's output from a page; change the component.
  - A new shared component gets a "comes from X" line in the Renderer patterns list above and in `renderer-patterns.md`.
- **Colours come from the theme tokens** in `index.html`, so both themes work. The token list is in `docs/DESIGN_SYSTEM.md` "Colors".
  - Use the theme-token Tailwind classes (`text-ink-secondary`, `bg-surface-card`, `border-line`, `bg-accent-fill`, `bg-tint-danger`, ...; `tailwind.config.js`) or `var(--…)` in inline styles. Don't add hex values, Tailwind palette classes (`text-gray-500`, `bg-red-50`, `purple-600`, ...), or `isDark` / `effectiveTheme` ternaries (the count is 0; keep it there).
  - If no token fits, add one to `:root` and `.dark` together (and to `tailwind.config.js` if classes will use it).
  - White text never sits on `var(--accent-primary)` (it's `#a78bfa` in dark mode): fills with white text use `--accent-fill` / `--on-accent` (`bg-accent-fill text-ink-on-accent`).
  - Status text uses `--text-success/-warning/-danger/-info`; white-text status fills use `--fill-*`; a status note's faint background and border use `--tint-*` / `--border-success/-warning/-info/-danger`. Never their own hex or `rgba()` values.
  - The accent is one value, `--accent-base`: every accent token is `color-mix()`ed from it. Never write a purple (or an `rgba()` of one) anywhere else.
  - A page's colour comes from `PAGE_COLORS` (`src/renderer/lib/page-colors.js`), which names `index.html`'s `--page-<id>` / `-fill` / `-hero` variables (Home's are the accent's); a service's from its plugin's `resolver.color`. Never a hard-coded copy.
  - A page's icon comes from `PAGE_ICONS` (`src/renderer/lib/page-icons.js`, keyed like `PAGE_COLORS`): the sidebar and What's New draw `Icons[PAGE_ICONS.<page>]`, never their own pick (`tests/renderer/page-icons.test.js`).
  - The playbar, queue drawer and AI panels are dark in both themes: they use `--surface-dark*`, never page tokens.
  - Black, white and grey come from role tokens too, never an `rgba()`: white on a coloured header or tile is `--on-color-*`; text, lines and fills on the dark surfaces are `--on-dark-*`; darkening over content is `--scrim-soft` / `--scrim` / `--scrim-strong`; shadows are by role (`--shadow-xs/sm/md/lg`, `--card-shadow`, `-tile`, `-popover`, `-panel`, `-dialog`, `-dialog-dark`, `-drawer`); text over a hero or photo uses `--hero-text-shadow*` / `--photo-text-shadow`. The list is DESIGN_SYSTEM.md "Neutral roles".
  - A brand's own colour (a logo's fills, Raycast's orange) lives in `brand-logos.js`; a page's in `--page-<id>`; an artist stand-in's palettes in `lib/artist-pattern.js`; release types' in `lib/release-types.js`. Those are the drift script's colour homes; anywhere else a colour is a token.
- **Stay on the scales.**
  - Type: 11 · 12 · 13 · 14 · 16 · 20 · 24 · 28 · 48px. Weights as numbers.
  - Spacing: the 4px scale. 10px is only for card padding.
  - Radius: 4 · 6 · 8 · 10 · 12 · 16 · full.
  - One 24px page gutter for hero, filter bar and content.
  - Motion: on the motion tokens (`--motion-fast` 150 / `-base` 200 / `-slow` 300 / `-deliberate` 400ms, `--ease-standard` / `-out` / `-in`; reduced motion zeroes them): Tailwind `transition-colors` etc. with `duration-fast/base/slow`, or `transition()` from `lib/motion.js` inline. Name the properties (transform, opacity, colours), never `transition-all`, a numbered `duration-300` or an inline string with its own times (design-drift's `rawTransitions`). One deliberate exception: the queue drawer's insert glow (`queue-track-insert`, 1s), which is the only "added to queue" signal since that toast went.
  - Section titles are `SectionHeader`. Filter buttons are `FilterChips`.
- **Interactive means `<button>` or `<a>`.** Never put `onClick` on a `div`, `span`, `li` or `img`.
  - Icon-only buttons get an `aria-label`.
  - Never set an inline `outline: 'none'`.
  - Focus rings show after keyboard use only: `lib/input-modality.js` marks `<html data-input="pointer">` while the last input was a click, and `index.html` hides every ring (outline, Tailwind ring, menu-item inset) then. Code that moves focus after a click (a dialog, a menu, a panel opening) made Chromium light the ring for mouse users. Draw a ring with `:focus-visible` (or Tailwind `focus-visible:`) and it follows this rule for free; never gate a ring on your own.
  - Hover actions also appear on keyboard focus, as Home's `useReveal` does.
  - Dialogs close on Escape, move focus in, and give it back on close.
  - No `alert()` / `confirm()` / `prompt()`: use `showToast` or a dialog.
  - Icons come from one shared set, not a pasted SVG path: `icons.js` (Lucide shapes, plus a few custom ones such as `Spinner`, `Spinoff`, `Playlist`, `PlayTop10`). Logos are not icons: a service's, a brand's or Parachord's own logo comes from `components/brand-logos.js` (`ResolverIcon`, `BrandMark`, `SERVICE_LOGOS`, `ParachordWordmark`). The drift script's `svgPaths` is 0: a pasted `<path>` anywhere else fails it.
- **Look before calling a UI change done.** Check it in light mode, in dark mode, and at the 1000px minimum window width (the content area is then 744px wide; Tailwind `md:`/`lg:` measure the window, not the content). Update its loading skeleton in the same PR (Renderer patterns above).
  - **Compare every variant of a data-driven surface side by side.** A surface that renders differently per item (each plug-in's settings dialog, each playlist type, Home's states) gets contact sheets of all its variants, light and dark: `npm run ui-sheets -- <recipe>` (`scripts/ui-contact-sheet.js`, against a dev app on a throwaway profile; add a recipe for a new surface). Attach them to the PR. Checking one variant is how the plug-in dialogs drifted into 23 layouts (docs/plans/2026-11-17-plugin-settings-audit.md).
  - **Check by task, not only by element.** For each job the surface does (turn something on, sign in, enter a key, save, remove), every variant does it with the same control in the same place. One job, one control. Token and component counts can't see two controls for one setting.
  - **A move is not a review.** A PR that moves UI code unchanged says "moved, not reviewed" and files what's visibly wrong as an issue, rather than carrying it silently. A smoke check (it opens, no errors) is not a design check, and the PR says which one was done.
- **Copy.**
  - Terms:
    - **plug-in**: what you install ("Plug-Ins" in Title Case; never "resolver" in UI text, whatever its type; code and docs may say plugin)
    - **service**: Spotify, Apple Music and so on
    - **source**: where a track plays from
    - also **Collection**, **Loves**, **Shuffleupagus**, **track**, **album**/**edition**, **sync**/**import**
  - Never in UI text: "resolver", ids, file extensions, raw `error.message`, or Settings paths that don't exist.
  - Sentence case everywhere except native menus, tabs, Settings section headings and page titles. Never type caps; use CSS `uppercase`.
  - "…" not "...".
  - Plurals go through one helper (`countOf`), never a hard-coded "tracks".
  - An error says what happened and what to do. A confirm button is named for its action and sits next to Cancel. Success is a toast, not a dialog.
- **The ratchet enforces this.** `tests/ci/design-drift.test.js` runs `scripts/design-drift.js` over `src/renderer/` and compares against `tests/ci/design-drift-baseline.json`.
  - It counts hex colours, coloured and neutral `rgb()`/`rgba()` values, palette classes, theme ternaries, clickable non-buttons, `outline: 'none'`, native dialogs, "...", pasted SVG paths, off-scale font sizes and radii, JS hover and focus handlers that change style, raw form controls outside `fields.js` (`inputCopies`), transitions off the motion tokens (`rawTransitions`), and buttons styled by hand instead of `Button` (`handBuiltButtons`; a shared component's own button doesn't count). It also flags CSS variables the renderer uses but `index.html` doesn't define.
  - It also counts hand-built copies of shared components: track rows (a `sourceRowState()` call outside `TrackRow`), "Play from" source buttons, spinners, "No …" empty states, pill buttons, sticky bars and page heroes. The audit counted colours but not copies, so pages kept their own rows and states while every colour in them was a token (2026-11-15).
  - It also counts branches on a plug-in's id (`serviceNameBranches`: `x.id === 'spotify'`, `resolverId !== 'applemusic'`), which break the registry invariant; and `tests/plugins/manifest-copy.test.js` fails on developer text in a plug-in's description or "needs" line, and on a capability with no label in `lib/capability-labels.js`. Both start from known lists that only shrink (#1498).
  - A count that rises fails: fix it with the shared component or token.
  - A count that falls fails until you lock it in with `npm run design-drift -- --write` and commit the baseline.
  - Raising the baseline is a last resort. The PR must say why no shared way existed.
- **`docs/DESIGN_SYSTEM.md` is the reference**: tokens, scales, colours, components ("Which component, when"), copy and animations, rewritten to match the code in the design audit. A PR that changes a token, scale or shared component updates it.

## Dialog Patterns

Each dialog's open state lives in `src/renderer/app.js` (a `show`/`open` boolean or a state object), and app.js renders the dialog conditionally; the dialog itself is a memo'd module in `src/renderer/components/` on the shared `Modal` (#1451), fed stable props like the pages.

- `confirmDialog`: simple OK dialog `{ show, type, title, message, onConfirm }`, rendered by `ConfirmModal` (`showConfirmDialog`)
- `syncDeleteDialog`: multi-action dialog `{ show, playlist }`, rendered by `SyncDeleteDialog` (`sync-delete-dialog.js`); the remote copies it offers to clean up come from `lib/playlist-mirrors.js`
- `amazonManageDialog`: promise-based sign-in dialog `{ show, onResolve, relaunching }`, rendered by `AmazonManageDialog` (`amazon-manage-dialog.js`)

## Releasing

When tagging a new version, three places must agree on the version string. Missing any one of them ships a build whose internal version disagrees with the git tag:

1. `package.json` — `"version"` field.
2. `package-lock.json` — TWO `"version"` fields at the top (root and the `packages.""` entry). Both must match `package.json`.
3. `RELEASE_NOTES.md` — add a new entry at the top with `# Parachord vX.Y.Z` heading, release date, and grouped highlights. The in-app "What's New" modal renders this file (parsed via the bundled fallback or fetched from GitHub) so users see your bullet points on first launch after upgrade.

Then commit (`X.Y.Z` is conventional for the commit subject), push, and `git tag vX.Y.Z` + `git push origin vX.Y.Z`. The CI build picks up from the tag.

PRs and `main` build Mac on Apple Silicon; the Intel build runs only on tags and manual runs (`build.yml`). PRs skipped Mac from 2026-11-04 to 2026-11-11 while hosted Mac runners were short (#1252, #1251). A job that never gets a runner during a Mac shortage is retried up to 3 times by `rerun-unacquired.yml`, on PRs, `main` and tags.

Two release-only failure modes to know about:

- **Apple notarization 403 "A required agreement is missing or has expired"** (surfaces as `Unexpected token 'E', "Error: HTT"... is not valid JSON` from @electron/notarize). Apple periodically requires the account holder to accept an updated agreement at developer.apple.com/account; until then every notarization is refused. Accept it, then `gh run rerun <id> --failed`. Acceptance can take a minute to propagate, so a job that started just before may need one more rerun (v0.9.8 did).
- **VMP signing** (see the Widevine section): release tags set `EVS_REQUIRED=1`, so if EVS is down or the `EVS_*` secrets are missing, the Mac and Windows builds fail on purpose rather than ship a build Apple's licence server would refuse.

## Voice when responding to external contributors

Parachord is a solo-maintainer project. When commenting on issues or PRs from external contributors (anyone other than @jherskowitz), don't use phrases that imply a team: "the maintainers," "we'd appreciate," "the team prefers." That framing reads as evasive once a contributor notices the project is essentially one person, and it understates the bus-factor reality.

The honest framing is also more recruitment-effective. Use first-person singular and admit limits: "I'm the only maintainer right now and X isn't where my expertise is — would love your help." Solo-maintainer projects with self-aware leads attract better contributors than ones pretending to be teams.

This applies to issue triage, PR review, RFC discussion, and any other contributor-facing communication. The single exception is when the comment is on behalf of a specific named co-author (Claude, an external contributor, etc.) — in which case attribute that person rather than using a plural.

## Mobile parity — proactively file the Android ticket

**Every bug fix or behavior change ends with the question.** Before you call one done, ask whether the mobile app may need the same fix or change, and if it might, ask the user whether to write a mobile ticket. Check the mobile code first when you can (a bug desktop just fixed is often still live there), and say what you found. Don't skip the question because the change looks desktop-sized; the exclusions below are the only reasons not to ask.

When desktop ships a new feature or architectural change that the Android client at [Parachord/parachord-mobile](https://github.com/Parachord/parachord-mobile) needs for parity, **offer to file a mobile ticket as part of the same workflow**. Don't wait to be asked; surface the question proactively, then file once the user confirms (or just file it if they've already said "and write a mobile issue" / similar). The Android side has its own agent operating in a separate repo — the issue is the handoff.

### When this applies

Anything that creates a shared invariant or data shape that Android also has to honor, including:

- Sync data-model changes (new playlist fields, new persistence keys, new IPC contracts that the Android-side equivalent has to mirror — see the "Android Parity Requirements" sections in [android-parity.md](docs/architecture/android-parity.md))
- Scrobble payload extensions (LB `additional_info` fields, Last.fm extras) — example: [parachord-mobile#170](https://github.com/Parachord/parachord-mobile/issues/170) mirroring the desktop's `origin_url` / `music_service` / MBID enrichment
- Track / album / artist data-model invariants (new fields, removal tombstones, suppression maps) — example: [parachord-mobile#172](https://github.com/Parachord/parachord-mobile/issues/172) mirroring the track-tombstones architecture from parachord#864 / parachord#865
- Resolver scoring / confidence model changes — `confidence-scoring.js` ↔ `ResolverScoring.kt` byte-equivalence is the strictest mirror requirement
- Achordion-facing endpoints (writer endpoints that the desktop calls and Android should also call, or where Android's submit semantics need to match)
- Protocol surface additions (`parachord://` deep links — see "Android Parity Requirements (protocol play handlers)" in [android-parity.md](docs/architecture/android-parity.md))
- Playlist import link types: mobile imports a playlist from every link desktop does, routed through the plugin registry on both (see "Android Parity Requirements (playlist link import)" in [android-parity.md](docs/architecture/android-parity.md))

### When this does NOT apply

Don't file mobile parity issues for:

- **Desktop-only fixes** — Electron-specific code (AppImage MCP path #867, Linux/Mac/Windows package format quirks, `BrowserWindow` config, IPC surface refactors)
- **Trivial bugs that don't touch shared semantics** — typo fixes, log-line additions, doc-only changes, single-file UI tweaks
- **Anything Android already has** — check before filing; desktop sometimes catches up to Android (e.g. Android shipped correct Spotify DELETE endpoints before desktop #863 fixed the broken `/me/library` endpoint, so no mobile ticket was needed there)

### Ticket shape

Write the Android issue to be **self-sufficient** — the parachord-mobile agent doesn't have desktop's context, so the issue must carry it:

- Reference the desktop PR / commit that shipped the change
- Reproduce the schema decisions (TTL, key shape, persistence-store key names) verbatim, not just "match desktop"
- Include the pure-JS reference module's API surface (function signatures, return shapes) so the Kotlin port has a target
- Note the cross-platform invariant explicitly — what would break if mobile drifted (e.g. "a track tombstoned on desktop reappears via Android's sync re-import")
- Sequence the work — wait for desktop merge before opening, OR open simultaneously with explicit "wait for parachord#XXX to merge first" note
- Same voice as #voice — solo-maintainer first-person, honest about limits, don't imply a team

### Anti-pattern: silent assumption that Android will catch up

The mobile client has lagged behind desktop on multiple invariants in the past — `suppressSync` for playlists, the `syncedFrom` heal for imported playlists, the AM endpoint-degradation rules. Each gap manifested as cross-platform data drift (corruption propagating from buggy client → shared remote → healthy client). **Don't assume "someone will get to it" — file the issue or accept that drift is permanent.** The cost of writing a thorough Android-side ticket is far smaller than the cost of debugging cross-platform sync corruption six months later.
