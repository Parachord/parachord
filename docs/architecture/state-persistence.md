## State Persistence

### Bulk Load Pattern (L18740)
- Single IPC roundtrip: `window.electron.store.getBatch(allKeys)` loads 40+ keys at once
- Includes caches (album art, artist data, track sources), settings, preferences, queues
- `cacheLoaded` flag (L7923) gates initialization effects until restore completes

### Key Persisted Values
- `saved_volume`, `active_resolvers`, `resolver_order`
- `cache_recommendations`: the Recommendations page's per-provider answers (`{ providers: { [id]: { sections, fetchedAt, account, ... } }, similarUsers: { [id]: { users, fetchedAt, account, shape } }, releaseDates: { [artist|title]: { date, at } }, savedAt }`; `releaseDates` are the album cards' MusicBrainz first release dates for the upcoming badge, a week each, newest 1500; `similarUsers` is the Friends row's answers, kept 7 days, and a cache saved before the row existed simply lacks the key), read with the critical keys so a launch onto the page shows them at once; see "Cache" in [../features/RECOMMENDATIONS.md](../features/RECOMMENDATIONS.md)
- `cache_history_mixes`: Home's "Made from your listening" mixes per provider (`{ providers: { [id]: { resolverId, resolverName, items, fetchedAt, account } }, savedAt }`; only answers with mixes, kept 7 days), one of the big caches (`BIG_CACHE_KEYS`), so nothing new holds up Home's first paint; `loadHistoryMixes` awaits `waitForBigCaches()` before it reads it, and Home's mixes and the Recommendations page's history-mix exclusion fill in a moment after first paint; see "History mixes" in [plugins.md](plugins.md)
- `saved_queue`, `saved_queue_position` (`{ trackKey, position, scrobbled? }`, the first track's resume point, and whether that listen was already scrobbled; #1319, #1346), `saved_playback_context`, `repeat_mode` (`'off'`, `'all'` or `'one'`; #1319), `auto_launch_spotify`, `skip_external_prompt`
- Caches with TTLs: album art (90 days), artist data (30 days, version-checked), release details / tracklists by MB release ID (`cache_release_details`, 30 days, pruned to the 400 most recent on save, entries are 10-30 KB; release-group IDs resolved on the album page are stored as `{ alias: releaseId }` so a revisit from search makes zero MB calls; every `/ws/2/release/{id}?inc=recordings` fetch goes through `fetchReleaseDetails(releaseId, fetchImpl?)` in app.js, which mimics the `ok`/`status`/`json()` subset of Response so the 404 → release-group fallbacks still work), MBID mapper (90 days), charts, new releases, concerts

### Big keys live in their own files (`main-process/split-store.js`)
electron-store re-reads, re-parses and rewrites its whole file on every `set()`, synchronously on the main thread. When `config.json` reached 40 MB (17 MB `local_playlists`, 9 MB `cache_track_sources`, …) one small setting cost ~0.5 s and the 5-minute cache save froze the window for seconds (the pinwheel, 2026-10). `main.js`'s `store` is now `createSplitStore`: `local_playlists`, `sync_playlist_state` and every `cache_*` key (by prefix, so a new cache is covered automatically) live in `userData/store/<key>.json`, everything else stays in `config.json` (~0.3 MB). Same get/set/delete/has/clear/`store` surface, same copy-on-get semantics, so callers don't change. Migration runs once at startup and is one-way; where a key is in both places the split file wins. An **older build** run afterwards sees no playlists or caches (the data is intact in `store/`), and anything it writes to those keys in `config.json` is discarded when a newer build starts. A big key still costs its own size per write (`local_playlists` ~0.2 s); per-playlist storage is #801. Tests: `tests/store/split-store.test.js` (real `conf` stores in a temp dir).

### Save Triggers
- On unmount (cleanup effect)
- Periodically (every 5 minutes)
- Immediately on preference change (volume, preferred device, etc.)

**In practice only the 5-minute timer persists most big caches between launches.** Quit goes through main's `before-quit` → `app.exit(0)`, which never unmounts the renderer, so the unmount save doesn't run. A cache populated in a session shorter than five minutes is lost. (Known gap; flushing several multi-MB `store.set` calls from `beforeunload` isn't reliable.)

**The track-sources cache is the exception: it saves soon after resolutions.** It is the one whose loss costs the most (every lost entry is a full fan-out to every resolver on the next launch; seen 2026-11-11 as the same Recommendations rows resolving on every short launch). Every write to `trackSourcesCache` calls `markTrackSourcesDirty()` first, and a debounced saver (`src/renderer/lib/debounced-saver.js`) writes `cache_track_sources` 15s after a burst of writes ends, and no later than 60s after the first unsaved one. A save clones the whole cache over IPC and rewrites its file (about 140ms in all at 6,000 entries, ~10 MB), which is why it waits for a burst to end rather than saving per resolution. Neither this saver nor the 5-minute save writes the key before it has loaded from disk (`trackSourcesLoadedRef`, set after the track-sources hydration, also when there is no file; a failed big-cache read never sets it), because the cache is empty until then and the save would wipe the file. Entries resolved before the file loads are merged over it rather than dropped. `tests/renderer/track-sources-save.test.js` fails when a new write to the cache skips the mark. A session can still lose up to the last 60s of resolutions.

**The big caches arrive after first paint, so a launch-time reader waits for them.** `loadCacheFromStore` reads the critical keys first (preferences, the last view) and the big `cache_*` keys in a second batch that `hydrateBigCaches` walks in an idle callback after first paint; `bigCachesHydrated` settles when it finishes or fails. Anything that reads a big cache during launch awaits `waitForBigCaches()` (that promise, capped at 10s) first: Concerts, Fresh Drops, Home's history mixes (`loadHistoryMixes`), and the restored artist page (the last view, when the app reopens on an artist). The restore used to fetch the artist 100ms after the critical keys, before the artist cache was in, so every launch on an artist page refetched its discography from MusicBrainz and repainted it one release type at a time (#1201).

### Allowlist trap: every persisted key must be in `ALLOWED_STORE_KEYS` (main-process/ipc/store.js)
The `store-get` / `store-set` / `store-delete` / `store-get-batch` IPC handlers refuse keys that aren't in `ALLOWED_STORE_KEYS`. **The refusal is silent from the renderer's side**: `store.set` resolves `false` (nobody checks it) and main logs `⚠️ Blocked store-set for non-whitelisted key: <key>`. Until 2026-10-12 `cache_critics_picks`, `hosted_playlists`, `sync_engine_mode`, `sync_playlist_channels`, `discovery_seen_concerts` and `discovery_seen_newReleases` were all missing, so Critical Darlings never persisted, the sync-engine mode toggle never stuck across restarts, and the renderer always read `{}` for channel overrides. `tests/store/allowed-store-keys.test.js` parses the allowlist and every literal key the renderer passes to `store.*` (plus the `discovery_seen_${feature}` and `scrobbler-config-${id}` families) and fails on any key that isn't allowlisted. When adding a persisted key: add it to `ALLOWED_STORE_KEYS` first, then use it. If a value "mysteriously" doesn't persist, grep the main-process log for `Blocked store-`.
