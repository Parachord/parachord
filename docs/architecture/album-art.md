## Album Art: one pipeline

`getAlbumArt(artist, album)` in app.js (search "THE album-art pipeline") is the only way a surface should get a cover: caches → MusicBrainz release search + Cover Art Archive → enabled resolvers' search results (`getAlbumArtFromResolvers`, walking resolvers in priority order until one returns a result **with** art via `searchResolvers({ earlyReturn: true, requireAlbumArt: true })`) → iTunes Search → Deezer (`album-art-catalog.js`, ported from Achordion's `lib/clients/{itunes,deezer,album-art}.ts`, with a validation step: a hit must name the requested artist and album after normalization, because both APIs return a best-effort top hit). Callers with a track title and no album use `getTrackArt(artist, title)`, the same catalog chain's song search. Resolver and catalog hits are cached in `albumArtCache` under `resolver:`/`catalog:` keys that `getCachedAlbumArt` also checks; a session miss (`resolverArtCache` null) is recorded only when every source answered, so a throttled or failed search is retried on the next render. Deezer has no CORS header for file:// origins, so it goes through `proxyFetch`; iTunes goes through `window.iTunesRateLimiter`. **Don't add a surface-specific shortcut.** The chat card had a resolvers-only "fast" path (commit `8960e20`, then `8bd881b`) and that is why AI-recommended tracks rendered without art. **Never write a URL into `albumArtCache` that was not requested.** Fresh Drops used to assign `coverartarchive.org/release-group/<id>/front-250` to every release and persist it as a hit: a release with no CAA art (most brand-new ones) showed the placeholder for 90 days and the fallbacks never ran (2026-10-17). `window.isUnverifiedCoverArtUrl` identifies that shape (a verified hit stores the final archive.org URL); the cache loader drops such entries, `window.hydrateReleaseArt` treats them as missing, and `fetchNewReleasesAlbumArt` verifies the release-group front with a HEAD request and otherwise runs `getAlbumArtFromResolvers` (resolvers, then iTunes and Deezer), four releases in flight, results batched into state. Tests: `tests/ui/fresh-drops-art.test.js`. **A cached URL can die before its 90 days are up**: a Bandcamp cover URL carries an image id that changes when the artist replaces the art (a cached `f4.bcbits.com/img/<id>_10.jpg` 404s), and archive.org mirror hosts move. The album-cover surfaces (`ReleaseCard`, `CollectionAlbumCard`, the `ReleasePage` header) answer a failed `<img>` by calling `window.reportBrokenAlbumArt(url, { artist, album, releaseId })` (`src/renderer/lib/broken-art.js`): every `albumArtCache` and `resolverArtCache` entry holding that URL is dropped, `getAlbumArt` runs again, the fresh URL is recorded under the release id and swapped into the card. Once per album per session, shared by every card showing it, so a still-broken replacement cannot loop. The inline grids in app.js that keep the cover on the item in their own list state (Fresh Drops, Pop of the Tops, Critical Darlings) call `retryBrokenListArt` instead, which patches the list item; Fresh Drops patches through its art writer so the copy persisted in `cache_new_releases` is fixed too. Their `<img>` is keyed on the URL: `onError` hides the element, and React would otherwise reuse the hidden element for the fresh URL. A new surface that renders a cached cover should do the same rather than only hiding the image. Tests: `tests/renderer/broken-art.test.js`. Tests: `tests/resolver/album-art-catalog.test.js`; sources table in `docs/architecture/METADATA_SOURCES.md`.
