## Album Art: one pipeline

`getAlbumArt(artist, album)` in app.js (search "THE album-art pipeline") is the only way a surface should get a cover: caches → MusicBrainz release search + Cover Art Archive → enabled resolvers' search results (`getAlbumArtFromResolvers`, walking resolvers in priority order until one returns a result **with** art via `searchResolvers({ earlyReturn: true, requireAlbumArt: true })`) → iTunes Search → Deezer (`album-art-catalog.js`, ported from Achordion's `lib/clients/{itunes,deezer,album-art}.ts`, with a validation step: a hit must name the requested artist and album after normalization, because both APIs return a best-effort top hit). Callers with a track title and no album use `getTrackArt(artist, title)`, the same catalog chain's song search. A caller that already knows the MusicBrainz ids passes them (`getAlbumArt(artist, album, { releaseGroupId, releaseId })`): step 2 then asks the Cover Art Archive for those ids instead of searching by name, and they are not written to `albumToReleaseIdCache`, because two release groups can share an artist and a title. `{ background: true }` puts step 2's MusicBrainz search in the background lane; Search's covers use both (`fetchSearchAlbumArt`), and before 2026-11 they were a fetcher of their own that ran a foreground MusicBrainz search per local track. Search also has a display-only fallback: a row a service already returned a cover for (`serviceArtFor` in `src/renderer/lib/search-catalog.js`: a merged source's `albumArt`, or the cover of a service album the row absorbed) shows that cover when the pipeline hasn't answered within 2s or finds nothing. It is the image the resolver step would find, without searching again; it is never written to `albumArtCache`, the pipeline still runs and fills the caches for other surfaces, and the first cover a row gets stays (no swap under the user). It exists because rows waited out the whole chain four at a time and stayed blank while the Cover Art Archive was unreachable (2026-11-01). A track row with no album name goes through `getTrackArt`. The first cover a Search slot shows stays (keyed by the row's display key, `_rowKey`), whether a higher-priority service later leads the merged row or a MusicBrainz row arrives without one; and a cover that fails to load does not stick: `handleSearchArtBroken` marks the URL bad for the query, drops it from the slot, reports it through `reportBrokenAlbumArt`, and the row takes another source's cover or asks the pipeline again. Bad URLs are never settled, kept or offered as a fallback, and the `<img>` is keyed on its URL. Without that, Bandcamp's dead search covers (it answers first) stuck for good. The artist page's covers (`fetchSingleAlbumArt`) go through `getAlbumArt` the same way, with the release group's id and the background lane; they used to be a fetcher of their own that made a foreground MusicBrainz lookup for every release without a release-group cover (2026-11). Every fill of the artist page's art queue tags its releases with the artist name it already has (`withArtArtist`), because the art loop runs a `fetchSingleAlbumArt` from the render before `setCurrentArtist` landed: reading the name from `currentArtist` gave `null` at launch (every lookup returned nothing, a page of placeholders) and the previous artist after a hop. A lookup by release-group id needs no name at all; it only feeds the resolver fallback. Resolver and catalog hits are cached in `albumArtCache` under `resolver:`/`catalog:` keys that `getCachedAlbumArt` also checks; a session miss (`resolverArtCache` null) is recorded only when every source answered, so a throttled or failed search is retried on the next render. Deezer has no CORS header for file:// origins, so it goes through `proxyFetch`; iTunes goes through `window.iTunesRateLimiter`. **Don't add a surface-specific shortcut.** The chat card had a resolvers-only "fast" path (commit `8960e20`, then `8bd881b`) and that is why AI-recommended tracks rendered without art. **Never write a URL into `albumArtCache` that was not requested.** Fresh Drops used to assign `coverartarchive.org/release-group/<id>/front-250` to every release and persist it as a hit: a release with no CAA art (most brand-new ones) showed the placeholder for 90 days and the fallbacks never ran (2026-10-17). `window.isUnverifiedCoverArtUrl` identifies that shape (a verified hit stores the final archive.org URL); the cache loader drops such entries, `window.hydrateReleaseArt` treats them as missing, and `fetchNewReleasesAlbumArt` verifies the release-group front with a HEAD request and otherwise runs `getAlbumArtFromResolvers` (resolvers, then iTunes and Deezer), four releases in flight, results batched into state. Tests: `tests/ui/fresh-drops-art.test.js`. **A cached URL can die before its 90 days are up**: a Bandcamp cover URL carries an image id that changes when the artist replaces the art (a cached `f4.bcbits.com/img/<id>_10.jpg` 404s), and archive.org mirror hosts move. The album-cover surfaces (`ReleaseCard`, `CollectionAlbumCard`, the `ReleasePage` header) answer a failed `<img>` by calling `window.reportBrokenAlbumArt(url, { artist, album, releaseId })` (`src/renderer/lib/broken-art.js`): every `albumArtCache` and `resolverArtCache` entry holding that URL is dropped, `getAlbumArt` runs again, the fresh URL is recorded under the release id and swapped into the card. Once per album per session, shared by every card showing it, so a still-broken replacement cannot loop. The inline grids in app.js that keep the cover on the item in their own list state (Fresh Drops, Pop of the Tops, Critical Darlings) call `retryBrokenListArt` instead, which patches the list item; Fresh Drops patches through its art writer so the copy persisted in `cache_new_releases` is fixed too. Their `<img>` is keyed on the URL: `onError` hides the element, and React would otherwise reuse the hidden element for the fresh URL. A new surface that renders a cached cover should do the same rather than only hiding the image. Tests: `tests/renderer/broken-art.test.js`. Tests: `tests/resolver/album-art-catalog.test.js`; sources table in `docs/architecture/METADATA_SOURCES.md`.

**An album page keeps the cover it opened with.** The playbar and Collection openers show a placeholder page with the cover the track or card already had; `fetchReleaseData` replaces it when MusicBrainz answers. That replacement used to take its cover only from id-keyed caches, so a miss blanked the cover, and the Cover Art Archive fetch then swapped in its own copy of the same image, which the header `<img>` (keyed on its URL) faded in a second time (2026-10-27). `fetchReleaseData` now falls back to the cover on screen for the same album (`carriedReleaseArt`, matched by artist and title because the page's id changes while it loads), and the Cover Art Archive result only fills a page with no cover (`withArchiveCover`); it is still cached for the other surfaces. Both are in `src/renderer/lib/release-open.js`, which also holds the session map of release groups (`createReleaseGroupPicks`) that the queue-album fetches write and the openers read, so opening an album you just queued costs no MusicBrainz search. Tests: `tests/renderer/release-open.test.js`.

**ListenBrainz covers come from ListenBrainz's own identifiers.** A listen's `track_metadata.mbid_mapping`, the stats payload's top releases, and generated playlists' JSPF `additional_metadata` carry `caa_release_mbid` and `caa_id`; `listenBrainzCoverUrl(meta)` (`src/renderer/lib/listenbrainz-cover.js`) builds `coverartarchive.org/release/<caa_release_mbid>/front-250` only when `caa_id` is set (ListenBrainz knows a front image exists), and returns `null` otherwise, so the surface falls back to `getAlbumArt`. Friends' recent listens and top albums, your own ListenBrainz history, and the weekly playlists use it; they used to run a MusicBrainz name search per item (#1181, #1185).
