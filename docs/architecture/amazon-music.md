### Amazon Music Resolver (native Widevine playback)

Amazon Music audio plays in **Parachord's own player** (since resolver manifest 1.7.0): the plugin's DRM pair (#1356 M4's renderer-mediated path, live since M9 — `getPlaybackManifest`/`relayLicense` in `plugins-src/amazonmusic/implementation.js`) talks to Amazon's `dmls` endpoint for DASH manifests and Widevine licenses over the `window.electron.webSession` bridge, the generic widevine bridge (`main-process/widevine-bridge.js`) opens the licence session per play under its gates, and the renderer's shared Shaka engine (`src/renderer/lib/widevine-player.js` on `vendor/shaka-player.compiled.js`) decrypts and plays them on the app-wide HTMLAudioElement. No Amazon page sits in the audio path anymore. The hornet-era audio pipeline (0×0 player view, `?do=play`, the poller, the stream-capture net hook, the hornet quality store) was **deleted** in the same change — and since the #1356 move finished (M11, the teardown), **the plugin owns every piece of Amazon service knowledge**: search, the album catalog, the playlist import, the recommendations, the DRM pair (its csrf mint included), sign-in/out, the status read and the diagnostic capture all live in `plugins-src/amazonmusic/` and drive the ONE host web-session instance (`main-process/amazon-web-session.js`, registered with the bridge in main.js) through `window.electron.webSession`; the host supplies the machinery only (the hidden view, the capture, the page-world fetch, the cookie jar, sign-in windows — `main-process/web-session.js` + `main-process/ipc/web-session-bridge.js`, see [web-session.md](web-session.md)). The host-side module that used to hold the flows (`amazon-web-player.js`, with `amazon-music-logic.js` and the `window.electron.amazonMusic` preload block) is deleted. Two live page surfaces remain: the offscreen search view (the web-session host's `layoutOffscreen` — `setBounds({ x: -1200, ... })`, `persist:amazon-music` session) and the real sign-in window. Parachord does not extract keys, launch the Amazon Music desktop app, or borrow a browser CDM (`--widevine-cdm-path` does nothing on this Electron). Amazon's licence server refuses the development VMP signature (`DEVELOPMENT_CERTIFICATE_NOT_ALLOWED`); playback needs a production EVS signature, same as Apple — audio plays from the packager-selected castlabs homebrew build (dev) and the production signed builds. If the CDM is missing or playback does not start, play fails and the next resolver is tried. Historical desktop-app CDP notes: `docs/plans/2026-09-23-amazon-music-resolver-brainstorm.md`.

**Sign-in.** Sign-in lives in the plugin (#1356 M10): its `signIn()` opens Amazon's page in a visible window through the `window.electron.webSession` bridge's signIn protocol (the host shows the window and ticks `{url, cookieNames}` once a second; the plugin supplies the verdict) — the renderer's prompt flow (`manageAmazonMusic` in app.js, still the consent dialog, single-flight and the decline quiet) calls the plugin's methods through the loaded resolver. Sign-in is not finished until a profile is chosen — `/identity/who-is-listening` and every `/ap/` page on an Amazon account host (`/ap/signin`, 2FA at `/ap/mfa`, push approval and verification under `/ap/cvf/`, challenges) are `not-signed-in` (`pageBlocksPlayback`), even if an auth cookie is already set. The completion gate (`signInLanded`, the plugin's `_lib` copy) needs a **positive** signal: a non-wall URL whose **host** is `music.amazon.com` (never a substring match: the portal's URLs carry `music.amazon.com` in their `return_to` query, and matching that closed the window two seconds into the 2FA prompt, reporting a sign-in that never happened) stable for two consecutive ticks AND either an auth cookie or, once the window has been through Amazon's sign-in pages (a tick on any host other than `music.amazon.com`, `signInTickLeftMusicHost`), a path off the bare home page or a third stable tick: the fallback that keeps the flow alive if Amazon rotates the `at-main`/`sess-at-main`/`at-acb` cookie names. "Not on a known wall" alone used to close the window on a logged-out first paint of `/`, and until 2026-11-17 the fallback did the same without the sign-in-pages condition: Amazon Music shows a signed-out visitor its home page instead of sending them to sign in, so on a fresh profile the window sat on `/` for three ticks and closed, reporting success, before the person could click Sign in. The signed-in verdict (the plugin's `isSignedIn`, over `webSession.state()`) is **cookies, then the sign-in window**: no auth cookie means signed out (`amazonAuthCookieState` reads cookie NAMES: the known `at-main`/`sess-at-main`/`at-acb`, else any `x-main`/`at-*`/`sess-at-*` as the hedge for Amazon renaming them; a logged-out jar holds none of these). The names come from the web-session host's `state()`, a **domain-scoped read that sees FEWER cookies than the old whole-partition one**: `cookies.get({ url })` per declared `cookieDomains` (`amazon.com`, `music.amazon.com`, `www.amazon.com`) — so a `.amazon.com` domain cookie is seen (where every known auth cookie lives), but a host-only cookie on some other Amazon host, or one scoped to a path other than `/`, is not; the "rotated" hedge exists exactly for names we don't know yet, so a future auth cookie landing host-only on another host would be missed by the read (the cheap hedge is adding that host to `cookieDomains`). A page is never proof of a session: the old rename hedge trusted any non-wall `music.amazon.com` page, and the logged-out home page is one, so the app reported signed in before sign-in. With a cookie present, only the sign-in window's URL is consulted — the search view keeps whatever URL its last navigation left behind, and a view parked on `/ap/signin` by an earlier failed search used to lock the account out right after a successful sign-in (nothing navigates the view while `isSignedIn` returns false). A genuinely dead session is caught mid-flight: search, lookup and play re-check the URL after every load and throw not-signed-in on a redirect. The template-replay fast path reads the warm view's URL too, but a wall there is a fast-path MISS, never a throw: the view keeps whatever URL its last navigation left behind, so a token-refresh redirect can park it on a wall with a live session, and a throw would block the very page flow that navigates it off — the page flow's own after-load URL re-check is where a genuinely dead session surfaces not-signed-in (it loads a fresh page, so its verdict is current). The search view parks on `about:blank` on a 30s fuse after activity ends (the web-session host's `warmMs` — a gql template replay needs an Amazon-origin page world: about:blank is a null origin and can neither pass CORS nor attach session cookies, so the view stays warm briefly). The fuse is **busy-aware, not just cancel-on-activity**: every chained flow and every in-flight page-world fetch holds the host's busy count, and at fire time the fuse re-arms instead of blanking while busy — it must never blank the view under a flow it cannot see (a 40s playlist import outlives it; a replay during one would otherwise re-arm a blank into the middle of its pagination and silently truncate the import). Cancel-at-entry on each flow is belt; the fire-time check is the suspenders (the whole fuse contract is the host's — "the idle park never blanks a busy view" in [web-session.md](web-session.md)). The idle-SPA-at-full-speed cost (`backgroundThrottling: false`) is bounded to idle windows, and a burst of searches shares one page load instead of paying one each. The prompt is single-flight and skipped during auto-advance/radio. **Background searches never prompt** (#1220): `__parachordNoteAmazonNotReady` only keeps a not-ready result out of the noMatch cache. Amazon plays only on Music Unlimited, so an unasked-for "Play Amazon Music in Parachord?" dialog would mostly reach accounts that can't use it; a signed-out Amazon shows **Setup required** on its tile instead (the plugin's status reply says it — `signedIn: false` flags the resolver's setup, and `statusLabel` carries the same wording for the Settings row), and the dialog opens only when the user asks for Amazon (Settings' Sign in, playing an Amazon track, importing an Amazon link). A not-signed-in while the auth cookies are live does not prompt at first (`signInPromptDecision`, the plugin's `_lib` copy of the rule — the renderer's flow calls it through the loaded resolver): Amazon reissues `session-token` every so often, and a page load caught in that refresh can be redirected to a sign-in or profile page while the session is fine (the prompt opened on an app signed in for hours, and the next search worked). `manageAmazonMusic` returns true after ~2s so the caller retries; only a streak lasting a minute (failures under 2 minutes apart, most likely the profile picker waiting) prompts. No cookies prompts at once, and Settings' Sign in button (`forcePrompt`) always opens the window. A sign-in window closed without a session starts the same 10-minute quiet period as declining the prompt (otherwise the next background search re-prompts at once), and an enabled Amazon resolver that is not signed in shows **Setup required** in the resolver grid, refreshed after every sign-in attempt and each time Settings opens (the generic plugin-status sweep — startup, Settings, the resolver panel, a plan refusal — reads the plugin's `getStatus`). Search/resolve throw `{ notReady: true }` when not signed in so that is not cached as a 30-day `noMatch`. Search does not require the CDM; play does. Sign-out (the plugin's `signOut()`, from the generic status-capable Settings row) drops every session-scoped plugin state (dropSessionState — the same list the generation drop carries), whose first act posts the stream's final telemetry accounting, and AWAITS that post before clearing the whole `persist:amazon-music` partition through the bridge (Amazon-only, so the clear is correctly scoped) — the accounting goes out while the session still lives, and the clear destroys the views and supersedes in-flight plays via the generation bump.

**Playback.** Resolve searches both terms quoted on the songs tab, ORing three clauses in one page load — the natural-language form first, then the two phrase orders: `"title" by "artist" OR "title" "artist" OR "artist" "title"` (`/search/…/songs`). A loose combined query misses songs (a phrase like `Stations Warning`), and a single quoted order is not enough either: Amazon's matching is order-sensitive in **both** directions — Warning's "Stations" only surfaces title-first while ХЛЕБ's "Яйца" only surfaces artist-first (live-verified 2026-10 through the app via MCP search). The `by` clause (2026-11) fixes a ranking failure the two bare orders share: Backstabbed's "Out Of Body Experience" is absent from the spec search's 30-row first page in BOTH orders (every row is a track by an artist literally named "Out of Body Experience") while the by-form returns it as row 1. The by-clause is a supplement, never a replacement — alone it returns ZERO rows for ХЛЕБ's "Яйца" and misses Warning's "Stations", so the bare orders stay. The OR union brings a few noise rows matching the literal keywords (titles containing "or" or "by"); the resolver's artist+title filter and the confidence gate drop them. **The track search runs in the plugin** (#1356 M5): the spec-search runner family moved out of the host module (`amazon-web-player.js`, deleted with the M11 teardown) into `plugins-src/amazonmusic/implementation.js` (the plugin's `_lib` library carries the pure helpers; the `requireLib` compat guard and `minAppVersion.desktop` 0.9.13 — the first release with #1402's loader — cover old apps), and it drives the ONE host web-session instance through the `window.electron.webSession` bridge (`main-process/ipc/web-session-bridge.js`; docs/architecture/web-session.md, "The IPC bridge"). **Search runs over the page's own GraphQL, not the DOM** (2026-10; previously a scraped track row): the songs page fires `SpecSearchSeeMorePage` with the exact `searchText` from the URL; the request (URL, headers, APQ hash, variables) is captured via webRequest while the page loads and replayed VERBATIM from the page world (`webSession.pageFetch` — the host supplies the origin, cookies and CORS; `requires.hostBridges: ["webSession"]` in the manifest declares the bridge), then parsed by the pure mapper in `_lib`. The request is matched on `variables.searchText` (case-insensitive) across ALL header-complete captures, **never the operationName** — and **only the track spec ever matches**: an album/artist/playlist spec for the same text is rejected even when it is the only match (its edges are Album nodes whose ASIN would pass the confidence gate on self-titled releases — the album-ASIN failure the DOM-era exclusion dance existed to prevent). The edge mapper likewise rejects non-`Track` nodes when `__typename` is present, and strips Amazon's in-title explicit marker (`"Kunnioita [Explicit]"` — the gql Track node has no explicit field) — a TRAILING bracketed/parenthesized `explicit` marker only, bare words like "Sexually Explicit" are real titles and kept — keeping the title clean for cross-provider matching and scrobbles. Structural failures throw `not-ready`, never cached as a 30-day `noMatch`: a page that never searched, another spec searched but the track spec never came (the plugin's page flow loads the tab and matches on the RETURNED captures — the bridge's quiet-bounded capture window, `quietMs` with no new captured request — an explicit 2500ms, not the host's 1000ms default, sized for a cold view whose first gql fires well after load-finish (boot + query is ~1-3s on a warm view; under the default the window would close before the page ever searched, reading as "never fired" and tripping the breaker) — never later than the old in-flow poll's 15s budget), or a response with no `specificationSearch` envelope. These structural failures also trip the plugin's own `searchBreaker` (`createSearchBreaker`, a `_lib` copy): after 3 consecutive it opens for 10 min, failing fast instead of burning the capture window on every search of a resolution run; after the cooldown the next search is a probe, any success closes it. An envelope with empty edges is a real miss and returns `[]`. The track nodes carry cover art (`albumArt`, via the edge mapper) which the resolver passes through for `getAlbumArtFromResolvers`. **Do not try to read the page's own search response instead of replaying it** — the stream-capture pattern does not work for the bootstrap search: hornet binds its fetch at module init, before any preload-injected wrapper can install (live-verified 2026-10). The replay's cost is one request on top of the ~9 ops the page load itself fires — and most searches skip even that: the captured request (URL, headers, APQ hash) is a reusable TEMPLATE. Within a deploy+session a search replays it with patched `searchText`/`specType` from the still-warm view — no page load, and replays run in PARALLEL (a playlist resolve no longer pays a page load per track; a per-instance chain serializes only the plugin's page flows so one re-mint heals every search queued behind it). Real navigation stays on the host's load chain (the fallback page flow that re-mints the template after a replay error, the plugin's album lookups, playlist imports and the DRM csrf mint, the diagnostic capture) and a navigation waits out in-flight replays before loading (the host's readers/writer gate; a `pageFetch` arriving while a navigation holds the gate answers `{ error: 'busy' }` — a template miss, not a drop). Template misses and replay errors (rotated APQ hash, rotated csrf/session headers) fall back to the full page flow, whose capture re-mints — including a replay that answers 200 with data but NO spec envelope (a partial GraphQL error — `data.specificationSearch` null with errors — the auth-failed-field shape of rotated session headers). One deliberate asymmetry: **only the page flow judges structure.** On a missing envelope the fast path can equally mean the template went bad, and replay-and-throw there made every later search replay-and-throw identically — the breaker's cooldown probe took the fast path with the same template and re-opened, so nothing healed for 24h (#1152 review). The fast path drops the template on a missing envelope and defers to the page flow, which makes the structural call with a fresh capture and alone trips the breaker for real renames. The remaining failure semantics are identical on both paths. The cross-talk rules, now on the data the bridge provides (captures carry an `echo` flag when a `pageFetch` was in flight as the request was seen — OUR replay traffic): an echoed same-spec capture answers the right search but must not re-mint the template (re-minting would re-certify session-aged headers as fresh — the #1152 poisoning), and an echoed other-spec capture is never read as "the page searched another spec" (it would fast-fail the flow structurally — the same class). Templates are plugin state (per resolver instance, dropped on any replay error, re-minted by every page flow, and dropped when a state read observes a new session `generation` — sign-out: the csrf headers embedded in a template belong to the account that was signed in when it was minted; a post-sign-out search re-mints anyway because the dead view forces the page flow) and the host never sees them. Since #1356 M6 the runner has no host-side copy at all: the album search and the artist-image lookup ride the plugin's same runner (same matchers, same helpers — the `_lib` copies are now the only ones); the playlist import followed in M7 and the recommendations in M8.

**Native playback (1.7.0+).** The `.axe` declares `capabilities.widevine` and its `play()` is host-owned: `lookupArtist/resolve` graphs unchanged; the engine branch runs OFF the resolver chain (`isWidevineResolver` in `use-playback-engine.js`). **Since #1356 M9 the DRM pair is the plugin's** (the M4 renderer-mediated path; the main-side `amazon-dmls.js` provider and `main-process/amazon-telemetry.js` are deleted — the error-field contract `reason`/`licenseDenied`/`denialReason`/`planKey` is byte-for-byte the same): the engine prefers the pair by presence (`pluginWidevine` in `use-playback-engine.js` — both methods or the provider fallback) and calls `resolver.getPlaybackManifest(track, config)` directly with the WHOLE track (the plugin digs its own ASIN out of the track's `amazonmusic` source record — the old host extraction's inputs), the plugin mints its session context (config.json over `webSession.fetch` + the csrf triplet from a page-flow capture — the old `mintSessionHeaders`' pattern: a load of the songs search for a BENIGN query, the plugin's own last search text falling back to `'the'`, with the placeholder filter — only real-looking csrf values count), gates the plan (`plan-ineligible` BEFORE any dmls request; since #1603 the gate runs before the mint, which can take the purchases page's csrf triplet) and POSTs `getDashManifestsV2` over `webSession.fetch` (the session's cookie jar rides it — Electron's net module only attaches the partition's jar reliably that way; `X-Amz-Target`, `Content-Encoding: amz-1.0`, the csrf triplet; a 400 that smells like auth drops the context, re-mints once, retries once, a second refusal is not-signed-in). The reply (`{manifest, type: 'dash', drm: 'widevine', asin, substituteAsin, musicDashVersion, cdnType, protectionSets, context}` — the SIREN_KATANA manifest inline, ~16 variants including the spatial sets (`ec-3` JOC, `ac-4` IMS, `mha1`/`mhm1`) and FLAC Ultra rungs, live-captured shapes in the tests) goes UP through `window.__parachordWidevine.playPlugin` → `widevine:open-session`, where MAIN mints the licence session under the same gates a provider manifest opened one → blob-URL `player.load()` with `drm.servers = parachord-license://amazonmusic?s=<sessionId>` → Shaka's license request crosses `widevine:license`, the bridge validates the sender/session/cap and forwards the challenge to the renderer (`widevine:plugin-license`, answered on `widevine:plugin-license-answer`), where the player's licence router hands it to the plugin's `relayLicense(challengeB64, context)` with the context the plugin sent with its manifest (`getLicenseForPlaybackV2`: `CAQ=` device cert once per session, then `{challenge} -> {"license": b64}`). The reply's `asin` rides the entity seam (the SERVED asin — `substituteAsin` layered over the extraction), so provenance and play-started telemetry attribute the deliverable pressing. Session ids are manifest-drawn and rotated on supersession; stop/ended match-close the license (`review: never superseded-close`). **A license 400 is parsed, never flattened**: the plugin's relayLicense branches on `denialReason` — only the CERT reasons (`UNTRUSTED_DEVICE_CERTIFICATE`/`DEVELOPMENT_CERTIFICATE_NOT_ALLOWED`, from the dev-signature captures) mean "this build's VMP signature" (`licenseDenied` → hard build-can't-play path); every other refusal (live-verified on a Prime plan: `CUSTOMER_NOT_ELIGIBLE` on the HD KID group while the opus groups played fine) is a per-content/per-KID-group refusal, carried through with the first sentence of Amazon's `message` to the player error (`licenseDenialSummary`: the rest of a content refusal's message is a `CustomerEligibility(customerId=…)` dump, and logs get pasted into issues, so the account's ids never reach a log or an error), and on plan denials the session stops asking for the refused family (#1262's `blockedFamilies`, which replaced the old provider's vestigial `hdSessionBlockedByPlan` latch — set, never read) — which group was refused is read off the variant active WHEN THE LICENSE REQUEST FIRED (the CDM asks for the selected variant's group; the challenge bytes are opaque, and a round-trip can outlive the load-time-pick → locked-selection handover). **The FAMILY-FAILURE TABLE (#1262): one generic `blockedFamilies` map (family → reason) in the engine, keyed by codec family and never by a hardcoded codec or a special spatial case.** `'license-denied'` entries are ACCOUNT facts — cleared by `clearPlanBlocks` (sign-out; a FLAC-group denial, a spatial-group denial, ANY family's refusal, the same one row). `'playback-failed'` entries are BUILD facts: the media stack rejected the family's data (the SourceBuffer append failed — 3014/3015) and no retry changes the decoder; never cleared in-process. Opus and AAC are never blocked this way (`NEVER_BLOCKED_ON_APPEND_FAILURE`): one bad segment would otherwise leave nothing to fall back to until a restart, so that track fails and the next one tries again. Whatever family fails, `playableVariants` drops it and the tier logic picks the best remaining rung — the NEXT BEST THING, family-agnostic: a refused FLAC group means the lossy ladder, a failed spatial append means stereo. And the fallback runs MID-PLAY, not just on the next track: the error the failure causes is attributed to the family (a license denial latches the family + play token moments before its error lands — `pendingDenialLatch`; an append failure attributes to the locked selection's family — the vendor's active flag can still read the PRE-switch rung mid-switch, live-observed in the #1262 dump — else the variant active at error time), that family is blocked, and the play re-selects from the shrunken roster instead of failing. The suppression is bounded and terminating: each one latches a family, a repeat for an already-blocked family (the re-selection did not take) propagates, and when every family has failed the play fails honestly. The fallback only acts for the CURRENT play's session (the session carries the play token — a teardown-race error during the next play's load/unload, 3015 wrapping a closed-MediaSource throw, must not block a good family on a dead play's attribution), and only a CRITICAL error consumes a denial latch (a license failure is always critical; an unrelated recoverable error in the microtask window between denial and error must not eat the suppression). Two known floors: shaka attempts its own media-source recovery for 3014/3015 before the error ever reaches the listener, so the first fallback can land one recovery cycle (~seconds) late — it still terminates; and a blocked INTERIOR stereo family (a rung below the roster top — no observed build probe-accepts-but-append-fails opus/aac) is not excluded from the shaka-side candidate set by the one-sided family-drop cap, so adaptive can re-reach it on a weak link — the repeat then propagates honestly and the next play's selection is protected. `blockedFamilies` is surfaced in `__parachordWidevine.getState()`. The #1262 shape that built this: the Atmos opt-in on a Linux castlabs build — both probe layers accepted E-AC-3, the locked pick selected the ec-3 rung, and the SourceBuffer rejected its data (a segment URL with `ql=SPATIAL_ATMOS_HIGH` at position 0, the element itself never erroring) on every track; macOS decodes E-AC-3 in software and plays the opt-in fine, so the probe passes and only the append fails — the "FLAC-only-on-paper" pattern one layer deeper, and the reason the fallback is generic instead of a spatial special case. The LOAD-TIME pick (shaka's ABR chooses a variant the moment `load()` parses the manifest, default estimate / the browser's downlink, and fires that variant's KID license request before the locked selection lands) is deliberately NOT estimate-steered: a low `abr.defaultBandwidthEstimate` seed only affects the FIRST track after launch (the estimator's samples survive plays — the ABR manager is reused while the factory is unchanged), landing it on the bottom rung with no clearBufferSwitch to climb away, and pinning `useNetworkInformation` off to make the seed stick also kills the estimator reset on network change; the seed was removed. What the pick IS shaped by is a RESTRICTION in the pre-load configure (#1247 review point 1): `abr.restrictions.maxBandwidth` = the tier ceiling (`loadTimePickCap` in widevine-quality.js) — with the spanning candidate set nothing else kept a locked Saver/Standard/High play off the FLAC rungs, and every such play fetched a FLAC init segment + license before the locked selection landed — further capped at the HIGH corridor ceiling when the process has been refused FLAC (a FLAC-rejecting probe or the plan latch; every observed Amazon FLAC rung sits above it), so the pick never asks for a family the process has been refused. The post-load `applyConfig` re-sends the authoritative value. The residual a max-tier play still carries is a FLAC pick on a fast estimate — that tier's own request. The default choice criteria narrows by `preferredAudioChannelCount` (2), so 6-channel spatial rungs are never the load-time pick, and the plan gate stops accounts that can't play before any manifest request. **`preferredAudioCodecs` must stay EMPTY everywhere on this engine** — two vendor hazards (both verified against the vendored build, review rounds 3-4): the parse-time filter narrows the manifest to the first preferred codec with prefix matches and WRITES THE NARROWED LIST BACK into the manifest (the roster collapses for good), and the choice criteria adopted at load never un-syncs the list (`player.configure()` does not reach its `preferredAudioCodecs`), so a load-time list confines the ABR candidate set to one family forever, even after `applyConfig` re-sends `[]` — silently regressing adaptive max-tier plays to top opus. The tier/quality read stays POST-load so a settings toggle landing during the load window still reaches the incoming track's selection; an unparseable body is a generic refusal, never claimed as the cert class. Relay gating is SENDER + SESSION + CAP (30 relays/session, 8 manifests/min/resolver — the plugin path SHARES the manifest rate window with the provider path) — plus an honest comment that this is abuse containment, not plug-in isolation (any plug-in can bundle webview traffic anyway). The plugin's DRM state (the minted session context, the cert warm, the telemetry instance and its health) is dropped when a state read observes a new session `generation` (the M5 rule — sign-out), with the stream's FINAL accounting posted first (the old `onSignOut`'s trackStreamed-before-the-clear; in practice the renderer stops the engine before the sign-out IPC, so the 'stopped' event posts it while the session still lives). Quality is the GLOBAL setting: `playback_quality`/`playback_abr` store keys drive `src/renderer/lib/widevine-quality.js` — tiers are bandwidth corridors (saver ≤100k / standard ≤200k / high ≤500k / max = best available) over the full playable roster, codec-neutral; adaptive roams below the corridor ceiling and tier switches apply mid-play (the earlier family-whitelist form is deleted: it filtered the roster mid-play, stranding exactly the family switch the tier asked for). **`manifest.enableAudioGroups` must stay FALSE (the #1243 fix)** — the ABR candidate set shaka feeds the manager on EVERY choice is not the roster: it is ONE `shaka.media.AdaptationSet`, built by the choice criteria and anchored on the first variant the criteria filters leave (manifest order for Amazon's all-stereo, all-primary shape), and `AdaptationSet.add` rejects variants whose `groupId` differs from the anchor's. With the default `enableAudioGroups:true` the DASH parser stamps every stream with its AdaptationSet's id as `groupId`, and Amazon's stereo rungs ride family-pure AdaptationSets (a set never mixes codec families — live capture: "three opus plus two FLAC renditions across five adaptation sets"; the opus rungs share one set, which is why ABR roamed 326k↔195k↔51k) — so the set was the opus set, anchored on an opus rung, and adaptive at Max could NEVER reach FLAC no matter the bandwidth estimate (live-reported: adaptive+max settled on opus 326k; ABR-off crossed families fine because `selectVariantTrack` crosses sets directly). With group ids off, on the default smooth codec switching (Electron has `SourceBuffer.changeType`), the set spans the stereo families; the 6-channel ec-3 and channel-less mha/mhm rungs stay excluded by the set's channel guard, so spatial keeps its locked path. The estimate seed is `ceil(rung/0.95)` (`seedBandwidth` in `shakaPlaybackConfig`): the chooser picks a rung when the estimate sits in `[rung/bandwidthDowngradeTarget, nextRung/bandwidthUpgradeTarget]` (0.95/0.85 in the vendored build; consecutive windows overlap — the higher rung wins — and the only unmatched region is below the lowest rung's floor, which falls back to the lowest rung), so seeding the rung's own bandwidth (below its own floor) lands ONE rung below. **Two more walls the spanning set raised, both capped by bandwidth:** (1) `playableVariants` filters OUR roster but the ABR candidate set is built from the SHAKA-side manifest, which never hears our filter — after a FLAC refusal (probe or plan latch) adaptive at Max would pick the refused FLAC rung on a good link, mint the license and fail the track, the repeat the latch exists to stop. `shakaPlaybackConfig` therefore receives the UNFILTERED roster (`allVariants`) and, when it carries a playable-family rung above the whole selection-playable roster (the observed refusal shape: Amazon's FLAC/HD rungs sit above every lossy rung), caps the adaptive `maxBandwidth` at the top selection-playable rung (`familyDropCapBps`). (2) The AC-4 IMS and MPEG-H rungs are categorically undecodable but ride 2-channel stereo bandwidths INSIDE the tier corridors (live capture: ac-4.02.02.00 at 115k/260k) — a spanning-set reach looked possible, and a manifest filter (`dropUnplayableAdaptationSets`) briefly existed for it, but it is NOT needed and was removed on review: shaka's own DRM-side playable filter drops those rungs before they ever reach `getVariantTracks()` or the ABR candidate set. Verified on the castlabs build (electron 44.5.1, CDM 4.10.3112.0) by driving shaka's exact predicate per family — `navigator.mediaCapabilities.decodingInfo` with the `media-source` audio config + `keySystemConfiguration` (the vendor's `ig` shape), cross-checked with `requestMediaKeySystemAccess`: opus/fLaC/ec-3/mp4a.40.2 SUPPORTED/ACCEPTED; ac-4.02.02.00/mha1.0x0e/mhm1.0x0d all UNSUPPORTED/REJECTED (and `MediaSource.isTypeSupported` false for the latter three). So `wg`'s `allowedByKeySystem` walls them off for every DRM manifest; the channel guard's exclusions (6-channel ec-3, null-channel mha/mhm) are a second layer, and the unobserved residual is a hypothetical 2-channel ec-3 rung on an ec-3-probe-rejecting build (no observed Amazon ec-3 rung has that shape — they are 6-channel JOC masters). All pinned against the vendored bundle in `tests/renderer/widevine-shaka-adaptation.test.js` — the set shapes, the real DashParser × the flag (a two-AdaptationSet MPD in Amazon's shape), the real SimpleAbrManager over the spanning set, and the seed: a shaka upgrade that changes any of it fails there. **Second vendor wall: any manual `selectVariantTrack` re-configures the choice criteria onto the selected rung's codec (audioCodec + channelCount), and `player.configure()` never re-widens it** — so after a locked play (ABR off, or the spatial lock) the ABR candidate set stays confined to that family until the next load adopts a fresh, wide criteria. `applyConfig`'s adaptive path repairs it (the CRITERIA RE-ANCHOR): when this engine made a selection on this track (`criteriaNarrowed` — reset per play, exposed in `getState()`) and the tier's target rung sits in a different family than the active variant, it `selectVariantTrack`s the tier's rung FIRST and hands control to the manager (tripping the "selected track will be overridden" advisory — accepted). The gate is load-bearing: on a fresh play the criteria is wide and a low-bandwidth active rung is the manager's own estimate-based pick — re-anchoring there would force the tier's top family onto a connection the estimator just called weak. Known floor, accepted: the re-anchor confines the family for the REST OF THE TRACK — a degrading link cannot drop below the family's cheapest rung (FLAC 1.06M at max) where a fresh adaptive play drops to opus; the next load re-widens (the vendor has no public API to re-widen mid-track), and never reaching FLAC at all was the alternative. **Spatial/Atmos is a global opt-in** (`playback_spatial`, a Settings toggle, live via `applyQuality`): Amazon's immersive sets carry E-AC-3 JOC (`ec-3`, the Dolby Digital Plus Atmos master — a 5.1 bed + JOC object metadata; Chromium's ffmpeg decodes the E-AC-3 core in software, so what plays is the spatial master's 5.1 core downmixed to the output — NOT object-based rendering), Dolby AC-4 (`ac-4.02.02.00`, IMS) and MPEG-H (`mha1`/`mhm1`). Only ec-3 is ever admitted (no Chromium build has an AC-4 or MPEG-H decoder — categorical), and only when the opt-in is on AND the per-build probe (`getSupportedCodecFamilies`, which EME-probes ec-3 like flac) accepts it — a probe-passing build can still fail the append (the #1262 Linux castlabs build: MSE and the EME probe both say yes to ec-3, the SourceBuffer rejects its data); the family-failure fallback covers that layer, codec-free, by dropping whatever family failed and re-selecting the next best rung mid-play. With the opt-in on and a decodable spatial set present, the pick is made WITHIN the spatial rungs for max/high (the tier ceiling shapes which rung, same flooring rule — never a silent drop back to stereo), while standard/saver let the CEILING win (a tier ceiling is the one promise the setting makes; a data-limiting tier never trades it for the family preference — no spatial rung under the corridor means stereo). The pick is LOCKED even in adaptive mode (ABR's restrictions are bandwidth-shaped and cannot pin a codec family, so roaming would leave the spatial set for stereo rungs under the same ceiling), and turning the preference off mid-track under adaptive works because applyConfig PRE-SELECTS the tier's rung before enabling ABR when the active variant is spatial — a locked selection re-configures Shaka's choice criteria onto the selected rung (audioCodec/channelCount), and enabling ABR alone would leave the candidate set confined to the ec-3 rungs, streaming ec-3 until the next track (review catch; the pre-select trips Shaka's "selected track will be overridden" advisory — accepted, the manager is meant to take over). A spatial-less manifest or an ec-3-rejecting build selects exactly as with the opt-in off. The playbar's stream-quality popup labels the rung "E-AC-3 ◗◖" (`streamQualityCodecLabel` — the ◗◖ spatial glyph pair, not the word "Atmos"). **Restrictions must always be re-sent with an explicit ceiling** — Shaka's config merge treats `{}` as a no-op, so a prior tier's cap would otherwise live forever (review #5 H1). The codec roster is additionally filtered by an EME `distinctiveIdentifier`-free probe at play (`getSupportedCodecFamilies`, cached per process): FLAC-only-on-paper builds (Linux class) select top opus instead of hitting shaka 4012. MPD per-AdaptationSet `cenc:default_KID` groups annotate errors (`kidForActiveVariant`) so a license-scope refusal names the KID family. Playing provenance, substitution (`contentResponseList[0].substituteAsin` — Amazon maps a catalog ASIN to a deliverable one) and the `cdnType` ride the trackSession. **Leaving an Amazon track stops the engine, never only pauses** — and only while the engine still owns the element (`trackSession` / `activeResolverId`). `stop()`'s unload removes `src`; calling it because Amazon is merely enabled silenced a later local file (sign-out, or the 500ms `handlePlay` race). A load interrupted by that stop is `reason: 'superseded'`, and the engine catch checks the generation before any auto-skip or dialog. `clearPlanBlocks` (sign-out) resets the license-denied families so a later account is not stuck on lossy; the playback-failed families stay — the decoder did not change with the account. Seek is the shared engine's; progress flows from the shared element like every html5 source. `stop()` carries the play token: a stale next() cannot tear down the newer play's license window.

**RENDITION GROUPS: a refused group stays out of later manifests.** Amazon tags every audio adaptation set with its rendition tier (`<SupplementalProperty schemeIdUri="amz-music:trackType" value="LD|SD|HD"/>`), one Widevine key group per tier, and a license refusal comes back in that same vocabulary (`not eligible for SD content`) — the label is the only cross-track-stable handle a refusal has (the KID is per-asset, and the license body carries no ASIN and no quality level). The plugin caches refused labels (`_refusedGroups`) and `mpdDropRenditionGroups` removes those whole `<AdaptationSet>` blocks from the manifests it serves: a key group in the manifest is a license request Shaka makes whether or not anything selects it, so remembering a refusal only at selection time still pays the round-trip on every track. The filter runs BEFORE the reply's `protectionSets` are computed, so those describe the SERVED manifest (a dropped group can never be blamed by error attribution). **The unit is the TIER, not the family and not the KID**: two sets can share a label (an Ultra-HD answer carries two FLAC sets both `value="HD"`, dropping together and reported once), and a family-scoped cache would re-pay the refusal on the next track whose refused tier rides another codec (SD and LD are both opus). **The label is read from the refusal's first sentence** (`licenseDenialSummary`'s slice, never the raw message — its `CustomerEligibility(customerId=…)` tail carries the phrase too, and a label must never be mined from PII), while **the refusal's scope reads the RAW message**: its `UNVERIFIED request` build signal is anchored at the sentence start (the redacted tail cannot impersonate it), and the summary's " - " cut can drop the very sentence that says build — so a message whose UNVERIFIED sentence sits after the separator yields no label at all and records nothing. **The scope needs a positive, recognized reason**: `VMP_VALIDATION_FAILED` or the anchored `UNVERIFIED request` sentence → `build-refused` (this build's VMP signature — it survives a sign-out), `CUSTOMER_NOT_ELIGIBLE` → `license-denied` (the account's), anything else records NOTHING — a recorded label keeps a tier out of the session's manifests, and an unrecognized reason (a per-title HD refusal, a reason Amazon invents tomorrow) must never take one away. A `build-refused` entry is never downgraded by a later account-shaped refusal for the same label (the second refusal does not unsay what the signature was refused for, and overwriting would quietly hand the group back after the next sign-in). A certificate-class refusal records no group at all (no license works on that build — group labels from it are noise). **The drop never unplays a track**: the filtered document must still carry playable audio (`mpdHasPlayableAudio` — a video set's representations are no substitute), and anything the text rewrite cannot answer whole (nested adaptation sets, self-closing or unbalanced tags) is served unfiltered rather than risk the vendored parser's hard "Unexpected close tag" — insurance for shapes today's flat Amazon audio answers never produce. The label stays opaque to the engine: `relayLicense`'s thrown `err.groupLabel` is provider-local diagnostics the bridge never forwards (the bridge contract carries reason/licenseDenied/denialReason only), and nothing renderer-side interprets LD/SD/HD — they are not the `playback_quality` tiers (saver/standard/high/max). **Sign-out (the session-generation drop) clears the account-scoped entries and keeps the build-scoped ones; a plan reading that turns `unlimited` from non-unlimited clears the account-scoped ones too** — on this stack a Prime account never reaches a licence (the plan gate refuses before any dmls request), so the reachable transition is unlimited → unknown (a bad scheduled re-read) → unlimited, and the return is the moment the old refusals must not outlive. An account switch WITHOUT a sign-out is not caught (the generation only bumps on `clear()`), so the old account's `license-denied` labels persist until a real sign-out; `build-refused` labels persist regardless — the signature did not change with the account.

**Buffer handover: the tier handover keeps the buffer.** `applyConfig`'s manual selections (the locked tier/spatial pick, the adaptive criteria re-anchor) pass `clearBuffer: false` to `selectVariantTrack` — the vendor's own ABR switch default (`clearBufferSwitch: false`): clearing at the handover discards what the pick already downloaded and re-fetches from 0, the start-of-track stutter. A mid-track tier switch therefore plays out the old rung's buffer for ~10-20s (`bufferingGoal: 10`) before the new rung's audio arrives — the same latency Shaka's own ABR switches have. Exactly ONE path asks for a clear: the family-failure fallback (the buffered bytes are what the build's media stack rejected). **A refused rung's buffer is the player's to flush, never the engine's** — the engine lets Shaka's own restriction-and-switch handle it: with more than one key session open (Amazon's manifests open one per group) a failed licence request raises no error at all, Shaka drops that session and, once the survivors have loaded, its key-status handler restricts the variant whose key never arrived (the manifest carries its own Widevine init data); a restricted ACTIVE variant re-chooses through `chooseVariantAndSwitch`, whose `clearBuffer` defaults to TRUE — the refused rung's chunk is flushed and the play continues on the rung whose key arrived, which is why Linux played before this PR at all, with only the start-of-track stutter (the engine handover's own then-`clearBuffer: true`, the fix above), never a stall. An engine-side clear ahead of that switch would only damage: the tier selection over the still-unfiltered roster (the group label is the provider's dialect) re-picks the SAME refused rung, and an SD refusal during an LD play (both opus) flushes the good LD buffer. The refusal cache shapes the NEXT track's manifest; the engine never sees the label.

**Album search and lookup** (the plugin's `albumSearch` capability, the album-page catalog fallback from #1129; both flows live in `plugins-src/amazonmusic/implementation.js` since #1356 M6, driving the ONE host web-session instance through the `window.electron.webSession` bridge like the track search). The albums tab (`/search/<q>/albums`) fires the **same** `SpecSearchSeeMorePage` operation as the songs tab, differing only in `variables.specType` (`'album'`) — live-verified 2026-10 by replaying the captured track-spec request with the album spec. The album search therefore rides the SAME spec-search runner as the track search (the M5 machinery: the replay-first template — one template serves every spec, `specBodyWithVars` patches `searchText`/`specType` — with the fallback `webSession.load` page flow, the echo rules, the breaker, and the session-generation drops), differing only in the URL builder (`amazonAlbumSearchUrl` — the same quoted-OR query on the `/albums` tab) and the parser. `searchAlbumsFromGql` + `albumFromGqlSearchNode` accept only `__typename: 'Album'` nodes — the ASIN-in-the-wrong-slot guard in reverse — and map `id`, `title` (trailing explicit marker stripped; `explicit` set from the marker or `parentalSettings`), `contributingArtists` (PRIMARY first) and the widest PRIMARY image. The album search spec carries **no `releaseDate`/`trackCount`**, so both stay null (the plugin contract allows it), and the result `url` is minted from the ASIN as `https://music.amazon.com/albums/<ASIN>` — the response's own `node.url` carries a `?ref=` tracker. The search is **not plan-gated** (the plan gate stops playback, not discovery) and carries the album-catalog jobs' #1135 staleness check: queued past the 8s step budget, it skips its page load and returns `[]`.

Album lookup (`lookupAlbumFlow`/`lookupAlbumPageFlow` in the plugin) is its OWN flow, not the runner: it replays `AlbumDetailPage`, but matching the request alone is not enough — the real album page also fires **AlbumSeo with the same `variables.id`** — a header-only op whose `data.album` has `title`/`trackCount` but no `tracksConnection` — and it arrives FIRST (live-captured 2026-10, which is how the first attempt shipped a "0 of 12 tracks" truncation). The winner is therefore judged by **response**: `amazonAlbumDetailCandidates` ranks every captured read request carrying the ASIN (detail-named, then album-named, then — the `{ anyName: true }` hornet-rename hedge — any name at all; write-shaped names are never replayed), candidates are replayed in order via `webSession.pageFetch` with a cap, and the first replay carrying `data.album.tracksConnection` (`albumTracksConnectionIn`) wins; a replayed header-only op is logged and skipped. Where the old host flow replayed candidates as they streamed in during an in-flow poll, the bridge's `load` returns the whole burst once it goes quiet — so the ranking replay runs over the complete candidate set. The capture window ENDS EARLY on the detail op itself: the load passes `capture.doneWhen` (the host's data-only stop condition, rule 5 in [web-session.md](web-session.md)) naming `"AlbumDetailPage"`'s operation-name value — the quoted JSON string, so the needle can only match the gql body's `operationName` field and never another operation's GraphQL document text — and the window closes the moment that op's headers land, before the page's subresources finish, so the whole lookup fits the renderer's 8s catalog step instead of paying page load plus a long quiet tail. The quiet window is the FALLBACK for a detail op the needle can't see (a hornet rename of the op name), and it is the album one, longer than the search tabs' shared 2.5s but sized to the same renderer step: 4.5s past the last capture (still capped by the shared 15s budget) keeps a lagging detail op inside — the old in-flow poll's wait-it-out rule, from #1135, where a detail op lagging its SEO sibling read as a bogus header-only miss — while page load + quiet still answer inside the step. When nothing carries the connection, the precedence matters: an errored replay outranks a header-only verdict — the AlbumSeo header proves the album EXISTS, so a failed replay is a failed lookup (`lookup-failed`, never a miss the album pages would cache), a header seen with no errored replay means the detail op never ran (miss with the ops log), and no candidates at all is the deleted/region miss. The envelope semantics live where they can actually bite — on the non-winning replays, since the winner is chosen by the connection, which requires `data.album`: a replay that parses with no `album` field at all (with no header seen proving the field intact) is the hornet rename of the response's `album` field — `lookup-failed`, not a miss (the playlist structural rule, mirrored; the pool is still replayed to the end first, because the response stays the arbiter), while `data.album` null — the field present, nulled — is the legitimate not-found miss (deleted / other region). The winner parses with `albumDetailFromGql`, whose envelope check is the belt for a loosened winner predicate. The `tracksConnection` has **no `pageInfo` at all** — a 100-track album answers all 100 edges in one response (live-verified), so unlike playlistDetail there is no continuation to follow; `trackCount` above the mapped rows logs as a truncation (and a 0-of-N map logs whether the edges were absent or unmappable). **Permissions + CDM.** The Amazon partition's permission handler is an allowlist — `fullscreen` only; every other request logs a one-line denial (a hidden third-party page has no business requesting anything else). **Playlist import.** `music.amazon.com/playlists/<id>`, `/my/playlists/<id>` and `/user-playlists/<id>` (the share-link shape for user-created playlists; its id is a bare hex uuid or a DASHED uuid — the id character class must accept dashes, a dashed id truncated at its first dash never matches the page's own request and the import times out into "Playlist not found") URLs route through the generic resolver `lookupPlaylist` path (`handleImportPlaylistFromUrl` and `parachord://play/playlist?url=`). All three shapes must be listed in the `.axe` manifest `urlPatterns` AND its `urlTypes` (a `/user-playlists/` URL does NOT contain the literal `/playlists/` substring — it needs its own pattern, which the manifest carries), and in the plugin's `_lib` `amazonPlaylistIdFromUrl`. **The flow lives in the plugin** (#1356 M7, `lookupPlaylistFlow`/`lookupPlaylistPageFlow`/`playlistImportPages` in `plugins-src/amazonmusic/implementation.js`, manifest 1.16.0): it drives the ONE host web-session instance through the `window.electron.webSession` bridge, and the host supplies only the primitives — `load` (the navigation + the capture window), `pageFetch` (the page-world replay) and `state`. The old host flow (and its `amazonmusic-lookup-playlist` IPC handler, its preload exposure and its helpers in `amazon-music-logic.js`) is deleted. The playlist page itself has **no ASINs in its DOM** — rows are `ListItem` buttons whose track identity lives in React fiber props — so lookupPlaylist does NOT scrape the DOM. It borrows the page's own GraphQL instead: one `load(url, {capture})` loads the playlist page in the (offscreen) search view with the capture window INSIDE the load (bodies from `onBeforeRequest`, headers paired by request id; the old host flow's 40×500ms in-flow poll is gone, replaced by the bridge's returned captures). The window ends the moment the page's own `playlistDetail` op is captured: `capture.doneWhen` (the host's data-only stop condition, rule 5 in [web-session.md](web-session.md)) names the quoted operation-name value the matcher keys on — the quoted JSON string can only match the gql body's `operationName` field, so a hornet rename never matches and falls back to the quiet window — and the import proceeds the moment the op's headers land, before `did-finish-load` included (#1423's slow-subresource fix restored the way `main` had it: the import went ahead the moment `playlistDetail` was captured, not after a 30s budget). The quiet window is the FALLBACK for a `playlistDetail` that never comes (deleted/private/other-region — or renamed), and it is the playlist's own width, not the searches' shared 2.5s: the #1437 round-2 concrete miss had an early unrelated gql at 1s, `did-finish-load` at 4s and `playlistDetail` at 4.5s — a 3.5s gap after the last capture that the shared window closed on, reading a live playlist as "not found" — so it is 4500ms past the last capture (the album layer's calibrated reference for the same SPA gql-burst class, with its pinned 4s detail-op lag; the import has no renderer step budget the way the album catalog step does, but the only case that ever pays the full window is the miss whose answer is null either way), still capped by the shared 15s budget. The returned captures are matched for the `playlistDetail` request the page itself fired for OUR id (a persisted query / APQ — `operationName` + `variables` + a `sha256Hash`, **no inline query text**, and the hash renumbers on every hornet redeploy, so nothing about the request is hardcoded). **A slow page never loses the capture (2026-11-15; doneWhen closes the found case at the op itself since #1437 round 2):** the host's `load(url, {capture})` budget escape is OPT-IN per load (`capture.returnOnTimeout: true`, passed only by this flow — #1437 review round 2, New 1): when the navigation budget runs out but the capture already holds requests, an opted-in load returns `{finalUrl, captures, loadTimedOut: true}` (one slow subresource keeps `did-finish-load` from firing long after the page's gql — the request was the point of the load, not the finished document, the #1423 bug class) while every other flow keeps the old contract — a budget timeout throws `load-failed`, transient, exactly what their `!load.success` paths already handle (a spec search must never read a slow page as a structural "never searched" that trips the breaker, and an album lookup must never take it for a not-found miss); a budget timeout with nothing captured throws for everyone. With `doneWhen` ending the window at the op, the escape is now the pathological tail — `playlistDetail` never arrived (not found/renamed) while other captures are held — and the playlist flow proceeds with the captures it got: the SPA already booted and queried, so the replay runs on the still-loading page, and a load that timed out without a `playlistDetail` is the ordinary miss with the ops log. That exact request is then replayed **to the captured URL** (never a hardcoded endpoint) from the page world via `webSession.pageFetch` with the captured headers (`x-api-key`, `csrf-*`, `music-territory`, `x-amzn-*`; browser-managed ones stripped by `amazonGqlFetchHeaders`), VERBATIM — the page's own `firstLimit` (100). **Never raise `firstLimit`**: the server serves one page per request however high the limit is raised (100 rows observed at firstLimit 500, 2026-10), so the raise buys nothing. **A playlist longer than one page continues via the response's `pageInfo.token`** — the page's own continuation state, a composite base64 blob (offset, page size, `playlistVersion`, and a dependent-service continuation marker keyed by the last row's entity) — passed VERBATIM as the `afterCursor` variable on the next request; each response's own token drives the next page. Live-verified 2026-10 against a 977-track playlist, after every plausible alternative failed: the Relay-style `pageInfo.endCursor` ("99:dfeab136-…-000099") is a **decoy** — the server ignores it and answers with page 1 again (the real web player's own endCursor-shaped request does too); the dependent blob alone errors `Invalid sequence token`; every other variable name (`after`, `cursor`, `token`, `pageToken`, …) is silently dropped; and offset-style cursors ("100:…") are ignored as well. Only the composite token advances, page over page. There is nothing to probe or synthesize — take the token from each response, stop when `hasNextPage` is false. The loop is the pure, unit-tested `paginatePlaylistTracks` (the plugin's `_lib` copy — the poller pattern: an injected `fetchPage(token)` and `now()`, its fetchPage wired to the plugin's pageFetch with the captured URL/headers), returning a named stop reason (`complete` / `exhausted` / `page-error` / `empty-page` / `no-advance` / `page-limit` / `time-limit` / `no-playlist`). **Progress is judged on RAW edges, never mapped tracks** (review feedback on #1072): a page that is entirely delisted rows maps to zero tracks but still advances, and a duplicate track first on two consecutive pages is not a repeated window — the per-edge cursor (position-encoded, present even on `node: null` edges) is what distinguishes a genuine advance from the same window served again. MAX_PAGES 40 / MAX_MS 120s cap a long import, and every stop keeps what was merged. Rows are appended, never deduped — cursor pages tile exactly (no overlap to guard), and a likes playlist CAN legitimately hold the same track at two positions (50 duplicates observed in the 977-track test playlist). Delisted tracks arrive as edges with a `node: null` (position + itemId only — no ASIN, no title, nothing to import; observed stable across runs, 30 of 977) and are dropped by the mapper — `trackCount` keeps the playlist's own count so the shortfall stays visible. The natural end (server out of tokens / `hasNextPage` false) with a shortfall logs `playlist complete: N of M rows are importable (K unavailable on Amazon)`; the `truncated` warning fires only when pages were left unfetched (failed page, no-advance, or the caps). **The chain discipline** is the M5 pattern with two M7 refinements. The LOAD phase rides the plugin's per-instance page-flow queue — TWO LANES, mirroring the host's own (`createLaneQueue` in the plugin's `_lib`, the semantics of the host's `enqueue(fn, { lane })` in main-process/web-session.js): a FOREGROUND job starts before every queued BACKGROUND job, FIFO within a lane, a running job never interrupted. **The playlist lookup's load is FOREGROUND** (2026-11-15): the user opened the playlist and is waiting on it, so it starts before every queued background page flow — the spec searches, album lookups, artist-photo jobs — behind at most the one in progress. The hover prefetch (a 250ms dwell) calls the same lookup, so it rides the foreground lane too. The replay + token-driven pagination after the load run PARALLEL-SAFE — `pageFetch` is reader traffic, and a busy answer (a concurrent navigation holds the host's readers/writer gate) is ridden out by the bounded backoff, never read as a failed page — so a 120s import does not starve every search queued behind it on the queue. **The backoff outlasts the host's load budget** (2026-11-15): the bound (`PLAYLIST_BUSY_BACKOFF_MAX_MS`, 45s) sits above `loadTimeoutMs` (30s, the host default the plugin's `load` rides — it passes no `timeoutMs`) plus margin, because a queued page flow's load takes the gate for that whole budget while the import paginates; the old ~13s bound gave up mid-import and truncated the playlist (`page-error`) or failed the lookup (`lookup-failed`, "busy"). A busy gate that outlasts even that bound fails the import honestly (`lookup-failed` / `page-error`), never a silent truncation. Two hard-won races/bugs in this path, now the bridge's contract: the captured entry must have its headers attached before it is accepted (`onBeforeSendHeaders` fires milliseconds *after* `onBeforeRequest`, so accepting on body alone races it), and `onBeforeSendHeaders` also fires for requests with no `onBeforeRequest` body (preflights, HEADs), so pair by request id, never by order. A page's own capture is preferred over an echoed one (a same-id re-import can capture the first import's in-flight replay; the echo's headers are session-aged). Pure parsers in the plugin's `_lib` (`amazonPlaylistDetailRequest`, `playlistPageInfoFromGql` — including the continuation `token`, `playlistEdgesFromGql` — the playlistDetail envelope, else a bounded shape-scan for any `edges[]`, `capturedOperationNames`, `amazonGqlFetchHeaders`, `trackFromGqlEdge`, `playlistFromGql`; album is `shortTitle` — the detail response has no full album title; artists are joined from `contributingArtists` with `role: 'PRIMARY'` first). A page that never fires `playlistDetail` (deleted/private/other-region playlist — or a hornet rename of the operation, which the miss log distinguishes by listing the operations the page did fire via `capturedOperationNames`) returns null → the resolver surfaces "Playlist not found on Amazon Music". A truncated import (pagination ended early: failed page, no advance, or the caps) is logged and the resolver keeps the playlist's own `trackCount` (not `tracks.length`) so the truncation is visible. The playlist-specific gql-error rule: errors are fatal unless `data.playlist` came back — an error envelope with a null playlist is a `lookup-failed` throw, never a miss; `data.playlist: null` with no errors — the field present, nulled — is the legitimate not-found miss (deleted/private), which surfaces as "Playlist not found" (the album section's not-found vs lookup-failed rule, mirrored). **The `.axe` offers the sign-in prompt only for `not-signed-in`**: `load-failed` is a network condition — it throws `notReady` instead, so a stalled network is neither a "missing playlist" nor a sign-in prompt. An error with no reason class (a programming error, a broken invoke) keeps the old IPC handler's shape — `Amazon Music playlist import failed: <message>`, never a silent null. Import does not require the CDM; only playback does (`no-cdm` is a playback-only failure class: the import flow never checks the CDM, and the IPC handler that surfaced it died with the old host flow). NOT plan-gated, like the album catalog (#1220: the plan gate stops playback, not discovery — the old handler never read the plan, and neither does the plugin's flow). Tests: `tests/resolver/amazon-music-plugin-playlist.test.js` (the flow against a mocked webSession bridge + the `_lib` parsers/pagination loop, ported from the logic tests) and `tests/resolver/amazon-music-resolver.test.js` (the resolver contract: the mapping, the sign-in prompt, miss vs notReady vs truncated, and the URL-pattern routing).

**Prime plays the tracks the account bought (#1494, plugin 1.22.0).** A track bought from Amazon plays on any plan, so on every plan but Music Unlimited (Prime, a free account, one Parachord couldn't read: `unknown`) the plugin plays exactly those, and enforces it itself; the host has no per-track rule. Amazon's search never says what the account owns (every search Track reads `purchaseContext.isPurchased: false`, bought ones included), so the plugin reads its own list from the library's Purchased page: `getOwnedTracks` runs `ownedTracksPageFlow` on the BACKGROUND lane, which loads `https://music.amazon.com/my/purchases` (`OWNED_PAGE_URL`) with the capture window, takes the page's own `LibraryPurchasedPageQuery` request (`OWNED_OPERATION`; variables `firstLimit` 50, `isAuthenticated`; the freshest csrf-ts among the page's own captures, never an echo), replays it, and walks its pages with `paginateOwnedTracks`: `pageInfo.token` as the `afterCursor` variable, the continuation the playlist pages and the home connection take too (live 2026-11-21: a 365-track library in 8 pages, about 6 s, ending on `hasNextPage: false`). The answer is `data.user.purchased`, a connection of `Track` nodes; `ownedTracksFromLibraryGql` finds it by a bounded scan, keeps only rows with `purchaseContext.isPurchased === true`, and takes the node `id` as the catalog ASIN (else the `/tracks/<ASIN>/` url). A response with no song connection is structural (not-ready), never "owns nothing". The Songs page (`/my/songs`, `LikedSongsPage`) lists bought and liked songs together and was the first candidate. The list is kept 3 h (`OWNED_TTL_MS`), joined while a read is in flight, started by `getStatus` on a Prime reading (never awaited), and dropped by the sign-out reset list; a read a sign-out overtook answers `superseded` instead of landing. **Search off Music Unlimited** answers from the list (`searchOwned`, `ownedTracksMatching`: a resolve's artist and title each contained either way round, folded, then resolve's own credit gate as for a catalog search; a Search-page string by its words), with no catalog search. No bought match for a resolve is `plan-ineligible` (not-ready, never a cached miss), so a new purchase or an upgrade resolves again; a Search-page string with no match is no rows. **The stream request off Music Unlimited** (`assertPlanPlaysAsin`) plays an ASIN only if it is on the plugin's own list, never because of a flag on the track; anything else is `plan-ineligible` before any dmls request, and a list that can't be read is a plain not-ready ("Couldn't read your Amazon purchases. Try again in a minute."). Each gate judges the one plan reading its call made (the search branches once on it; the old whole-catalog `assertPlanPlays` is gone), because a second read can land on the next account's plan when a sign-out races a search. **The host side:** the plugin's limit off Music Unlimited is `{ blocked: false, ownedOnly: true, planKey, label: 'Prime: purchases only' | 'Purchases only', ... }`, so Amazon stays in `playbackResolvers`; the shared playback-limits effect drops Amazon's saved sources on entering that state (`limitTransition`'s purge, "Playback limits" in [playback.md](playback.md)), since a source found on Unlimited may be a track the account doesn't own. **The first play after launch on Prime (#1603, plugin 1.22.1).** The page-flow queue runs one flow at a time, and the purchases read holds it for its page load and every replay (measured on a phone: 4.0 s and 3.8 s). The csrf mint used to run first in `getPlaybackManifest` and load a page of its own (the songs search, 5.3 s). So a play tapped while `getStatus`'s launch-time read was running waited for the read, then the mint, and missed the engine's 10 s `PLUGIN_MANIFEST_BUDGET_MS` as `playback-failed`. Now the plan gate runs before the mint. `ownedTracksPageFlow` keeps the live csrf triplet its own page sent (`keepCsrfHeaders`, through `csrfHeadersFromCaptures`, the mint's own lens: real-looking values only, the page's own request over an echo). It is kept with the session generation it was read under. The mint takes it instead of loading a page (`keptCsrfHeaders`) while it is under `CSRF_HARVEST_MAX_AGE_MS` (10 min) old and the generation still matches. The mint also reuses the gate's `config.json` read when it is under `CONFIG_REUSE_MS` (10 s) old, so a first play on Prime costs one page load and one `config.json` read, and Unlimited's costs are unchanged. A dmls auth refusal drops the kept triplet, so its one re-mint loads a page. The sign-out reset list drops both the triplet and the `config.json` read. What's left is the read itself: on a cold launch a play can still wait the whole read. Tests: the drm test's "the first play on Prime (#1603)".

**A purchase's plain stream (#1612, plugin 1.23.0).** Amazon's own web player plays a bought track without DRM: Safari fetched it from the library locker as a progressive MP3 (the capture is on parachord-mobile#780). `getStreamUrl(track, config)` asks for the same thing:
- `POST /<region>/api/dmls/` with `X-Amz-Target: …DigitalMusicLocatorServiceExternal.getStreamingURLs` (the `dmls` helper: the session's csrf triplet, its cookies);
- the body (`amazonStreamingUrlsBody`): `contentIdList: [{ identifier: <COID>, identifierType: 'COID' }]`, `bitRate: 'HIGH'`, `deviceToken`, `appMetadata` (`GreenHornet_Web`), `clientMetadata` (`WebCP`, a random request id), `customerId`;
- the answer: `protocol: 'PROGRESSIVE'` and a signed CloudFront URL that expires in about 25 minutes (`streamingUrlFromReply` takes the first https URL of a `SUCCESS`).

The COID is the purchased copy's library object id, from the purchases list the plug-in already reads: `ownedTracksFromLibraryGql` keeps `playParams.id`'s `mrn:1.0:library:track:objectid:<id>` as each row's `coid`, and `getOwnedTracks` answers `coidByAsin`. So `getStreamUrl` answers only for a track on that list, looked up by its ASIN; anything else is `null`, and a list that can't be read is the purchases' "try again". The URL is never kept or logged.

**When it plays.** On desktop, after the DRM stream fails to start (a licence refused, as on an unsigned dev build, a manifest past its budget), never after a plan refusal or the sign-in prompt ("A plain stream beside the pair" in [plugins.md](plugins.md)). Widevine stays first, for quality: Opus or FLAC against the purchase's MP3. On iOS, which has no Widevine, it would be the only way a purchase plays (parachord-mobile#779 and an iOS stream engine first). The plug-in doesn't declare `html5Stream`, so Android keeps routing it through its Widevine engine. What `bitRate: 'HIGH'` gives isn't recorded yet.

**FairPlay for an iOS host (#1627, plugin 1.24.0).** iOS has no Widevine, so on a host whose `this.host.platform` is `'ios'` (`wantsFairPlay`), `getPlaybackManifest` asks for FairPlay HLS instead of Widevine DASH; desktop and Android are unchanged. Both requests are the ones Amazon's web player sends from Safari for a catalog track on Music Unlimited (captured on parachord-mobile#780 and 2026-11-22):
- **The manifest:** `getStreamingURLsWithFirstChunkV2` on `/api/dmls/`, keyed by the catalog ASIN, with `protocol: 'HLS'`, `format: 'ENCRYPTED_AAC'`, `drmType: 'FAIRPLAY'` and the web app's `appMetadata` / `clientMetadata` (`amazonFairPlayManifestBody`). `customerInfo.entitlementList` (the plan's codes) is sent only when the session has it; `config.json` doesn't, and whether Amazon needs it is checked when the iOS engine first plays.
- **The reply** (`fairPlayStreamFromReply`): the `.m3u8` URL, Amazon's FairPlay application certificate (inline, so no certificate request), and three header lists, for the manifest, the segments and the key (a per-play `rid` cookie, the key's `x-amz-music-*` headers). The plug-in answers `{ type: 'hls-fairplay', drm: 'fairplay', url, certificate, headers: { manifest, segments, key }, asin, context }`, with `context.drmType: 'FAIRPLAY'`. The URL and headers are per-play credentials: handed to the host, never logged.
- **The licence:** the same call as Widevine's, `getLicenseForPlaybackV2` on `/api/dmls/` with `DrmType: 'FAIRPLAY'` and the SPC as `licenseChallenge` (`amazonDmlsLicenseBody`'s `drmType`), not the `getLicenseForPlaybackV3` the reply's `keyHeaders` name. `relayLicense` picks the type from the session's `context.drmType`, else the host. The answer is `{ license: <CKC, base64> }`, as for Widevine, and refusals map the same way.
- **Quality:** the HLS is AAC only (256 kbps AAC-LC, 128 and 48 kbps HE-AAC), whatever the plan, so iOS tops out at 256 kbps AAC.
- **The plan gate runs first**, as on Widevine: off Music Unlimited only a bought track passes, and a bought track also has `getStreamUrl`'s plain MP3, which needs no licence. Which one an iOS host tries first is the host's choice (parachord-mobile#794).
- **Not yet known:** whether Amazon's licence server accepts an SPC made by an app rather than Safari, and whether segments load with only the `rid` cookie. Only the iOS engine can tell.
- Tests: the "FairPlay for an iOS host (#1627)" block in `tests/resolver/amazon-music-plugin-drm.test.js`.

The one gap: an iOS TestFlight build from before #753 reads only `mobile: false`, so it lists Amazon, broken, until it updates. The catalog entry in `marketplace-manifest.json` mirrors the floors (`build-axes.js` syncs `minAppVersion`) and drops `mobile` by hand, since mobile's catalog sync reads it too.

**HTTP 294 is a partial answer, and community playlists get one (2026-11-15).** Amazon's gql server answers 294 when one field's resolver failed: the body carries `errors` for that path and `data` for everything else. ### Embedded web players: OS media-surface hijack

> **As of the native Amazon player (1.7.0), Amazon plays NO embedded audio** — its views today hold only search / playlist pages and the sign-in flow. The kit below survives for any future embedded consumer (the Bandcamp mini window was the named reason it was built generic, but Bandcamp now plays in a hidden iframe in the main window) and for the hornet-era diagnosis trail; Amazon's page silence is what makes its mediaSession facade inert there. The IPC/registry/gate rules still apply to whatever view registers. (References to hornet-era symbols in this section — e.g. `amazonWebPlayer.currentAsin` — name the pre-1.7.0 pipeline and are kept as the diagnosis trail.)

Chromium's OS media integration follows the **audio**, and an embedded web player — a third-party page playing audio in its own WebContents, Amazon's hidden views before 1.7.0 — is the only audio playing in the app while it owns playback. Its page-level media session becomes the app's *active* session: on Linux a second `chromium` MPRIS player appears next to the native `org.mpris.MediaPlayer2.parachord` (verified live with `playerctl metadata -a`, 2026-10 — full hornet metadata, and the two coexist with no bus-name collision), and OS media keys are delivered to the **page's** session — pausing the element behind Parachord's transport and desyncing the poller, the scrobbler and the UI.

**The hijack** (`installMediaSessionHijack` in `embedded-player-kit.js`, root — strict tier): at document-start in the page world it (1) unless `onAction` is null, registers **our** transport handlers on the *real* `navigator.mediaSession` (play/pause/previoustrack/nexttrack/stop — registered from the same world the page would use, before shadowing, so there is no per-world session ambiguity), then (2) shadows `navigator.mediaSession` with an inert facade so the page's own metadata, action handlers and position pushes never reach Chromium.

**Platform policy (live-verified on Linux, 2026-10 — three rounds).** Chromium publishes its MPRIS entry whenever the view's session is **active** (audio playing) — regardless of registered actions and metadata, and for ANY renderer audio (a Subsonic/local-files track in the main window showed a `Parachord Desktop`-titled entry; #848's premise was never actually true). Handlers and metadata changed only the entry's content, never its existence. The kill is a **feature switch**: main.js disables `MediaSession,InternalMediaSession,HardwareMediaKeyHandling` on Linux (the trio verified as a set; `MediaSessionService` is proven non-gating; the names were mined from the Linux binary's `k…` feature symbols — the mac build carries no Linux MPRIS code to check against). That leaves the native `org.mpris.MediaPlayer2.parachord` player as the single Linux MPRIS surface, media keys arriving over its D-Bus, and the mirror + the #976 renderer feed re-gated OFF on Linux (nothing to feed). On **macOS/Windows the session stays** — SMTC/Control Center is the designed surface the mirror feeds and the hijacked handlers receive keys through. The kit's handlers still register on every platform (moot on Linux, load-bearing elsewhere). A `media-key-handling: never` opt-out therefore means NO MPRIS at all on Linux (neither player) — consistent with the opt-out.

- **Key routing + security model (PR review, 2026-10)**: our handlers → `window.postMessage` bridge (the page world has no `ipcRenderer`; DOM events cross worlds under contextIsolation) → the preload's `ipcRenderer.send('embedded-player-media-key')` — the bridge drops events whose `source` is not its own window (cross-origin iframes inside the page can postMessage to it) → `main-process/ipc/embedded-player.js` → the **existing `mpris-control` renderer channel**, so hijacked keys land in the same idempotent, `isDuplicateTransport`-deduped transport handler native MPRIS uses (one keypress can now arrive via native MPRIS, Chromium's session and globalShortcuts at once — that guard was built for exactly this). The bridge is page-forgeable by design; what bounds it: only the **player view** is registered (the SEARCH view also runs live Amazon pages during background resolution / playlist import — a script there must not reach the transport), the registry's **`isOwned()` gate** accepts keys only while that resolver owns playback (`amazonWebPlayer.currentAsin`), a **per-sender sliding-window rate limit** (30 actions / 10s) caps transport spam, `Object.hasOwn` gates the action allowlist against prototype keys, and the worst case is transport only (play/pause/next/previous/stop). Gated on the `media-key-handling` setting like globalShortcuts/MPRIS: a `never` opt-out silences this path too.
- **Seek actions are NOT hijacked** (deliberate): Parachord's OS surfaces report `canSeek=false` today; registering a `seekto` handler would promise a seek we do not route, and without one Chromium reports no seek support so DE widgets render read-only controls.
- **The postMessage marker is page-forgeable by design** — the payload only carries idempotent transport actions. Accepted threat model for a page we already inject into.
- **Sandbox constraint**: `embedded-player-kit.js` is the single source of truth; sandboxed preloads cannot require local modules, so consumers inline a **literal copy** into their page-world stub (`amazon-player-preload.js` — the exact pattern the `__r` trap and stream capture follow). `tests/preload/embedded-player-kit.test.js` unit-tests the module (post-`.toString()` serialization check included); `tests/resolver/amazon-player-preload.test.js` runs the same scenario battery against both copies and fails on drift; `tests/main-process/embedded-player-ipc.test.js` covers the forwarder; the registration smoke test includes it.
- **Diagnostics**: the preload's hijack install (the canary the old host `getStatus().preload` carried died with the M10 status move; the M11 teardown deleted the host module itself — the stub's own console line below is the canary now).
- **Now-playing mirror (macOS/Windows)**: the embedded view's session is the app's ACTIVE session during its playback, and with the page's metadata blocked the OS card falls back to the page's own label — "Amazon Music" (the document title; observed live on macOS, 2026-10). Main mirrors Parachord's now-playing INTO the view's real session behind the facade: the existing renderer pushes (`mpris:update-track` / `-playback-state` / `-position`) feed `createEmbeddedPlayerMirror` (main-process/ipc/embedded-player.js — stateful: setPositionState needs the duration the position pushes don't carry). **Position semantics (PR review, 2026-10)**: the renderer re-fires update-track on every currentTrack identity churn (the Amazon poller's progress emits re-create the object on a duration repair or a stream-quality change — every ~2s before the VBR hysteresis below, still possible on a real change), and a position-0 push per churn loops the OS card's progress 0:00→0:02→reset — but a bare state push with no position leaves a stale rate anchor. So: a real track change re-anchors (position 0 + current rate); a real playback-state TRANSITION pushes the CACHED position + matching rate; a same-track churn that first makes the duration known re-anchors (search-resolved Amazon tracks start at duration 0 and repair mid-play); repeated identical state pushes push nothing; and the renderer pushes `mpris:updatePosition(progressRef.current)` alongside state changes and on the seek settle (it previously NEVER pushed position — the native player's position was stale too). → `sendMirrorToEmbeddedPlayer('amazonmusic')` → the view's preload relays `embedded-player-mirror` via postMessage → the stub's `applyMediaSessionMirror` (embedded-player-kit.js) writes the real session the stub CAPTURED from `installMediaSessionHijack` — held in a closure, deliberately NOT on window (a plain window property is page-writable). Gated on `amazonWebPlayer.currentAsin` (non-null exactly while Amazon owns playback — another resolver's track must not be written into Amazon's session) and **skipped on Linux** (Chromium's OS media integration is disabled process-wide there — the disable-features switch at the top of main.js; the native MPRIS player is the single surface). Artwork is filtered https-only in MAIN — the mirror payload is postMessage-broadcast in the page world where page listeners can observe it, so a file:// cover path must never make the trip; a `MediaMetadata` the engine rejects degrades to text-only (#976 pattern). Full page-world isolation is NOT achievable (a determined script can still reach the real session through Navigator.prototype's getter) — the kit docs say only what is true.
