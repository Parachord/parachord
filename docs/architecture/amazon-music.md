### Amazon Music Resolver (in-app Widevine)

`amazon-web-player.js` loads `music.amazon.com` in a `WebContentsView` on the main window, `setBounds({ x: 0, y: 0, width: 0, height: 0 })`, `persist:amazon-music` session. Zero size so it cannot cover the app. No playback OS window. Sign-in is still a real window — the user has to see Amazon's page. castlabs Electron's Widevine CDM (see Widevine section) decrypts; Amazon's page does the license exchange. Parachord does not reimplement DASH, extract keys, launch the Amazon Music desktop app, or borrow a browser CDM (`--widevine-cdm-path` does nothing on this Electron). Amazon's licence server refuses the development VMP signature (`DEVELOPMENT_CERTIFICATE_NOT_ALLOWED`); playback needs a production EVS signature, same as Apple. If the CDM is missing or playback does not start, play fails and the next resolver is tried. Historical desktop-app CDP notes: `docs/plans/2026-09-23-amazon-music-resolver-brainstorm.md`.

**Sign-in.** `amazonmusic-open-login` opens Amazon's page in Parachord. Sign-in is not finished until a profile is chosen — `/identity/who-is-listening` and `/ap/signin` are `not-signed-in` (`pageBlocksPlayback`), even if an auth cookie is already set. `openLogin`'s completion gate needs a **positive** signal (`signInLanded`): a non-wall `music.amazon.com` URL stable for two consecutive ticks AND one of (an auth cookie, a path off the bare home page, or a third stable tick — the fallback that keeps the flow alive if Amazon rotates the `at-main`/`sess-at-main`/`at-acb` cookie names). "Not on a known wall" alone used to close the window on a logged-out first paint of `/`. `isSignedIn` is **cookie-first, page-second**: with a cookie present, only the sign-in window's URL is consulted — the player/search views keep whatever URL their last navigation left behind, and a view parked on `/ap/signin` by an earlier failed search used to lock the account out right after a successful sign-in (nothing navigates those views while `isSignedIn` returns false). A genuinely dead session is caught mid-flight: search, lookup and play re-check the URL after every load and throw not-signed-in on a redirect. The search view is parked on `about:blank` when a search/lookup finishes (all exits) — no idle SPA at full speed (`backgroundThrottling: false`), no stale wall URL. The prompt is single-flight and skipped during auto-advance/radio. Search/resolve throw `{ notReady: true }` when not signed in so that is not cached as a 30-day `noMatch`. Search does not require the CDM; play does. `amazonmusic-sign-out` clears the whole `persist:amazon-music` partition (Amazon-only, so the clear is correctly scoped), destroys the views, and supersedes in-flight plays via the generation bump.

**Playback.** Resolve searches both terms quoted on the songs tab, ORing the two phrase orders in one page load — `"title" "artist" OR "artist" "title"` (`/search/…/songs`). A loose combined query misses songs (a phrase like `Stations Warning`), and a single quoted order is not enough either: Amazon's matching is order-sensitive in **both** directions — Warning's "Stations" only surfaces title-first while ХЛЕБ's "Яйца" only surfaces artist-first (live-verified 2026-10 through the app via MCP search). The OR union brings a few noise rows matching the literal keyword (titles containing "or"); the resolver's artist+title filter and the confidence gate drop them. **Search runs over the page's own GraphQL, not the DOM** (2026-10; previously a scraped track row): the songs page fires `SpecSearchSeeMorePage` with the exact `searchText` from the URL; the request (URL, headers, APQ hash, variables) is captured via webRequest while the page loads and replayed VERBATIM from the page world (`attachGqlCapture`/`replayGql` in amazon-web-player.js — the same pattern as playlist import), then parsed by pure `searchTracksFromGql`. The request is matched on `variables.searchText` (case-insensitive) across ALL header-complete bodies each poll, **never the operationName** — and **only the track spec ever matches**: an album/artist/playlist spec for the same text is rejected even when it is the only match (its edges are Album nodes whose ASIN would pass the confidence gate on self-titled releases — the album-ASIN failure the DOM-era exclusion dance existed to prevent). The shared edge mapper likewise rejects non-`Track` nodes when `__typename` is present, and strips Amazon's in-title explicit marker: the gql Track node has no explicit field, so titles arrive as `"Kunnioita [Explicit]"` — `stripAmazonTitleMarker` removes a TRAILING bracketed/parenthesized `explicit` marker (bare words like "Sexually Explicit" are real titles and kept) and sets the `explicit` flag the payload lacks, keeping the title clean for cross-provider matching and scrobbles. Structural failures throw `not-ready`, never cached as a 30-day `noMatch`: a page that never searched, another spec searched but the track spec never came (short grace, then fail), or a response with no `specificationSearch` envelope. These structural failures also trip `searchBreaker` (`createSearchBreaker` in amazon-music-logic.js, unit-tested): after 3 consecutive it opens for 10 min, failing fast instead of burning the 15s capture window on every search of a resolution run (serially on the search chain, that also starves playlist imports); after the cooldown the next search is a probe, any success closes it. An envelope with empty edges is a real miss and returns `[]`. The track nodes carry cover art (`albumArt`, via the shared edge mapper) which the resolver passes through for `getAlbumArtFromResolvers`. **Do not try to read the page's own search response instead of replaying it** — the stream-capture pattern does not work for the bootstrap search: hornet binds its fetch at module init, before any preload-injected wrapper can install (the isolated-world stub evaluates after the first page scripts run; live-verified 2026-10 — the page's own search bypasses the wrapper while a post-load fetch through `window.fetch` is observed). The stream capture only survives because media segments are fetched seconds later, at play time. The replay's cost is one request on top of the ~9 ops the page load itself fires. The player view stays at 0×0; the search view is parked at a real size **left of the window** (`x: -1200`) — a 0×0 view cannot be given the window's content size (`contentView` children paint above the page and will replace the UI). Sign-in is a real window. If play does not start, `haltPlayback()` pauses and loads `about:blank` so a late start cannot overlap the next resolver. Play loads `/tracks/{asin}?do=play` and confirms the media element is advancing. **Leaving an Amazon track halts, not pauses** (`stopAmazonIfActive` in app.js → `amazonmusic-stop`): the visibility stub keeps the page convinced it is shown, so its transport may resume an element that was only paused.

**Search gql identity** lives in the pure module so it is tested: `amazonSpecSearchRequest` (finds the page's own track search among everything the page fires — matches `variables.searchText` across all header-complete bodies, **accepts only `specType: 'track'`** by default, or an absent specType; an album/artist spec never matches the default, even alone — the album search passes `{ spec: 'album' }` instead — and `{ anySpec: true }` exists only for the grace decision in the spec-search runner, never for replay), `searchTracksFromGql` (the `data.specificationSearch.result[].edges[]` envelope → tracks; an absent envelope is `envelope: false`, which the caller must surface as not-ready — a hornet rename of the response field must not be cached as a noMatch), and `createSearchBreaker` (the structural-failure circuit breaker described above). The edge mapper is **shared with playlist import** (`playlistTrackFromGqlEdge`): the search response returns the same Track entity (`id`/`title`/`contributingArtists` with `role: 'PRIMARY'` first/`album.shortTitle`/`duration` seconds) plus `images` (widest `imageType: 'PRIMARY'` → `albumArt`), and it rejects non-`Track` nodes when `__typename` is present. Tests: `tests/resolver/amazon-music-logic.test.js`. A search-resolved track's duration 0 is repaired at play time: the poller learns the real duration from the media element and `ScrobbleManager.updateTrackDuration` patches the track the scrobble manager holds (the React duration patch creates a new object and does not reach it).

**Album search and lookup** (the plugin's `albumSearch` capability, the album-page catalog fallback from #1129). The albums tab (`/search/<q>/albums`) fires the **same** `SpecSearchSeeMorePage` operation as the songs tab, differing only in `variables.specType` (`'album'`) — live-verified 2026-10 by replaying the captured track-spec request with the album spec. It therefore shares the whole spec-search runner with the track search (`specSearch` in amazon-web-player.js: capture the page's own request, replay verbatim, the shared breaker, the parked search view); only the URL builder (`amazonAlbumSearchUrl` — the same quoted-OR query on the `/albums` tab) and the parser differ. `searchAlbumsFromGql` + `albumFromGqlSearchNode` accept only `__typename: 'Album'` nodes — the ASIN-in-the-wrong-slot guard in reverse — and map `id`, `title` (trailing explicit marker stripped; `explicit` set from the marker or `parentalSettings`), `contributingArtists` (PRIMARY first) and the widest PRIMARY image. The album search spec carries **no `releaseDate`/`trackCount`**, so both stay null (the plugin contract allows it), and the result `url` is minted from the ASIN as `https://music.amazon.com/albums/<ASIN>` — the response's own `node.url` carries a `?ref=` tracker. Album lookup replays `AlbumDetailPage` (`amazonAlbumDetailRequest` — matched on `variables.id` = the ASIN across header-complete bodies, like `amazonPlaylistDetailRequest`; only an album-named read operation matches, so an unrelated read that carries the ASIN cannot win the replay by arriving first, and after the poll window the `{ anyName: true }` hedge accepts any read carrying the ASIN in case hornet renamed the detail op — a wrong-envelope replay surfaces as `lookup-failed`, loud, instead of a silent miss; write-shaped names are never replayed) and parses with `albumDetailFromGql`: `data.album` null is the legitimate not-found (deleted / other region), a response with no `album` field at all is a hornet rename — `lookup-failed`, not a miss (the playlist structural rule, mirrored). The `tracksConnection` has **no `pageInfo` at all** — a 100-track album answers all 100 edges in one response (live-verified), so unlike playlistDetail there is no continuation to follow; `trackCount` above the mapped rows logs as a truncation. The detail response numbers tracks **per disc** (1..n, 1..m, observed on 2-disc, 3-disc and 100-track sets) but has no `discNumber` field anywhere: `assignDiscNumbers` derives disc 1, 2, … from the trackNumber resets. Tracks map with `albumTrackFromGqlEdge` — per-track `contributingArtists` (a VA compilation keeps its own artists), the title-marker strip, `trackNumber`, seconds duration. IPC: `amazonmusic-search-albums` and `amazonmusic-lookup-album` next to the track/playlist ones (reason passthrough included), preloaded as `amazonMusic.searchAlbums` / `amazonMusic.lookupAlbum`. The `.axe` declares `albumSearch` and lists `music.amazon.com/albums/*` in `urlPatterns`, so a dropped album URL imports via the generic resolver `lookupAlbum` path (`getUrlType` already typed `/albums/`); the plugin's `searchAlbums`/`lookupAlbum` throw `notReady` only on sign-in/readiness failures and return the miss (`[]` / `null`) otherwise, the same rule as `search`. Tests: `tests/resolver/amazon-music-logic.test.js` (parsers from redacted live captures) and `tests/resolver/amazon-music-resolver.test.js` (bridge mapping, the sign-in prompt, miss vs notReady).

**Auto-advance.** `amazonMusicPoller` (`amazon-music-poller.js`, extracted from main.js so the state machine is unit-tested — `tests/resolver/amazon-music-poller.test.js`) reads the in-app media element. It polls faster near the end and signals advance only in the last ~700ms, or when position wraps to ~0 after 80% (Amazon's own autoplay). A backward seek is not a finish. `stop()` cancels the startup delay so a quick skip cannot stack intervals. Three invariants the poller enforces: (1) **single flight** — `poll()` drops interval ticks while a previous poll is still awaiting `haltPlayback()` (the halt can outrun the 400ms fast interval; overlapping polls used to send advance twice per track end); (2) **the advance halt is generation-bound** — `stop()` during the halt (user skip) cancels the advance signal, and the poller passes the `playGeneration` it decided to stop into `haltPlayback`. A halt that captured the generation itself could not fail that check, so a skip that had already claimed the view got its ASIN nulled and its page blanked. Omit the generation only for an explicit stop of whatever is playing now; (3) **the pause-death latch** — a page torn down while paused advances after a grace window (`EMPTY_WHILE_PAUSED_POLL_LIMIT` dead polls), and the latch survives the `lastState` churn (the `'track'` action overwrites `lastState` with the dead value, so gating the counter on `lastState === 'PAUSED'` alone reset it every tick and the window never elapsed). The poller's `actualAsin` is **URL-first** (`reportedPlaybackAsin`): the page URL is the document we loaded; the mini-player read is the fallback for surfaces with no `/tracks/` URL, because a stale or "up next" mini-player row used to make the track-changed branch skip tracks two polls in.

**Audio quality.** The player view is 0×0, so Amazon's Audio Quality modal is unreachable. Settings writes the same hornet store the modal writes (`playbackController.audioQualitySettings`): `BEST_AVAILABLE` (labeled HD/Ultra HD), `STANDARD`, `DATA_SAVER`, plus `abrEnabled` (Auto adjust). `setQuality` validates the tier first (`normalizeStreamingQuality`; legacy `HD` maps to `BEST_AVAILABLE`, unknown tiers are rejected) — a bogus value written into the persisted entry is rehydrated at every boot until Amazon's own modal overwrites it. The change is also written to the `playback-controller` localStorage entry, because hornet's persistence reaction does not notice a nested field change while nothing is playing. The persisted `playback-controller` localStorage entry is the working mechanism for quality reads/writes: hornet rehydrates `audioQualitySettings` from it at boot, so a settings change applies on the next track. **Quality reads and EME probes must not navigate the player to the home page unmuted**: autoplay is allowed and the visibility stub tells the page it is shown, so `withQualityController`/`probeEme` self-loads are MUTED for their whole window and parked (about:blank) afterward unless a newer play claimed the view (generation check) — an unmuted home load could start audible ghost playback from a settings read. A **passive `window.__r` trap installed at document-start** (`installAmazonRequireTrap`, defined in `amazon-music-logic.js` and inlined as a literal copy in `amazon-player-preload.js`'s page-world stub — sandboxed preloads cannot `require` local modules, and an early revision's `require('./amazon-music-logic')` threw `module not found` and silently killed the entire preload; `tests/resolver/amazon-player-preload.test.js` enforces the no-local-require rule and behavioral parity of the inlined copy) is an **opportunistic** upgrade that would let writes hit the live store mid-playback — live observation (2026-10, hornet 1.18x) says it does not fire on track pages (hornet's factories appear to use a closure-scoped require, or the store materializes after require time), so expect `storeCaptured: false` there; it costs nothing to keep installed in case a hornet deploy routes requires through the global. `withQualityController` waits only `QUALITY_WAIT_MS` (3s) for the trap before falling back to the persisted entry. **Never find the module by calling `__r(id)` over an id range** — executing hornet module factories out of order wedges the page (a renderer pegged in V8 churn with every Amazon call hanging, observed 2026-10-13), and hardcoded module ids rot on every hornet redeploy anyway. Tests: `tests/resolver/amazon-music-logic.test.js` (`installAmazonRequireTrap`, `readPersistedQuality`, `writePersistedQuality`).

**Stream quality capture** (the `streamQuality` record for the Amazon source). Two cooperating mechanisms, both generation-scoped to the play:

1. **Net hook in the preload** (`installAmazonStreamCapture`, `amazon-music-logic.js`, inlined as a literal copy in `amazon-player-preload.js`'s page-world stub — same sandbox constraint and parity test as the `__r` trap). Installed at document-start, before hornet's scripts, it passively wraps page-world `fetch` and `XMLHttpRequest`: responses for `.mpd` URLs are captured as text (via `clone()`), small (≤64 KB) responses for init-segment-shaped URLs (`.mp4/.m4s/.cmfv/.cmfa/.cmf/.dash`) as bytes. The wrappers call straight through, all observation is in try/catch, and responses are only ever cloned — playback behavior must never change. Caps live in `window.__parachordStreamCaps` (≤4 manifests, ≤8 inits). Chosen over webRequest (single listener slot per method per session — would clobber the playlist gql capture) and over refetching the captured URL (signed CDN URLs).
2. **Parse in main after playback confirms** (`readStreamRepresentations`, fire-and-forget from `playByAsin` — never awaited, never fails playback): `mpdAudioRepresentations` (tolerant regex scan — audio codec/sampleRate/bandwidth/channels/init URLs from `@codecs`/`@audioSamplingRate`/`@bandwidth`/`AudioChannelConfiguration`/`SegmentTemplate`/`SegmentList`, entity-decoded, `$RepresentationID$`/`$Bandwidth$` substituted) and `flacStreamInfoFromInit` (the FLAC specific box's 34-byte STREAMINFO — sample rate/bit depth/channels, found by fourcc scan since ISOBMFF boxes nest; it's the same bytes the decoder reads). Parsed reps are paired with inits by URL (`attachInitStreamInfo`; a URL-matched init is authoritative over MPD attrs), stored on `streamRepresentations`, and exposed via `streamInfo(kbps)`.

   **Field observations (2026-10-15, live debugging via SIGUSR1 inspector):** Amazon Music's web player does **NOT fetch a DASH MPD for music** — playback URLs (init + media segments) arrive signed from hornet's backend (e.g. `cloudfront.net/…/<uuid>.mp4?r=<uuid>&rs=NA&mt=US&ql=HD_44&dtype=…` — note `ql=HD_44`, the quality label, in the query). So the `.mpd` capture stays dormant capability and the **init-segment path is the live one**: no manifest → reps are synthesized from the parsed inits alone (a `dfLa` box is proof of codec + params on its own). Second hard-won detail: Amazon's muxer spells the FLAC specific box **`dfLa`** (64 66 4C 61) — NOT the spec's `dfla` — and it sits inside an `enca` (encrypted audio) sample entry whose `sinf`/`frma` is `fLaC`, with a second clear `fLaC` entry alongside. `flacStreamInfoFromInit` scans both spellings; a spec-only scan parsed nothing for every track. Init segments are ~1KB each, two per play (refetch).

The `amazonMusicPoller` supplies the measured bitrate (`createStreamBitrateMeter`, one per track — the median of EVERY steady pair rate of the track from `webkitAudioDecodedByteCount` reads, so a VBR stream settles on its average instead of following a 16s window (review on #1100); a median rather than a mean because the first pairs read 3-5x high while the decoder's buffers fill; when the recent 8-pair median is more than `QUALITY_SHIFT_RATIO` (35%) from the track's, the tier changed (auto adjust) and the track's rates restart from the recent window. A whole-file bytes/position average is wrong twice: decoder runs ahead while buffers fill, and a seek never resets the counter), picks the ladder rung by bandwidth (`pickMpdRepresentation`), and builds the record with `amazonStreamQualityRecord`: `{ tier, codec, container, bitrate, sampleRate, bitDepth, channels, origin: 'measured' }` — fields attach only when present. The tier is derived from measured facts (`amazonStreamTier`: lossy → SD, FLAC ≤16-bit/≤48 kHz → HD, 24-bit or >48 kHz → Ultra HD) — never scraped as a label, so it cannot rot with a hornet redeploy. The renderer's onProgress handler attaches the record ASIN-gated (a stale in-flight poll emit cannot attribute the previous track's measurement). It replaces the stored record only on `window.isStreamQualityChange` (stream-quality.js): every tier above 160 kbps is VBR, so a measured median still ticks by a kbps now and then (it moved on almost every 2s poll before the whole-track meter), and replacing it each time re-created `currentTrack` (every memoized page re-rendered, the queue was re-saved). A bitrate within 10% of the stored one is not a change; any other field changing always is. The saved-queue effect also keys on `currentTrack?.id`, not the object, and reads the latest track from `currentTrackRef` when it saves. Every capture miss degrades to the bitrate-only record — nothing is fabricated. Diagnostics: `getStatus().preload` also reports `streamCapture`/`streamManifests`/`streamInits`; a manifest with no parseable audio representations logs its first 160 chars. Tests: `tests/resolver/amazon-music-logic.test.js` (capture, MPD, STREAMINFO, pairing, tier, record), `tests/resolver/amazon-music-poller.test.js` (merged record, degradation), `tests/resolver/amazon-player-preload.test.js` (parity), `tests/resolver/amazon-page-scripts.test.js` (read script).

**IPC** (`window.electron.amazonMusic`): `getStatus`, `openLogin()`, `signOut()`, `searchTracks`, `lookupPlaylist`, `debugCaptureGql` (diagnostic, below), `playTrack`, `pause`, `resume`, `stop`, `seek`, `setVolume`, `getPlaybackState`, `getQuality`, `setQuality`, `polling.*`. `getStatus` also returns `preload: { stub, storeCaptured, mediaSessionShim, streamCapture, streamManifests, streamInits }` — live proof the preload's stub/trap/hijack/net hook ran in the player page (`null` = no page loaded / unreadable; `stub: false` on a loaded page = the sandboxed-preload failure mode came back; `mediaSessionShim: false` on a loaded track page = the mediaSession hijack is not installed and the page's session is driving the OS media surface again; `storeCaptured` is **opportunistic** — it flips true only if the page's own requires route through the global `__r`, observed **false** on track pages (2026-10, hornet 1.18x), where the persisted localStorage entry is what quality actually uses; `streamCapture`/`streamManifests`/`streamInits` diagnose the net hook during a play). Errors are `{success:false, reason}` — `not-signed-in`, `no-cdm`, `not-ready`, `load-failed` (a bounded 30s page-load timeout: transient, never cached as noMatch, never offered a sign-in prompt), `superseded` (a newer play owns the player — the play-track IPC must not halt for it). All page loads go through `loadURLBudgeted`; only the user-visible sign-in window and `haltPlayback`'s `about:blank` are unbudgeted. There is no desktop-app IPC. **Permissions are an allowlist** (`fullscreen` only) on the Amazon partition: playback and the sign-in flow need no permission grant at all (HTMLMediaElement and EME are not gated by permission handlers), and a hidden third-party page has no business requesting anything else — denials log once per permission name. **CDM presence** (`cdmAvailable`) reads the status fields of `components.status()` via `cdmStatusHealthy` — optimistic for unrecognized shapes because the EME probe is the real gate, and a spurious "no CDM" disables the resolver outright.

**Playlist import.** `music.amazon.com/playlists/<id>`, `/my/playlists/<id>` and `/user-playlists/<id>` (the share-link shape for user-created playlists; its id is a bare hex uuid or a DASHED uuid — the id character class must accept dashes, a dashed id truncated at its first dash never matches the page's own request and the import times out into "Playlist not found") URLs route through the generic resolver `lookupPlaylist` path (`handleImportPlaylistFromUrl` and `parachord://play/playlist?url=`). All three shapes must be listed in the `.axe` manifest `urlPatterns`, `resolver-loader.js` `getUrlType` (a `/user-playlists/` URL does NOT contain the literal `/playlists/` substring — it needs its own arm) and `amazonPlaylistIdFromUrl`. The playlist page itself has **no ASINs in its DOM** — rows are `ListItem` buttons whose track identity lives in React fiber props — so lookupPlaylist does NOT scrape the DOM. It borrows the page's own GraphQL instead: the playlist page loads in the offscreen search view (same `enqueueSearch` chain as search — they share the view and must not interleave page loads), a main-process `webRequest` capture (bodies from `onBeforeRequest`, headers paired by request id) records the `playlistDetail` request the page itself fires (a persisted query / APQ — `operationName` + `variables` + a `sha256Hash`, **no inline query text**, and the hash renumbers on every hornet redeploy, so nothing about the request is hardcoded), and that exact request is replayed **to the captured URL** (never a hardcoded endpoint) from the page world via `fetch` with `credentials: 'include'` and the captured headers (`x-api-key`, `csrf-*`, `music-territory`, `x-amzn-*`; browser-managed ones stripped by `amazonGqlFetchHeaders`), VERBATIM — the page's own `firstLimit` (100). **Never raise `firstLimit`**: the server serves one page per request however high the limit is raised (100 rows observed at firstLimit 500, 2026-10), so the raise buys nothing. **A playlist longer than one page continues via the response's `pageInfo.token`** — the page's own continuation state, a composite base64 blob (offset, page size, `playlistVersion`, and a dependent-service continuation marker keyed by the last row's entity) — passed VERBATIM as the `afterCursor` variable on the next request; each response's own token drives the next page. Live-verified 2026-10 against a 977-track playlist, after every plausible alternative failed: the Relay-style `pageInfo.endCursor` ("99:dfeab136-…-000099") is a **decoy** — the server ignores it and answers with page 1 again (the real web player's own endCursor-shaped request does too); the dependent blob alone errors `Invalid sequence token`; every other variable name (`after`, `cursor`, `token`, `pageToken`, …) is silently dropped; and offset-style cursors ("100:…") are ignored as well. Only the composite token advances, page over page. There is nothing to probe or synthesize — take the token from each response, stop when `hasNextPage` is false. The loop is the pure, unit-tested `paginatePlaylistTracks` (amazon-music-logic.js — the poller pattern: an injected `fetchPage(token)` and `now()`), returning a named stop reason (`complete` / `exhausted` / `page-error` / `empty-page` / `no-advance` / `page-limit` / `time-limit` / `no-playlist`). **Progress is judged on RAW edges, never mapped tracks** (review feedback on #1072): a page that is entirely delisted rows maps to zero tracks but still advances, and a duplicate track first on two consecutive pages is not a repeated window — the per-edge cursor (position-encoded, present even on `node: null` edges) is what distinguishes a genuine advance from the same window served again. MAX_PAGES 40 / MAX_MS 120s cap a long import's hold on the search chain, and every stop keeps what was merged. Rows are appended, never deduped — cursor pages tile exactly (no overlap to guard), and a likes playlist CAN legitimately hold the same track at two positions (50 duplicates observed in the 977-track test playlist). Delisted tracks arrive as edges with a `node: null` (position + itemId only — no ASIN, no title, nothing to import; observed stable across runs, 30 of 977) and are dropped by the mapper — `trackCount` keeps the playlist's own count so the shortfall stays visible. The natural end (server out of tokens / `hasNextPage` false) with a shortfall logs `playlist complete: N of M rows are importable (K unavailable on Amazon)`; the `truncated` warning fires only when pages were left unfetched (failed page, no-advance, or the caps). Two hard-won races/bugs in this path: the captured entry must have its headers attached before it is accepted (`onBeforeSendHeaders` fires milliseconds *after* `onBeforeRequest`, so accepting on body alone races it), and `onBeforeSendHeaders` also fires for requests with no `onBeforeRequest` body (preflights, HEADs), so pair by request id, never by order. Pure parsers in `amazon-music-logic` (`amazonPlaylistDetailRequest`, `playlistPageInfoFromGql` — including the continuation `token`, `playlistEdgesFromGql` — the playlistDetail envelope, else a bounded shape-scan for any `edges[]`, `capturedOperationNames`, `amazonGqlFetchHeaders`, `playlistTrackFromGqlEdge`, `playlistFromGql`; album is `shortTitle` — the detail response has no full album title; artists are joined from `contributingArtists` with `role: 'PRIMARY'` first). A page that never fires `playlistDetail` (deleted/private/other-region playlist — or a hornet rename of the operation, which the miss log distinguishes by listing the operations the page did fire via `capturedOperationNames`) returns null → the resolver surfaces "Playlist not found on Amazon Music". A truncated import (pagination ended early: failed page, no advance, or the caps) is logged and the resolver keeps the playlist's own `trackCount` (not `tracks.length`) so the truncation is visible. **The `.axe` offers the sign-in prompt only for `not-signed-in`**: `load-failed` is a network condition and `no-cdm` is a playback problem (importing needs neither) — both throw `notReady` instead, so a stalled network is neither a "missing playlist" nor a sign-in prompt. Import does not require the CDM; only playback does. Tests: `tests/resolver/amazon-music-resolver.test.js` (lookupPlaylist + URL-pattern routing) and `tests/resolver/amazon-music-logic.test.js` (parsers).

**gql capture (diagnostic, no UI).** Every Amazon flow replays a request Amazon's own page fires, so a new one starts by learning that request and its response from a live signed-in session (album search and album lookup were built this way, #1130/#1131). `window.electron.amazonMusic.debugCaptureGql(url)` (DevTools; IPC `amazonmusic-debug-capture-gql`, `amazonWebPlayer.debugCaptureGql`) loads one album page (`/albums/<ASIN>`) or search page (`/search/<text>/<tab>`, e.g. `/albums`) in the search view on the search chain, waits for its gql to go quiet (3s, at most 20s), and writes `userData/amazon-gql-capture-<kind>-<ts>.json`: every operation's name, endpoint, redacted variables and header NAMES (never values; they carry the session). Only the page's own read queries about its subject are replayed, once each, to read their response shape (`gqlRequestIsAboutSubject`: the album ASIN or the search text in the variables, and never an operation that looks like a write: `add…`, `record…`, `like…`, `track[A-Z]…`, anything named or written as a mutation). Responses go through `redactGqlSample` (credential-like keys redacted, query strings cut from URLs since signed CDN links carry credentials, arrays trimmed to 3, strings to 300 chars). The helpers are pure and tested (`tests/resolver/amazon-gql-capture.test.js`). Review a capture before sharing it.

### Embedded web players: OS media-surface hijack

Chromium's OS media integration follows the **audio**, and an embedded web player — a third-party page playing audio in its own WebContents, Amazon's hidden views today, the Bandcamp mini playbackWindow a future consumer — is the only audio playing in the app while it owns playback. Its page-level media session becomes the app's *active* session: on Linux a second `chromium` MPRIS player appears next to the native `org.mpris.MediaPlayer2.parachord` (verified live with `playerctl metadata -a`, 2026-10 — full hornet metadata, and the two coexist with no bus-name collision), and OS media keys are delivered to the **page's** session — pausing the element behind Parachord's transport and desyncing the poller, the scrobbler and the UI.

**The hijack** (`installMediaSessionHijack` in `embedded-player-kit.js`, root — strict tier): at document-start in the page world it (1) unless `onAction` is null, registers **our** transport handlers on the *real* `navigator.mediaSession` (play/pause/previoustrack/nexttrack/stop — registered from the same world the page would use, before shadowing, so there is no per-world session ambiguity), then (2) shadows `navigator.mediaSession` with an inert facade so the page's own metadata, action handlers and position pushes never reach Chromium.

**Platform policy (live-verified on Linux, 2026-10 — three rounds).** Chromium publishes its MPRIS entry whenever the view's session is **active** (audio playing) — regardless of registered actions and metadata, and for ANY renderer audio (a Subsonic/local-files track in the main window showed a `Parachord Desktop`-titled entry; #848's premise was never actually true). Handlers and metadata changed only the entry's content, never its existence. The kill is a **feature switch**: main.js disables `MediaSession,InternalMediaSession,HardwareMediaKeyHandling` on Linux (the trio verified as a set; `MediaSessionService` is proven non-gating; the names were mined from the Linux binary's `k…` feature symbols — the mac build carries no Linux MPRIS code to check against). That leaves the native `org.mpris.MediaPlayer2.parachord` player as the single Linux MPRIS surface, media keys arriving over its D-Bus, and the mirror + the #976 renderer feed re-gated OFF on Linux (nothing to feed). On **macOS/Windows the session stays** — SMTC/Control Center is the designed surface the mirror feeds and the hijacked handlers receive keys through. The kit's handlers still register on every platform (moot on Linux, load-bearing elsewhere). A `media-key-handling: never` opt-out therefore means NO MPRIS at all on Linux (neither player) — consistent with the opt-out.

- **Key routing + security model (PR review, 2026-10)**: our handlers → `window.postMessage` bridge (the page world has no `ipcRenderer`; DOM events cross worlds under contextIsolation) → the preload's `ipcRenderer.send('embedded-player-media-key')` — the bridge drops events whose `source` is not its own window (cross-origin iframes inside the page can postMessage to it) → `main-process/ipc/embedded-player.js` → the **existing `mpris-control` renderer channel**, so hijacked keys land in the same idempotent, `isDuplicateTransport`-deduped transport handler native MPRIS uses (one keypress can now arrive via native MPRIS, Chromium's session and globalShortcuts at once — that guard was built for exactly this). The bridge is page-forgeable by design; what bounds it: only the **player view** is registered (the SEARCH view also runs live Amazon pages during background resolution / playlist import — a script there must not reach the transport), the registry's **`isOwned()` gate** accepts keys only while that resolver owns playback (`amazonWebPlayer.currentAsin`), a **per-sender sliding-window rate limit** (30 actions / 10s) caps transport spam, `Object.hasOwn` gates the action allowlist against prototype keys, and the worst case is transport only (play/pause/next/previous/stop). Gated on the `media-key-handling` setting like globalShortcuts/MPRIS: a `never` opt-out silences this path too.
- **Seek actions are NOT hijacked** (deliberate): Parachord's OS surfaces report `canSeek=false` today; registering a `seekto` handler would promise a seek we do not route, and without one Chromium reports no seek support so DE widgets render read-only controls.
- **The postMessage marker is page-forgeable by design** — the payload only carries idempotent transport actions. Accepted threat model for a page we already inject into.
- **Sandbox constraint**: `embedded-player-kit.js` is the single source of truth; sandboxed preloads cannot require local modules, so consumers inline a **literal copy** into their page-world stub (`amazon-player-preload.js` — the exact pattern the `__r` trap and stream capture follow). `tests/preload/embedded-player-kit.test.js` unit-tests the module (post-`.toString()` serialization check included); `tests/resolver/amazon-player-preload.test.js` runs the same scenario battery against both copies and fails on drift; `tests/main-process/embedded-player-ipc.test.js` covers the forwarder; the registration smoke test includes it.
- **Diagnostics**: `getStatus().preload.mediaSessionShim` (see the Amazon resolver section).
- **Now-playing mirror (macOS/Windows)**: the embedded view's session is the app's ACTIVE session during its playback, and with the page's metadata blocked the OS card falls back to the page's own label — "Amazon Music" (the document title; observed live on macOS, 2026-10). Main mirrors Parachord's now-playing INTO the view's real session behind the facade: the existing renderer pushes (`mpris:update-track` / `-playback-state` / `-position`) feed `createEmbeddedPlayerMirror` (main-process/ipc/embedded-player.js — stateful: setPositionState needs the duration the position pushes don't carry). **Position semantics (PR review, 2026-10)**: the renderer re-fires update-track on every currentTrack identity churn (the Amazon poller's progress emits re-create the object on a duration repair or a stream-quality change — every ~2s before the VBR hysteresis below, still possible on a real change), and a position-0 push per churn loops the OS card's progress 0:00→0:02→reset — but a bare state push with no position leaves a stale rate anchor. So: a real track change re-anchors (position 0 + current rate); a real playback-state TRANSITION pushes the CACHED position + matching rate; a same-track churn that first makes the duration known re-anchors (search-resolved Amazon tracks start at duration 0 and repair mid-play); repeated identical state pushes push nothing; and the renderer pushes `mpris:updatePosition(progressRef.current)` alongside state changes and on the seek settle (it previously NEVER pushed position — the native player's position was stale too). → `sendMirrorToEmbeddedPlayer('amazonmusic')` → the view's preload relays `embedded-player-mirror` via postMessage → the stub's `applyMediaSessionMirror` (embedded-player-kit.js) writes the real session the stub CAPTURED from `installMediaSessionHijack` — held in a closure, deliberately NOT on window (a plain window property is page-writable). Gated on `amazonWebPlayer.currentAsin` (non-null exactly while Amazon owns playback — another resolver's track must not be written into Amazon's session) and **skipped on Linux** (Chromium's OS media integration is disabled process-wide there — the disable-features switch at the top of main.js; the native MPRIS player is the single surface). Artwork is filtered https-only in MAIN — the mirror payload is postMessage-broadcast in the page world where page listeners can observe it, so a file:// cover path must never make the trip; a `MediaMetadata` the engine rejects degrades to text-only (#976 pattern). Full page-world isolation is NOT achievable (a determined script can still reach the real session through Navigator.prototype's getter) — the kit docs say only what is true.
