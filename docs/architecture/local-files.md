## Local Files Library

`local-files/` is a SQLite-backed scanner/indexer for music files in user-configured watch folders. DB lives at `userData/local-files.db`. Tables: `tracks` (metadata + paths) and `watch_folders` (configured roots).

### Where the renderer side lives

The renderer's Local Files state is the `useLocalFiles` hook, `src/renderer/hooks/use-local-files.js` (#1487, moved out of the `Parachord` component in `src/renderer/app.js`). It owns the local library (`library`) and its file-path index (`libraryFilePathsRef`, `libraryPathsVersion`), the loading flag and change counter (`localLibraryVersion`), the watch folders and their stats, the scan flag and progress, the library load (`loadLocalFilesLibrary`) and change applier (`applyLibraryChanges`), both art passes, the folder actions (add, remove, rescan, rescan all, Remove Missing Files), and two effects: the scan-progress and library-changed listeners, and the watch-folder load once the cache has loaded. Tests: `tests/renderer/use-local-files.test.js`.

Still in `app.js`, reading what the hook returns: the startup effect that calls `loadLocalFilesLibrary` and registers `applyLibraryChanges` as its `onLibraryChanged` listener (it also loads playlists and search history), the stale-local-source reconcile (it writes the cache, the collection, playlists and the queue), the re-resolve of the open album or playlist on `localLibraryVersion`, the plug-in dialog's stats load, `resolveTrack`'s stale-path checks, the ID3 editor's library patch, and the stream-quality backfill below. The hook's call sits above the first render-time read of `library`; its header has the effect-order note.

### In the Collection: merged, never saved (#1532)

The Collection's three tabs list the local library alongside what the user saved, one entry per song, album and artist, each carrying every source it has. The rules are `src/renderer/lib/local-albums.js` (pure, tested in `tests/renderer/local-albums.test.js`); app.js derives from `library` in component-scope `useMemo`s, so a rescan or a removed folder updates the tabs by itself:

- **Songs** (`collectionSongs`, then `collectionSongsSorted`): every saved track plus every library track that isn't one of them. A saved song with a matching file is one row: the saved record (its id, its love state, `syncSources`) with the file's Local Files source added, and the file's path as `filePath` (from the library row, else its local source), so the row's menu offers Show in Finder (or Remove Missing File) like a local-only row's, while Remove from Collection still means the saved record with a saved track's semantics. Same song means the library-sync rules of `sync-engine/track-identity.js`: the same artist and title through `normalizeStr`, and compatible albums (the same album without a store's " - Single" / " - EP" suffix, or a placeholder album on either side). Until #1532 the tab deduplicated by id only, and a file (`local-<n>`) never shared an id with its saved copy, so the song showed twice. `collectionTracksRef` (the Songs tab's visibility-driven resolution, the idle cross-resolver trickle, Collection Radio) reads the merged list, so a local track resolves against the other enabled plug-ins through `resolveTrack` like any collection track.
- **Albums** (`collectionAlbums`): the saved albums plus the library's albums, grouped by album artist (else track artist) and album title. Same album means the same folded artist and the same title without a store suffix, so "X" and "X - EP" are one card; a local album's id is `generateAlbumId`, as for saved albums. Every copy of one album is one card: a local copy and a saved one, and also two saved copies (a saved "X" and a saved "X - EP"), in any mix. The card is display only, never a rewrite of either saved record; it shows as saved and gets `tracks`: the union of its copies' saved songs and its files, one row per song with every source.
  - **Which copy the card shows** (`pickCardCopy`): its id, title, track count and added date come from the saved copy without a store suffix, else the earliest saved; its cover and year from the first copy that has one, else the files. `savedIds` lists every saved copy it stands for.
  - **Saving an album already saved under another copy is a duplicate.** `addAlbumToCollection` (every add-album path: the release menu, the Collection card menu, a dropped album) checks `findSavedAlbumCopy`, the same identity the tab merges by, so saving "X" while "X - EP" is saved (or the reverse) writes nothing and shows the same "already in your collection" toast as an exact duplicate. Saving an album saves no tracks, so there is nothing for a second copy to add. Library sync keeps its own matching (`calculateDiff`'s tiers).
  - **Removing or un-hearting it** removes every saved copy it stands for (`savedAlbumIdsFor`: the copy it names, its `savedIds`, and every saved album with the same identity), each with a saved album's removal semantics (the Spotify unsave where that already happens), and hides its local copy. The release menu counts an album as saved when any copy of it is (`albumInCollection` in `lib/menu-collection-state.js`), so "Remove Album from Collection" on either title takes them all.
  -  Albums with no title or a placeholder one ("Unknown Album", "Single", a service's name) stay off the tab; their tracks stay on Songs. Opening an album that has files only takes a MusicBrainz result with its own title, else opens from the catalog its files come from (the plug-in that declares `capabilities.local`).
- **Artists** (`collectionArtists`): the saved (followed) artists plus the library's, by album artist else track artist ("Various Artists" and "Unknown Artist" skipped), one card per `generateArtistId` id or folded name. An artist no service knows opens on their local albums (`fetchArtistFromLocalLibrary`, the artist page's last fallback).

**Showing is not saving.** Nothing derived is written into `collectionData`: the star, the hearts, the album and artist menus (`lib/menu-collection-state.js`), the library push and the love push and backfill all read `collectionData` (or the persisted collection), so an entry that is there only because of local files is never followed, hearted or loved and is never pushed to a service. Only the user's own follow, heart or save makes it saved; undoing that leaves it listed, unsaved. This is the failure mobile had in #705, where every scanned file became a love.

**Removing a local album hides it.** "Remove from Collection" on an album that is only local adds its album key (`"<artist>:<title>"`, both folded) to `collection_hidden_local_albums` (allowlisted in `main-process/ipc/store.js`, read with the critical keys): no collection write, no tombstone, no service call, and the files and the library stay. A saved album that also has files is unsaved as before and hidden, or it would come straight back. Adding the album to the Collection later clears the hide. Artists have no hide: unfollowing a local artist leaves them listed, unstarred.

**Every source on every track: the gate holds for the library-wide pass, not on screen.** `resolveTrack`'s eager-enrichment gate (`hasLocalSource`) skips the cross-resolver fill for a track with a local file, because resolving a whole library at once fired one search per file on every service. It still applies to every library-wide or off-screen resolution: the scheduler's background pass over the collection, queue and pool look-ahead, and the re-resolve after a library change. A local track on screen resolves like any other, so it shows its service icons up front: a row a page's scheduler context reports visible or the hovered row (the Songs tab, a playlist, an artist's tracks, search, history; the scheduler passes the context type and the callback sets `onScreen`), and every track of the open album page (`resolveAlbumTrack` passes `onScreen: true`). The idle trickle (`forceEnrichment`) fills the rest in the background, one track every 10 seconds. A service can still miss a track it has: Bandcamp's search ranks an artist's own recording below a page of remixes and covers ("Radiohead Nude": row 31 of 50), so its resolve reads every row the API returns, not the search page's 20 (`bandcamp` 1.4.9, `tests/resolver/bandcamp-deep-results.test.js`). The resolver limiter's search wrapper (`resolver-limiter.js`) passes every argument through for that; it used to drop all but the query and config. A miss cached before that stays a miss until its cache entry expires. The rule is `lib/enrichment-gate.js` (`tests/renderer/enrichment-gate.test.js`); see "Cross-Resolver Enrichment" in [playback.md](playback.md).

### Stream quality HUD (play-time, no DB)

Hovering the track title in the now-playing bar shows the exact stream parameters (`Ultra HD · FLAC · 48.0 kHz · 24-bit · 1478 kbps`) when — and only when — the playing resolver provides a `streamQuality` record on its source entry (contract: root `stream-quality.js`; see "Resolver Result Shape"). Other resolvers render the title exactly as before. **Providers today: localfiles (full record), amazonmusic (measured bitrate + captured manifest/init params — see "Stream quality capture" under the Amazon Music resolver), and subsonic + bandcamp (measured bitrate only — the shared players' decoded-byte meter, `src/renderer/lib/stream-bitrate-meter.js`; see "Resolver Result Shape" in [playback.md](playback.md)).**

**Deliberately NOT stored in the scan DB.** The info is parsed at play time: the renderer's backfill effect (app.js, next to the album-art backfill in the currentTrack effects cluster) sees that the playing resolver declares `capabilities.local` (Local Files; see "The `local` capability" below), calls `window.electron.localFiles.getStreamInfo(filePath)` (`localFiles:stream-info` IPC → `LocalFilesService.getStreamInfo` → `MetadataReader.getStreamInfo`), and attaches the result to that resolver's source, `currentTrack.sources.localfiles.streamQuality` — in-memory only, never written to the track-sources cache. (The playing-track clone does ride along in the saved queue; the backfill deliberately re-reads and deep-compares on every run instead of early-returning, so a restored session self-heals if the file changed while the app was closed.) Rationale: every file works on day one (DB columns would leave rows indexed before the feature with NULL bit depth until each file changed or got rescanned), no schema migration, and the file is the source of truth. `bitrate` is normalized to kbps once at capture (music-metadata reports bits/sec). The service caches per (path, mtime) so replays/scrubs are free. If a future non-playback surface needs this (e.g. a quality column in the library view), scan-time capture can be added then — don't add it speculatively.

### Cadences

- **Foreground:** chokidar real-time watcher per folder, `awaitWriteFinish` 2s, 2s debounce on event batches.
- **Background:** chokidar watchers torn down (Electron throttles them aggressively), replaced with a 5-min `pollForChanges` interval that calls `scanner.scanFolder` on every enabled root.

### Diff-and-delete invariant — DO NOT regress

`scanner.scanFolder` does a tree walk, builds the current set of files, and removes DB entries not in that set. Three guards exist to prevent an unreadable folder (unmounted external drive, offline network share, transient permission lapse, iCloud offload race) from being interpreted as "all files deleted" and wiping the DB:

1. **Pre-scan stat check.** `fs.statSync(folderPath)` before doing anything. If it throws or the path isn't a directory, return early with `skipped: 'unreadable'` / `'not-a-directory'`.
2. **Root-walk error propagation.** `collectAudioFiles` returns `{ok: true|false, files|error}`. The recursive `walk` only swallows errors for *subdirectories*; failure on the root path bubbles up so the caller can abort. (Subdir failures still skip silently — those are usually individual unreadable folders, not whole-volume issues.)
3. **Empty-but-DB-populated guard.** If the scan returns zero files but the DB has any entries for that folder, refuse to delete and log a warning. Mirrors the >70% completeness guard in `sync:start` for the same class of "looks like environmental, not a real change" pattern.

Without these, a user with their music library on an external drive would see the entire scanned library disappear every time the drive disconnected, and reappear on the next 5-min poll once it reconnected. That was the symptom that surfaced the bug in user reports.

### Stale local sources (parachord#1002)

A track that resolved to a local file keeps `sources.localfiles` in three places: the resolution cache (`cache_track_sources`, 30 days), the session's `trackSources`, and the `sources` on collection, playlist and queue tracks. The library DB is the source of truth for which files exist. After every **successful** library load (startup, and each `onLibraryChanged`), `libraryFilePathsRef` holds the library's file paths, and an effect strips `localfiles` sources whose `filePath` is not in it from all of those places (`src/renderer/lib/local-sources.js`, pure + tested; in memory for the collection and playlists, since it reruns every launch). `resolveTrack` also ignores a stale local source, persisted or cached. **Only a successful load may set the path set**: the error path also calls `setLibrary([])`, and an empty set strips every local source. Before handing a local file to the audio element, handlePlay asks `localFiles:file-status` ('present' | 'missing' | 'unknown', answered only for paths the DB knows): a missing file falls back to the track's other sources, or shows "File Not Found", instead of reaching the element as a 404 that Chromium reports as "source not supported" (which used to produce the "could not be decoded" dialog). It never deletes the DB row: a vanished volume looks the same as a deleted file from there, and the scanner's empty-folder guard exists to stop exactly that wipe.

### The `local` capability (#1520)

The renderer never tests the id `localfiles` in playback or resolution. Local Files' manifest declares `capabilities.local: true`, which means: its sources are files in this library (the local-files DB), so the host plays them from disk through the shared element's `local-audio:` path (`handlePlay`'s local branch), they need no network (the offline stop doesn't apply), the file is checked with `localFiles:file-status` before it plays, a source whose file has left the library is a miss (`resolveTrack`'s persisted-source filter), the wall-clock progress timer skips them, a local source stops the eager cross-resolver fill, and the stream-quality backfill above reads the file. A failed local play falls back to the track's other sources by dropping the failing resolver's source (`fallbackAfter` in `lib/playback-helpers.js`), not a named one. Another plug-in whose files are in the library would declare it and get all of this without a code change.

The check is `isLocalResolver(id)` in app.js (passed to the engine with the other capability lookups): the loaded registry answers, and before `initResolvers` has filled it the bundled copy (`FALLBACK_RESOLVERS`) does, because a restored track, a page's first resolutions and the stream-quality backfill can ask that early, and the old id check answered them then (`lib/resolver-capabilities.js`). It is a hidden capability (`lib/capability-labels.js`): it never shows as a chip. Tests: `tests/renderer/local-capability.test.js`, which plays a file through `handlePlay` for a plug-in with another id that declares it, and sends Local Files without it to its own `play()`.

Still keyed on the `localfiles` source key, by design for now: `lib/local-sources.js` and the reconcile effect that strips stale sources from the cache, collection, playlists and queue (it reads `sources.localfiles`), the source-object detection in `handlePlay` (a bare source with `filePath` is Local Files'), `use-volume.js`'s resolver detection, and the plug-in settings screens.

### Removing missing files on request (parachord#1002)

The empty-folder guard above means a folder the user emptied on purpose keeps its rows. The explicit path is Settings → Local Files → **Remove Missing Files** (`localFiles:find-missing`, then `localFiles:remove-missing` after a confirm dialog with the count; `handleRemoveMissingFiles` in `useLocalFiles`), and, for one track, the context-menu item **Remove Missing File from Library**. The logic is `local-files/missing-files.js` (pure, filesystem injected, tested) and keeps the guard's promise: a watch folder whose root can't be read is skipped and named, never counted as missing; only a definite ENOENT/ENOTDIR is missing (a permission error or a stalled mount is "unknown" and kept); and removal re-checks every path, since a file can come back between the count and the confirm. The Collection songs tab lists local-library tracks alongside collection tracks; it used to tell the context menu `isInCollection: true` for every row, so library-only tracks got a "Remove from Collection" that failed with "not in your collection". It now sends the real membership plus `isLibraryTrack`, and main offers Show in Finder/Folder for those, or Remove Missing File when the file is gone.

### chokidar caveat

The watcher (foreground mode) listens for individual `unlink` events and deletes per-file from the DB. Chokidar may fire a flood of `unlink` events when a watched volume disappears mid-session — there's currently no batched safeguard there equivalent to the scanFolder guard. If users still report disappearance with a foreground app, look at `processFileChange('unlink', ...)` next.

### Library Load Performance

Big libraries (50k–150k tracks) used to freeze the app for tens of seconds during enrichment. Three changes keep load reasonable across the size range:

**Sync warm-cache fast-path for album art.** `formatTrackForRenderer` (local-files/index.js) returns `file://` URLs for `folder_art_path` and the embedded-art cache file (`cache/embedded-<md5(file_path)>.{jpg,png}`) if they exist on disk — no IPC, no extraction. Tracks with already-extracted art render with art immediately on library load. A whole-library load (`getAllTracks`) passes `buildArtIndex()`: one `readdir` of the art cache plus one memoized existence check per other path (a folder's `cover.jpg` once per folder), instead of 2–3 blocking `fs.existsSync` calls per track in the main process (#784; 150k tracks on SSD: 915 ms → 387 ms, far more on network drives). Single-track callers check directly. **The background poll reports `poll-complete` only when a scan added, updated or removed something** (with the counts): it used to fire every 5 minutes regardless, and the renderer answers it with a full library reload. Tests: `tests/local-files/library-load.test.js`.

**Lazy embedded-art warmup** (`enrichLocalTracksWithEmbeddedArt` in `useLocalFiles`). For tracks that have embedded ID3 art or sibling `cover.jpg` but no extracted cache entry yet, an 8-way concurrency-limited background loop walks them, calls the new `localFiles:resolveArt` IPC (`resolveArtForTrack(track)` in local-files/index.js), and patches the renderer's library state in batches of 50. Runs unconditionally on every library load — costs nothing for small libraries, pays the extraction cost lazily for big ones.

**Library-scale artwork lookup, and incremental library updates (#784).** `enrichLocalTracksWithArtwork` looks up ONE track per album (`albumArtGroupKey`: album artist + album; album-less tracks are their own group), on the background lane, 4 in flight, with `skipIsrcFallback` (the MusicBrainz ISRC endpoint yields no release MBID, and at library scale it would fill the 1 req/s background lane for hours), fetches the release's Cover Art Archive front once, and publishes the URL onto the CURRENT library rows by file path in batches (never by mutation: a reload mid-pass replaces the row objects, and the memoized pages would not re-render). Each album is attempted once per session (`localArtAttemptedRef`). This replaced a 10k-track cutoff above which the pass was skipped. A watcher change no longer reloads the whole library: `applyLibraryChanges` (`useLocalFiles`) runs `classifyLibraryChanges` (`src/renderer/lib/library-changes.js`), which turns per-file results (`added`/`updated`/`removed`, and the ID3 editor's `{ type: 'update' }`) into paths, the renderer fetches just those rows (`localFiles:getTracksByPaths`, capped at 5,000), patches by file path (`applyLibraryPatch`; a re-indexed file gets a new DB row id), updates `libraryFilePathsRef` in place and bumps the reconcile. Bulk events (folder scan, rescan, folder removed, missing-files removal, background poll with changes) and anything before the first full load still reload in full. Tests: `tests/renderer/library-changes.test.js`.

**Library scan progress toast.** The `onScanProgress` listener in `useLocalFiles`, throttled at 250ms so navigating away from the scan screen mid-import still shows scan status. Prevents the "did it freeze?" reaction.

### Searching by "artist title"

`LocalFilesDatabase.search` serves the Search page and every caller that joins two names into one query: `parachord://play?artist=&title=`, the chat-link copy of it, the AI and MCP `play` and `queue_add` tools, the album-name lookup for track art (all "artist title"), and the resolver step of `getAlbumArt` ("artist album"). No column holds the joined string, so a phrase match alone never found a track that exists only as a local file: the link showed "Could not find" while searching for one word of the title worked. A row now also matches when every word of the query is a whole word somewhere in its title, artist or album.

Whole words, not substrings, because the `getAlbumArt` step accepts any result with art: "Go" + "It" must not bring back Gorillaz "Sit Down". Rows rank exact "artist title" first (so the 50-row limit can't cut it), then the phrase in the title, artist and album as before, then the rows that only hold all the words, so a phrase search keeps every row it had. One-word queries are unchanged. The words are capped at 32 because SQLite refuses a very long AND chain; dropping words only widens the match, and callers still pick with `pickTrackMatch`. At 150k tracks a multi-word search takes about 65-95 ms against about 30 ms for the phrase match alone. Tests: `tests/local-files/search-combined-query.test.js`, against a real SQLite file.

### Normalized columns

`title_normalized`, `artist_normalized` and `album_normalized` are what every lookup compares (`search`, `searchAlbums`, `getAlbumTracks`, `resolve`). `normalize()` folds a name the way the match gate does (`normalizeStr` in `sync-providers/confidence-scoring.js`), keeping the spaces: lower case, NFKD with the marks removed, letters and digits of any script, and runs of whitespace collapsed. So `search` finds what `pickTrackMatch` would accept: "Bjork" finds "Björk", and full-width forms and decomposed tags match too.

Until 2026-11 it kept only ASCII. "光" and "宇多田ヒカル" were stored and searched as nothing: a link to either matched every row and picked from the first 50, so a track outside those was never found, every non-Latin album fell into one group in `searchAlbums`, and "Björk" was stored as "bjrk". A query or title that normalizes to nothing (only punctuation or emoji) now returns no rows from `search` and `resolve`, since an empty `LIKE` pattern matches everything.

**When `normalize()` changes, bump `NORMALIZED_COLUMNS_VERSION`.** A file that hasn't changed is never scanned again, so the stored values don't fix themselves. `rewriteNormalizedColumns` runs at startup when `PRAGMA user_version` is below that constant, rewrites the rows that differ and sets the version in one transaction. If it fails, the rows keep their old values, the library still opens, and the next start tries again. It blocks the main process once: at 150k tracks, about 0.2 s when few rows change and about 1.7 s when all of them do.

### Album queries for the catalog fallback

`localFiles:searchAlbums(query)` and `localFiles:getAlbumTracks({ album, albumArtist })` (`LocalFilesDatabase.searchAlbums` / `getAlbumTracks`) back the Local Files plugin's `searchAlbums` / `lookupAlbum`, which the album pages use when MusicBrainz can't supply a track list (docs/architecture/plugins.md, "Album search"). `search()` can't serve this: it matches tracks and stops at 50 rows, so a big album was cut short and an album name shared with a song title was crowded out. `searchAlbums` groups by `album_normalized` and the album artist (else the track artist); `getAlbumTracks` returns every track in disc and track order, matching the artist in JS with the same `normalize` the columns were stored with (there is no normalized album-artist column). Tests: `tests/local-files/album-queries.test.js`, against a real SQLite file.

### IPC field translation for resolveArt

`localFiles:resolveArt` (main.js) accepts the renderer-shaped track payload (camelCase: `filePath`, `hasEmbeddedArt`, `folderArtPath`, `musicbrainzReleaseId`, `musicbrainzArtUrl`) and translates to the snake_case the resolver expects (`file_path`, `has_embedded_art`, `folder_art_path`, etc.) before calling `service.resolveArtForTrack(dbShaped)`. The renderer-side track may strip the `local-` prefix from `id`; the handler restores it for DB lookups. Forward-compatible: passing the raw snake_case shape also works since the handler reads from both keys.
