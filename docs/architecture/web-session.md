# Web sessions: the generic web-session host

> Host machinery for the #1356 split: a plugin (Amazon Music first) owns every piece of service knowledge, and each host supplies the same small set of generic primitives for driving a cookie-session web service through capture-and-replay. **The move is complete** (#1356 M1–M11, the teardown included): `amazon-web-player.js`, `amazon-music-logic.js` and the `window.electron.amazonMusic` preload block are deleted. The ONE `createWebSessionHost` instance for `persist:amazon-music` lives in `main-process/amazon-web-session.js` (registered with the bridge by main.js by reference, `setHost` wired to the app window), and EVERY Amazon flow — the track search (the spec-search runner family, M5), the album catalog (the album search, the album lookup and the artist-image lookup, M6), the playlist import (M7), the recommendations (the music-home walk and the see-more route, M8), the DRM pair (the dmls manifest/licence flows with their csrf mint and streaming telemetry, M9 — `amazon-dmls.js` and `main-process/amazon-telemetry.js` deleted with it), the session surfaces (sign-in over the bridge's signIn protocol with the plugin's decide rule, sign-out over clear, the status read — M10) AND the diagnostic capture (M11) — lives in `plugins-src/amazonmusic/`, driving the instance through the bridge (`pageFetch` replays, `load(url, {capture})` page flows matched on the returned captures, `state()` for its signed-in verdict, `fetch` for the plan read, the dmls POSTs and the telemetry events), its `_lib` plugin library carrying the pure helpers. Every rule below is what the pre-split module learned the hard way; the host is the generalization, and the tests (`tests/main-process/web-session.test.js`, `tests/main-process/web-session-bridge.test.js`, plus the plugin's `tests/resolver/amazon-music-plugin-spec-search.test.js`, `tests/resolver/amazon-music-plugin-catalog.test.js`, `tests/resolver/amazon-music-plugin-playlist.test.js`, `tests/resolver/amazon-music-plugin-recommendations.test.js` and `tests/resolver/amazon-gql-capture.test.js`) pin the contract.

## The primitives

One `createWebSessionHost(config)` instance per session (Amazon's config: `id: 'amazon-music'`, `partition: 'persist:amazon-music'`, `cookieDomains: ['amazon.com', 'music.amazon.com', 'www.amazon.com']`, `allowedHosts: ['music.amazon.com', 'gql.music.amazon.com']`, `signInTitle: 'Sign in to Amazon Music'`, the Amazon preload, a hardened UA; see the module header for every field):

| Primitive | Does |
|---|---|
| `setHost(win)` | The app window that hosts the hidden view; when it closes, the view dies |
| `load(url, { timeoutMs, capture })` → `{ finalUrl, captures? }` | A budgeted page navigation in the persistent hidden session, serialized per session, with the requests the page fired captured for the caller (bodies paired with headers by request id; over the IPC bridge, the URL must be https on one of the session's `allowedHosts`). The capture window ends on quiet or the budget (rule 5) — or, when `capture.doneWhen` names the match as data, the moment a header-complete capture satisfies it (before `did-finish-load` included) — or, when the navigation budget runs out with the capture already holding requests AND the caller opted in (`capture.returnOnTimeout: true` — the caller that knows how to judge a half-loaded page's captures), the load resolves with `loadTimedOut: true` instead of throwing (the requests were the point of the load, not the finished document; rule 5's escape). Not opted in, a budget timeout — with captures held or not — still throws `load-failed`, the old contract every flow already treats as transient |
| `pageFetch(request)` → `{ status, text }` \| `{ error }` | A fetch from inside the page world — its origin, cookies, CORS — parallel-safe; never throws, every failure is a recoverable `{ error }`; `redirect: 'error'` — a replay never redirects (a credentialed hop to wherever an allowed host redirects is not followed) |
| `fetch(request)` → `{ status, headers, text }` | A request outside the page carrying the session's cookie jar; the URL must be https on one of the session's `allowedHosts` (an EXACT-host list — much narrower than the cookie domains on purpose: `amazon.com` is the whole retail account) and EVERY redirect hop is re-checked (a hop off the list is not followed — the jar rides every hop); **Chromium owns the jar** (`useSessionCookies: true` — request cookies attach on every hop including redirects, response cookies save/delete/reject by browser rules, and the host never parses `Set-Cookie`); the caller's own Cookie header is dropped and the returned headers carry set-cookie **names** only; budgeted like every other wait (default `loadTimeoutMs`), and the request aborts when the budget fires |
| `state()` → `{ url, signInUrl, cookieNames, generation }` | The facts a plugin composes its signed-in/wall verdicts from — the hidden view's URL, the sign-in window's, cookie NAMES (empty values dropped), and the clear()-bumped session `generation` (a plugin's only window onto a sign-out it cannot see the event of: caches minted under one generation — a plan reading, a request template — must not serve the account that signs in under the next) |
| `signIn(url, { decide })` → `{ signedIn }` | A visible window (no preload — it must behave like a normal browser window; the title is host config `signInTitle`, never a caller choice) ticked once a second; `decide({ url, cookieNames, stableTicks })` is the plugin's pure verdict; the person closing it first is NOT signed in |
(fix(plugins): cold-view quiet window + session generation (#1356))
| `clear()` | Sign out: views die, the sign-in window closes, the partition's storage clears (the declared `cookieDomains` are the portable contract; Electron clears the whole partition, a superset), and the load chain — both lanes — is cut: a new account starts clean |

What stays in the host and must never leak into a plugin: the view and its capture hook, the cookie store (values especially), the player, the per-session limits, the quality-to-track-selection policy. What lives in the plugin and must never leak into this module: every service name, URL, wall predicate, GraphQL shape and parsing rule — **this file must never grow a service name**. (`chromeUserAgent` is a deliberate host-owned helper — the host config wants a hardened UA without any service knowing how it is built; the pre-split module's own copy died with it.)

## The move: one owner of the partition

During the flow-by-flow move, the pre-split module's own machinery and a host instance would BOTH run on `persist:amazon-music`: they would share the partition's single `webRequest` listener slot while each keeping its own view, chain and gate — so rules 1 and 2 would not hold *between* the two modules, and either one's capture could silently replace the other's listener. (The permission handlers are guarded by a one-time flag on the session and only one allowlist would apply — harmless while both allow only `fullscreen`.)

**The order that avoided this, as it ran:** the first consumer step moved the pre-split module's view, chain, capture, gate, fuse, sign-in window and sign-out onto ONE `createWebSessionHost` instance — before any flow logic moved. From then on the slot had exactly one owner, and every flow moved onto that instance one at a time (the searches and the album/artist catalog M5/M6, the playlist import M7, the recommendations M8, the DRM pair M9, the session surfaces M10, the diagnostic capture M11). The teardown (M11) then deleted the host module entirely: the ONE instance for `persist:amazon-music` lives in `main-process/amazon-web-session.js` (config + `setHost` wiring; main.js registers it with the bridge), and no service logic remains host-side anywhere.

## The concurrency contract

The primitive signatures don't show the half that makes them safe; these rules are the contract, pinned by the tests (each is "rule N" in the module header and the test suite):

1. **Loads serialize.** `webRequest` has a single listener slot per method per session, so two page loads must never interleave captures. Every `load` runs on an internal chain — `enqueue(fn, { lane })`, the host's job queue in two lanes (#1423's semantics): a FOREGROUND job (something the user is waiting on, by the plugin's judgment) starts before every queued BACKGROUND job, FIFO within a lane, the one running job never interrupted; `clear()` resets both lanes. A plugin wanting flow-level serialization (a multi-step import) serializes itself.
2. **A navigation waits out in-flight pageFetches.** Tearing a frame mid-fetch kills a replay: pageFetch is a reader, `load` and the idle park are writers on a readers/writer gate. A pageFetch arriving while a navigation holds the gate resolves `{ error: 'busy' }` — the caller falls back to its page flow.
3. **The idle park never blanks a busy view.** A page fetch needs an origin page world (`about:blank` is a null origin: no cookies, no CORS), so the view stays warm `warmMs` after the last activity and parks then (an idle SPA otherwise runs at full speed forever). The fuse re-arms at fire time while any load/pageFetch is in flight. Known residual: a plugin flow's gaps BETWEEN host calls (pure parsing) don't hold the view — keep inter-call gaps well under `warmMs` or accept the re-mint.
4. **Captures flag our own traffic.** The capture listener is session-wide, so a pageFetch racing a load's capture window shows up in that load's captures. Any capture observed while a pageFetch was in flight is flagged `echo: true`; the plugin's matchers use that to skip template re-mints and degrade fast-fail graces (the #1152 class: an echoed replay once poisoned a template and left the search breaker open for a day).
5. **The capture window is quiet-bounded, and only data requests are recorded — and it can end on the caller's own named match.** `load` returns its captures when the page's request burst goes quiet (`quietMs` with no new captured request after the last capture), never later than `budgetMs`. A page that has fired NOTHING yet is not quiet — it has not started: with zero captures the wait runs to `budgetMs` (the old in-flow poll's unconditional window), so a cold view whose first gql lands well after load-finish is captured instead of reading "never fired". The host cannot know which request matters — the matcher is plugin-side, pure, over the returned captures — so it must not stop early on a match it can't see. The same rule bounds the navigation budget itself, OPT-IN (`capture.returnOnTimeout`, a boolean): **a budget that runs out with captures already held returns them with `loadTimedOut: true` instead of throwing — but only for the caller that opted in** (rule 5's escape, the #1423 bug class — one slow subresource keeps `did-finish-load` from firing long after the page's gql, and the plugin's matcher, not the host, judges whether what was captured is enough; a quiet window never runs past that point, the captures return at once). The default keeps the old contract for every flow that has not said it can judge a half-loaded page: a budget timeout — with captures held or not — throws `load-failed`, which those flows already treat as transient (a spec search must never read a slow page as a structural "never searched", and an album lookup must never take it for a miss). The one exception is the caller SAYING what the match is, as data: `capture.doneWhen`, a small declarative record (`{ bodyIncludes?, urlIncludes? }` — non-empty strings, known keys only, validated before any state is touched; over the bridge, rejected like a bad prefix). A capture matching it — header-complete (headers paired by request id, the same bar a snapshot's consumers see), never an echo (rule 4) — ends the window AT the match, before `did-finish-load` included: the load returns while the navigation keeps loading in the background, so a flow whose answer arrived mid-page-load is not held hostage to the page's slowest subresource. No match, and everything behaves as today (quiet window + budget). A capture records only `resourceType` `xhr`/`fetch` (#1432 advisory follow-up: the registered prefixes are gql and `/api/` endpoints — always data; a main-frame navigation or redirect hop to a prefix host would otherwise carry a return-leg URL, a signed assertion or a code included, into a caller's captures). And **the sign-in window's requests are the only ones refused**: the listener is session-wide, so each request's `webContentsId` is checked against the sign-in window's, read live — the sign-in window shares the partition, and its requests (a sign-in form's POST body, password included) never land in a capture. Everything else is KEPT, including requests Electron leaves the `webContentsId` off (worker-issued traffic): a keep-list shaped on the hidden view's id would drop those silently, and a capture a page's worker drives would come back empty.
Error convention: `load` throws `Error`s with `.reason` (`'load-failed'`, `'not-ready'`, `'invalid'`, `'superseded'` — a `clear()` superseded the load, and its captures belong to the old account) — the same shape the pre-split module's flows threw; `pageFetch` never throws. One exception, rule 5's opt-in escape: a load with a capture that passed `returnOnTimeout: true` and whose navigation BUDGET runs out while the capture already holds requests resolves `{ finalUrl, captures, loadTimedOut: true }` instead of throwing (see rule 5). Another: a navigation aborted by a client redirect or by the view being destroyed rejects with Chromium's raw error (`ERR_ABORTED`), which carries no `.reason` — the same thing the host's `loadURLBudgeted` propagates; callers treat it as a failed load.

## The IPC bridge

**How a plug-in reaches it.** The bridge's methods below are a contract every host implements, not an Electron API: a host with a web session supplies the same `load`, `pageFetch`, `fetch`, `state`, `signIn` and `clear`, with the same semantics, and advertises `webSession` in `window.__parachordHostBridges`. Under the plug-in host contract (#1561, "The plug-in host contract" in [plugins.md](plugins.md)), a plug-in that declares `webSession` in `requires.hostBridges` reaches it as `this.host.webSession`; Amazon Music does, through its `hostBridge` accessor. Desktop still exposes it as `window.electron.webSession.*` (below): that is where the supplier reads it from, and it stays as the fallback for desktop builds from before the contract.

`main-process/ipc/web-session-bridge.js` exposes registered host instances to the renderer as `window.electron.webSession.*` (the thin wrappers live in `preload.js`). Every call names its session by the id its host registered under — Amazon's is `amazon-music`; the plugin owns the knowledge of which session it drives. `registerWebSession(id, host)` is main.js's seam: Amazon's ONE host instance (owned by `main-process/amazon-web-session.js`) registers there **by reference** (never re-created — a second instance would fight for the partition's single webRequest slot, see "The move" above), and main.js stays thin.

**Honest scope (the same note the widevine bridge carries):** the session id is chosen by the CALLER. Every plugin runs in the main window's top frame and passes the sender gate exactly like app code, so any plugin — or any script that ends up in the main window — can drive ANY registered session by its id, and any renderer code can answer `sign-in-decide` for any callId. That is NOT plugin isolation, and per-session namespacing is NOT an isolation boundary; nothing here names a plugin as the owner of a session. The protection is the URL scoping below (the https exact-host allowlist for `fetch`/`pageFetch`/capture prefixes/`load`/`signIn`) and the sender gate — the session-bearing surface outside those scopes does not exist. Real isolation arrives only when plugins stop sharing a renderer.

Channels (`ipcMain.handle`), all gated like the widevine bridge — only the main window's top frame may call (`isAllowedSender`, literally the same predicate main.js passes both bridges; a registration that forgets its predicate DENIES every caller, the gate fails closed) — with the same honest note the widevine bridge carries: that is sender gating, NOT plugin isolation.

| Channel | Invoke payload | Resolves |
|---|---|---|
| `webSession:load` | `{id, url, opts}` | `{success: true, finalUrl, captures?, loadTimedOut?}` |
| `webSession:pageFetch` | `{id, request}` | `{success: true, status, text}` or `{success: true, error}` |
| `webSession:fetch` | `{id, request}` | `{success: true, status, headers, text}` |
| `webSession:state` | `{id}` | `{success: true, url, signInUrl, cookieNames, generation}` |
| `webSession:clear` | `{id}` | `{success: true}` or `{success: false, reason: 'clear-failed', error}` |
| `webSession:signIn` | `{id, url, window?}` (`window` is `{width, height}` — the title is host config) | `{success: true, callId}` — settles via the settled event below |
| `webSession:sign-in-decide` | `{callId, verdict}` | `{success: true}` |

Error contract, same as the widevine bridge: handlers resolve `{success: false, reason, error}` — never throw over IPC — and a host throw's `.reason` crosses verbatim (`'load-failed'`, `'not-ready'`, `'invalid'`, `'superseded'`). Unknown session id → `reason: 'not-ready'`. `pageFetch` never throws (the host's contract), so its channel outcomes are always `{success: true, ...outcome}` — a caller distinguishes a response (`status` present) from a recoverable miss (`error: 'busy' | 'no-origin-page' | …`) by the error key.

**URL scoping (the protection; see "Honest scope" above).**

- `webSession:fetch` and `webSession:pageFetch` reject with `reason: 'invalid'` any URL that is not https on one of the session's `allowedHosts` — an EXACT-host list the host declares at construction (Amazon's: the music host and the gql host), separate from `cookieDomains` and much narrower than it on purpose: the jar rides these requests, and `amazon.com` (the cookie domain) is the whole retail account — a fetcher scoped only by the cookie domains could read it. The host's `fetch` enforces the same list on its own initial URL and re-checks EVERY redirect hop (a hop off the list is not followed; `net.request` follows redirects by default), so the bridge's check and the host's hop checks cannot drift — they share one predicate (`urlOnAllowedHost`).
- `webSession:load`'s `opts.capture.urlPrefixes` are scoped to the same allowlist (a capture prefix chooses what gets RECORDED — request bodies included — so it is at least as sensitive as a fetch target).
- `webSession:load` and `webSession:signIn` accept only https URLs on the session's `allowedHosts` — the same exact-host list as `fetch`/`pageFetch` and the capture prefixes (Amazon's flows only ever navigate `music.amazon.com`, so the shared list costs the service nothing; a service whose sign-in starts on another host adds a navigation allowlist in the host config when it arrives).
- **Budgets are capped at the bridge:** `load` passes the host `min(the caller's value, the cap)` — timeoutMs ≤ 60s, capture budgetMs ≤ 30s, capture quietMs ≤ 10s. An absent or non-numeric budget stays absent (the host defaults apply).
- **`capture.doneWhen` is validated, not clamped** (it is data, the data-only stop condition of rule 5): the bridge applies the host's own shape rule — known keys (`bodyIncludes`, `urlIncludes`), non-empty strings of at most 512 chars, at least one of them — and rejects anything else with `reason: 'invalid'` before the host is touched, the same refusal a bad capture prefix gets. A stop condition is a wait-ending power, so an unknown key or a non-string value must not ride through on a typo.

**Capture scope (the host's half).** The capture listener is session-wide; it records only `resourceType` `xhr`/`fetch` (the registered prefixes are gql and `/api/` endpoints — a main-frame navigation to a prefix host would carry a return-leg URL into the captures), and it refuses ONLY the sign-in window's requests beyond that: each kept detail's `webContentsId` is checked against the sign-in window's, read live — the sign-in window shares the partition, and its requests (a sign-in form's POST body, password included) never land in a caller's captures. Everything else is kept, including requests Electron leaves the id off (worker-issued traffic) — a keep-list shaped on the hidden view's id would drop those silently and empty every capture a page's workers drive. Each capture registration logs the count of requests it refused (no URLs) when it detaches, so a future regression is readable in the field. Separately, the hidden view refuses a main-frame redirect off the cookie domains (`will-redirect` — the open-redirect half of the same follow-up; the sign-in window follows its identity hops, so only its start URL is scoped).

**The hidden view stays on the service's pages.** A main-frame hop that leaves the cookie domains is refused, both a server redirect (`will-redirect`) and a navigation the page starts itself (`will-navigate`: a script setting `location`, a meta refresh, a link or form). The cookie domains, not the allowlist, so the service's own identity hop stays free. The host's own loads don't fire `will-navigate`; their URLs are scoped at the bridge. The sign-in window has no such guard, since following identity hops is its job; its start URL is what keeps it on the service.

**`pageFetch` runs only in a page on an allowed host.** It runs in the page's own world, so the page must be on one of the session's `allowedHosts` (`urlOnAllowedHost`); otherwise it answers `{ error: 'page-off-host' }` without running. It checks again after the fetch, and drops the result if the page changed while it ran.

**The sign-in window's title** comes from the host config (`signInTitle`), never from the caller: a caller-chosen title on a window with no URL bar is a phishing surface. The channel's `window` payload is `{ width, height }`.

**The signIn protocol.** The plugin's `decide()` verdict cannot cross IPC as a function, so the bridge runs the host's ticker with its OWN decide() and shuttles the verdict across:

1. `signIn(id, url, {decide, window})` (the preload wrapper) invokes `webSession:signIn`; the channel answers `{success: true, callId}` immediately and the host opens the window.
2. Every host tick is forwarded to the main window as `webSession:sign-in-tick` `{callId, url, cookieNames, stableTicks}`.
3. The wrapper runs the plugin's `decide(tick)` — the host's tick shape (`{url, cookieNames, stableTicks}`; the callId is the protocol's routing key, stripped before the call — the plugin's decide is the same pure verdict it would hand the host) — and invokes `webSession:sign-in-decide` `{callId, verdict}` (a throwing decide is ignored — verdict false — exactly what the host does with one).
4. The bridge's decide() answers the host with the LATCHED verdict — the latest renderer answer per callId, true when any joined call says true — so a true verdict lands on the NEXT tick, up to one `signInTickMs` (1s) later than a host-side decide would have settled. That one-tick latency is the price of reusing the host's ticker unduplicated: the bridge never runs its own interval, so it can never double-tick or drift from the host's trace logging.
5. When the host promise settles (a true verdict closes the window; the person closing it first is NOT signed in), every callId gets `webSession:sign-in-settled` `{callId, signedIn, error?}`, and the wrapper's promise resolves `{success: true, signedIn}`. A refused invoke (unknown session, gated sender) resolves `{success: false, reason, error}` instead — the wrapper's promise always settles.

Two signIn calls for the same session JOIN, exactly like the host's own join: one window, one ticker, one `host.signIn` call — the bridge mints a `callId` per invoke and mirrors them onto the same run, so no second window opens and no second interval runs. Both callIds receive every tick, and both settle together. A joined call's `url`/`window` are ignored — the open window's flow is the one that runs.

The Amazon plugin is the bridge's caller for every primitive: the track search (#1356 M5, `load`/`pageFetch`/`state`/`fetch`) came first — and the exposure went LIVE with that move, the #1432 review's note-8 option (the layer that first drives the bridge registers the session and turns the preload's block on, together): main.js registers the `amazon-music` session, and the preload's `webSession` block and the `webSession` entry in `window.__parachordHostBridges` are on `window.electron` for every caller — the album catalog (M6) second (the album search and artist images ride the same calls, the album lookup its own `load` + candidate `pageFetch` flow); the playlist import (M7) and the recommendations (M8 — the music-home walk and the see-more route, multi-page `pageFetch` walks over one `load`) followed; the DRM pair (M9, `fetch` for the dmls POSTs and the telemetry events) and the session surfaces (M10 — `signIn`'s first renderer-mediated caller: the plugin supplies the decide rule, the preload wrapper runs it per tick) after them; the diagnostic capture (M11, `load` with a wide capture window) is the last. The hostBridges declaration a plugin uses to require the bridge (`requires.hostBridges`, `window.__parachordHostBridges` — the Amazon plugin's manifest declares `["webSession"]`) is #1355's per-platform loading rule; see "Minimum app version" / "Required host bridges" in [plugins.md](plugins.md).

## The #1356 plan: complete

The whole move is done. What the plan delivered, milestone by milestone: the IPC bridge with sender gating (the gate fails closed) and caller-named sessions — the session id is chosen by the caller, any plugin can drive any registered session, and the URL scoping is the protection (see "Honest scope" above;
