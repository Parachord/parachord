# Renderer patterns (full text)

> Moved verbatim out of `CLAUDE.md` on 2026-10-22 so the always-loaded guide stays short; `CLAUDE.md` indexes this file. Line references such as `app.js L####` date from when each passage was written and have drifted: search for the named function instead. Cross-references to other sections point at sibling files in `docs/architecture/`.

## Common Patterns

- **Track ids must be Unicode-aware: `src/renderer/lib/track-slug.js` (`trackSlug(artist, title[, album])`, `slug(name)`)** — never hand-roll `` `${a}-${b}`.toLowerCase().replace(/[^a-z0-9-]/g, '') ``. That ASCII strip deletes every Cyrillic/CJK/Arabic character, collapsing EVERY track on a non-Latin release to the same id: all rows showed as playing, all rows shared whichever one track resolved first (badges for the wrong song), and clicking any other row re-scored the shared source against the clicked row's title and failed the 0.6 confidence floor — "sources exist + resolver active + still No Enabled Source" (live-reported 2026-10, Король и Шут release; both tracks resolved fine individually — the id was the bug). The fold is **NFKD → combining-mark strip → lowercase, in that order** (lowercase-before-NFKD lets `™`→`TM` leak uppercase into ids — review, #1079) and is byte-identical to the old formula for pure-ASCII input; accented-Latin ids change once (Beyoncé: `beyonc` → `beyonce`). These ids key session state (`trackSources`) and queue entries, NOT `cache_track_sources` (keyed by raw `artist|title`) — worst case a restored queue item doesn't show as playing on a release page until replayed. The two-part form is a distinct call (`arguments.length`): a 3-part call with an explicitly undefined album keeps the 3-part shape instead of falling into the 2-part form and colliding across albums. All ~55 id sites (release pages, playlist/queue/context fallbacks, artist ids) route through the helper; `tests/renderer/track-slug.test.js` includes a zero-tolerance drift guard, an import-destructure check, and a **runtime guard that renders the artist cards and invokes their drag/context handlers** (the render smoke test renders with empty props, so a helper used only inside a handler resolves by accident in the bundle and ReferenceErrors in the field). **Collection ids** (`generateTrackId`/`generateAlbumId`/`generateArtistId`, the collection, love-push and library-sync keys) had the same collapse and were fixed in #1401: one formula in `sync-engine/collection-id.js` (`trackSlug` itself now lives in `sync-engine/track-slug.js`, re-exported here), shared by the renderer and the sync providers, with a one-time migration ("Collection ids" in [sync.md](sync.md)). **Known siblings, not yet fixed** (review, #1079): the remaining same-class id sites in app.js: `createTrackFromMeta` (~L6152), `critics-${artist}-${album}` (~L27085), the hyphen-replace artist ids (~L29288/L29389/L41763/L41777).
- **Every setState is a full-app render; coalesce bursts.** The UI is one component with ~380 state hooks and ~3,700 elements per render, nothing memoized per page, so a setState per item during a scroll (one resolved track every ~150ms from the scheduler, one artist image per lookup) is one full render per item and visible stutter (Fresh Drops / Recommendations, 2026-10-17). `window.createCoalescedUpdater(apply, delayMs)` (module scope, tests in `tests/ui/scroll-state-coalescing.test.js`) batches per-key writes into one setState: `queueTrackSources(key, value, { merge?, immediate? })` replaces every whole-entry `setTrackSources(prev => ({ ...prev, [key]: ... }))` in the resolution paths (merge for the missing-resolver flush, immediate for playback-time writes so they stay ordered with queued ones), and bulk rewrites call `flushTrackSources()` first. Recommendation artist images go through `recArtistImageWriterRef`. Two related rules from the same fix: hover prefetch on card grids runs on a 250ms dwell (a shared card's `onHoverPrefetch`, or `hoverDwell` from `lib/hover-dwell.js` on any other element; `scheduleHoverPrefetch` is gone), never raw `onMouseEnter`, because cards scrolling under a stationary pointer fire mouseenter each; and hero-header collapse-on-scroll goes through `window.headerCollapseDecision` (hysteresis 100/50px plus a content-height guard), because a single threshold flip-flops when collapsing the header clamps scrollTop back under it. The structural fix is memoizing page subtrees (track 2 of `docs/plans/2026-10-15-maintainability-refactor.md`). Derived lists a page builds from big state belong in a component-scope `useMemo`, never inline in the render: the Collection → Songs list (library + collection, deduplicated, filtered, sorted) cost ~60 ms per render at 150k tracks until it became `collectionSongsSorted`, which also reuses track objects that already have an id rather than copying them, because the MBID/artwork enrichment mutates library tracks in place (`tests/ui/collection-songs-memo.test.js`).
- **Pages have MusicBrainz request budgets, and `tests/renderer/page-load-budget.test.js` holds them.** Every MusicBrainz request on a page's critical path costs a second or more (one start per 1.1s), so the budgets are counted against a fake `fetch` rather than timed: an album page costs 0 requests when cached, 1 for a release id or a flagged release-group id, 2 for an unflagged group id (`loadRelease` in `src/renderer/lib/release-lookup.js`); an uncached artist page costs 3 with a known MBID and 4 otherwise, with its three release-group requests started together and each type shown as it answers (`artistLookupPlan` / `loadArtistReleaseGroups` in `src/renderer/lib/artist-discography.js`). A change that adds a request to one of these paths fails there; raise the budget only on purpose. The album page's source dropdown (#1238) stays off these paths on purpose: its group-editions fetch (`fetchReleaseGroupReleases` in `src/renderer/lib/release-lookup.js`) runs only when the user opens the dropdown, after the page loaded, and the browse that loaded the page usually kept the list already (see "Album search" in [plugins.md](plugins.md)).
- **A click must change the view before its MusicBrainz lookup, and prefetches use the background lane.** Every `musicbrainz.org/ws/2/` request goes through the fetch interceptor's limiter (`window.musicbrainzLimiter`): starts at least 1.1s apart, two in flight, and background work never holds the second slot (`backgroundMaxConcurrency: 1`), so a click never waits for a slow background request that has already started. A lookup is still up to a second away, and longer behind whatever foreground work is queued. `openChartsAlbum`, `openCriticsPicksAlbum`, `openTopAlbum` (Fresh Drops, charts, Critic's Picks, and Home's Fresh Drops and Critical Darlings cards) and the playbar's `openAlbumForTrack` used to await the lookup and only then navigate, which read as "the click did nothing" (2026-10-17). Openers call `showReleasePlaceholder` (artist, a `_isPartial` release, `loadingRelease`, `navigateTo('artist')`) and look up after, like the collection-album opener; the three card openers are one function (`openChartsAlbum`, the other two are field-mapping wrappers), a release MusicBrainz does not have clears the placeholder (`setCurrentRelease(null)` + `setLoadingRelease(false)`) and falls back to the artist page, and a lookup that failed (an outage, throttling) stays on the album page: `showReleaseLoadError` sets `_loadError` (wording from `describeMusicBrainzError`) and a `_retry` descriptor, and `ReleasePage` shows the reason and Try Again in place of the track skeleton (`fetchReleaseData` failures too). Before either, every opener (and `fetchReleaseData`) tries the plugins' catalogs (`loadAlbumFromCatalogs`, see "Album search" in plugins.md), and a release that came from a service skips MusicBrainz; an opener that searches MusicBrainz itself (the collection opener, `parachord://album`) shows a placeholder release first, so the catalog result fills only the page still waiting for it. A page still waiting after 5s (MusicBrainz queued, not failing) gets the catalog list too, and MusicBrainz's list replaces it on arrival. The artist-page fallback for a failed lookup sent a second round of requests to the service that was down and left the user on a page they had not opened (2026-10). The interceptor is the only MusicBrainz retry layer (`mbFetchWithRetries` in `src/renderer/lib/musicbrainz-fetch.js`: 429/503 and dropped connections, backoff that `Retry-After: 0` cannot cancel); callers use plain `fetch`. Underneath it, a request to MusicBrainz or the Cover Art Archive that fails at the network level is retried over IPv4 through the main process (`createIpv4Fallback` in `src/renderer/lib/metabrainz-ipv4.js`, `main-process/ipc/metabrainz-ipv4.js`), and for 10 minutes after one, requests go there directly: both hosts share one IPv6 address, which on 2026-11-01 accepted connections and then reset the TLS handshake for hours while IPv4 worked, and Chromium falls back to IPv4 only when the connection itself fails. Only what the user asked for takes the foreground lane. Covers are decoration: `getAlbumArt`'s MusicBrainz search is background unless a caller passes `background: false`, and so are the Wikidata-id fallback behind bios and photos (`createWikidataIdLookup`), the playbar bio tooltip's artist search, and the Shuffleupagus suggestions' MusicBrainz validation. On 2026-11-01 five cover searches queued at launch (the queue's and the restored page's covers) made the artist page's own lookup wait 11s, and its first releases land at 15s; with covers in the background they landed at 5.9s. Anything speculative (the five hover tracklist prefetchers, Fresh Drops' artist pass) passes `mbBackground: true` (`searchMusicBrainzRelease(..., { background: true })` for the shared search) so it drains only when no user-initiated request is waiting. The artist page (`fetchArtistData`) shows each release type (album, EP, single) as its request answers instead of waiting for all three; if none has shown after `ARTIST_SLOW_FALLBACK_MS` (3s) on an uncached visit, it shows a service's discography meanwhile (Spotify, Apple Music, Last.fm, Discogs, the sources the not-on-MusicBrainz path uses), which MusicBrainz's first batch replaces and which stays, uncached, if MusicBrainz ends up with none; and skips its MusicBrainz name search when the caller passes the artist's MBID (`fetchArtistData(name, { mbid })`; Search passes it from MusicBrainz rows and artist credits via `src/renderer/lib/artist-open.js`), which also keeps it off a namesake. A MusicBrainz failure is not an empty discography (#874): `loadArtistReleaseGroups` reports a refused request as well as a thrown one, `discographyOutcome` (`src/renderer/lib/artist-discography.js`) tells `failed` (no releases, a type failed) and `partial` (releases, a type failed) from `complete` and `empty`, and only `complete` and `empty` are cached. On a failure, MusicBrainz releases already showing stay; otherwise the services' discography stands in (one pass, shared with the slow-load timer), and only when none has one does the page show `artistLoadError` (wording from `describeMusicBrainzError`) with Try Again in place of "No albums found". An outage used to read as an artist with no releases, and when the release-group requests were the ones failing, that empty list was cached for a month. A release-group opened once is remembered via `rememberReleaseGroupAlias`, so the revisit is served from `releaseDetailsCache` with no request. `tests/ui/scroll-state-coalescing.test.js` pins all of this.
- **Pages are React.memo'd modules fed stable props (Track 2b state-domain split).** So far: the Collection page (Library view: Songs/Albums/Artists/Friends, `src/renderer/components/collection-page.js`), the Home page (`home-page.js`), the Playlists page (`playlists-page.js`; `_allResolvers` invalidates it, since `linkUpdateMode` reads the plug-in loader for each card), the playlist view and its loading state (`playlist-view-page.js`: `PlaylistViewPage`, `PlaylistViewLoading`), the artist page with its release drilldown (`artist-page.js`) Fresh Drops (`fresh-drops-page.js`), Recommendations (`recommendations-page.js`), Concerts (`concerts-page.js`), Pop of the Tops (`charts-page.js`), Critical Darlings (`critics-picks-page.js`), History (`history-page.js`) and a friend's history (`friend-history-page.js`), plus the tag editor (`tag-editor-dialog.js`, a memo'd dialog on `Modal`) the Shuffleupagus chat panel (`results-panel.js`) the queue drawer (`queue-drawer.js`, always mounted; its drop overlay is `drop-zone-overlay.js`) the Add to playlist panel (`add-to-playlist-panel.js`, on `SidePanel`) and the two sync dialogs (`sync-setup-dialog.js`, `sync-status-dialog.js`), and Settings (`settings-page.js`, the last page; `authPort` is derived in it from `authServerStatus`, and its Discord status copy is `lib/discord-presence-status.js`), the plug-in settings dialog (`plugin-settings-dialog.js`; the canonical plug-in order and its helpers moved with it to `lib/resolver-order.js`), the sidebar (`sidebar.js`; it works out which item a playlist page lights) and the playbar (`playbar.js`; seek progress stays a subscription, and `_cacheLoaded` re-renders it once the persisted sources cache is in, for its Buy button), the first of the pages still inline in app.js to move (#1451): the rest follow one per PR, the markup moved verbatim, and a source-marker test reads `appWithPages()` from `tests/helpers/renderer-source.js` (app.js plus the moved pages; each extraction adds its module there) and Search (`search-page.js`); the last three are branches of the `activeView` ternary chain. A page that reads a cache ref during render is fine only if the data reaching that cache also changes a prop (Search's art fallback: `fetchSearchAlbumArt` writes `albumArtCache` and then `setSearchResults`). A page module must load under plain Node (the render smoke test): reach shared renderer objects through `globalThis`, not `window`, at module scope. Module-level helpers a page needs move to `src/renderer/lib/` (the collection id helpers `normalizeForId`/`generateTrackId`/`generateAlbumId`/`generateArtistId` are `lib/collection-ids.js` now, still the byte-parity pair with `sync-providers/spotify.js`). A derived value passed as a prop must be memoized unless it is a primitive (`isCompactHeader`); `artistSortOptions` and `resolvers` became `useMemo` for that reason. Each is `React.memo`, so a Parachord setState no longer re-renders it unless one of its props changed. The memo only works while every prop is stable unless its data changed: state values, `useState` setters, refs, `useCallback`/`useMemo` results, and the plain functions Parachord recreates each render, which go through `useStableHandlers` (`src/renderer/lib/stable-handlers.js`: fixed identity, always calls the latest closure; keys listed in each page's `*_PAGE_HANDLERS`). An object literal or a body-level function passed straight through re-renders the page on every Parachord render again with nothing failing, so `tests/renderer/page-memo.test.js` scope-analyses the app.js call site and fails on any prop that is not one of those kinds (that is why `syncProviderConfig` is a `useMemo`). If a wrapped function's RESULT is rendered and it reads state the page does not otherwise receive, pass that state as a `_`-prefixed invalidator prop the page does not destructure, or better, compute the result in app.js as a `useMemo` and pass that (Home had `_metaServices` for `getChatServices()` until the 2026-11 redesign passed `chatAvailable` instead). Otherwise a wrapped function whose RESULT the page renders must depend only on props (e.g. `isOnAir` reads the friend + the clock; on-air status refreshes when `friends` updates, not on every app render). Do not add hooks inside the page body without moving the page off the extraction pattern. Home has moved off it (2026-11 redesign): it keeps view-local state (its coalesced cover map) and effects (one idle-time background load), and its derived lists are `useMemo`s in the page or in app.js. Next pages follow the same recipe: extract the render expression by AST (the free-identifier list is the props), stabilize the functions, add the call-site test.
- **A layout change ships with its loading skeleton.** A skeleton is a promise about the layout: when it has a different box from the content it stands in for, the page jumps as the content lands, and when a layout change leaves the skeleton behind it promises the old layout. Both have happened. Critical Darlings' skeleton used a 112px cover and a bordered white box against 180px album cards, so the list jumped when the picks arrived. The Recommendations page's single 10-card grid outlived the move to the sectioned page (#1309), so a page of song lists and mixed sections opened on a grid it never showed. And 86dd867 removed the Recommendations Artists skeleton as a "double skeleton", leaving the page blank while the fetch ran, because cards that shimmer their own images only exist once the data does. The rules: a new page or section, or a change to a card's or row's box (size, padding, grid, columns, how many items a collapsed section shows), updates its skeleton in the same PR. A view that can wait on data with nothing to show renders a skeleton in its layout's shape, never a blank area or a lone spinner. That covers the first load, a source still loading while others already show (the Recommendations page shows a section skeleton where the providers' rows will land; unlabeled because a provider can turn out to have nothing, and a skeleton must not promise content that may never come), a page fetch at the end of an expanded list (placeholder cards or rows where the new items land, not only a header spinner), and Shuffleupagus still thinking (3 placeholder cards after the real ones in each "For you" row it will join). The page itself is five sections (Songs, Albums, Artists, Playlists, Friends), each but Friends opening with a blended "For you" row, so the cold-start skeleton draws the Songs and Albums sections the page opens with in that shape; "See all" / "Show less" on a row is Home's purple link style and the source tags in a blended row's title are session-only filters. Skeletons live in a components module beside the page (`src/renderer/components/recommendation-skeletons.js`) and reuse the page's own constants and box styles, and `tests/ui/loading-skeletons.test.js` reads the real cards' dimensions out of the source and requires the skeleton to use the same ones, so a restyle of either fails there.
- **Page heroes come from `PageHero`** (`src/renderer/components/page-hero.js`): the coloured banner at the top of Collection, Playlists, History (and a friend's), Recommendations, Pop of the Tops, Fresh Drops, Critical Darlings and Concerts. 320px, collapsing to an 80px bar; the page's gradient and pattern come from `PAGE_COLORS` (`hero`, `pattern`, `patternOpacity`); the title is written in words (CSS draws the capitals). A page passes what goes under the title (`expanded`) and after it in the bar (`collapsedContent`). The artist page's photo hero and the playlist view's blurred cover are different designs.
- **Art hover actions come from `ArtOverlay`** (`src/renderer/components/card-art.js`, shown by `useReveal` on hover or keyboard focus): Add to playlist, Play, Add to queue over a cover, on every card and on the album and playlist pages' covers. **Release-type colours come from `lib/release-types.js`**: the album page's badge, the cards' on-art badge and the type filter chips.
- **A Settings section comes from `SettingsSection`** (`src/renderer/components/settings-cards.js`): the card, the small-capitals heading and an optional line under it. Every section of Settings › General uses it (there was a copy per section, and Playback Quality had drifted to a grey card).
- **Section titles come from `SectionHeader`** (`src/renderer/components/section-header.js`). A heading over a row or grid of content (Home's rows, the Recommendations rows, the search results, an artist's concert count) is Home's style, shared so every page's sections read alike: a 20px bold title (`SECTION_TITLE_STYLE`), an optional 12px grey subtitle (`SECTION_SUB_STYLE`), and on the right a 13px semibold link with no underline. A link to another page is "See all in <Page>" (`page`, `view`, `navigateTo`) in that page's sidebar colour (`PAGE_COLOR`: Playlists `#ec4899`, Recommendations `#f59e0b`, Concerts `#10c9b4`); a link that acts in place (`action: { label, onClick, expanded }`, e.g. a row's See all / Show less, search's Show more) keeps its own label and takes `var(--accent-primary)`. `size: 'sub'` is the subsection title (15px semibold, an h3, `SUBSECTION_TITLE_STYLE`) for titled rows under a section title, used by the Recommendations playlist categories under "Playlists". `as` sets the heading level; `SECTION_HEADER_GAP` (16px) is the gap under a header in normal flow, and a skeleton standing in for a header draws a `SectionHeader` too, its bar inline in the title's line, so the two are the same height. Never copy the style into a page: before this, Home and Recommendations had drifted apart (18px semibold with a 14px purple link on Recommendations, 20px bold on Home). Page heroes, dialog titles, settings headings and the small uppercase group labels (`text-xs ... uppercase tracking-wider`: Concerts' month labels, search's Recent Searches and Suggestions) are different elements and keep their own styles. `tests/renderer/section-header.test.js` pins the style and the pages that use it.
- **Track rows come from `TrackRow`** (`src/renderer/components/track-lists.js`). Every page list renders the one row: number (or a `lead` node, the playlist page's Move up / Move down in edit mode), title, artist link, `cells` (album link, "2h ago", "12 plays", listeners), then the source icons (`TrackSources`, each a `SourceIconButton` coloured by the plugin's `color`, hover growth in CSS, right-aligned in a column one icon per playable service wide, `--source-col` on the app root) and an optional `duration`, the last column, so the icons always touch it. `TrackRowSkeleton` is its placeholder, in the same columns. `onPlay(resolverId?)` covers both a row click and one source's icon, so the two can't disagree about the queue or the context (Charts' icons used to queue under "Last.fm Charts" even on Apple Music's chart). The row runs `sourceRowState` itself on the `sources` it is given (`{ trackSources, playbackResolvers, resolverOrder }`). Per-list differences are props: `showArtist: false` (an album's own tracklist), `resolving: false` (Search before its lookup reaches a row: no shimmer, no dimming), `dimResolving: false` (the album page: no flash of "unavailable"). A local file gets no special place: its Local Files icon is one more source, shown and ordered by the user's source order (it used to be pinned on Collection whatever the order). Each page had its own copy of the row until 2026-11-15, and they had drifted (JS hover on some icons, 13px artists on two pages, a second margin before the icons). The queue drawer's row has its own layout and stays separate.
- **Source icons come from `visibleSources`** (`src/renderer/lib/visible-sources.js`). A track row's service icons, their order and their dimming are one rule: merge `track.sources` with `trackSources[track.id]`, drop `noMatch` sentinels and other non-sources, keep `playbackResolvers`, sort by `resolverOrder`, dim below `getBestSourceConfidence` (or unscored). `sourceRowState` adds the row's state: resolving (shimmer), unplayable (dimmed, no icons) or playable. The queue drawer, Collection, the playlist view, Search, album rows and the app.js badge lists use it; a list that hand-copies the steps drifts (the queue showed plan-blocked and no-match services until 2026-11). See "Playback limits" in [playback.md](playback.md).
- **Track lengths come from `trackDurationLabel`** (`src/renderer/lib/track-duration.js`). A row's duration is the track's own `duration` (seconds) when it has one, else the duration of its best source, merged the way `visibleSources` merges them (`track.sources` with `trackSources[track.id]`, no-match sentinels dropped): highest confidence first, then `resolverOrder`. When nothing knows the length the cell is blank, never "0:00". `trackDuration` returns the seconds (or null) for anything else that needs the number. The queue drawer, the playlist view, Collection, Search, album rows (MusicBrainz's `length` in ms first) and the Recommendations songs use it. Until 2026-11 every list read `track.duration` alone, so a playlist imported from a URL (a hosted XSPF with no durations) showed 0:00 on every row even after its tracks resolved.
- **A playlist's playback context comes from `playlistPlaybackContext`** (`src/renderer/lib/playlist-context.js`), and the queue's context bar ("Playing from …") opens `contextPlaylistTarget(playbackContext, playlists)`: a saved playlist by id, an ephemeral one (Weekly Jams, Weekly Exploration) from the slim `playlist` reference the context carries (`playlistRef`: the fields `loadPlaylist` needs, no tracks and no functions, because the context is copied onto every queued track and persisted with the queue). A recommended playlist with no ListenBrainz id can't be refetched from a reference, so its bar goes to Recommendations. Until 2026-11 an ephemeral playlist's context held only its id, so the bar's click found nothing and only closed the drawer.
- **A playlist link's "keep it updated or snapshot" question comes from `PlaylistUpdateDialog` / `UpdateModeChoice`** (`src/renderer/components/playlist-update-dialog.js`). Dropping a link and opening a `parachord://import?url=` link show the dialog (built on `Modal`, `RadioGroup` and `Button`); the import dialog shows `UpdateModeChoice` inline, because a second dialog over it would fight it for Escape. The options' wording (`updateModeOptions`) names the service and how often it is checked, and says a change there replaces the copy here. Never ask it with a hand-built dialog or a confirm. What each mode does: "Link imports: kept updated or a snapshot" in [sync.md](sync.md).
- **A page's filter box and sticky bar come from `FilterBox` / `StickyBar`** (`src/renderer/components/filter-box.js`): the search icon that opens into "Filter…" (focused on open; an empty box closes on blur; ✕ or Escape empties and closes it), and the strip that stays at the top of a page's scroll area (`variant` 'filter' or 'header'). Twelve pages had their own copy of the box and eight their own bar.
- **Filter buttons come from `FilterChips`** (`src/renderer/components/filter-chips.js`). A row of chips where one is picked (Home's source filters, Fresh Drops' and the artist page's release types, the artist page's related-artist sources, the Recommendations sources, the plugin marketplace's categories) is Home's source filter, shared so every page's filters look alike: 12px semibold pills, 8px 12px padding, 36px tall, 8px apart. A chip is `{ id, label, color?, gradient? }`. With a `color` it shows a dot in that colour when idle and fills with it when picked, its text white or near-black by contrast (`readableTextOn`); `gradient` paints over both. Without one (All, a category) it is neutral: `var(--bg-secondary)` when idle, the fixed accent `#7c3aed` (`CHIP_NEUTRAL_FILL`; the accent variable turns light purple in dark mode) when picked. Pass the group an `aria-label`; each chip carries `aria-pressed`. Never restyle chips in a page: before this the other pages had their own `px-3 py-1.5 rounded-full text-sm` pills (grey idle, a colour fill picked, no dot) and the marketplace an indigo outline. Tabs, sort dropdowns, search boxes and one-off chips (the Concerts location chip) are other elements. `tests/renderer/filter-chips.test.js` pins the style and the pages that use it. An action chip (a search suggestion, an active location, with an optional ✕) is its `Chip`, never a hand-built pill; its ✕ is a button beside the chip's, never inside it.
- **Status pills come from `Badge`** (`src/renderer/components/badge.js`). A small pill that never wraps: 12px semibold, `tone` neutral, info, accent or surface (over a cover), or a service's `color` (its plugin's `resolver.color`, tinted with `color-mix`), with an optional icon from the shared set. The Playlists page's Hosted, AI and Shared pills and a playlist's sync services use it. Before, they used emoji (🌐, ✨), palette fills with no dark-mode remap, and a service name guessed from two ids (anything not Spotify read "Apple Music").
- **A page's scroll area carries `.scroll-edge`** (`index.html`). Content used to run into a hard edge under the hero or toolbar (the artist biography most visibly). Once the area scrolls, one capture `scroll` listener in app.js sets `data-scrolled` on it (an attribute, so nothing re-renders), and its `::before`, a zero-height sticky marker at the top, casts a soft shadow over what scrolls beneath, sticky bars included. Every page-level scroll area has the class (Home, Collection, Playlists and a playlist, Search, the artist page, Pop of the Tops, Fresh Drops, Critical Darlings, Recommendations, History, a friend's page, Concerts, Settings). Menus, side panels and inner columns don't.

The card's own actions go in a `.card-actions` container: above the hit button, shown on card hover and whenever anything in the card has keyboard focus (`:has(:focus-visible)`), passing clicks through while hidden. `.card-zoom` is the cover's hover zoom. Shift+F10 or the Menu key calls `onContextMenu`. A card can't be a `<button>` because it holds buttons (Collection's album card was one, which HTML doesn't allow). Every clickable card and row uses it: the card family in cards.js, the Charts, Fresh Drops, Critical Darlings, Recommendations, History, friend, Search, Collection, playlist and album track rows and cards, the queue rows, the sidebar's friends and the chat results. A hover-revealed part inside one (`group-hover:opacity-100`) also gets `card-reveal`, so it shows on keyboard focus; the card's own buttons and links sit above the stretched one through a zero-specificity rule in index.html, so an `absolute` one keeps its position. The ~80 `role="button"` divs (lib/activate-on-key.js, removed) are gone, and design-drift's `roleButtonDivs` holds them at 0.
- **Hero tabs come from `HeroTabs`** (`src/renderer/components/hero-tabs.js`, #1385): `{ items, isSelected(item), onSelect(item), renderLabel(item), label }`. It's a `role="tablist"` of `role="tab"` buttons with `aria-selected` and a roving tabindex; ArrowLeft/Right move and select, Home/End jump; the `|` separators are `aria-hidden`; inactive tabs are white at 80% (60% was about 1.7:1 on the bright gradients). Charts, History, a friend's history, Collection and the release page header use it; the artist page's main tabs, which animate the On Tour tab in, carry the same roles by hand. Settings' section list is a `nav` with `aria-current="page"`.
- **Form fields come from `components/fields.js`** (#1385): `SettingRow` (a setting's name and hint on the left, its control on the right; the name labels the control and the hint describes it), `Select`, `TextField` (inline `error` with `aria-invalid`), `SecretField` (Show/Hide), `Switch` (`role="switch"`, the control tokens; `onToggle` works out the next value) and `RadioGroup` (option cards, the picked one in the accent tint), `Checkbox` (a native checkbox in the accent or a service's `color`, in the caller's `<label>`) and `Slider` (a range input on the one `.slider` look in `index.html`: a 4px track and a 12px thumb; `tone: 'dark'` on the playbar, `color` for a page's colour; `onChange` gets a number). The field look is 36px tall (32 for `size: 'sm'`, 48 and 16px text for `'lg'`), 13px, an 8px radius (12 for `lg`, full for `pill`), `--bg-elevated` on a `--border-default` line, the accent ring on keyboard focus (`focus-visible`), never focus styling in JS. `TextField` also takes `tone: 'dark'` (the Shuffleupagus prompt and chat, in the `--on-dark-*` tokens), `icon` (a glyph at the left: Plug-Ins search), `trailing` (a button inside at the right: Generate), `muted` (an example prompt reads as a placeholder) and `bare` (no box: the Search page's big type, where the caret is the focus sign). `Switch` takes `tone: 'dark'`. A field that saves on Enter sits in a real `<form onSubmit>`. No raw `<input>`, `<select>` or `<textarea>` is left outside `fields.js` and FilterBox (#1448; design-drift's `inputCopies` keeps it at 0). The AI provider is `ProviderMenu` (`components/provider-menu.js`), the shared `Menu` of AI plug-ins with their logos, on both Shuffleupagus panels (it was a native select on one). `SegmentedChoice` is a pick-one row of equal-width tiles with an icon each (Settings' theme: Light / Dark / System), radio semantics, the current tile outlined in the accent. - **Progress bars come from `ProgressBar`** (`src/renderer/components/progress-bar.js`): a folder scan, a library sync; a 6px rounded track, the fill eased to `value / max` in a service's colour or the accent, and `role="progressbar"` with its value. Local Files' scan and the sync setup dialog each hand-built one (2026-11-17).
- **Empty and error states come from `components/states.js`** (#1385): `EmptyState` (`role="status"`: an icon in a soft circle, a title, a line on why or what to do, optional `actions`) and `ErrorState` (`role="alert"`: a warning icon in the danger colour, a title saying what failed, the reason as `body`, `onRetry` for "Try again"; a fix in `actions` leads and Try again follows as secondary). `compact` is for a section, `align: 'start'` for a column, `tone: 'dark'` on the always-dark panels (the AI playlist panel, the album edition menu), `icon: null` for a small one in a list or menu. Never a hand-built "Retry" / "Try Again" button; a test fails on one.
- **A list's React key is unique among its siblings: de-duplicate the data by the same id the key uses, or key by something that is unique.** A repeated key leaves stale cards behind after a filter or search (Fresh Drops, Concerts, Search playlists, 2026-11). When the key is right but the data repeats it, de-duplicate by that id and merge what the copies carry rather than dropping one: Fresh Drops' `uniqueReleases` (`src/renderer/lib/fresh-drops-releases.js`, one row per release-group id), Concerts' `uniqueConcerts` (`src/renderer/lib/concert-events.js`, one row per event id under its headliner, ticket sources unioned and every artist on the bill in its lineup, run on the restored cache too), the Recommendations `mergeOwned` and Home's `homeRecommendationAlbums` (`src/renderer/lib/recommendation-model.js`, a provider's own id as well as the name key). When the key is wrong, change the key and leave the data alone: Search's playlist results are keyed by playlist id (two real playlists share the title "Starred"), History's listen rows by `${track.id}|${track.playedAt ?? index}` (one song listened to twice is two rows with one id; `track.id` stays the `trackSources` key), and Collection's album cards by album id, never by position (an index key handed a card and its cover to whichever album moved into its place). A list rendered from ids is appended to without repeats (`appendUniqueId` for the plugin order). Two related rules for filters: a filter's default is set once, when its page or entity starts loading, and data arriving never overwrites a pick (the artist page's release types, `startReleaseTypeFilterFor` / `pickReleaseTypeFilter`); and a picked chip that isn't shown filters as All, with the filter reset when the entity changes (the artist page's related-artist sources). `tests/renderer/list-keys.test.js` pins these.
- **Refs for stale closure avoidance**: Most state values have a companion ref (e.g., `volumeRef`, `isPlayingRef`) synced via `useEffect`. Always use refs in async callbacks.
- **Memoized sub-components**: the presentational kit lives in `src/renderer/components/` (ui-atoms.js: Tooltip/FixedTooltip, the service-logo kit, ParachordWordmark, PlaybackProgress; icons.js: the lucide wrapper; track-lists.js: TrackRow + VirtualizedQueueList/VirtualizedTrackList (badge icons from lib/visible-sources.js); cards.js: the card family + ReleaseCard/ReleasePage + generateArtistPattern + lib/hash-string.js; settings-cards.js: ResolverCard + McpSettingsSection + ScrobblerSettingsCard + FriendMiniPlaybar; playlist-cover.js: PlaylistCoverImage — a playlist's own cover layered over the mosaic fallback, see "Playlist covers" in [album-art.md](album-art.md)). The pre-component presentational split is COMPLETE; what remains in app.js’s pre-component scope is constants, non-presentational helpers, and the DJ-tools/AI-chat block. Extracted modules use React.-qualified hooks — never bare destructured ones — all `React.memo`'d, defined outside the main component.
- **Toast notifications**: `showToast(message, type, action, options)` for transient feedback. The 4th `options` arg accepts:
  - `persistent: true` — toast never auto-dismisses; stays until replaced by another `showToast` call or manually closed.
  - `duration: <ms>` — override the default auto-dismiss timeout. Default is 3000ms (or 6000ms when an `action` button is present). Use this when an in-flight acknowledgment toast may take longer than 3s to be replaced — e.g. protocol acknowledgments at the `parachord://` URL handler entry use `duration: 30000` so the "Loading album…" / "Loading radio…" / etc. toast holds across the resolution window (URL fetch + parse + N=2 lookahead resolve) until the success/error toast fires to replace it. Calling `showToast` again at any time replaces the current toast immediately, so a longer duration only matters when no follow-up is queued.
  - `action: { label, onClick }` — adds a button to the toast (extends default to 6000ms unless `duration` overrides).
- **CSS variables for theming**: All colors use CSS vars, supporting light/dark themes.
- **Tailwind classes come from the committed `vendor/tailwind.css`.** `npm start`, `npm run dev` and the tests load it as is; only the release builds regenerate it (`prebuild:<platform>` runs `build:css`). A class the file doesn't have does nothing when the app runs from source, so after adding a Tailwind class run `npm run build:css` and commit the result. `tests/ci/tailwind-css-fresh.test.js` rebuilds it and fails when the committed file is stale. It went eight months without a rebuild, and the Recommendations hero's `text-white/85` line rendered in the page's dark default color.
- **useEffect dep array TDZ trap**: React evaluates a `useEffect`'s deps array synchronously during render — so any variable referenced in the deps array must be declared before the `useEffect` call site in source order. The callback body itself runs after render and captures by closure, so it can freely reference later-declared `const` / function values; only the deps array is constrained. Practical implication: if you're adding a new effect that depends on, say, `cacheLoaded` (declared at app.js ~L8878), the effect must live below that line. Logical-grouping with other related effects sometimes loses to this constraint — see the Cross-Resolver Enrichment slow-trickle effect, which lives in the cacheLoaded-effects cluster (~L9818) rather than next to its sibling background-sync effect (~L6177). A leading comment at the natural placement point ("moved past the cacheLoaded declaration — see L9820") keeps future readers from being surprised.
- **Show a calendar date with `formatCalendarDate`** (`src/renderer/lib/calendar-date.js`). Release and founding dates (`"2026-11-06"`, `"2026-11"`, `"2026"`) are calendar dates, and `new Date("2026-11-06")` is midnight UTC, the evening before anywhere west of UTC. That showed a November 6 release as "November 5, 2026", and a year-only date as December 31 of the year before (#1288). `formatCalendarDate(value, 'long' | 'short', fallback)` builds the date in local time and shows a year or year-month as written.

## Tracks with no album

A track with no album has `album: ''`, never a stand-in. `isPlaceholderAlbum(album, sources)` is the one rule. It lives in `sync-engine/track-identity.js`, because library sync in the main process uses it too and packaging leaves out `src/`; `src/renderer/lib/collection-ids.js` re-exports it. The rule: nothing, "Single", or the name of one of the track's own sources. It never lists service names, so a new plugin is covered, and it doesn't go through `normalizeForId`, which strips non-Latin text to nothing.

A saved track's id includes the album it was saved with, so a changed album stops the id matching. **Ask whether a track is saved through `findSavedTrack`**, never by comparing ids: it tries the track's id, then the generated id, then a `trackSlug` id — only when the ASCII strip collapses the artist or the title (the same gate `loveRowId` uses, computed once per call), because a love-imported non-Latin row keeps its album and `generateTrackId` never matches it — then a track whose own album is a placeholder (a heart from search, the queue or now-playing carries none) against any saved row on artist and title, then artist and title against rows whose album is a placeholder. Two real albums stay two tracks. The slug tier is gated so Latin matching is unchanged: "Every Day" does not match a saved "Everyday". `clearPlaceholderAlbums` clears old placeholders when the collection loads and keeps the ids. It leaves rows a provider synced alone, since "Single" from a provider is that release's real name.

A row saved with no album and a provider's copy of the same track with its real album are still two rows after a sync, because the sync paths build ids from the album. That was already true.
