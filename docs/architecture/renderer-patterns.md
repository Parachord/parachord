## Common Patterns

- **Track ids must be Unicode-aware: `src/renderer/lib/track-slug.js` (`trackSlug(artist, title[, album])`, `slug(name)`)** — never hand-roll `` `${a}-${b}`.toLowerCase().replace(/[^a-z0-9-]/g, '') ``. That ASCII strip deletes every Cyrillic/CJK/Arabic character, collapsing EVERY track on a non-Latin release to the same id: all rows showed as playing, all rows shared whichever one track resolved first (badges for the wrong song), and clicking any other row re-scored the shared source against the clicked row's title and failed the 0.6 confidence floor — "sources exist + resolver active + still No Enabled Source" (live-reported 2026-10, Король и Шут release; both tracks resolved fine individually — the id was the bug). The fold is **NFKD → combining-mark strip → lowercase, in that order** (lowercase-before-NFKD lets `™`→`TM` leak uppercase into ids — review, #1079) and is byte-identical to the old formula for pure-ASCII input; accented-Latin ids change once (Beyoncé: `beyonc` → `beyonce`). These ids key session state (`trackSources`) and queue entries, NOT `cache_track_sources` (keyed by raw `artist|title`) — worst case a restored queue item doesn't show as playing on a release page until replayed. The two-part form is a distinct call (`arguments.length`): a 3-part call with an explicitly undefined album keeps the 3-part shape instead of falling into the 2-part form and colliding across albums. All ~55 id sites (release pages, playlist/queue/context fallbacks, artist ids) route through the helper; `tests/renderer/track-slug.test.js` includes a zero-tolerance drift guard, an import-destructure check, and a **runtime guard that renders the artist cards and invokes their drag/context handlers** (the render smoke test renders with empty props, so a helper used only inside a handler resolves by accident in the bundle and ReferenceErrors in the field). **Known siblings, not yet fixed** (review, #1079): `normalizeForId` in app.js + `sync-providers/spotify.js` (the byte-parity pair behind `generateTrackId`/`generateAlbumId`/`generateArtistId` — collection/library ids) collapses non-Latin the same way; and the remaining same-class id sites in app.js: `createTrackFromMeta` (~L6152), `critics-${artist}-${album}` (~L27085), the hyphen-replace artist ids (~L29288/L29389/L41763/L41777).
- **Every setState is a full-app render; coalesce bursts.** The UI is one component with ~380 state hooks and ~3,700 elements per render, nothing memoized per page, so a setState per item during a scroll (one resolved track every ~150ms from the scheduler, one artist image per lookup) is one full render per item and visible stutter (Fresh Drops / Recommendations, 2026-10-17). `window.createCoalescedUpdater(apply, delayMs)` (module scope, tests in `tests/ui/scroll-state-coalescing.test.js`) batches per-key writes into one setState: `queueTrackSources(key, value, { merge?, immediate? })` replaces every whole-entry `setTrackSources(prev => ({ ...prev, [key]: ... }))` in the resolution paths (merge for the missing-resolver flush, immediate for playback-time writes so they stay ordered with queued ones), and bulk rewrites call `flushTrackSources()` first. Recommendation artist images go through `recArtistImageWriterRef`. Two related rules from the same fix: hover prefetch on card grids runs on a 250ms dwell (`scheduleHoverPrefetch` / `cancelHoverPrefetch`), never raw `onMouseEnter`, because cards scrolling under a stationary pointer fire mouseenter each; and hero-header collapse-on-scroll goes through `window.headerCollapseDecision` (hysteresis 100/50px plus a content-height guard), because a single threshold flip-flops when collapsing the header clamps scrollTop back under it. The structural fix is memoizing page subtrees (track 2 of `docs/plans/2026-10-15-maintainability-refactor.md`). Derived lists a page builds from big state belong in a component-scope `useMemo`, never inline in the render: the Collection → Songs list (library + collection, deduplicated, filtered, sorted) cost ~60 ms per render at 150k tracks until it became `collectionSongsSorted`, which also reuses track objects that already have an id rather than copying them, because the MBID/artwork enrichment mutates library tracks in place (`tests/ui/collection-songs-memo.test.js`).
- **A click must change the view before its MusicBrainz lookup, and prefetches use the background lane.** Every `musicbrainz.org/ws/2/` request is serialized at 1 req/s by the fetch interceptor (`window.musicbrainzLimiter`), so a lookup is at least a second away and longer behind whatever is queued. `openChartsAlbum`, `openCriticsPicksAlbum`, `openTopAlbum` (Fresh Drops, charts, Critic's Picks, the home hero cards) and the playbar's `openAlbumForTrack` used to await the lookup and only then navigate, which read as "the click did nothing" (2026-10-17). Openers call `showReleasePlaceholder` (artist, a `_isPartial` release, `loadingRelease`, `navigateTo('artist')`) and look up after, like the collection-album opener; the three card openers are one function (`openChartsAlbum`, the other two are field-mapping wrappers), and a failure path that showed the placeholder clears it (`setCurrentRelease(null)` + `setLoadingRelease(false)`) before falling back to the artist page. Anything speculative (the five hover tracklist prefetchers, Fresh Drops' artist pass) passes `mbBackground: true` (`searchMusicBrainzRelease(..., { background: true })` for the shared search) so it drains only when no user-initiated request is waiting. A release-group opened once is remembered via `rememberReleaseGroupAlias`, so the revisit is served from `releaseDetailsCache` with no request. `tests/ui/scroll-state-coalescing.test.js` pins all of this.
- **Pages are React.memo'd modules fed stable props (Track 2b state-domain split).** So far: the Collection page (Library view: Songs/Albums/Artists/Friends, `src/renderer/components/collection-page.js`), the Home page (`home-page.js`), the playlist view (`playlist-view-page.js`), the artist page with its release drilldown (`artist-page.js`) and Search (`search-page.js`); the last three are branches of the `activeView` ternary chain. A page that reads a cache ref during render is fine only if the data reaching that cache also changes a prop (Search's art fallback: `fetchSearchAlbumArt` writes `albumArtCache` and then `setSearchResults`). A page module must load under plain Node (the render smoke test): reach shared renderer objects through `globalThis`, not `window`, at module scope. Module-level helpers a page needs move to `src/renderer/lib/` (the collection id helpers `normalizeForId`/`generateTrackId`/`generateAlbumId`/`generateArtistId` are `lib/collection-ids.js` now, still the byte-parity pair with `sync-providers/spotify.js`). A derived value passed as a prop must be memoized unless it is a primitive (`isCompactHeader`); `artistSortOptions` and `resolvers` became `useMemo` for that reason. Each is `React.memo`, so a Parachord setState no longer re-renders it unless one of its props changed. The memo only works while every prop is stable unless its data changed: state values, `useState` setters, refs, `useCallback`/`useMemo` results, and the plain functions Parachord recreates each render, which go through `useStableHandlers` (`src/renderer/lib/stable-handlers.js`: fixed identity, always calls the latest closure; keys listed in each page's `*_PAGE_HANDLERS`). An object literal or a body-level function passed straight through re-renders the page on every Parachord render again with nothing failing, so `tests/renderer/page-memo.test.js` scope-analyses the app.js call site and fails on any prop that is not one of those kinds (that is why `syncProviderConfig` is a `useMemo`). If a wrapped function's RESULT is rendered and it reads state the page does not otherwise receive, pass that state as a `_`-prefixed invalidator prop the page does not destructure (Home's `_metaServices`, read by `getChatServices()` during render). Otherwise a wrapped function whose RESULT the page renders must depend only on props (e.g. `isOnAir` reads the friend + the clock; on-air status refreshes when `friends` updates, not on every app render). Do not add hooks inside the page body without moving the page off the extraction pattern. Next pages follow the same recipe: extract the render expression by AST (the free-identifier list is the props), stabilize the functions, add the call-site test.
- **Refs for stale closure avoidance**: Most state values have a companion ref (e.g., `volumeRef`, `isPlayingRef`) synced via `useEffect`. Always use refs in async callbacks.
- **Memoized sub-components**: the presentational kit lives in `src/renderer/components/` (ui-atoms.js: Tooltip/FixedTooltip, the service-logo kit, ParachordWordmark, PlaybackProgress; icons.js: the lucide wrapper; track-lists.js: TrackRow + VirtualizedQueueList/VirtualizedTrackList + getBestSourceConfidence; cards.js: the card family + ReleaseCard/ReleasePage + generateArtistPattern + lib/hash-string.js; settings-cards.js: ResolverCard + McpSettingsSection + ScrobblerSettingsCard + FriendMiniPlaybar). The pre-component presentational split is COMPLETE; what remains in app.js’s pre-component scope is constants, non-presentational helpers, and the DJ-tools/AI-chat block. Extracted modules use React.-qualified hooks — never bare destructured ones — all `React.memo`'d, defined outside the main component.
- **Toast notifications**: `showToast(message, type, action, options)` for transient feedback. The 4th `options` arg accepts:
  - `persistent: true` — toast never auto-dismisses; stays until replaced by another `showToast` call or manually closed.
  - `duration: <ms>` — override the default auto-dismiss timeout. Default is 3000ms (or 6000ms when an `action` button is present). Use this when an in-flight acknowledgment toast may take longer than 3s to be replaced — e.g. protocol acknowledgments at the `parachord://` URL handler entry use `duration: 30000` so the "Loading album…" / "Loading radio…" / etc. toast holds across the resolution window (URL fetch + parse + N=2 lookahead resolve) until the success/error toast fires to replace it. Calling `showToast` again at any time replaces the current toast immediately, so a longer duration only matters when no follow-up is queued.
  - `action: { label, onClick }` — adds a button to the toast (extends default to 6000ms unless `duration` overrides).
- **CSS variables for theming**: All colors use CSS vars, supporting light/dark themes.
- **useEffect dep array TDZ trap**: React evaluates a `useEffect`'s deps array synchronously during render — so any variable referenced in the deps array must be declared before the `useEffect` call site in source order. The callback body itself runs after render and captures by closure, so it can freely reference later-declared `const` / function values; only the deps array is constrained. Practical implication: if you're adding a new effect that depends on, say, `cacheLoaded` (declared at app.js ~L8878), the effect must live below that line. Logical-grouping with other related effects sometimes loses to this constraint — see the Cross-Resolver Enrichment slow-trickle effect, which lives in the cacheLoaded-effects cluster (~L9818) rather than next to its sibling background-sync effect (~L6177). A leading comment at the natural placement point ("moved past the cacheLoaded declaration — see L9820") keeps future readers from being surprised.
