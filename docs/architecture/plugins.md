## Plugin (`.axe`) Marketplace System

### Extensibility principle — abstract over the plugin registry, don't hardwire services

Any feature shaped like "given a provider URL or entity, do X" MUST route through the resolver-loader capability surface, never a hardcoded service switch. The surface (`resolver-loader.js`):

- `findResolverForUrl(url)` → which resolver owns this URL (matches each `.axe`'s `urlPatterns`)
- `getUrlType(url)` → `'track' | 'album' | 'playlist' | 'artist' | 'unknown'` (each `.axe`'s `urlTypes` patterns — first match wins; see "URL patterns and lookups" below) A meta-service can own links too: Achordion (v1.1.0, #1493) declares `capabilities.urlLookup`, `urlPatterns` and `urlTypes` for `achordion.xyz/recording|release-group|playlist/*`, and implements `lookupUrl` (by MBID through MusicBrainz, or by the `lookup?artist=&title=` links Parachord shares), `lookupAlbum` (the release group's earliest official release) and `lookupPlaylist` (Achordion's public XSPF). A dropped Achordion link then plays from your own services like any other link. A meta-service with `urlLookup` that the playback-telemetry load also brings in is loaded there, once.
- `lookupUrl(url)` / `lookupAlbum(url)` / `lookupPlaylist(url)` → entity → tracks, dispatched to the owning resolver's capability
- `resolve` / `search` on `loadedResolversRef` for playback + search
- `listModels(config)` for AI `dynamic-select` plugins

The payoff: whichever `.axe` declares matching `urlPatterns` + the capability handles it, so **adding a new streaming service is a plugin drop-in with zero feature code.** The anti-pattern is hardcoding the dispatch:

```js
// WRONG — every new service needs a feature-code edit, and the .axe registry is bypassed:
switch (host) { case 'open.spotify.com': return spotifyImport(url); case 'music.apple.com': ... }

// RIGHT — the registry decides; a new service is just another .axe with urlPatterns + lookupPlaylist:
const id = resolverLoaderRef.current.findResolverForUrl(url);
if (id && resolverLoaderRef.current.getUrlType(url) === 'playlist') {
  const { playlist } = await resolverLoaderRef.current.lookupPlaylist(url, await getResolverConfig(id));
}
```

**Worked example — `resolveProviderPlaylistUrl` for `parachord://play/playlist?url=` (parachord#930/#932).** The provider-page branch routes entirely through `findResolverForUrl` + `getUrlType` + `lookupPlaylist`, so Spotify / Apple Music / SoundCloud / any future resolver are handled without naming them. The two `host ===` checks in the pure helper `classifyPlaylistUrl` (protocol-url.js) are **justified pre-processing, not service hardwiring** — keep them, don't "fix" them into the switch anti-pattern:

- **`achordion.xyz`** isn't a streaming resolver; it's a first-party playlist *host* whose `/api/playlist/<mbid>/xspf` returns a tracklist *document*. It feeds the generic `parseProtocolTracklist` path (the document fallback), not a resolver. No `.axe` owns it by design.
- **`on.soundcloud.com`** is a short link the capability surface *can't* classify (no `/sets/` segment for `getUrlType`). It's a redirect-resolve step that produces a canonical `soundcloud.com/.../sets/...` URL which is then handed back to `findResolverForUrl` — it feeds the surface, it doesn't replace it.

**Reusable mechanics when extending this:**

- **Native fast-paths are an optimization, not the gate.** `resolveProtocolPlayInput` has direct `spotify.lookupAlbum` / `window.appleMusicLookupAlbum` arms for cached IDs, but the general path still goes through the loader. Don't let a fast-path become the only path.
- **Audit the capability before assuming it exists.** `lookupPlaylist` is not universal — `resolver-loader.js` returns `null` (and logs "does not support playlist lookup") for resolvers that don't implement it, and some `.axe` lacked it until added (SoundCloud needed `lookupPlaylist` + OAuth before it could resolve a set). A new consumer must handle the `null`, not assume tracks.
- **Cross-platform parity.** This mirrors the mobile principle (`ProviderPlaylistResolver`, the two `lookupPlaylist` polls, `parachord-plugins/<service>.axe`). The mobile note also documents a JS-bridge quirk (a bare async IIFE reaching an `.axe` serializes to `[object Promise]` on iOS / `{}` on Android, so reaching the plugin needs the unique-key poll on both runtimes) — that's a mobile-runtime concern; desktop calls the loader methods directly in-process and isn't affected, but the *registry-abstraction* contract is identical on both sides.

### HTML5 stream resolvers and plugin-rendered settings (drop-in contract)

Subsonic and Plex used to be named in ten transport lists, two config gates and a bespoke settings block each; the renderer now reads three things from the `.axe` instead, and a new self-hosted resolver adds **no** app.js code (`tests/resolver/html5-stream-capability.test.js` pins this):

- **`capabilities.html5Stream: true` + `getStreamUrl(track, config)`**: the host plays the returned `http(s)` URL through the shared HTML5 element. `isHtml5StreamResolver(id)` / `usesSharedAudio(id)` (app.js, next to `loadedResolversRef`) replace every `=== 'subsonic'` style check: the play branch of `handlePlay`, play/pause, seek, volume, the wall-clock progress-tracker skip, and the element's error dialog, which is labelled with the manifest `name`. The play branch tags the track it hands the element with `_streamOwner`, because every such resolver loads an `http(s)` URL and the element's `src` alone can't say whose it is. Build the URL from the **saved config**, never from fields stored on the track (tracks persist into the queue and playlists).
- **`capabilities.local: true`**: the plug-in's sources are files in the local library (the local-files DB). The host plays them from disk through the shared element's `local-audio:` path instead of calling `play()`, treats them as needing no network, checks the file before playing and falls back to the track's other sources when it's gone, and drops a source whose file has left the library during resolution. `isLocalResolver(id)` (app.js, next to `usesSharedAudio`) is the one check; before the registry loads, the bundled copy answers (`lib/resolver-capabilities.js`). Local Files declares it (#1520); details in "The `local` capability" in [local-files.md](local-files.md).
- **`capabilities.embedPlayer: true`**: the host plays the track in the service's own embeddable player through a host adapter. See "Embedded-player resolvers (drop-in contract)" below.
- **`capabilities.widevine: true`**: the host plays the track's DRM-protected adaptive stream through the shared Widevine player (Shaka on the same shared HTML5 element; `src/renderer/lib/widevine-player.js`). The resolver's audio role is host-owned: `play()` returns false like `html5Stream`'s, and `cleanup()` stops the shared engine via `window.__parachordWidevine.stop()`. Per-resolver playback code shrinks to TWO operations, supplied one of two ways (see "The plugin-supplied Widevine path" below): registered MAIN-side on the widevine bridge (`main-process/widevine-bridge.js`) as `getManifest(entity) → { manifest: <DASH MPD text>, ... }` + `relayLicense(challengeB64) → <license bytes, base64>` — session cookies, CSRF and provider endpoints never reach the renderer — or implemented IN the `.axe` itself, renderer-mediated (Amazon's DRM pair has lived there since #1356 M9, plugin 1.17.0, over the `webSession` bridge). Variant selection is NOT per-resolver either: the global Settings → General → Playback Quality tiers (store keys `playback_quality`, `playback_abr`, codec-neutral bandwidth corridors (saver ≤100k / standard ≤200k / high ≤500k / max = best available) — adaptive roams below the corridor ceiling over the full playable roster) drive `shakaPlaybackConfig` in `src/renderer/lib/widevine-quality.js`. Stream-quality records come from Shaka's ACTIVE variant on load and every `adaptation` event; lifecycle telemetry is the supplier's — a main-side provider's `handlePlayerEvent` behind the `widevine:player-event` bridge channel, or the plugin's own `handlePlayerEvent` fanned out beside it on the plugin-supplied path (Amazon's maps them to hornet's `trackStreamed`/`streamingTerminated` reports through its `_lib` telemetry).
- **`isConfigured(config)`**: the Plugins page asks this before flagging an enabled resolver's card as needing configuration. Without it, the card warns while the settings fields the manifest needs (neither `advanced` nor given a `default`) have nothing saved, and otherwise never.
- **The "Needs setup" mark** on Settings › Plug-Ins comes from one map, `pluginNeedsSetup` (`{ [id]: true }`), that app.js builds with `needsSetupMap` in `src/renderer/lib/plugin-setup.js` (#1522); the page never names a service. In order: the plug-in's own status reply (`capabilities.status`, below: `signedIn: false` marks it, `true` clears it, no verdict marks nothing); then what the host holds for it (the sign-ins whose tokens live in app.js, `hostSignIns`, and the Local Files plug-in's watch folders); then `isConfigured(config)`, else the settings fields above. Home's getting-started tiles read the same sign-ins (`signedInMap`, app.js `pluginAccounts`). A meta service's tile is decided on the Plug-Ins page from its manifest: one whose settings have a `username` field (Last.fm, ListenBrainz, Libre.fm) needs setting up while it's switched on with no username saved; AI and concert services while they're on without their key (#1522).
- **Signing out turns the plug-in off through one path.** A sign-out that takes its plug-in out of play (Spotify, SoundCloud and Apple Music today) calls app.js's `deactivateResolver(id)` (`src/renderer/lib/deactivate-resolver.js`): the plug-in's sources leave every track (`removeResolverSources`), and its id leaves `activeResolvers` and `savedActiveResolversRef`, so `reEnableResolver` treats the sign-out as the person's choice and never restores it.
- **`capabilities.resolvePicks: true`**: the plugin's `resolve` knows the service better than a generic pick among its search results, so the play-time resolve in `use-playback-engine.js` calls `resolve` (then the gate) instead of `search` plus `pickTrackMatch`. SoundCloud declares it (#1306): `pickTrackMatch`'s artist check is the gate's containment, which takes a podcast by "Ramones of the Day" for a Ramones song. Bandcamp declares it too (1.5.0): its `resolve` checks the pick for streaming and answers a buy-only one as a purchase-only source, never another Bandcamp copy; `search` drops buy-only rows, so a pick among them could only land on another account's upload (live, clicking Radiohead's buy-only "15 Step" started a Bandcamp source that wasn't Radiohead's). Searches across every resolver at once (`parachord://play`, the DJ tools) still use `pickTrackMatch`, where an exact match from another service ranks first.
- **Config**: `getResolverConfig` hands any plugin it has no branch for its saved `meta_service_configs[id]` entry, read through `metaServiceConfigsRef` so search and play see the latest save, and from the store when the startup bulk load hasn't filled the ref yet (the result is cached for 10 seconds, so answering empty would leave the plugin unconfigured for a deep link's first resolution). The userpass settings panel saves Subsonic's server URL, username and password there.
- **`settings.authType: 'custom'` + `renderSettings(ctx)`**: the settings modal renders the plugin's own panel through `PluginSettingsPanel` (`src/renderer/components/settings-cards.js`, next to `ResolverCard`; app.js imports it). `ctx` is `{ React, components, resolver, config, saveConfig(next), clearConfig(), isActive, setActive(bool), showToast, showConfirmDialog }`. **A panel draws only with `ctx.components`**: `{ AccountRow, SettingRow, NestedSettings, Switch, Button, ProgressBar, EmptyState, ErrorState, Disclosure }`, the same shared parts every plug-in's settings use (CLAUDE.md, "every plug-in's settings are one layout"). It builds no buttons, inputs or colours of its own, and shows no raw error text; Plex's panel is the reference (an `AccountRow` for the account, nested `SettingRow`s with switches for its libraries, a `ProgressBar` for its index, `EmptyState` / `ErrorState`). A host without `components` gets no panel from it rather than a broken one. A plug-in that draws its panel this way declares `minAppVersion` for the release that added `components`. The wrapper is a real component, so the plugin may call hooks via `ctx.React` as long as it calls them unconditionally; `saveConfig`/`clearConfig` write `meta_service_configs[id]` and invalidate `resolverConfigCache`, and `getResolverConfig` hands any plugin without a hardcoded branch that saved entry (through the ref, so a save is visible to the next search/play). `setActive(true)` after a successful sign-in is what enables the resolver.
- Badge and icon colours fall back to the manifest `color` (`pluginBadgeMeta`, next to `TrackRow` in `src/renderer/components/track-lists.js`); the only per-service art left in the renderer is the optional logo in `SERVICE_LOGO_PATHS` / `SERVICE_LOGOS` (`src/renderer/components/ui-atoms.js`), and `CANONICAL_RESOLVER_ORDER` gives a bundled resolver its default priority slot.

What stays in main: the scoped fetch policy a self-hosted server needs (`main-process/ipc/plex-fetch.js`): an `.axe` must not be able to grant itself unrestricted or TLS-off fetch, so that part is host code by design.

### The plugin-supplied Widevine path (renderer-mediated, #1356 M4)

A `capabilities.widevine` plugin may also supply the DRM plumbing itself, renderer-side, instead of a main-side provider. The engine checks by presence (like every capability gate — BOTH must exist or the host falls back to the provider path):

- **`getPlaybackManifest(track, config)`** → `{ manifest: <DASH MPD text>, type: 'dash', drm: 'widevine', context: <object> }`. The engine calls it FIRST, before any host machinery, with the WHOLE track (its `sources` map included — the plugin digs its own identifier out; the host stops pre-extracting one) and the resolver's saved config. Optional extras riding the provider reply's fields: `protectionSets` (KID-group annotation for error attribution), `substituteAsin`, `cdnType`. **The call has a budget: 10 seconds** (the resolver limiter's `RESOLVE_BUDGET_MS` spirit, sized for a manifest fetch's heavier auth → catalog → MPD sequence). Past it the play fails with reason `'playback-failed'` — a hung fetch can't leave the track loading forever.
- **`relayLicense(challengeB64, context)`** → the licence, base64. The host calls it with the challenge and the session's `context` — the exact object the plugin returned from `getPlaybackManifest`, held renderer-side by the host's licence router and handed back with every challenge. **The context never crosses IPC** — it is plugin-private data (`widevine:plugin-license` is a push, and main takes the first answer for a requestId; the preload's subscription is single-owner: the host's router claims it when the player module loads, before any plug-in code runs, and a second `onPluginLicenseRequest` call gets a warning and `null` instead of an unsubscribe, so nothing else can race an answer in, and a refused claim fails a play with a message that says so), so nothing a plugin wouldn't publish itself may ride it, and it must not carry credentials. It is data (passed by reference, same renderer world), never closures.

Flow: the engine's manifest call is direct (same renderer world, so a thrown Error's fields arrive intact) and declares the reply UP — `window.__parachordWidevine.playPlugin` → `widevine:open-session` — so MAIN opens the licence session under its existing gates (sender, the per-resolver manifest rate window shared with the provider path, supersession). Only the manifest's LENGTH crosses that open (the rate window's gate — the text stays renderer-side, where its only consumer already holds it); the plugin's `context` stays renderer-side with it. Licence challenges then flow main→renderer (`widevine:plugin-license`, answered on `widevine:plugin-license-answer`) carrying only `{ requestId, resolverId, sessionId, challenge }`: main validates the sender/session/cap (30 relays) exactly as for a provider relay, forwards the challenge, and awaits the plugin's answer; the host's renderer-side router pairs the challenge with the plugin's own context and calls its `relayLicense`. Main never reverse-invokes the plugin for manifests, and never holds plugin data.

Error contract (the fields are load-bearing — the engine's refusal handlers and the #1262 family-failure latch key on them): `getPlaybackManifest` rejects with `.reason` `'plan-ineligible'` (plus `.planKey`, the plan as the service names it) / `'not-signed-in'` / `'load-failed'` / `'playback-failed'`; `relayLicense` rejects with `.reason` (`'playback-failed'`/`'load-failed'`), `.licenseDenied: boolean` (the build-can't-play class), `.denialReason: string|null` (`'CUSTOMER_NOT_ELIGIBLE'`-shaped per-content refusals latch the refused codec family) — the same fields the old `amazon-dmls.js` provider threw, and they cross into the engine's error paths unchanged (a licence refusal's `.reason` included). A plugin supplying its own manifest may also drop key groups it was refused from its own manifests — the group label is the plugin's own dialect and stays opaque to the engine, which never filters by it ("Rendition groups" in [amazon-music.md](amazon-music.md)). The reply may also carry `asin` (the plugin's own identifier extraction — it rides the entity seam the engine's play-started telemetry and provenance read, with `substituteAsin` layered over it) and the optional `protectionSets`/`substituteAsin`/`cdnType` extras.

Both paths at once: when a resolver has BOTH a main-side provider and the plugin pair, the plugin path wins — the engine's presence check runs first, and every play rotates the resolver's one licence session either way (the newest manifest-shaped open owns it). A migration can move flow by flow without a both-paths window.

A plugin with NO main-side provider is the whole service half, so its manifest must set `minAppVersion.desktop` (see "Minimum app version" above) naming the first release with this path: an older app doesn't know the plugin pair, falls back to the provider path, and fails with "no widevine provider registered".
**Amazon's DRM pair lives on this path since #1356 M9** (plugin 1.17.0; `amazon-dmls.js`, `main-process/amazon-telemetry.js` and the provider registration died with the move) — the pair also owns its player events: the engine hands the plugin's `handlePlayerEvent` to `playPlugin`, which fans every lifecycle event out to it beside the bridge's `widevine:player-event` IPC (whose matched session close stays main-owned).

### Embedded-player resolvers (drop-in contract)

Some services won't stream full tracks to an app but will play them in their own embeddable player. SoundCloud is the first: its API gives 30-second previews at most, its widget plays whole tracks with no sign-in (see "SoundCloud (the widget)" in [playback.md](playback.md)). An embedded-player resolver plays in that player, hidden in the main window, driven by **host** code. Adding one is a plugin change plus one adapter; nothing in the engine, transport or volume code changes.

**The plugin provides:**
- `capabilities.embedPlayer: true` and a top-level `"embedPlayer": { "adapter": "<name>" }` block naming the host adapter. The name stays out of `capabilities` on purpose: Android and iOS decode `capabilities` as `Map<String, Boolean>`, and a string value there makes them drop the whole plugin (`tests/renderer/embed-player-capability.test.js` keeps every plugin's capability values boolean).
- Source records that carry the link the adapter loads (SoundCloud's `soundcloudUrl`, the track permalink). The adapter's `linkFor(source)` picks it.
- A `play()` that still does something sensible on its own, such as opening the track on the service's site. An app that doesn't know the capability ignores the new fields and calls it. From 0.9.13 so does an app that knows the capability but not the adapter (`embedPlayerKind` returns null). **Set `minAppVersion.desktop` on a plugin that adds a new adapter**: 0.9.12 knows the capability, not the adapter, and fails on it.

**The adapter** (an entry in `ADAPTERS` in `src/renderer/lib/embed-players.js`: `create()` and `linkFor(source)`) returns a player with:
- `load(link, handlers, source) → Promise`: `source` is the resolver's source record, for an adapter that needs more than the link. Resolves only once the position has actually advanced **and** the track is the whole thing, rejects with reason `unplayable` when it hasn't moved within a timeout (SoundCloud uses 10s), `preview` when the service is only playing a snippet, or `superseded` when another `load` or `stop()` came first. Services can refuse a track inside their player without any error (SoundCloud's widget just never starts), or play a preview that looks like a full play until it ends (SoundCloud: `getCurrentSound` reports `policy: SNIP`, or a `duration` short of `full_duration`), so "loaded", "a play event" and even "the position moved" are not proof on their own. The engine treats every rejection except `superseded` as a failed source.
- `stop()`: halts it (SoundCloud's blanks its iframe). Leaving a track never only pauses it.
- `isActive()`, and `element`: an HTMLMediaElement-shaped facade (`paused`, `currentTime` settable to seek, `duration`, `volume` 0-1 settable, `play()`, `pause()`).
- Handlers it calls: `onProgress(seconds)`, `onDuration(seconds)`, `onPlay()`, `onPause()`, `onFinish()`, and the optional `onStreamQuality(facts)` — a measured `streamQuality` fragment (`{ bitrate (kbps), origin: 'measured' }`, the root `stream-quality.js` contract) an adapter emits when the service's player exposes what the stream actually decodes. Bandcamp's embed reports its page's decoded audio bytes (`decodedBytes` off `bcState()`, through `lib/stream-bitrate-meter.js`); SoundCloud's widget exposes nothing and never calls it. The engine merges each emission into the playing track's source record (`attachStreamQualityFacts` in use-playback-engine.js, behind the `isStreamQualityChange` save-guard).

Rules for an adapter:
- **No protocol?** A player with no message protocol is driven from the main process instead, under the rules in "Bandcamp (the embed)" in [playback.md](playback.md).
- **Host code only.** Speak the player's message protocol yourself; never load the service's own controller script (SoundCloud's `api.js`, YouTube's `iframe_api`) into the main window, where it would run beside `window.electron`.
- **Trust only your frame.** Accept a message only if its origin is the player's origin and its source is your frame's window.
- **One generation per load.** Ignore everything from an earlier load, and anything from the new one before the player says it is ready.
- **Forward transport events only after the track has started.** Players report state changes while starting up (SoundCloud's widget sends a pause first).
- **Create lazily.** `embed-players.js` must load under plain Node, where there is no `document`.

**The host does the rest** (`embedPlayerKind(id)` in app.js is the lookup):
- The play branch in `handlePlay`: applies the effective volume (per-resolver offsets included), loads, sets the now-playing track, and feeds progress, duration and scrobbling from the handlers. `finish` advances the queue.
- A refusal (`unplayable`) is a failed source: another enabled source for the track plays, else auto-skip in auto-advance and radio contexts, else a toast with an "Open in <service>" action. The browser never opens by itself.
- `mediaElementFor(id)` returns the adapter's `element`, so seek, volume, mute, the system-mute handler and the MCP seek and position tools work unchanged. `handlePlayPause` has an embedded-player arm ahead of the shared-element one, `playsInApp(id)` turns the volume slider on and skips Spotify polling, and the wall-clock progress fallback skips embedded players.
- `stopAllLocalAudio` calls `stopAllEmbedPlayers()`, so starting any other track halts it.

**Known gaps:** OS media keys may reach the player's frame instead of Parachord (its pause and play events keep the UI in step, but nothing re-routes the keys), and how Chromium throttles a hidden cross-origin frame hasn't been tested for long sessions.

**Testing:** drive the adapter with a fake window (`tests/renderer/soundcloud-widget-player.test.js`: handshake, start detection, the `unplayable` timeout, supersession, origin and frame filtering, the facade, handler gating, stop), and extend `tests/renderer/embed-player-capability.test.js` with the new adapter.

**Candidates:** Mixcloud's widget has a message API for play, pause, seek, progress and end, much like SoundCloud's. YouTube's embed has one too, but the engine notes YouTube embedding is blocked in Electron (its embed refuses `file://` pages), and its terms restrict hidden players. Bandcamp's embedded player has no control API, so it stays in its separate window.

### Architecture
- Plugins are `.axe` files (JSON) in `plugins/` (`/plugins/*.axe` is gitignored — generated artifacts live there, see the next bullet), each with a `manifest` (id, version, etc.) and `implementation`
- **`plugins/*.axe` are GENERATED, UNTRACKED artifacts** (untracked since parachord#1107). The source of truth is `plugins-src/<id>/` — `manifest.json` (the .axe minus its implementation) + `implementation.js` (a real module: `module.exports = { search: fn, ... }`). `scripts/build-axes.js` regenerates the `.axe`, the `src/renderer/lib/fallback-resolvers.generated.js` module (also gitignored since bucket C — the `FALLBACK_RESOLVERS` array required by `src/renderer/app.js`), and the `marketplace-manifest.json` entry version from that source. **Never hand-edit `.axe` files or the fallback module** — edit `plugins-src/`, bump `manifest.version` there; regeneration runs in the `pretest`/`prestart`/`predev`/`prebuild*` hooks (build-axes FIRST, then build-renderer), and a manual `node scripts/build-axes.js` works too. **The writer still owns one output that STAYS tracked**: the entry versions in `marketplace-manifest.json` — a PR that changes a plugin's source must commit that sync. The guards on it (replacing the retired `tests/plugins/axes-drift.test.js`):
  - **The committed-state drift gate** — `.github/workflows/test.yml` runs `git diff --exit-code -- marketplace-manifest.json` after `npm test`'s pretest writer. A check that runs after a hook ran the writer cannot fail on on-disk artifacts (the writer has already regenerated them), so the gate compares committed tracked outputs instead. (Found in review on parachord#1107; the FALLBACK half of its remit moved to bucket C's whole-file byte-compare inside `build-axes --check`.)
  - **`build-axes.js` runs before `build-renderer.js` in every hook** — otherwise the bundle is built from a source tree whose fallback module the writer has not regenerated yet, and a one-shot CI `prebuild` ships a stale array. (The old form mentioned an inline `src/renderer/app.js` block — the generated-module shape moves the same ordering rule.)
  - **The PR-only version-bump gate** (`scripts/check-plugin-version-bumps.js`, same workflow) — any PR that touches `plugins-src/<id>/` must change its `manifest.version` (the nested `.manifest.version` path; plugins-src manifests are the `.axe` shell minus `implementation`), or marketplace clients never re-download. This is the enforced form of build-axes' local content-vs-disk warning, which went silent when the artifacts were untracked. New plugins and deletions are exempt. Local-run caveat: with its default `origin/main` base the diff compares against main's tip, so a branch behind main can false-positive — fetch/rebase first (CI can't hit this: HEAD is the merge commit).
- **Marketplace source**: Raw GitHub files from `Parachord/parachord-plugins` repo
- **Manifest**: `marketplace-manifest.json` in this repo — the central catalog of all plugins with version numbers (entry `version` and `minAppVersion` are generator-synced; category/tags/downloadUrl/capabilities in the entry are editorial, hand-maintained)
- **Client sync**: `main.js` fetches manifest + `.axe` files from `https://raw.githubusercontent.com/Parachord/parachord-plugins/main/`

### Plugin Loading Order (main.js `resolvers-load-builtin`)
1. Shipped plugins from app `plugins/` directory (bundled in ASAR for packaged builds)
2. Cached marketplace plugins from `~/.parachord/plugins/`
3. Version comparison: newer version always wins; same version prefers shipped over cached
4. A cached copy whose `minAppVersion.desktop` is above this app's version is skipped (see "Minimum app version" below), so the shipped copy stays in use. The shipped copy is never checked: it was built with this app.
5. In the renderer (`initResolvers`), a plugin whose `requires.hostBridges` this host doesn't supply is hidden — not loaded (see "Required host bridges" below).

### Minimum app version
The marketplace serves only the latest copy of each plugin, and every installed app downloads it, so a plugin that needs a host feature an older app lacks (a new IPC surface, a native player) would otherwise reach that app and break there. A plugin can declare the oldest app it runs on, per platform, in its manifest:

```json
"minAppVersion": { "desktop": "0.9.12", "android": "1.4.0", "ios": "1.0.0" }
```

- **Per platform, because desktop and mobile version separately** and gain host features at different times. A platform with no entry, or a plugin with no field, has no floor. Values are plain `x.y.z`; an app's pre-release suffix is ignored, so `0.9.12-beta.1` meets a `0.9.12` floor.
- **An app below the floor keeps the copy it has.** Marketplace sync (`plugins-sync-marketplace`) checks the catalog entry before downloading and the downloaded `.axe` before saving, and reports the plugin under `skipped`. The loader skips a cached copy below the floor. Installing from Settings or from a file refuses with "needs Parachord X or later".
- **Rules live in `main-process/plugin-compat.js`** (`pluginCompatibility(manifest, appVersion, platform)`, `validateMinAppVersion`). The Android and iOS clients mirror them; keep the two in step.
- **`build-axes.js` validates the field and copies it to the marketplace entry**, so a client can skip a download without fetching the `.axe`; `--check` fails on drift.
- **Apps released before the field existed ignore it** (v0.9.11 and earlier on desktop). Until most people have updated past that, a plugin that depends on a new host feature still has to detect the feature and fall back, not only declare the floor.
- **Set the floor to the first release that has the feature.** During development `package.json` still carries the previous release, so a dev build skips the marketplace copy and runs its own bundled one, which is the copy you're working on.

### Required host bridges

A plugin that calls a host bridge (`webSession`, …) declares the ones it needs as a top-level `.axe` field (#1355). Each declared name is also the bridge's key on `this.host` (see "The plug-in host contract" below; until that is built, plug-ins reach the bridge at `window.electron.<name>`):

```json
"requires": { "hostBridges": ["webSession"] }
```

Each host advertises what it supplies — desktop's `preload.js` sets `window.__parachordHostBridges` (today `['webSession']`; keep the list in step with the bridges the preload actually exposes); the mobile apps set the same global in their JS runtimes — and the plugin loader **hides** a plugin whose required bridges are not all supplied. Hidden, not refused: the same `.axe` installs everywhere and runs where the host has the bridge, so the marketplace serves one copy to every platform. A loaded plugin without its bridge would throw not-ready on every resolve, and a retrying resolver would keep re-asking it.

- The rule shapes mirror minAppVersion's: absent is no requirement, and a malformed declaration is no requirement (`build-axes.js` rejects a malformed one at source, so a shipped plugin never carries one).
- On desktop the hiding happens in the renderer's plugin loading — one rule, every `.axe` load path: the main `initResolvers` load, the fallback resolver load, the install/reload paths (install-from-file, marketplace install), and the meta-service hot-reload after a marketplace sync (`handlePluginsUpdated`), all through `hideAxesLackingHostBridges` (`src/renderer/lib/host-bridges-hide.js`), which reads the advertised list and runs the hide-filter the rules module carries (`hostBridgesHideFilter`); the rules live in `main-process/plugin-compat.js` (`pluginRequiredHostBridges`, `hostBridgesCompatibility`, `hostBridgesHideFilter`, `validateRequires`), mirrored by mobile's `PluginCompat.kt`.
- Marketplace install and download do NOT check hostBridges — a plugin hidden on this host may still be installable there and run on the user's other devices' hosts; hiding is a load-time decision, not a download-time one. `minAppVersion` remains the field that gates downloads.
- The Amazon Music plugin declares `["webSession"]` since its track search moved onto the bridge (#1356 M5) — the first shipped plugin to declare a requirement; since the #1356 move finished, every one of its flows (the catalog, playlist import, recommendations, DRM pair, session surfaces and the diagnostic capture) rides it.

### The plug-in host contract (`this.host`, #1561)

**Status: built on desktop; the migration has started.** The contract below was settled in #1561 with the Android side. Desktop's loader builds `this.host` for every plug-in (`ResolverLoader.buildPluginHost` in `resolver-loader.js`, from the supplier in `src/renderer/lib/plugin-host-supplier.js`). Amazon Music is the first plug-in on it: its `webSession` and `widevine` bridges and the app version come from `this.host`, so it can run on the phones (Parachord/parachord-mobile#663). The other plug-ins still reach the host through the globals in the migration table below. This section is the spec every host's loader builds to: desktop's `resolver-loader.js`, and the Android and iOS plug-in managers.

**The rule: a plug-in reaches the host only through `this.host`.** Not through `window.electron.*`, not through an app object on `window` (`window.scrobbleManager`, `window.achordion`, …), not through an underscored global (`window.__parachordWidevine`). Web platform APIs aren't host APIs and stay as they are: `fetch`, `crypto`, `URL`, `AbortController`, timers. Why injection and not one global (the comparison is on #1561):
- **Scoped to the manifest.** A plug-in sees only the bridges it declares, so the declaration is the permission, not a note. These are marketplace plug-ins: one shouldn't see another service's signed-in session.
- **The declaration can't drift from the code.** A bridge's name in the manifest is exactly its key on `this.host`, so a test can check one against the other.
- **Per plug-in.** The host builds a separate object for each plug-in, so whatever needs the plug-in's id (its config, its scrobble registration, its rate limit, its log tag) has it bound in, and a plug-in can't pass someone else's.
- **No `window` needed**, so a host can run plug-ins in a worker or a bare JS engine, and tests pass a fake host instead of stubbing globals.

#### What `this.host` holds

The loader sets `this.host` on each resolver instance before `init` runs and keeps it for the instance's lifetime. A hot reload gets a new instance and a new object. The object is frozen, so a plug-in can't add to it or swap out a bridge. Bridges are read through getters, so a bridge the host sets up after plug-ins load (desktop's shared Widevine player) is still the live object. A loader built without a supplier (a test, an older call site) sets `this.host` to `null`, and the plug-in takes its older-app path.

**Where desktop's bridges come from** (`desktopPluginHostSupplier`): the preload's, listed in `window.__parachordHostBridges` (the hide rule's list) and read from `window.electron.<name>`; and the renderer's own, today only `widevine` (`window.__parachordWidevine`, set by `hooks/use-playback-engine.js`). A renderer bridge isn't in the advertised list, so it can be declared only as optional until the hide rule reads the renderer's list too.

**The core, on every host, for every plug-in:**

| Key | What it is |
|---|---|
| `appVersion()` | The app's version string (`0.9.14`, or the phone app's own). Amazon Music sends it in its music-agent string. |
| `platform` | `'desktop'`, `'android'` or `'ios'`, the same keys `minAppVersion` uses. |
| `getConfig()` | A promise of the plug-in's saved settings, read fresh on each call, so a switch or a password changed in Settings applies without a reload. It's what playback telemetry's `init(config, host)` already passes. |
| `openExternal(url)` | Opens an `https` link in the user's browser: a sign-in page, a buy link, a service's own page. Anything else rejects. It replaces `window.electron.shell.openExternal` and `window.open`. |

**Bridges, one key per declared name.** Each name in the manifest's `requires.hostBridges` is a key on `this.host` with that exact name: `"requires": { "hostBridges": ["webSession"] }` gives `this.host.webSession`. A bridge a plug-in didn't declare is absent, even when the host has it. Two kinds:
- **Required** (`requires.hostBridges`): the plug-in can't work without it. A host that lacks one hides the plug-in (the rule above), so a required bridge is always present when the plug-in runs.
- **Optional** (`requires.optionalHostBridges`, new): the plug-in uses it when it's there and works without it. A host that lacks one leaves the key out and loads the plug-in anyway, and the plug-in checks for the key. Amazon Music's `cleanup()` stopping the shared Widevine player is the case: the phones have no shared player. Older loaders ignore the field, since `validateRequires` and `pluginRequiredHostBridges` read only `hostBridges`.

Each bridge's methods and their semantics are documented with the bridge, not here. The web session's are in [web-session.md](web-session.md) ("The IPC bridge"). A host that implements a bridge implements all of it, and advertises it in `window.__parachordHostBridges`, the list the hide rule reads.

**`host` is a reserved implementation key**, like `lib`. A method named `host` would clobber the object, so the loader skips it with a warning.

**`_lib` stays pure.** The library can't reach `this.host`, and doesn't try: a helper that needs a bridge takes it as an argument (the rule in "Implementation functions" below). `init(config, host)`'s second argument becomes the same object as `this.host`, so playback telemetry plug-ins keep working unchanged.

#### Older apps: one accessor, one fallback

An app whose loader predates the contract sets no `this.host`. Until `minAppVersion` floors make those apps rare (the same rule as `_lib`'s `requireLib`), a plug-in reads bridges through one accessor entry, so the fallback lives in one place:

```js
// implementation.js: the one place a plug-in reaches the host (Amazon Music's)
hostBridge: function (name) {
  if (this.host) return this.host[name] || null;                    // a host with the contract
  if (typeof window === 'undefined') return null;
  if (name === 'widevine') return window.__parachordWidevine || null; // an older desktop build
  return (window.electron && window.electron[name]) || null;
},
search: async function (query, config) {
  if (!this.hostBridge('webSession')) return [];
  // ...
}
```

The fallback reads `window.electron.<name>`, which matches the bridge name for `webSession`. A bridge whose old home was elsewhere (`window.__parachordWidevine`) names it in its own branch. With `this.host` set, the fallback is never read: a bridge missing from `this.host` is missing. The fallback goes once the plug-in's `minAppVersion` on every platform is at or past the first release that builds `this.host`. Until then a new host feature still needs a fallback, as "Minimum app version" says.

#### Enforcement

On desktop, plug-ins aren't sandboxed ("Implementation functions" below), so nothing stops a plug-in from reading `window.electron` directly. The contract is held by tests:
- **A ratchet** over `plugins-src/` (`tests/plugins/host-contract.test.js`, baseline `tests/plugins/host-globals-baseline.json`): per plug-in, the count of host globals (`window.electron.*`, app objects, `window.__parachord*`) and of its own state on `window`. A rise fails; a fall fails until it's locked in with `UPDATE_HOST_GLOBALS_BASELINE=1 npx jest tests/plugins/host-contract.test.js` and the baseline committed. The `hostBridge` accessor's own fallback is the one exception.
- **Declared means used, and used means declared** (the same file). Every `this.host.<name>` and `hostBridge('<name>')` in a plug-in is a core key or a name in its `requires`, and every name there is used.
- **A contract test per moved plug-in.** It's loaded twice: once by the real loader with only `this.host` and no `window.electron` (a phone), and once with no `this.host` and only `window.electron` (an older desktop build). Its methods must work both ways. Amazon Music's is `tests/resolver/amazon-music-plugin-host-contract.test.js`.
- **The loader's half:** `tests/resolver/resolver-loader-plugin-host.test.js` (only declared bridges, frozen, per plug-in `getConfig`, https-only `openExternal`, the reserved `host` key, `init`'s second argument); desktop's supplier in `tests/renderer/plugin-host-supplier.test.js`.

### How Updates Reach Users (No New Build Required)
1. **Edit `plugins-src/<id>/implementation.js`** (or `manifest.json`) — and bump `manifest.version` in `plugins-src/<id>/manifest.json`
2. **Regenerate** — any lifecycle hook does it (`pretest`/`prestart`/…, build-axes first), or `node scripts/build-axes.js` by hand: regenerates `plugins/<id>.axe`, the fallback-resolvers module, and syncs the `marketplace-manifest.json` entry version (warns if content changed without a version bump — and the CI version-bump gate FAILS the PR on it)
3. **Commit the regenerated tracked output** — `marketplace-manifest.json` (the only tracked writer output left), or the drift gate fails
4. **Push to main** — the `sync-repos.yml` CI workflow generates the `.axe` files from `plugins-src/` and syncs them plus the manifest to `Parachord/parachord-plugins`
5. **User relaunches Parachord** — `syncPluginsWithMarketplace()` (src/renderer/app.js) compares cached version against marketplace manifest version; if different, downloads the new `.axe` and fires `parachord-plugins-updated` event for hot-reload

### Critical: Both Files Must Be Updated
This footgun is now generator-owned: `node scripts/build-axes.js` writes the `.axe` version and the `marketplace-manifest.json` entry version from the same source manifest. The only manual rule that remains: bump `manifest.version` in `plugins-src/<id>/manifest.json` when the implementation changes — the writer warns on content churn on an unchanged version, and the PR-only CI version-bump gate fails the build on it.

### Absorbing a Reverse-Sync Community Edit (automatic)
`reverse-sync.yml` PRs already carry `plugins-src/` diffs, not `.axe` files: the workflow generates our artifacts from `plugins-src/` first, compares each remote `.axe` against them (adoption only on strictly-greater semver or an unknown plugin — never downgrades/sidegrades, the #754 guard; equal-version-different-bytes is kept-ours and annotated as a workflow warning), and runs `build-axes.js --import` for anything adopted before opening the PR. So a community edit arrives pre-absorbed — review the `plugins-src` diff, never the `.axe`. Two failure behaviors to know: a failed import git-restores both paths so a PR never half-adopts (the daily run retries), and `plugins-src/<id>/build.json` (the es5 flag, which the `.axe` doesn't carry) is stashed/restored across the import. The manifest merge appends community-only entries (synthesizing a minimal one if the remote manifest lacks the adopted plugin) and runs BEFORE the import/regen, because build-axes' write mode hard-requires a marketplace entry per plugins-src id. Manual one-file re-absorb is still: delete the plugin's `plugins-src/<id>/` dir, then `node scripts/build-axes.js --import --plugin <id>`.

### Engine-Portable (ES5) Plugins
To keep a plugin's implementation text ES5-level, flag it with `{ "es5": true }` in `plugins-src/<id>/build.json`: the writer transpiles through esbuild `--target=es5` before serializing (requires esbuild installed). Unflagged plugins may use modern syntax in `implementation.js`. No plugin is flagged today, and this section used to say Subsonic and Bandcamp had to be: both ship `async` functions. Mobile doesn't run Subsonic or Amazon Music at all (`capabilities.mobile: false`, which its `PluginManager` hides); it does run Bandcamp, and Android runs Apple Music's `resolve` as Tier 2 of its native Apple Music resolver (`AndroidResolverRuntime.resolveAppleMusic`, whenever MusicKit isn't configured or finds nothing) even though `applemusic` is in its `nativeResolverIds`. iOS resolves Apple Music natively and never calls the plugin's `resolve`.

**Unicode property escapes.** Android's WebView and iOS's JavaScriptCore both support them (the Subsonic, Amazon Music, Bandcamp and Apple Music `resolve` were run under `jsc` over the credit vectors), but a `/\p{L}/u` literal in an engine that doesn't is a syntax error that stops the whole function materializing. So a plugin that wants them builds them inside a guard, with an ASCII fallback: `try { re = new RegExp('[^\\p{L}\\p{N}]', 'gu'); } catch (e) {}`.

**A `resolve` that picks among search results picks the way `pickTrackMatch` does.** Mobile's iOS resolver and any host path that calls a plugin's `resolve` take the one track it returns, and the confidence gate scores another version of a track (a demo, a live cut, a medley) 0.95 like the original, so the pick is where a wrong version is turned away. Bandcamp and Amazon Music go: the exact track, then a match the gate would accept that is not another version, then their own fallback (Bandcamp: the top result that is not another version, else nothing; Amazon: any match). SoundCloud is mostly fan uploads, so its `resolve` first decides whose upload a result is: the uploader must be the artist (names equal, a leading "The" aside), or the title an "Artist - Title" upload naming the artist, which the result then reports as its artist and title. Containment isn't enough: "Ramones of the Day" contains "Ramones", and its "ROTD-Ep100 Judy Is a Punk" is a 29-minute podcast. Among those (the artist's own uploads first): the exact title, a title that isn't another version, another version; previews and blocked tracks never; and with none, nothing rather than the top result. Mobile's `pickSoundCloudTrack` (parachord-mobile#597) has the same rule. "Another version" is `isOtherVersion` in `sync-providers/track-variants.js`: a version word the request lacks (`VARIANT_WORDS`, which includes "medley"), or a title that joins several songs with a slash (`joinsSongs`, #1306). Plugin functions can't require it, so each of the three keeps a copy; `tests/resolver/bandcamp-version-variants.test.js` holds the copies to the shared list and slash check. SoundCloud's `resolve` used to return the first result and played Ramones' "Judy Is A Punk (1975 Demo)"; Bandcamp's accepted a medley whose title listed "Her Majesty" (#1306).

**Bandcamp plays only tracks that stream; a buy-only track is purchase-only** (plug-in 1.5.0). An artist can make a track buy-only: Radiohead's own "Nude" and "Reckoner" have no audio on their pages, and once `resolve` read 50 rows (#1534) it picked them, so they showed a Bandcamp icon and failed when played. The search API carries no streamability, so the plug-in asks Bandcamp's mobile API, `GET bandcamp.com/api/mobile/24/tralbum_details?band_id=<band_id>&tralbum_type=t&tralbum_id=<track id>`, which lists a streamable track with its `streaming_url` and a buy-only one with no tracks (or a track without one). `isStreamable(bandId, trackId)` is that check, a method reached through `this` (true, false, or `null` when the check failed or took over 2s); answers are kept on the resolver object for the session by track id, so a track is checked once, and a failed check is not kept. Where each caller uses it:
- **`resolve`** picks as before, then checks the pick. If it's buy-only, the pick comes back marked `streamable: false`, a **purchase-only source**: the app never plays it or shows an icon for it, and the playbar offers Buy from it. We never look for another Bandcamp copy of the same song, because the next match down is almost always someone else's upload (Radiohead's "Nude" has a "stripped mix" credited to Radiohead on another account), not the artist's recording. Unknown keeps the pick as playable (we don't drop a source because Bandcamp's API hiccuped; playback still falls back). It searches with `streamCheck: false`, so it costs one search and one check, and no check starts after 5s, inside `RESOLVE_BUDGET_MS`.
- **`search`** drops results that don't stream, checking up to 5 at a time (a Search page of 20 costs 20 checks the first time, about 2s, and nothing after). Unknown keeps a result, and so does a row with no `band_id` (the `app_autocomplete` fallback's rows can lack it).
- **Album and track pages** (`lookupAlbum`, `lookupUrl`) read it from the page they already fetched: each `data-tralbum` `trackinfo` entry carries its audio `file`, `null` on a buy-only track. An album keeps every track in its list, and a buy-only one keeps its Bandcamp source (`bandcampUrl`, `purchaseUrl`) marked `streamable: false`; a buy-only track link comes back the same way. The answers join the session cache, and `sourceFromUrl` gives a purchase-only source for a page known not to stream.

**Purchase-only sources, in the app.** One rule: `streamable === false` means not playable, `isPlayableSource(source)` in `src/renderer/lib/playable-source.js`. Every path that plays goes through it: `handlePlay`'s candidates and fallbacks (`playableSourceIds`, `fallbackAfter`, the engine's plan-refusal and retry fallbacks, and a purchase-only source handed over as the thing to play, which is resolved like a track with no sources), the playbar's "Play from" list and its line 3 (which names no service when nothing plays the track, and then shows Buy alone), the source icons (`visibleSources`, so a row whose only source is purchase-only is greyed), `hasPlayableSource` (radio, spinoff) and the background pass's "already playable" check, so a buy-only Bandcamp source never stops the other services from being asked. What isn't about playing keeps it: the track-sources cache stores it like any found source, and `purchaseSource` offers Buy from it under the usual rules (a sure match by the same artist, not another version). It is the per-source version of a plug-in the plan can't play (`playbackResolvers`). **No floor change:** an app or a mobile build that predates the flag reads a purchase-only source as playable, which is how every buy-only track behaved before 1.5.0, so `minAppVersion` stays 0.9.13.

## Authoring a plugin (.axe format)

An `.axe` file is JSON with up to seven top-level keys: `manifest`, `capabilities`, `urlPatterns`, `settings`, `embedPlayer` (only for an embedded-player resolver; see above), `requires` (only for a plugin that needs host bridges; see "Required host bridges" above) and `implementation`. For a bundled plugin you never write that JSON by hand. You write `plugins-src/<id>/manifest.json` (everything except `implementation`) and `plugins-src/<id>/implementation.js` (`module.exports = { search: async function (query, config) { ... }, ... }`), then run `node scripts/build-axes.js`, which serializes each exported function with `String(fn)` into the `.axe`. Because the source is a real module, modern syntax including template literals is fine, except in plugins flagged `es5` (see above). A community plugin installed from a file is the same JSON, however it was produced.

### Manifest

`resolver-loader.js` (`createResolverInstance`) reads `id` and `name` (both required; the file installer rejects a file without them), `version` (semver; the loader and marketplace sync compare it), `minAppVersion` (optional, per platform; see "Minimum app version" above), `author`, `description`, `icon` (an emoji; defaults to 🎵), `color` (hex; defaults to `#888888`), `homepage`, `email` and `requirement` (optional: one sentence on what the plug-in needs to work, such as "Needs Spotify Premium, the Spotify app and your own free Spotify developer Client ID." or "Works right away. No account needed."; shown in its panel, so a service's sign-in, subscription or developer key is named where you turn it on. Meta services carry it too: app.js builds each one's entry with `metaServiceFromAxe` (`src/renderer/lib/meta-service.js`) on every path (startup, a marketplace reload, an install), which reads it the loader's way. Every music plug-in has one, which `tests/renderer/plugin-requirement.test.js` checks; a meta-service that needs a key or an account has one too). `type` is either absent (or `"resolver"`), meaning a content resolver that plays or finds tracks, or `"meta-service"`, meaning everything else: AI providers, concert sources, metadata and recommendation services, scrobbling services and the Achordion telemetry plugin. A `manifest.id` may contain only letters, digits, dots, dashes and underscores.

### URL patterns and lookups

`urlPatterns` is a top-level array of glob-like strings, for example `"open.spotify.com/playlist/*"`, `"*.bandcamp.com/album/*"` or `"spotify:track:*"`. The protocol and a trailing slash are ignored, a leading `*.` matches any subdomain, a middle `*` matches one path segment, a trailing `*` matches the rest of the path, and the query string is ignored unless the pattern itself contains `?` (`matchUrlPattern`). `findResolverForUrl(url)` returns the first resolver whose pattern matches.

**`urlTypes`** (optional, top level, #1356 M11) declares how `getUrlType(url)` classifies a matched URL — the same glob language as `urlPatterns`, as manifest data instead of the per-host switch that used to live in `resolver-loader.js`:

```json
"urlTypes": {
  "track":   ["music.amazon.com/albums/*?trackAsin=*", "music.amazon.com/albums/*?*trackAsin=*"],
  "album":   ["music.amazon.com/albums/*"],
  "playlist": ["music.amazon.com/playlists/*", "music.amazon.com/user-playlists/*"]
}
```

Rules: `getUrlType` classifies a URL **only through the resolver `findResolverForUrl` routes it to** — a broad typed pattern in another plugin's manifest can never classify a URL that resolver doesn't own, so the type can never disagree with the routing. Within the routed resolver, the object's **key order is the priority** — `getUrlType` iterates its flattened patterns first-match-wins, so a manifest lists its most-specific patterns first (Amazon's `albums/*?trackAsin=*` before `albums/*`, so a song share link types as a track; YouTube's `watch?v=*&list=*` before `watch?v=*`; SoundCloud's `…/sets/*` and `…/*/*` before its one-segment artist pattern). A pattern containing `?` matches the query string — the shape that expresses Apple's `?i=`, Amazon's `?trackAsin=` (one track of the album) and YouTube's `&list=`. A URL no resolver routes, or one whose routed resolver declares no matching pattern, classifies as `'unknown'`, and a plugin with no `urlTypes` gets `'unknown'` for everything (old apps ignore the field and keep their own classification, so no `minAppVersion` is needed). Every shipped URL-carrying plugin declares one (`spotify`, `applemusic`, `youtube`, `amazonmusic`, `bandcamp`, `soundcloud`, `listenbrainz` — `tests/resolver/resolver-loader-url-types.test.js` drives the loader over each manifest's own declaration).

`lookupUrl(url, config)` returns a track, `lookupAlbum(url, config)` returns `{ name, artist, albumArt, tracks, ... }`, and `lookupPlaylist(url, config)` returns `{ name, tracks, trackCount, ... }`. A playlist lookup may also return `albumArt` — the playlist's OWN cover, the image the service shows for the playlist (Spotify, Amazon Music and Apple Music fill it); the host puts it on the saved record's `coverArt` so every playlist-cover surface shows the provider's image instead of a generated mosaic (see "Playlist covers" in [album-art.md](album-art.md)). It is never the cover of any track: tracks carry their own `albumArt` when the service sent one. Each may return `null`, and callers must handle that. `getUrlType(url)` (which decides whether a matched URL is a track, album, playlist or artist) reads the same manifest's `urlTypes` (above) — a new service declares its own shapes and needs no host change.

**`sourceFromUrl(url, track, config)`** (optional, #1523): a track can arrive knowing its link on a service (`track.sourceUrl`; a Bandcamp track scraped from a playlist page keeps its page). When resolution reaches the plug-in that `findResolverForUrl` routes that link to, and `getUrlType` calls it a track link, the host asks this method for a source built from the link (`track` is `{ title, artist, album, duration }`) instead of calling `resolve()` (`src/renderer/lib/source-url-hint.js`). It answers without a fetch or a search; `null` falls back to `resolve()`. Bandcamp implements it (1.4.8). Until #1523 `resolveTrack` tested `resolver.id === 'bandcamp'` for this.

### Album search (`searchAlbums`, optional)

A content resolver that can find an album by name declares `capabilities.albumSearch: true` and implements two functions:

- `searchAlbums(query, config)`. `query` is `{ artist, title }` from an album page, or a free-text string from Search. Returns `[{ id, name, artist, albumArt, releaseDate, trackCount, url }]` (any field but `name` and `url` may be `null`), or `[]` on a miss. Never throws for a miss, and returns `[]` without a request when it lacks the credentials it needs (Spotify without a token, Subsonic without a server).
- `lookupAlbum(url, config)`, which must accept every `url` its own `searchAlbums` returns. The host calls it on the resolver that found the album (`ResolverLoader.lookupAlbumFrom`), not through `findResolverForUrl`, so a `url` may be private to the plugin and match no `urlPatterns` (`subsonic:album:<id>`, `localfiles:album:<artist>/<album>`). It returns the usual `{ name, artist, albumArt, releaseDate, trackCount, tracks, url }`, where each track has at least `title`, plus `duration` (seconds), `trackNumber` and `discNumber` when known.

`tests/resolver/album-search-capability.test.js` fails a plugin that declares the capability without both functions. Keep credentials out of anything returned: results and their urls are held in page state, and a Subsonic token in a cover or stream url replays until the password changes.

**Who uses it.** Every album page gets its canonical track list from MusicBrainz through `fetchReleaseData` (Fresh Drops, Charts, Critic's Picks, Home, Search, Collection, the artist page, the playbar, `parachord://album` links). A page opened by name searches MusicBrainz release groups first, and which result is the album comes from `pickReleaseGroupForAlbum` (`src/renderer/lib/album-catalog.js`): the title and the artist decide (edition suffixes aside). The artist rule is `creditMatches`: a joint credit counts however the source joined it ("A, B", "A & B", "A feat. B"), because every source writes one its own way — with one side a single name, one artist of the other side's joint credit is enough (the catalog rule below), and when both sides are joint credits the same names in any order are needed, so "A & B" is not "A & C", and only among results for that album does a studio edition beat a live or compilation one; among the artist's own results the closest title ranks first (MusicBrainz often spells a title out: "Back to the Beginning" for the album a source calls "Back to the Beginning", full title "Back to the Beginning: The Final Show, Live from Villa Park"; a prefix counts only at a word boundary, so "Rumours" finds "Rumours: Live from the Forum 1977" and "Go" is not "Goodbye"). A result is only ever the album if its credit matches the artist asked for: when none does the answer is null and the opener goes to the services' catalogs, never to "whatever MusicBrainz ranked first" — a search for an album MusicBrainz doesn't have ("Another Day Once Called Tomorrow" by Defenders Of The Faith and Therion, 2026-11-20) answers same-words albums by other artists, and opening one of those is worse than saying the album wasn't found. Every opener uses it — `handleCollectionAlbumClick` (Home, Recommendations, the Collection), the `parachord://album` link, the playbar's `openAlbumForTrack`, and the album-card actions' release-group search in `loadAlbumTrackList`. Until 2026-11-20 each had its own "an Album by the right artist, else any Album, else the first result" chain, which ignored the album's title, and in `handleCollectionAlbumClick` the artist compare was the whole credit string: an album Amazon credits "Ozzy Osbourne, Black Sabbath" and MusicBrainz "Ozzy Osbourne & Black Sabbath" matched no result, and the page opened the first studio album in the list — an unrelated tribute record. Then a release-group id loads up to 25 of its official releases with `inc=recordings` in the browse itself (`fetchReleaseGroupDetails`), and `pickRelease` (`src/renderer/lib/release-pick.js`) chooses one: digital-only releases first, since those are what the services carry, then the most common track count, then a Worldwide release (country `XW`), then a US one, then the earliest date. MusicBrainz lists one digital release per storefront on the same day, and taking the first listed put Bahrain on Bon Iver's "For Emma, Forever Ago" (#1312). A group's pick is remembered for 30 days as an alias in the persisted release-details cache, stamped with the rule's version (`PICK_RULE`); `hasCurrentAlias` ignores an alias from an older rule, so a change to the rule re-picks each album once (one browse) instead of leaving the old choice in place for a month. It used to take the first release MusicBrainz listed, which for George Michael's "The Faith Tour" was a 9-track CD while the digital release has all 18 (#1288). The hover prefetch, Fresh Drops, `parachord://album` MBID links and the collection's track counts make the same choice, and an id known to be a group (an artist-page card or a `parachord://album` match carries `isReleaseGroup`) skips the release-id probe that would 404. An album opened from the artist page used to cost three requests, a second and more apart. When MusicBrainz fails or doesn't have the album, `loadAlbumFromCatalogs` (src/renderer/app.js; the pure part is `src/renderer/lib/album-catalog.js`) asks the albumSearch resolvers in order (the one a release id came from, then the user's active services in their priority order, then every other installed one), keeps the first result whose artist and title match (`pickCatalogAlbum`: edition suffixes aside, the same `creditMatches` artist rule), and loads it with `lookupAlbum`. It also races MusicBrainz: as soon as a page is waiting for its track list, the catalogs are asked too (unless MusicBrainz's answer is already cached), and their list shows if it lands first, which it usually does (a service answers in well under a second; every MusicBrainz request waits its turn in the 1 req/s queue). Whichever list lands first stays: when MusicBrainz answers after a catalog list is on screen, `fetchReleaseData`'s success keeps the catalog list (its source line keeps naming the service, and MusicBrainz's editions stay in the source dropdown). Until 2026-11-15 MusicBrainz's answer replaced it, which flickered the page's source from the service to MusicBrainz. `fetchReleaseData`'s own load leaves a catalog list on screen alone, and a MusicBrainz failure leaves it standing. Until 2026-11 the catalogs were asked only after the page had waited 5s. The album-card actions (Play, Add to Queue, Add to Playlist on Search, Home, Fresh Drops, Charts and the Top Albums lists, AI chat's "play this album", and albums the browser extension sends) get their track list from `loadAlbumTrackList`, which races MusicBrainz against `loadAlbumFromCatalogs` and takes the first list with tracks (`src/renderer/lib/album-track-list.js`). There is no page to settle afterwards, so whichever answers first is the list; track ids still come from the names the card asked for. A Search row from a service skips MusicBrainz, and a MusicBrainz answer already cached skips the race. They used to wait on MusicBrainz alone, two or three requests, with nothing when it failed. Both lists resolve their tracks through `resolveAlbumTrack`, which joins a resolution already running for the same track id, so a matching MusicBrainz list doesn't search every track a second time. The **album page's source card** (#1238) is the third consumer: the card under the album title (where the year / date / track-count lines used to sit — a non-album release type is a badge beside the title instead) carries the edition on screen (a top line with only the source's badge and name, then one line per detail: a MusicBrainz release's formats ("Digital Media"), the date, the region and the song count, so nothing is cut off at the card's width; #1312) and opens to list the other editions of the album — "Your services" first, then "MusicBrainz editions" — the release group's official MusicBrainz releases (`fetchReleaseGroupReleases` in `src/renderer/lib/release-lookup.js`: the browse the page open already made kept them, so it usually costs no request; else one light `inc=media` browse) and every edition the user's ACTIVE albumSearch resolvers carry (`searchAlbums` results kept via `isCatalogAlbumEdition`, the same-album filter — which uses the same `creditMatches` rule, so a service's edition of a jointly credited album is listed whatever its join, while another collaboration is not; any trailing parenthetical is dropped from both titles, so Amazon's "Back To The Beginning (Live)" is an edition of MusicBrainz's "Back to the Beginning" (2026-11-20) — `pickCatalogAlbum`'s containment is deliberately too loose here: "Queen I" contains into "Queen II"). Every row shows its date and song count. A service whose search answers without them (Bandcamp and Amazon Music carry neither) has each such edition looked up when the menu opens (`fillAlbumEditionDetails`, through `lookupAlbumEditionCached`, so a later pick of it is instant), with a shimmer on the row meanwhile; a lookup that fails leaves the row without them, and the next open asks again (#1312). It loads lazily, when the dropdown opens, so it is not in a page's MusicBrainz budget. A service whose search fails or loses to the 8s catalog bound (the page's own track resolution can keep the shared limiters busy) is retried PARTIALLY on the next open: the parts that answered stay, only the failed ones re-run (the loader's `searchAlbums` rejects on a plugin error for exactly this — a miss answers `[]`, an error rejects). Picking an edition switches the page's track list (`selectAlbumVersion` in app.js: an MB release via `fetchReleaseDetails`, a catalog edition via `lookupAlbumEditionCached`), resolves the tracks through the usual pass, and the pick sticks for the session in both kinds: `albumEditionPicksRef` remembers it under the album's identity AND its release group (`albumEditionPickKeys`), and every reopen consults it — `fetchReleaseData` (artist page, charts, search, collection), the playbar's `openAlbumForTrack` (which skips its release-group search when a pick is known), the album-card actions (`loadAlbumTrackList`) and the hover prefetch. A catalog pick loads straight from the cached edition lookup (`lookupAlbumEditionCached`: resolver + url, cached for the session — a catalog album's track list never changes for a given url), and the catalog race refuses to fill a page whose pick is loading. The pick survives neither the persisted `releaseDetailsCache` nor restarts. That effect keys on the album (`sameAlbumIdentity`: artist and title), not the id, since a page moves from a release-group id to a release id while it loads, and concurrent lookups for one album share a single request. A release with a service's id (`spotify-…`, `applemusic-…`, `lastfm-…`, `discogs-…`, from a Search result or an artist-page card built from that service) skips MusicBrainz: these used to be sent to MusicBrainz and never open. Search asks every active albumSearch resolver at the same time as MusicBrainz (and the inactive ones too when MusicBrainz returns fewer than three, including when it is down), and a result carries `_catalog: { resolverId, url }` so the click loads it without searching again. See "Search" below.

MusicBrainz stays first for albums that have a MusicBrainz id. Its track titles are the ones track ids (`trackSlug` of artist, title, album) and the resolution cache are keyed on, and its recording ids feed scrobbles and Achordion; a service's titles differ by edition ("Song (Remastered 2011)"). For the same reason the converted release (`catalogAlbumToRelease`) keeps the requested artist and album title, drops the plugin's track ids and sources (the usual resolution pass finds each track on the user's services), and is not written to the MusicBrainz caches. The page says where the list came from ("Track list from Bandcamp").

Implemented by Apple Music (Apple's catalog through the host's `window.appleMusicSearchAlbumsWithMusicKit` when MusicKit is configured, else the public iTunes catalog, so no account is needed; a miss on artist + title retries with the artist alone. iTunes album search lags the catalog badly: "Mount Zero" by Swapmeet was missing for over three months after release. The hook returns the catalog's albums, `[]` for a real miss, or `null` when MusicKit can't answer, which sends the plugin to iTunes. The mobile hosts supply the same hook over their own catalog bridge), Spotify (signed in), Bandcamp (its public search API, albums only; covers are built from `art_id` as `img/a<art_id>_10.jpg`, since the API's own `img` field lacks the `a` prefix album art lives under and 404s at every size), Local Files (the user's own library, `localFiles:searchAlbums` / `localFiles:getAlbumTracks`), Subsonic (`search3`, `getAlbum`) and Amazon Music (the capture-and-replay gql flows — the albums tab of the same `SpecSearchSeeMorePage` the track search uses, and the album page's `AlbumDetailPage`; see [amazon-music.md](amazon-music.md), "Album search and lookup").

### Search

The Search page (`performSearch` in src/renderer/app.js; the pure part is `src/renderer/lib/search-catalog.js`, and its requests, MusicBrainz's three searches and ListenBrainz popularity, are `src/renderer/lib/search-requests.js`, whose budget `tests/renderer/search-load-budget.test.js` counts: 3 MusicBrainz requests per query, at most 1 ListenBrainz request per category) runs two sides at once. MusicBrainz answers artists, albums and tracks with three requests in the 1 req/s queue, so they land one to several seconds apart. The user's services answer in a few hundred milliseconds: every active resolver that declares `search` (and can `play`) for tracks, and every active `albumSearch` resolver for albums, in the user's priority order, each bounded at 8s (`withCatalogTimeout`). There is no artist-search capability; Search lists the artists those track and album results name when the name matches the query. Each answer re-publishes its category, and the page shows each category as soon as it has rows: the skeleton stands in only until the first rows land (it used to cover the whole list until the last request finished, so Search showed nothing until MusicBrainz's tracks came back, five seconds and more), and a new query with nothing cached clears the previous query's rows. MusicBrainz rows are canonical: a service hit with the same artist and title (normalized; not the scorer's containment test, which would fold "Creep (Acoustic)" into "Creep") and the same album, edition suffixes aside, or no album on either side, adds its source to the MusicBrainz row, at the confidence the scorer gives it and only above `MIN_CONFIDENCE_THRESHOLD`. The album condition is there because MusicBrainz returns several recordings of a song: without it, the studio "Roads" every service found joined a live recording's row and the studio version never showed. The same track from two services is one row, the higher-priority service's, carrying both sources. A row only a service found has that hit as its own source at confidence 1, and a service row that repeats a local file's row is dropped. Every list is re-ranked by `reRankResults` (`rankSearchRows` in search-catalog.js): fuzzy relevance (tracks against "artist title", `TRACK_RANK_KEY`, so "portishead roads" finds Portishead's "Roads" ahead of the covers titled "Portishead - Roads"; albums the same way, `ALBUM_RANK_KEY`) blended with MusicBrainz's search score (how well the text matched, not popularity) or a service row's score, which is 100 less 5 per place down that service's list and 5 per service ahead of it in the priority order, plus 5 for each further service that returned the same track. Before 2026-11 MusicBrainz was the only source, with Spotify and Apple Music hard-wired in for artists and tracks only when it returned fewer than three results. Tracks and albums the query names, by artist as whole words (`queryNamesArtist`) or by exact title, edition suffixes aside (`queryNamesRow`; the title half keeps a tribute band named Abbey Road from outranking the Beatles' Abbey Road), get `ARTIST_NAMED_BONUS` (20), and form a top tier that holds still above the rest: titles alone ranked a search for "Mazzy Star" by which albums had the name in the title, so the covers ("Into Dust (Mazzy Star Cover)") topped Mazzy Star's own albums, and a fast service's covers kept the top slots even once those arrived (2026-11-02). Popularity, where a source has it, is averaged into a row's standing: ListenBrainz listen counts (no account needed; one batched `/1/popularity/<kind>` request per category, fetched before MusicBrainz's rows show, capped at 800ms, cached a day) by release group for albums and by artist for tracks (a song's plays are split across duplicate recordings, so an original's recording often has no count; artist totals do: Mazzy Star ~4.2M, a covering artist ~18k), on a log scale (`popularityFromListens`), and Spotify's own 0-100 track popularity for users with Spotify. A row without popularity counts as its list's median, so having or lacking the signal is neutral and a list with none ranks as it would without popularity. Rows hold still as sources answer (`stabilizeRows`): a row that stands for one already on screen keeps its display key (`_rowKey`, which keys the card) and its position, and rows new to the list follow in ranked order. A row that outranks one shown ahead of it by at least `PROMOTE_MARGIN` (5) moves past it, once and within its tier, so the original song, arriving with its artist's popularity after a fast service's covers, still reaches the top ("Fade Into You": Mazzy Star's at the top 0.9s in); smaller gaps hold still. Merges record the ids a row stands for (`_aliases`), so a MusicBrainz row that absorbs a shown service row takes over its card without a remount; the real `id` still changes (MusicBrainz wins identity), and `data-track-id` stays on it for the resolution scheduler. Re-ranking the whole list on every answer used to move every card, and covers faded out and back in (2026-11-01: slots changed at 1.0s, 1.8s, 7.3s and 8.0s; now 22 sampled slots, 0 changes). Covers for the results go through `getAlbumArt` in the background lane (see [album-art.md](album-art.md)); a superseded query's queued MusicBrainz requests leave the queue without using a slot (`createLimiter`'s `signal` option). Tests: `tests/renderer/search-catalog.test.js`, `tests/renderer/search-speed.test.js`, `tests/resolver/limiter-abort.test.js`.

### Artist images (`searchArtistImage`, optional)

A content resolver that can find a photo of an artist declares `capabilities.artistImage: true` and implements `searchArtistImage(artistName, config)`, which returns an image URL or `null`. It returns `null` for a miss, and without a request when it lacks what it needs (Subsonic without a server). When the service couldn't answer (unreachable, a refused request, an error reply) it **throws**, and `ResolverLoader.searchArtistImage` passes the throw on: the photo chain remembers "no photo" for 6 hours only when every step answered, so a failure read as `null` turned one outage into a 6-hour miss (#1358). This is the "a miss is empty; a failure throws" rule below, applied to photos. The URL goes into the persisted artist-image cache, so it must not carry credentials: the host refuses any URL with a credential-shaped query parameter (`looksLikeCredentialBearingUrl` in `discord-presence-logic.js`), which rules out a Subsonic `getCoverArt` URL.

**Who uses it.** `getArtistImage` (src/renderer/app.js; the pure part is `src/renderer/lib/artist-image-chain.js`) serves every artist photo: recommendations (Shuffleupagus's artist suggestions now show only there; Home dropped its artist row), related artists, Search, top artists, friends, chat cards and the artist page. First photo wins: Spotify (signed in), Apple Music (MusicKit configured), the user's *active* artistImage resolvers in their priority order (inactive ones are not asked: this runs for every artist on a page), Deezer's public artist search (no account; through the main-process proxy, like the album-art chain), Wikipedia via Wikidata when the caller passes the artist's MusicBrainz id (`getArtistImage(name, { mbid })`; no MusicBrainz lookup is made just for a photo), and Discogs when the user has a Discogs token (its search needs one). Each step is bounded at 8s. A miss is remembered for 6 hours when every step answered, and forgotten when the Spotify token changes. It used to ask only Spotify and Apple Music, so a user signed in to neither saw only placeholders outside the artist page (2026-10-27).

Implemented by Subsonic (`search3` for the artist, then the OpenSubsonic `artistImageUrl` or `getArtistInfo2`'s image, credential-free URLs only; Navidrome's `/share/img/` links qualify) and Amazon Music (the artists tab of the same `SpecSearchSeeMorePage` the album search uses — the photo comes from an Artist node whose name matches exactly after normalization, and a lookup queued past the step budget skips its page load so a page asking for 5–20 photos cannot starve track resolution; see [amazon-music.md](amazon-music.md), "Artist images"). Bandcamp is deliberately not: its public search answers 429 under load, and the track resolver shares that budget.

### Recommendations (`getRecommendations`, optional)

A resolver or a meta-service that can recommend music declares `capabilities.recommendations: true` and implements:

- `getRecommendations(config)` → `{ sections: [{ id?: string, title?: string, description?: string, nextCursor?: string, items: [...] }] }`. Each item is `{ type: 'artist' | 'album' | 'song' | 'playlist', id?: string, name: string, artist?: string (songs/albums), duration?: number (songs, seconds), imageUrl?: string, url?: string (the service page for the thing), reason?: string (shown as a tooltip), mbid?: string, isrc?: string (stable ids the service already knows — copied onto a song item's track, so MBID enrichment and the exact-MBID match tier work without another lookup), releaseDate?: string (albums: 'YYYY', 'YYYY-MM' or 'YYYY-MM-DD', the page's "Coming" badge uses it instead of a MusicBrainz lookup) }`. A song with no `id` gets `trackSlug(artist, name)` — the id every no-album track context keys session state on — so a provider should leave `id` out rather than invent one that two songs could share. Every section's items, titled or not, feed the page's blended rows, one per item type (playlists and albums split further by category, below), alongside Shuffleupagus; section titles are not shown (they matter to the provider, and a titled section with an `id` can page). A playlist item may carry a `weekly` marker; weekly playlists are placed first in the Playlists section (in Made for you when the section has category rows, below), Exploration before Jams. A miss is `{ sections: [] }`, never a throw, and an unconfigured service answers `[]` without a request. A readiness failure (signed out, offline) THROWS — the page distinguishes it from a miss and keeps other providers' sections. A section that carries `nextCursor` (Amazon's synthesized "Playlists for You", whose first page the provider pre-fetched) starts its "Load more" from that cursor.

  **Categories (playlists and albums).** A section may carry `category`, one of `new`, `personal`, `artist`, `editorial` or `community`, and an `artist` section may also carry `seedArtist` (the artist name it is built around). A playlist or album item may carry its own `category`, which overrides its section's. The page uses them to split the Playlists and Albums sections into rows, each type with its own table and titles:

  | Category | Playlists | Albums |
  |---|---|---|
  | `new` | not valid (counts as missing) | New for you |
  | `personal` | Made for you | Based on your listening |
  | `artist` | Because you like ... | Because you like ... |
  | `editorial` | From the editors | From the editors |
  | `community` | From other listeners | not valid (counts as missing) |
  | none | More playlists | More albums |

  `weekly: true` always means personal, for playlists. An unknown or invalid value for the type counts as missing. Artists and songs ignore both fields. A paged item takes its section's category, and a pageable entry carries the section's category whenever it is valid for any type. The fields are additive, so a plugin declares no `minAppVersion` for them: an older app ignores them and keeps one row per type. Shuffleupagus's albums count as personal. `new` is sent by Amazon Music's New Releases for You shelf, and Apple Music will send it once its recommendation groups are mapped (#1378). Providers that send categories today: Amazon Music 1.13.0 (the playlists, recents, Albums for You, Your Frequent Plays and Recently Played shelves to personal; New Releases for You to new; the by-artist shelf to artist; the community playlists shelf to community; the genre shelf and every editorial shelf to editorial; Featured This Week is left out; any other strategy gets none, so it lands in More albums or More playlists; see amazon-music.md "Recommendations"), ListenBrainz 1.6.0 (`weekly-exploration` and `weekly-jams` to personal) and Apple Music 1.5.0 (playlists only, below). Apple's albums wait on #1378. Last.fm sends none. Amazon's `seedArtist` for an artist shelf is the one `artist` every album in it shares (trimmed, compared case-insensitively, the first item's spelling); it is never read from the shelf title, and mixed or blank artists give no seed, so the row title falls back.

  The page keeps `expandedSections[key].lastPageCategories` as typed `<type>:<category>` strings (for example `playlist:personal`, `album:new`), so a playlist and an album category never collide; the loading tail follows the rows the last page filled.
- `expandRecommendationSection(sectionId, afterCursor, config)` (optional) → `{ items: [...], nextCursor: string | null }` — the next page of a titled section that carries a section `id`. The page background-paginates such sections while the type section holding their items stays open (See all drives the fetches, one chain per provider section even when it holds two types; a section's first expansion passes no cursor and the provider's page 1 dedupes against the section base).

`resolver-loader.js` dispatches: `getRecommendationResolvers()`, `getRecommendations(resolverId, config)` and `expandRecommendationSection(resolverId, sectionId, afterCursor, config)`.

**Apple Music** (plugin 1.5.0) implements it from Apple's personal recommendations, `GET /v1/me/recommendations`, through a narrow host hook, `window.appleMusicPersonalRecommendations(limit)` (src/renderer/app.js). The hook sends the developer token and the app's user token of record (`musickit_user_token`); on a 401/403 it runs `checkAppleMusicUserToken` once to adopt another stored token Apple accepts, and otherwise throws a `notReady` error ('no-developer-token', 'not-signed-in', 'token-refused'). Each of Apple's groups becomes a titled section of albums (with `releaseDate`), playlists (the discovery mixes included: Chill, Get Up!, New Music) and songs. Left out: stations (Parachord can't play them), the "Recently Played" group (`kind: 'recently-played'`, history), and the mixes made from what the account already plays, which belong on Home's "Made from your listening" row rather than a page of recommendations (see "History mixes" below). Apple marks every personal mix `playlistType: 'personal-mix'` alike, so Heavy Rotation, Your Essentials and Favorites are told apart by name or URL slug (English only; a translated name still matches when the slug is English), and Replay by `playlistType: 'replay'`. A group of groups (`isGroupRecommendation`, `relationships.recommendations`) is flattened. Apple Music 1.5.0 sets each recommended playlist's `category` from its `playlistType` (personal-mix to personal, editorial to editorial, user-shared to community, others none). Whether Apple's recommendation groups name a seed artist in structured data is not yet verified (no signed-in Apple Music session was available on 2026-11-12), so Apple sends no `artist` category until that is checked. A host without the hook is a quiet empty provider. The plugin declares no `minAppVersion`, since its other capabilities work on older apps; the feature check covers them.

**Who uses it.** The Recommendations page (`loadRecommendations` in src/renderer/app.js; the pure model is `src/renderer/lib/recommendation-model.js`); Home runs the same load after first paint for its "Albums you might love" row, which shows every provider's album picks, and skips it when a full load finished in the last 10 minutes (`shouldLoadHomeRecommendations` in `src/renderer/lib/home-model.js`). Providers run in parallel, each bounded at 20s and cached per provider for an hour (`CACHE_TTL.recommendations`); content resolvers are asked only when ACTIVE (a disabled resolver is not a recommendations source) in the user's priority order, meta-services after them. The Shuffleupagus (LLM) suggestions are interleaved into the Albums and Artists rows (round-robin with the providers, Shuffleupagus last in each round), fed by `loadAiRecommendations`, not a plugin — the same state Home's "Albums you might love" row shows (and refreshes with its Refresh icon). Songs resolve through the shared resolution scheduler like every other track list; albums open through `handleCollectionAlbumClick`; playlists play through the generic `lookupPlaylist` path (`resolveProviderPlaylistUrl`) and import through `handleImportPlaylistFromUrl`. A playlist item's `imageUrl` rides on the ephemeral playlist as `coverArt` when it opens in the playlist view (the exact image the card showed), and the import keeps it / the lookup's own `albumArt` as the saved record's `coverArt` ("Playlist covers" in [album-art.md](album-art.md)). The recommendation blocklist applies to every item at merge time, so a block made since a cache was filled takes effect at once. So does the history-mix exclusion: a playlist whose `id` is one of the cached history mixes (below) is left out of the Playlists row (`excludePlaylistIds` in `buildRecommendationPage`, applied after the newest-week pick, so dropping this week's Jams never brings last week's back). Home's weekly mirror (`homeData.weeklyJams` / `weeklyExploration`, which a restored playlist view and the queue drawer's "Go to source" read) is built from the page before that exclusion (`buildRecommendationViews`), so a Jams playlist that is also a history mix stays findable.

Implemented by Last.fm (the recommended station), ListenBrainz (one recommendation playlist picked by type for the songs: a current Weekly Exploration, else the newest Daily or Weekly Jams, never the yearly round-ups; no fallback to the user's own top recordings, parachord#1021; plus the `weekly-exploration` and `weekly-jams` titled playlist sections from its `createdfor` playlists, which Home used to fetch itself and which still answer when the songs pick misses) and Amazon Music (the music home's `MusicHomePage`/`RecommenderSeeMorePage` gql, plus the "Playlists for You" section synthesized from the playlists strategy — the user's mixes included; see [amazon-music.md](amazon-music.md), "Recommendations").

### History mixes (`getHistoryMixes`, optional)

A resolver or meta-service whose service makes mixes from the user's own listening (Apple Music's Heavy Rotation, Favorites and Replay; ListenBrainz's Daily and Weekly Jams) declares `capabilities.historyMixes: true` and implements:

- `getHistoryMixes(config)` → `{ mixes: [{ type: 'playlist', id: string, name: string, description?: string, imageUrl?: string, url: string }] }`. `id` is the service's playlist id and must be the same id the plugin uses for that playlist anywhere else (the Recommendations page leaves out a playlist whose id is a history mix). `url` is the service page the generic `lookupPlaylist` path opens and plays (`resolveProviderPlaylistUrl`), so a mix without one is dropped. `description` is the card's one line ("Your most played, refreshed daily"). A miss is `{ mixes: [] }`, and an unconfigured service answers it without a request. **A failure THROWS, never `{ mixes: [] }`**: an empty answer replaces the cached mixes, a throw keeps them. Throw an error with `notReady: true` for a signed-out account (its cached mixes are then dropped, as for recommendations).
- **The `url` must be routable.** `resolveProviderPlaylistUrl` proceeds only when `findResolverForUrl(url)` matches the plugin's `urlPatterns` AND `getUrlType(url)` is `'playlist'` (the plugin's own `urlTypes` declaration), then calls the plugin's `lookupPlaylist(url, config)`. A plugin whose mixes have no such page needs all three (ListenBrainz declares `urlLookup`, `urlPatterns` for `listenbrainz.org/playlist/*`, and `lookupPlaylist`).
- **History mixes never go in `getRecommendations` in a new plugin.** An app older than this capability doesn't know the method, and mixes returned inside `getRecommendations` with a marker would put play history back on its Recommendations page (#1342). A plugin that already returned some of them there may keep doing so for older apps; this app drops them by id. Only Weekly Jams come back as playlists from ListenBrainz's `getRecommendations` (its `weekly-jams` section); Daily Jams only feed the Songs pick there.
- **Implementers.** Apple Music 1.5.0 and ListenBrainz 1.6.0 (plus its `lookupPlaylist` for `listenbrainz.org/playlist/<mbid>`, which takes each track's album from the JSPF track extension's `release_name` when the track has none, so the mix's mosaic shows album covers). Amazon Music does not implement it yet. ListenBrainz names its mixes "Daily Jams" and "Weekly Jams" and makes the date part of its title the `description` ("Week of Sep 14, 2026", "Nov 11, 2026"; a title of another shape stays whole); Apple Music's `description` is the playlist's short (else standard) blurb with markup stripped.

`resolver-loader.js` dispatches `getHistoryMixResolvers()` (declares the capability AND implements the method, since a marketplace install can be older than the app) and `getHistoryMixes(resolverId, config)`, which answers `[]` for a resolver without the capability or an answer without a `mixes` array, drops entries that aren't objects, and REJECTS when the plugin throws.

**Who uses it.** Home (`loadHistoryMixes` in src/renderer/app.js; the pure helpers are `normalizeHistoryMixes` and `flattenHistoryMixes` in `src/renderer/lib/home-model.js`): the "Made from your listening" row (up to six cards, round-robin across providers, with one source chip per service) and Jump back in's mix tile (the first of those). Providers are found by capability and ordered like the recommendation providers (active content resolvers in priority order, then meta-services). Each runs in parallel under the same 20s bound, is cached per provider for an hour (`CACHE_TTL.recommendations`) and per account (a meta-service's username), and is saved as `cache_history_mixes` (`{ providers: { [resolverId]: { resolverId, resolverName, items, fetchedAt, account } }, savedAt }`, one of the big caches read after first paint: the load waits for it with `waitForBigCaches`, so the row and tile appear a moment after Home paints). The cache shows only for the account it was saved under, in provider priority order, and an answer that changes nothing (all served from the cache) keeps the previous entries, so it costs no Recommendations re-merge or Home render. A provider that throws keeps its cached mixes, except a `notReady` one. Home's background effect runs it through the recommendations throttle (`loadHomeHistoryMixes`: not while one runs, and not within 10 minutes of one that answered with mixes); opening Recommendations runs the same throttled load, since that page needs the ids. A card opens the mix with `openServicePlaylist` (the remote-playlist view the Recommendations cards open), and its hover actions, the ones every playlist card has, load its tracks with `addServicePlaylistToPlaylist` / `playServicePlaylist` / `queueServicePlaylist` (the same lookup, `recommendationPlaylistTracks`; the Recommendations page's playlist cards call the same three), Play and Add to Queue under a `{ type: 'mix', id, name }` playback context (`mixContext` in home-model.js; its `id` is the mix's link, `m.url`, since #1592) so Jump back in leaves out a mix that is playing or queued, and the queue's "Playing from" opens the mix itself (`openMixFromContext` in app.js): the mix on Home when it's still there (by link, or by the mix's own id, which a queue saved before #1592 carries; `mixForContext`), else the same view built from the link, its service found with `findResolverForUrl`, else Home. Android and iOS build the same context. A mix with no `imageUrl` (ListenBrainz sends none) gets the 2x2 mosaic every playlist card shows: while Home is showing, one mix at a time, its tracks come through that same lookup and its covers through `getPlaylistCovers` (`mixesNeedingMosaic` and `withMixMosaics` in home-model.js); a failed lookup is retried a minute later, up to 3 attempts a session (`HOME_MIX_COVER_ATTEMPTS`), and a mix that still fails, or has no covers, keeps the placeholder.

### Similar users (`getSimilarUsers`, optional)

A meta-service that can name listeners with taste close to the user's declares `capabilities.similarUsers: true` and implements `getSimilarUsers(config)` → `[{ username, similarity, avatarUrl?, topArtists? }]` (most similar first; `similarity` is 0 to 1; `topArtists` is up to 3 artist names the person has played most recently, for their card). Like `getRecommendations`, an unconfigured service answers `[]` without a request and a readiness failure THROWS (the page keeps other providers' rows). `resolver-loader.js` dispatches `getSimilarUsersResolvers()` and `getSimilarUsers(resolverId, config)`; the Recommendations page's Listeners section is its only consumer (`similarUsersProviders` in src/renderer/app.js).

- **ListenBrainz** (1.3.0) uses its similar-users API (`GET /1/user/{username}/similar-users`). `topArtists` and activity: for the 20 most similar (the rest are dropped unchecked), `GET /1/stats/user/{name}/artists?range=this_month&count=3`, then `range=month` when this month has no stats yet (204). No stats either month (204 both times) is an inactive listener, dropped. Each request is asked once with no retry; a failed one is not "inactive": the person stays, without the line.
- **Last.fm** (1.2.1) has no similar-users method, so the plugin computes it from friends of friends: up to 20 of the user's friends' friend lists are read, the top 40 candidates by mutual-friend count are scored by shared top artists (a binary cosine over the two 6-month top-50 artist-name sets, `shared / sqrt(|a| * |b|)`, names lowercased, against the user's own), and anything under 0.06 (3 shared of 50 each) is dropped. A rank-weighted cosine with a 0.05 cutoff over 30 candidates found nobody on a real account (an artist shared far down both lists counted for almost nothing), hence the binary score. It runs at most 4 requests a second, a 429 throws (so a rate-limited run is retried later, not cached as empty), it needs the API key (the user's or the app's built-in one) and costs about 60 requests, which is why the result is cached for a week. `topArtists` and activity: each person over the cutoff gets one more request, `user.gettopartists` with `period=1month&limit=3`. Nothing played in the last month is an inactive listener, dropped; a failed request keeps the person with the top 3 of the 6-month list already fetched for the score.
- **Caching and exclusions.** The page keeps the answer in `cache_recommendations` under `similarUsers` (`{ [resolverId]: { users, fetchedAt, account, shape } }`; an answer without the current `shape`, 3 since inactive listeners are dropped, is shown while it is fetched again), refetches only after 7 days (an empty answer too: a successful empty answer is real, failures throw and store nothing, and a provider whose last answer was empty gets no Listeners skeleton), shares one in-flight run between callers, and treats a missing key as not ready rather than as an empty answer. A provider's id is the friend `service` it speaks for, so only providers whose id is a friend service (a plug-in with `capabilities.friends`, see "Friends" below; the app passes those ids to the model as `exclude.friendServices`) are asked or feed the section; Follow (`addFriendCore`) throws on any other service. The Listeners section drops people you follow, people you removed from Friends, yourself and, for Last.fm, your own Last.fm friends (they are not recommendations).

### Similar artists and tracks (`getSimilarArtists`, `getSimilarTracks`, `getArtistTopTracks`, `getArtistReleases`, optional)

A plug-in that can name artists like a given one declares `capabilities.similarArtists: true` and implements `getSimilarArtists({ name, mbid?, limit? }, config)` → `[{ name, mbid?, match, url? }]`; one that can name tracks like a given one declares `similarTracks` and implements `getSimilarTracks({ artist, title, mbid?, limit? }, config)` → `[{ artist, title, mbid?, match }]`. Both answer most similar first, `match` 0 to 100. A plug-in that can't answer for this input (no MBID for ListenBrainz, the service's "not found") answers `[]`; a failed or refused request THROWS, so an outage is never read as "none" (CLAUDE.md "No resolver holds a row"). `resolver-loader.js` dispatches `getSimilarArtistsResolvers()` / `getSimilarArtists(id, artist, config)` and `getSimilarTracksResolvers()` / `getSimilarTracks(id, track, config)`; both reject when the plug-in throws (#1539).

The app asks every plug-in with the capability at once (`src/renderer/lib/similar-music.js`): active plug-ins and meta-services, in the user's order (`orderCatalogResolvers`), minus one whose Enable switch is off (`enabled: false`) or whose "Use metadata from" switch is off (`metadata_off_resolvers`, #1505). A config whose key isn't ready yet (`credentialsPending`) counts as that plug-in failing. The answers are merged by name (artists) or by artist and title (tracks), keeping the higher `match` and recording every plug-in that named an item in `sources`; a plug-in that fails is left out, and the whole ask fails only when none answered. Consumers: the artist page's Related Artists (`getRelatedArtists`; one filter chip per plug-in in `sources`) and Spinoff (`lib/spinoff-pool.js`: similar tracks, topped up from similar artists).

- **Last.fm** (1.2.8): both, from `artist.getsimilar` and `track.getsimilar`. Needs the API key (the user's or the app's built-in one, `lib/lastfm-key.js`); error 6 is `[]`, any other error body or a failed request throws.
- **ListenBrainz** (1.6.7): similar artists from the labs `similar-artists` API, by the artist's MBID; no account needed. Its `score` is a raw count, so `match` is each score against the top one.

**An artist's top tracks** (`getArtistTopTracks`, #1539 step 2). A plug-in that lists an artist's most played tracks declares `capabilities.artistTopTracks: true` and implements `getArtistTopTracks({ name, mbid?, limit? }, config)` → `[{ title, artist, album?, duration? (ms), mbid?, listens? }]`, most played first, with the same miss and failure rules; `resolver-loader.js` dispatches `getArtistTopTracksResolvers()` / `getArtistTopTracks(id, artist, config)`. The same plug-ins are asked by the same rule (`similarProviders(loader, 'artistTopTracks', …)`), but the lists are never merged: each is ranked by its own service's plays, so the first non-empty one in the user's order is played (`firstAnswer`). `findArtistTopTracks(artist, limit)` in app.js answers `{ tracks, source, failed }`; `artist` is a name or `{ name, mbid }`, and without an MBID the MBID mapper's cache is asked for one. Consumers: Play on an artist (`playArtistTopTracks`) and Add Top 10 to Queue, which say "Couldn’t load …" rather than "No top tracks" when no plug-in answered; Spinoff's top-up (`lib/spinoff-pool.js`, passing each similar artist's MBID); and an artist-only radio seed (`parachord://play/radio?artist=`).

- **Last.fm** (1.2.9): `artist.gettoptracks`, by name.
- **ListenBrainz** (1.6.8): `/1/popularity/top-recordings-for-artist/<mbid>`, by MBID, only for a signed-in user: ListenBrainz refuses this endpoint without the user's token (a 401 since 2026-11), so signed out it throws rather than asking. A song's plays are split across duplicate recordings, so each title is kept once.


**An artist's releases** (`getArtistReleases`, #1539 step 2). The artist page's discography when MusicBrainz is slow (after `ARTIST_SLOW_FALLBACK_MS`) or doesn't know the artist. A plug-in declares `capabilities.artistReleases: true` and implements `getArtistReleases({ name, mbid?, limit? }, config)` → `{ artist: { name, mbid? }, releases: [{ id, title, date?, releaseType?, albumArt? }] }` with its own release ids, or `null` when it doesn't know the artist; a failure throws. The plug-in searches by name and picks the result whose name matches; `resolver-loader.js` dispatches `getArtistReleasesResolvers()` / `getArtistReleases(id, artist, config)` and drops releases without an id or title. The app (`fetchArtistFromPlugins` in app.js) asks the same plug-ins by the same rule, but one at a time (`askInTurn`; active plug-ins in the user's order, then the meta-services, which have no place in that order and come in the order they loaded: Discogs before Last.fm today), since this is a fallback and asking all of them on every slow page would spend their rate limits. It checks the returned name again (`isFallbackNameMatch`), takes the first answer with releases (the not-on-MusicBrainz path settles for an artist found with none), prefixes each id with the plug-in's id (`spotify-…`, as album-catalog.js's `resolverIdFromReleaseId` reads it, so opening one asks that plug-in's `lookupAlbum` first and the album page's Source dropdown works as for any album) and sorts newest first. The user's own files come last (`fetchArtistFromLocalLibrary`).

- **Spotify** (1.2.9): artist search, then `/v1/artists/{id}/albums` (albums and singles). Needs the sign-in.
- **Apple Music** (1.5.6): Apple's catalog through the host's MusicKit (the developer token, no sign-in), in the plug-in's storefront.
- **Last.fm** (1.2.10): `artist.gettopalbums`, most played first, with no dates or types.
- **Discogs** (1.1.0): artist search, then the artist's releases where they're the main artist, one per title. A personal access token (Advanced) raises the rate limit.

### Listening history (`getTopItems`, `getRecentListens`, optional)

A user's own listening stats (#1539 step 4). A plug-in declares `capabilities.listeningHistory: true` and implements both:

- `getTopItems({ user?, kind: 'tracks' | 'albums' | 'artists', period, limit? }, config)` → tracks `[{ title, artist, album?, plays, mbid?, albumArt? }]`, albums `[{ title, artist, plays, mbid?, albumArt? }]` or artists `[{ name, plays, mbid? }]`, most played first. `period` is `'week' | 'month' | 'quarter' | 'half_year' | 'year' | 'all'` (the History page's menu values, Last.fm's names because `parachord://` links carry them, map through `historyPeriodFor` in `src/renderer/lib/listening-history.js`).
- `getRecentListens({ user?, limit? }, config)` → `[{ title, artist, album?, albumArt?, playedAt (ms, null while playing), nowPlaying, mbid?, msid? }]`, newest first.

`user` defaults to the signed-in username (`config.username`), so the same methods answer for friends too (#1539 step 5). An optional third method, `getNowPlaying({ user }, config)` → `{ title, artist, album? }` or `null`, says what someone is playing right now (a friend's radio); the loader answers `null` for a plug-in without it. A failed request's error carries its HTTP `status` (the friend poll's backoff reads it), and a Last.fm profile that hides its recent listening (403, error 17) throws with `hidesListening: true`, which the friend UI shows as "Listening hidden" rather than as a failure. No user is `null`; the service's "no such user" is `[]`; a failure throws. A cover is sent only when the service matched it itself (ListenBrainz's, gated on `caa_id` as `lib/listenbrainz-cover.js` is; never Last.fm's grey star). `resolver-loader.js` dispatches `getListeningHistoryResolvers()` (the capability and both methods), `getTopItems(id, query, config)` and `getRecentListens(id, query, config)`, which drop unnamed rows and reject when the plug-in throws.

The app's sources (`historySourcesFor` in app.js) are the plug-ins with the capability that `similarProviders` gives (active or meta-services, minus one switched off, in the user's order) **and that you've signed in to**: a `username` in the plug-in's settings (`signedInSources`). Consumers:

- **The History page:** Recently Played merges every source (`mergeRecentListens`: newest first, one per song per five minutes). The Top Tracks, Top Albums and Top Artists tabs show one source, picked in a Source menu when you have more than one, else the first in your order (`historyTopSource`). Its line under the title, and its "Connect …" offer when none is set up, are built from the plug-ins.
- **The AI's listening context** (`fetchListeningContext`): every source's top items for four periods plus recent listens, merged.
- **The Fresh Drops and Concerts seeds**: every source's top artists (a year, half a year), merged (`mergeArtistNames`).
- **Friends** (#1539 step 5): a friend's listening comes from their own service's plug-in (`friend.service` is its id) through `askFriend` in app.js, with `user` set to their username: the friend poll (`fetchFriendRecentTrack`, one recent listen), their weekly stats for the AI (`fetchFriendWeeklyStats`), their page's Recent, Top Tracks, Top Albums and Top Artists tabs, and the radio's "playing now" (`getNowPlaying`). A plug-in that isn't loaded is a failure there (the tab says it couldn't reach the service), never an empty list.

- **Last.fm** (1.2.12; `getNowPlaying`, error statuses and hidden profiles 1.2.13): `user.gettoptracks`, `user.gettopalbums`, `user.gettopartists` (periods `7day` … `overall`) and `user.getrecenttracks`. Needs the API key.
- **ListenBrainz** (1.6.10; `getNowPlaying` and error statuses 1.6.11): `/1/stats/user/<user>/{recordings,releases,artists}` (ranges `week`, `month`, `quarter`, `half_yearly`, `year`, `all_time`: the last full one of each) and `/1/user/<user>/listens` (and `/playing-now`); the user's token goes along when there is one.

### Friends (`findUser`, `getFollowing`, `follow`, `unfollow`, optional)

The friend list and Add Friend (#1539 step 5). A plug-in declares `capabilities.friends: true` and implements:

- `findUser({ query }, config)` → `{ username, displayName?, avatarUrl? }` or `null`. `query` is a username or the service's own profile link; another service's link is `null` without a request, which is how the app finds whose link it is. No such person is `null`; a failure throws.
- `getFollowing({ user? }, config)` → `[{ username, displayName?, avatarUrl? }]`: who the user (by default the signed-in one, `config.username`) follows, every page. No user is `null`; a failure throws.
- `follow({ user }, config)` / `unfollow({ user }, config)`, optional → `true` when done, `false` when it can't from here (no sign-in token). A plug-in without them is pull-only: the app keeps a removal there with `hidden_friend_keys` (docs/architecture/friends.md).

`resolver-loader.js` dispatches `getFriendsResolvers()` (the capability, `findUser` and `getFollowing`), `findUser`, `getFollowing` and `setFollowing(id, 'follow' | 'unfollow', query, config)` (`null` without the method). In app.js the friend services are `friendProvidersFor()` (`similarProviders`: active or meta-services, minus one switched off, in your order) and the ones you're signed in to, `friendAccountsFor()` (a `username`). The sync pulls `getFollowing` from each account; Add Friend asks the services you're signed in to first, then the rest, one at a time (`askInTurn`), and adds the first who finds the person; `addFriendCore` refuses a service that isn't a friend service; follow and unfollow go to the friend's own plug-in. A friend's listening comes from the same plug-in's `listeningHistory` methods (see "Listening history").

- **Last.fm** (1.2.15): `findUser` (`user.getinfo`, `last.fm/user/<name>` links) and `getFollowing` (`user.getfriends`, 200 a page, at most 50 pages). No follow or unfollow: `user.addFriend` and `removeFriend` were deprecated in 2018.
- **ListenBrainz** (1.6.12): `findUser` (its listen count says the user exists, since `/1/user/<name>` doesn't answer; `listenbrainz.org/user/<name>` links; no avatars), `getFollowing` (`/1/user/<user>/following`), `follow` and `unfollow` (`POST` / `DELETE /1/user/<user>/follow` with the user's token; an unfollow's 404 counts as done).

### Charts (`getCharts`, optional)

Pop of the Tops' charts (#1539 step 3). A plug-in declares `capabilities.charts: true`, says what it charts in a **top-level** `charts` field of its manifest (outside `capabilities`, whose values every client reads as booleans): `{ period?, tracks?, albums? }`, each kind `{ global?: true, countries?: ['us', ...] }` (lowercase ISO codes), and `period` a few words for the page's line ("this week"). The loader keeps it, cleaned, as `resolver.charts` (`ResolverLoader.chartsInfo`; a kind with neither global nor a country is dropped). It implements `getCharts({ kind: 'tracks' | 'albums', country, countryName, limit }, config)` → `[{ title, artist, album?, albumArt?, url?, genres?, releaseDate?, listens?, listeners?, mbid? }]`, most played first. `country` is null for Global; `countryName` is the country's English name (from `CHARTS_COUNTRIES`, for services that take names). A kind or region it doesn't chart is `null`; a failure throws. An album's `mbid` is its release group's, and opens the album page without a search. `resolver-loader.js` dispatches `getChartResolvers()` (the capability, `charts` and the method) and `getCharts(id, query, config)`, which drops items without a title or artist and rejects when the plug-in throws.

The app (`src/renderer/lib/charts.js`, `loadChartFor` in app.js) offers **every installed plug-in** with the capability, turned on for playing or not (a chart needs no account, and Apple Music is off in a new install), minus one switched off (Enable, or "Use metadata from"), in the user's order with active plug-ins first. Each tab's Source and Region menus come from that list (`chartSources`). The picked source is the only one asked; with no pick, the sources are tried in order until one has a chart. Cached 24 hours per kind, source and region.

- **Apple Music** (1.5.7): the most-played feeds, albums and tracks, by country; 5 s per try and one retry.
- **Last.fm** (1.2.11): tracks, Global (`chart.gettoptracks`) or by country (`geo.gettoptracks`).
- **ListenBrainz** (1.6.9): sitewide statistics for the week, tracks and albums, Global; the user's token goes along when there is one (ListenBrainz turns some anonymous requests away), and each request gives up after 10 s.

### Artist bios (`getArtistBio`, optional)

The artist page's Biography tab, the playbar's bio tooltip and Search's artist preview (#1539 step 6). A plug-in that writes an artist's biography declares `capabilities.biography: true` and implements `getArtistBio({ name, mbid? }, config)` → `{ text, summary?, url?, markup? }`, or `null` when it has no bio for the artist (no MBID for Wikipedia, the service's "not found", an empty or stub bio); a failed or refused request THROWS. `text` is plain text with paragraphs separated by blank lines; `summary` a short version for previews; `url` the source's own page (kept only when https); `markup: 'bbcode'` says `text` carries `[b]`, `[i]`, `[u]` and `[url=…]` tags, which the tab renders (`src/renderer/lib/bio-markup.js`) and the previews drop. `resolver-loader.js` dispatches `getBiographyResolvers()` / `getArtistBio(id, artist, config)` and keeps only those fields.

The app asks every plug-in with the capability at once, by the same rule as similar artists (`similarProviders(loader, 'biography', …)`: active plug-ins and meta-services in the user's order, minus one switched off), and keeps every bio found (`bioWithSources`, `src/renderer/lib/artist-bio.js`). The bio shown is the source the user last picked, when it has one for the artist; else that of a plug-in whose manifest has a **top-level** `biography: { preferred: true }` (outside `capabilities`, like `charts`; the loader keeps it as `resolver.biography`; Wikipedia declares it); else the first in the user's order (`bioPreference`, `preferredBio`). The tab's Source picker (`SortMenu`, `variant: 'button'`) lists every bio and switches to one; the pick is saved (`artist_bio_source`) and applies to every artist after, including bios already cached. With one source the line names it. The whole answer is cached for the session by artist name and MBID (`artistBioCache`); none found is never cached.

- **Wikipedia** (1.1.1, the preferred source): the artist's Wikidata id (Wikidata's own P434 search, MusicBrainz url-rels as the fallback in the background lane; kept on the instance), its English article, trimmed to the lead and the prose sections (`this.lib.bioFromExtract`). Needs the MBID; no account.
- **Discogs** (1.2.0): artist search, the same-named result, its profile with references resolved to names (`markup: 'bbcode'`). A personal access token (Advanced) raises the rate limit.
- **Last.fm** (1.2.14): `artist.getinfo`, by name, without the "Read more on Last.fm" link and licence line (the app's old check for that phrase dropped every Last.fm bio). Needs the API key.

### Implementation functions

Each entry in `implementation` is materialized with `new Function('return ' + src)()` in the renderer, then bound so `this` is the resolver object (a `resolve` can call `this.search(...)`). Consequences:

- **Plugins are not sandboxed.** The code runs in the renderer with the same privileges as the app's own renderer code: `fetch`, `window` (including `window.electron.*` bridges such as `proxyFetch`), the DOM, and globals the app sets up. Install only plugins you trust. Being able to reach those isn't permission to: a plugin reaches the host only through `this.host` ("The plug-in host contract" above), and tests hold shipped plugins to it.
- **Each function is isolated from the others — except through the plugin library.** There is no shared module scope, so a helper two functions need lives in `implementation._lib` (below) or is defined inside each.
- Implementation keys that collide with resolver fields (`id`, `name`, `capabilities`, `config`, `__proto__` and similar) are skipped with a warning; `lib` and `_lib` are reserved (the library and its factory). `_lib` is the **only** underscore-prefixed key with a meaning — nothing interprets `_init`, `_helpers` or any other underscore name, so nobody should invent one expecting the same treatment.

**`implementation._lib` — the plugin library (#1356).** An optional entry that is not a method: a factory function, materialized with the same `new Function('return ' + src)()` as every entry and then **invoked exactly once per resolver instance**, whose return value every implementation function sees as `this.lib`. It is the one shared scope a plugin gets: helpers live in it once instead of copy-pasted into each function (the confidence gate is duplicated across four shipped plugins today). The whole-module format (`implementationModule` — one module source string, real lexical scope) is the intended end state; `_lib` is written so that migration is mechanical.

- **The library is pure: helpers and constants only.** The factory returns functions and immutable values — no I/O, no timers, no `window`/`globalThis` access, no mutable state — and the loader enforces it: the returned library is **frozen** (`Object.freeze`), so an assignment to `this.lib.x` does not stick (silently, in sloppy mode). It takes its inputs (config, a host bridge) as arguments, so the same helpers run on every host. It runs at load, takes no arguments, must return an object, and can close over nothing but itself (a serialized function loses its closure — `build-axes` materializes every entry in a clean scope and calls `_lib` once, so a factory that reaches for module scope fails the **build**, not a user's machine).
- **State lives on `this`, not on the library.** Per-instance state (a request-template cache, a breaker) goes on the resolver instance — `_bindContext` already shares it across every method. Nothing is shared across two loaded instances of the same plugin: the app builds a resolver instance per load, so a marketplace hot reload or a plugin loaded in more than one list gets a **fresh instance and a fresh library**. State that must outlive a reload or span instances belongs host-side.
- **A library that fails fails the plugin.** If `_lib` is malformed, throws, or returns a non-object, the load fails with that error — the same treatment as a malformed manifest, never a null `this.lib` plugin that looks enabled and throws on every call. (The loader evaluates the factory for every instance, including disabled plugins and hot reloads — another reason it must be pure.)
- **Old apps get a readable error, not a TypeError.** An app whose loader predates `_lib` materializes the entry as an inert method — and then every `this.lib.x` call throws `TypeError: Cannot read properties of null`. A plugin that adopts `_lib` therefore declares `manifest.minAppVersion` on **every platform**, set to the first release whose loader has it. Apps from before floors existed (desktop 0.9.11 and earlier, Android 0.9.9 and earlier) ignore floors, so until those are rare each library-using method opens with a guard; ship the guard ONCE as a `requireLib` implementation entry (a normal entry — old loaders materialize it like any method, which is exactly why the guard cannot be loader-side) and open every library-using method with `const lib = this.requireLib();`:

```js
// implementation.js — one entry, works on every app version
requireLib: function () {
  if (!this.lib) {
    throw new Error('Amazon Music needs a newer Parachord — please update the app.');
  }
  return this.lib;
},
search: async function (query, config) {
  const lib = this.requireLib();
  // ...
}
```

Common signatures, taken from the shipped plugins: `search(query, config)` returns an array of tracks; `resolve(artist, track, album, config)` returns one track or `null`; `play(track, config)` returns a truthy value on success (falsy makes `handlePlay` try the next source). When the host wants the track to start mid-way (a restored queue's resume), the track carries `_startAt` (seconds). A plugin that can start there does, and sets `track._startedAt = track._startAt` on the same object once playback started there. One that doesn't starts at 0:00 and the host seeks; see "A restored queue resumes where it was" in [playback.md](playback.md). Spotify and Apple Music do this. `init(config)` and `cleanup()` run on load and unload. A track carries `id`, `title`, `artist`, `album`, `duration` (seconds, or `null` when the service gives none, never a made-up placeholder: track lists show a source's length as the track's; see "Resolver Result Shape" in [playback.md](playback.md)), `sources: ['<resolverId>']`, the resolver's own identifier (`spotifyId`, `bandcampUrl`, `youtubeId`, `soundcloudId`, `appleMusicId`, ...) and any cross-cutting metadata such as `isrc` (see "Resolver Result Shape" in [playback.md](playback.md)). Meta-services implement the functions their capability names: `generate(prompt, config, listeningContext)`, `chat(messages, tools, config)`, `listModels(config)`, `searchArtistEvents(artistName, config)` and `searchArtist(artistName, config)`.

**A `resolve` that filters its own results must accept what the platform's gate accepts.** `resolve` returns one track, so a result it drops never reaches `validateResolvedTrack` (`sync-providers/confidence-scoring.js`). Subsonic and Amazon Music carry a copy of the gate's artist and title rules, because a function here can't import it, and `tests/resolver/plugin-credit-match.test.js` runs both through `ARTIST_CREDIT_VECTORS`; a new filtering plugin joins that test. The gate can't do this job itself: given only the top hit it would drop a wrong artist and lose the right one ranked below it. Also check the query: Navidrome requires every word of a search, so Subsonic leaves join words and title credits out of it ("A and B" would miss a library tagged "A & B"). That means a track tagged with only some of the requested names still misses on the server ("A feat. B" with a library that credits just "A"), though the gate would accept it. And punctuation decides the match on Navidrome's CJK path: a query with CJK in it is matched word-for-word as written (a literal substring of the title/album/artist text — its non-CJK FTS path strips punctuation on both sides instead), so the same title tagged `ぶっ生き返す!!` and `ぶっ生き返す！！` (half-width and full-width exclamation marks, MusicBrainz vs the user's tags) is no match either way. Subsonic asks with the query as written first and, when a CJK query finds nothing, asks again with the query's letter/number runs (`search` and `searchAlbums`; every run is a substring of the spelling as given, so an exactly-punctuated library was already found by the first ask); non-CJK queries always go as written, because the server handles punctuation there.

**A `resolve` that falls back to a top result must still prefer what the gate accepts.** Bandcamp and Apple Music return a result the gate may refuse rather than `null`, so they can't lose a track by filtering it out, and the equivalence above doesn't hold for them. They lose it by choosing: a wrong artist ranked above the right one is all the gate sees. They carry the same copy of the rules, and `tests/resolver/plugin-credit-preference.test.js` puts a refused result above each accepted row of `ARTIST_CREDIT_VECTORS`. The gate's rule is wider than a request, since it also accepts a shorter title ("Stay" for "Stay With Me") and one name of a credit, so each tries the closer match first: Bandcamp an exact title under the same credit, Apple Music a result that holds the whole request. Apple Music's album search stops early only on that closer match, or a shorter title on the album would end the resolve before its artist + title search could find the requested one.

Practical rules: return `[]` or `null` instead of throwing on a miss; check a service's minimum query length before calling it; respect the service's rate limits (content resolvers other than Apple Music, Spotify and local files are wrapped by the shared resolver limiter automatically); and log enough to debug a failure.

**A miss is empty; a failure throws.** An empty `search` answer or a `null` from `resolve` means "this service doesn't have it", and the app caches that as a `noMatch` for that track (7 days in the track cache, `CACHE_TTL.trackSources`, and 30 days once saved with a playlist or the collection, `CACHE_TTL.persistedSources`). So when the service refused the request (401/403/429), failed (5xx), timed out or the network dropped, throw instead: `resolveTrack` stores nothing for a resolver that threw and asks it again on the next resolution. Never wrap a whole function in a `try` whose `catch` returns `[]`; Apple Music's did, and an iTunes throttle was being recorded as tracks missing from Apple Music (2026-11, parachord#1335). A readiness failure (signed out, no token, the account's plan) is a throw with `err.notReady = true` and a `code`, which callers treat as "ask again later" without a sign-in prompt.

**`resolve` has 8 seconds.** `wrapResolverSearchesWithLimiter` (`resolver-limiter.js`) wraps every resolver's `resolve`, including the ones the search limiter skips, in `RESOLVE_BUDGET_MS` (8000). Past it the call rejects with `ResolverTimeoutError`, the track moves on with what the other services found, and (it's a failure, not an answer) the resolver is asked again later. A resolve that makes several requests should keep them sequential and few; one that can take longer than the budget will keep timing out.

**Pass `config` through to `this.search`.** The caller picks the queue lane (`config.__lane`: `'priority'` for a play click, `'background'` for a cover lookup; see "Resolver queue lanes" in [playback.md](playback.md)), and the limiter reads it from the config `search` is called with. A `resolve` that calls `this.search(query, config)` with the config it was given keeps the caller's lane; one that builds a fresh object drops a play click to the back of the queue.

### Plans that can't play on demand (`plan-ineligible`)

Many services have a tier that can search, browse and sync but can't play a chosen track on demand: Amazon Prime (vs Music Unlimited) is the one Parachord handles today. (Spotify Free would be another, but a Free account can't run the Development Mode app a Parachord Spotify sign-in uses; see playback.md.) Parachord keeps such a resolver enabled for what it still does (search, album search, artist photos, links, playlist sync) and leaves it out of playback: no source icons, no priority number in Settings (it sits after the numbered resolvers), never picked as a source, and the tile and settings panel say why. How the app decides is "Playback limits" in [playback.md](playback.md); what a plugin does:

- **Refuse a play with the plan, not a plain failure.** When the service says the account's plan can't play the track (a refusal the service gives for the plan specifically, not any 403), `play()` throws an error with `reason: 'plan-ineligible'` and, if it knows it, `planKey` (the plan as the service names it, e.g. `'free'`), instead of returning `false`. The app records the plan, plays another enabled source if the track has one (or shows the message), and stops offering this resolver for playback. A plain `false` looks like a missing device or a bad match.
- **Only where the app understands it.** Check for `window.__parachordNotePlanRefusal` first and fall back to returning `false` without it (older apps and the mobile clients), and declare `manifest.minAppVersion.desktop` as the first desktop release with the hook (see "Minimum app version" above). The refusal shape has a reference since #1356 M9 — the plugin path's `getPlaybackManifest` throws `plan-ineligible` with `planKey` before any manifest request — but the `play()`-method hook check itself still waits for its first user.
- **A search that can't run on the plan is not-ready, not a miss.** If the service refuses searches on that plan too (Amazon gates its track search), surface it as `notReady` with `code: 'plan-ineligible'`, so nothing is cached as a 30-day `noMatch` and an upgrade searches again; the app never opens a sign-in prompt for it. A service whose search works on every plan needs nothing here.
- **The app supplies the wording and the plan reading.** A new service is one mapper in `src/renderer/lib/playback-limits.js` (`{ blocked, planKey, label, message, searchesHeldBack }`) fed from wherever the plan is known (the plugin's own `getStatus`, below, or the play refusal itself when the service doesn't report the plan until you play). Mobile mirrors none of this yet.

### Status and playback limits (`getStatus`, optional)

A plugin that knows its own sign-in and playback-limit state declares `capabilities.status: true` (a plain boolean; the mobile decoders read every `capabilities` value as one) and implements `getStatus(config)`, which the renderer calls directly through the resolver registry (`ResolverLoader.getStatusResolvers()` / `getStatus(resolverId, config)` — no IPC). One reply feeds every consumer of a service's state: the playback limit map (`pluginStatusLimit`/`pluginStatusLimits` in `src/renderer/lib/playback-limits.js`, below), the resolver tile's label and tooltip (`tileStatus`), the Settings sign-in row (`pluginStatusRow` — the generic row the #1356 plan calls "Status text for settings | A generic Sign in / Sign out row") and, when the plugin also implements `signIn()`/`signOut()` (the web-session surface), that row's Sign in / Sign out buttons. Amazon Music is the first (and so far only) plugin on the surface (#1356 M10): its reply carries the Amazon plan, the tile labels ('Prime: no playback' / 'Plan not confirmed'), the 'Setup required' wording and an extra `cdm` field (the build's Widevine verdict) that the renderer's sign-in prompt gate reads — a reply may carry service facts beyond the shape below as long as it stays credential-free.

The reply:

```
{
  signedIn: boolean | null,    // null: the plugin can't tell yet; without a statusLabel the Settings row reads 'Checking…' even after the read finished
  playbackLimit: {             // null: no verdict (the account can play, or nothing is known)
    blocked: boolean,          // required — the account's plan can't play here
    planKey: string | null,    // the plan as the service names it ('prime', 'free', ...), for logs
    label: string | null,      // a short tile label ('Free: no playback'); tileStatus falls back to 'No playback'
    message: string | null,    // the full sentence for the tile tooltip, the Settings row and the play refusal
    searchesHeldBack: boolean // the service's searches answer not-ready while blocked (Amazon), so an upgrade re-searches
  } | null,
  statusLabel: string | null,    // the Settings sign-in row's primary line; null → signedIn's wording ('Signed in' / 'Not signed in')
  statusMessage: string | null  // the Settings sign-in row's second line
}
```

- **A status outage never unplugs playback.** A `getStatus` that throws, answers nothing object-shaped, or runs past the read budget (8 seconds — `ResolverLoader.STATUS_BUDGET_MS`, in the spirit of `RESOLVE_BUDGET_MS`; the app reads every status plugin in one batch, so one hung `getStatus` must not stall the sweep) is logged by the loader and answered with its failed-read marker (`STATUS_READ_FAILED`); a reply without a `playbackLimit`, or one that isn't shaped like an entry, is no verdict (`pluginStatusLimit` returns null). This is the one accessor that swallows a plugin error on purpose — every other accessor rejects so a caller can tell a miss from a failure, but "unknown" is the safe reading for every status consumer, and a blocked resolver is never guessed from a failure. The one place that tells a miss from a failure is the Settings sign-in row: a failed read says it couldn't check and to open the panel again, instead of "Checking…" forever.
- **The plugin is the authority — when it actually gives a verdict.** A plugin's entry wins over a per-service mapper for the same resolver id (the migration order: a service's plugin entry takes over the moment it starts declaring the capability), but only when its reply carries a verdict: a no-verdict entry is dropped before it reaches the limit map (`pluginStatusLimits`), so it never overrides the host's own verdict for that service — a service with both keeps the mapper's block while the plugin's read is down. A plugin moving its plan gate into `getStatus` needs `manifest.minAppVersion.desktop` set to the version that ships this capability: an older app ignores the capability, so the gate silently disappears there.
- **A play refused as not signed in prompts for that plug-in** (#1523). When the shared Widevine path's play fails with `reason: 'not-signed-in'`, the engine calls `window.__parachordPromptPluginSignIn(resolverId, opts)` (app.js `promptPluginSignIn`) and retries once if it signs in. It prompts only a plug-in on this surface (`capabilities.status`) with a `signIn()` method, so one plug-in's refusal never opens another's sign-in. A plug-in whose sign-in has host UX of its own runs that flow (Amazon's consent dialog, hiccup rule and CDM gate, `manageAmazonMusic`); any other runs its own `signIn()` and the status is read again. The engine names no service.
- **Keep credentials out of the reply** — the whole reply reaches page state; say `signedIn: true`, never the session itself.
- **When it is read.** At startup, when Settings opens, when the resolver's detail panel opens, and after a play refused for the plan (`refreshPluginStatus`/`refreshPluginStatuses` in app.js — the same trigger set as the old Amazon status); an uninstall drops the plugin's entry, and a reinstall reads fresh. A plugin has no push channel: a plan change shows at the next read (Amazon's own reply re-reads the plan fresh every time, so Settings opening is the worst case). Keep a `getStatus` cheap: it runs on the settings path, and answer within the 8-second budget — past it the read counts as failed.

Tests: `tests/resolver/plugin-status-capability.test.js` (the loader gate, the no-throw contract and the read budget, the reply feeding the limit map and the tile), `tests/renderer/playback-limits.test.js` (the mappers, the plugin-entry drop).

### Where plugins load from, and installing one

At startup the main process (`resolvers-load-builtin`) reads the app's own `plugins/` directory (inside the ASAR in a packaged build) and `~/.parachord/plugins/` (marketplace downloads and user installs), keeping the newer version of each id and preferring the shipped copy on a tie. The renderer also carries a `FALLBACK_RESOLVERS` copy of every bundled plugin (the generated `src/renderer/lib/fallback-resolvers.generated.js` module, required by `src/renderer/app.js` and bundled into it) for when that load fails or misses one. The "Add from file" button in Settings → Plug-Ins installs an `.axe` from a file (`resolvers-pick-file` then `resolvers-install`, which writes it into `~/.parachord/plugins/`) and hot-loads it without a restart; the marketplace installs and updates plugins the same way. To contribute a plugin to everyone, add it to [Parachord/parachord-plugins](https://github.com/Parachord/parachord-plugins).
