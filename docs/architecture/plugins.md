## Plugin (`.axe`) Marketplace System

### Extensibility principle — abstract over the plugin registry, don't hardwire services

Any feature shaped like "given a provider URL or entity, do X" MUST route through the resolver-loader capability surface, never a hardcoded service switch. The surface (`resolver-loader.js`):

- `findResolverForUrl(url)` → which resolver owns this URL (matches each `.axe`'s `urlPatterns`)
- `getUrlType(url)` → `'track' | 'album' | 'playlist' | 'artist' | 'unknown'`
- `lookupUrl(url)` / `lookupAlbum(url)` / `lookupPlaylist(url)` → entity → tracks, dispatched to the owning resolver's capability
- `resolve` / `search` on `loadedResolversRef` for playback + search
- `listModels(config)` for AI `dynamic-select` plugins

The payoff: whichever `.axe` declares matching `urlPatterns` + the capability handles it, so **adding a new streaming service is a plugin drop-in with zero feature code.** The anti-pattern is hardcoding the dispatch:

```js
// WRONG — every new service needs a feature-code edit, and the .axe registry is bypassed:
switch (host) { case 'open.spotify.com': return spotifyImport(url); case 'music.apple.com': ... }

// RIGHT — the registry decides; a new service is just another .axe with urlPatterns + lookupPlaylist:
const id = resolverLoaderRef.current.findResolverForUrl(url);
if (id && resolverLoaderRef.current.getUrlType(url) === 'playlist') {
  const { playlist } = await resolverLoaderRef.current.lookupPlaylist(url, await getResolverConfig(id));
}
```

**Worked example — `resolveProviderPlaylistUrl` for `parachord://play/playlist?url=` (parachord#930/#932).** The provider-page branch routes entirely through `findResolverForUrl` + `getUrlType` + `lookupPlaylist`, so Spotify / Apple Music / SoundCloud / any future resolver are handled without naming them. The two `host ===` checks in the pure helper `classifyPlaylistUrl` (protocol-url.js) are **justified pre-processing, not service hardwiring** — keep them, don't "fix" them into the switch anti-pattern:

- **`achordion.xyz`** isn't a streaming resolver; it's a first-party playlist *host* whose `/api/playlist/<mbid>/xspf` returns a tracklist *document*. It feeds the generic `parseProtocolTracklist` path (the document fallback), not a resolver. No `.axe` owns it by design.
- **`on.soundcloud.com`** is a short link the capability surface *can't* classify (no `/sets/` segment for `getUrlType`). It's a redirect-resolve step that produces a canonical `soundcloud.com/.../sets/...` URL which is then handed back to `findResolverForUrl` — it feeds the surface, it doesn't replace it.

**Reusable mechanics when extending this:**

- **Native fast-paths are an optimization, not the gate.** `resolveProtocolPlayInput` has direct `spotify.lookupAlbum` / `window.appleMusicLookupAlbum` arms for cached IDs, but the general path still goes through the loader. Don't let a fast-path become the only path.
- **Audit the capability before assuming it exists.** `lookupPlaylist` is not universal — `resolver-loader.js` returns `null` (and logs "does not support playlist lookup") for resolvers that don't implement it, and some `.axe` lacked it until added (SoundCloud needed `lookupPlaylist` + OAuth before it could resolve a set). A new consumer must handle the `null`, not assume tracks.
- **Cross-platform parity.** This mirrors the mobile principle (`ProviderPlaylistResolver`, the two `lookupPlaylist` polls, `parachord-plugins/<service>.axe`). The mobile note also documents a JS-bridge quirk (a bare async IIFE reaching an `.axe` serializes to `[object Promise]` on iOS / `{}` on Android, so reaching the plugin needs the unique-key poll on both runtimes) — that's a mobile-runtime concern; desktop calls the loader methods directly in-process and isn't affected, but the *registry-abstraction* contract is identical on both sides.

### HTML5 stream resolvers (drop-in contract)

Subsonic used to be named in ten transport lists, a config gate and a bespoke `getResolverConfig` branch; the renderer now reads two things from the `.axe` instead, and a new self-hosted resolver that plays a direct stream URL adds **no** app.js code (`tests/resolver/html5-stream-capability.test.js` pins this):

- **`capabilities.html5Stream: true` + `getStreamUrl(track, config)`**: the host plays the returned `http(s)` URL through the shared HTML5 element. `isHtml5StreamResolver(id)` / `usesSharedAudio(id)` (app.js, next to `loadedResolversRef`) replace every `=== 'subsonic'` style check: the play branch of `handlePlay`, play/pause, seek, volume, the wall-clock progress-tracker skip, and the element's error dialog, which is labelled with the manifest `name`. The play branch tags the track it hands the element with `_streamOwner`, because every such resolver loads an `http(s)` URL and the element's `src` alone can't say whose it is. Build the URL from the **saved config**, never from fields stored on the track (tracks persist into the queue and playlists).
- **`capabilities.widevine: true`**: the host plays the track's DRM-protected adaptive stream through the shared Widevine player (Shaka on the same shared HTML5 element; `src/renderer/lib/widevine-player.js`). The resolver's audio role is host-owned: `play()` returns false like `html5Stream`'s, and `cleanup()` stops the shared engine via `window.__parachordWidevine.stop()`. Per-resolver playback code shrinks to TWO main-side operations registered on the widevine bridge (`main-process/widevine-bridge.js`): `getManifest(entity) → { manifest: <DASH MPD text>, ... }` and `relayLicense(challengeB64) → <license bytes, base64>` — session cookies, CSRF and provider endpoints never reach the renderer (Amazon's provider is `amazon-dmls.js`). Variant selection is NOT per-resolver either: the global Settings → General → Playback Quality tiers (store keys `playback_quality`, `playback_abr`, codec-family-scoped ABR so smooth switching never crosses opus↔FLAC) drive `shakaPlaybackConfig` in `src/renderer/lib/widevine-quality.js`. Stream-quality records come from Shaka's ACTIVE variant on load and every `adaptation` event; lifecycle telemetry is provider-owned behind the `widevine:player-event` bridge channel (`handlePlayerEvent` — Amazon maps it to hornet's `trackStreamed`/`streamingTerminated` reports in `main-process/amazon-telemetry.js`).
- **`isConfigured(config)`**: the Plugins page asks this before flagging an enabled resolver's card as needing configuration. Without it the card never warns.
- **Config**: `getResolverConfig` hands any plugin it has no branch for its saved `meta_service_configs[id]` entry, read through `metaServiceConfigsRef` so search and play see the latest save. The userpass settings panel saves Subsonic's server URL, username and password there.

### Architecture
- Plugins are `.axe` files (JSON) in `plugins/` (`/plugins/*.axe` is gitignored — generated artifacts live there, see the next bullet), each with a `manifest` (id, version, etc.) and `implementation`
- **`plugins/*.axe` are GENERATED, UNTRACKED artifacts** (untracked since parachord#1107). The source of truth is `plugins-src/<id>/` — `manifest.json` (the .axe minus its implementation) + `implementation.js` (a real module: `module.exports = { search: fn, ... }`). `scripts/build-axes.js` regenerates the `.axe`, the `src/renderer/lib/fallback-resolvers.generated.js` module (also gitignored since bucket C — the `FALLBACK_RESOLVERS` array required by `src/renderer/app.js`), and the `marketplace-manifest.json` entry version from that source. **Never hand-edit `.axe` files or the fallback module** — edit `plugins-src/`, bump `manifest.version` there; regeneration runs in the `pretest`/`prestart`/`predev`/`prebuild*` hooks (build-axes FIRST, then build-renderer), and a manual `node scripts/build-axes.js` works too. **The writer still owns one output that STAYS tracked**: the entry versions in `marketplace-manifest.json` — a PR that changes a plugin's source must commit that sync. The guards on it (replacing the retired `tests/plugins/axes-drift.test.js`):
  - **The committed-state drift gate** — `.github/workflows/test.yml` runs `git diff --exit-code -- marketplace-manifest.json` after `npm test`'s pretest writer. A check that runs after a hook ran the writer cannot fail on on-disk artifacts (the writer has already regenerated them), so the gate compares committed tracked outputs instead. (Found in review on parachord#1107; the FALLBACK half of its remit moved to bucket C's whole-file byte-compare inside `build-axes --check`.)
  - **`build-axes.js` runs before `build-renderer.js` in every hook** — otherwise the bundle is built from a source tree whose fallback module the writer has not regenerated yet, and a one-shot CI `prebuild` ships a stale array. (The old form mentioned an inline `src/renderer/app.js` block — the generated-module shape moves the same ordering rule.)
  - **The PR-only version-bump gate** (`scripts/check-plugin-version-bumps.js`, same workflow) — any PR that touches `plugins-src/<id>/` must change its `manifest.version` (the nested `.manifest.version` path; plugins-src manifests are the `.axe` shell minus `implementation`), or marketplace clients never re-download. This is the enforced form of build-axes' local content-vs-disk warning, which went silent when the artifacts were untracked. New plugins and deletions are exempt. Local-run caveat: with its default `origin/main` base the diff compares against main's tip, so a branch behind main can false-positive — fetch/rebase first (CI can't hit this: HEAD is the merge commit).
- **Marketplace source**: Raw GitHub files from `Parachord/parachord-plugins` repo
- **Manifest**: `marketplace-manifest.json` in this repo — the central catalog of all plugins with version numbers (entry `version` and `minAppVersion` are generator-synced; category/tags/downloadUrl/capabilities in the entry are editorial, hand-maintained)
- **Client sync**: `main.js` fetches manifest + `.axe` files from `https://raw.githubusercontent.com/Parachord/parachord-plugins/main/`

### Plugin Loading Order (main.js `resolvers-load-builtin`)
1. Shipped plugins from app `plugins/` directory (bundled in ASAR for packaged builds)
2. Cached marketplace plugins from `~/.parachord/plugins/`
3. Version comparison: newer version always wins; same version prefers shipped over cached
4. A cached copy whose `minAppVersion.desktop` is above this app's version is skipped (see "Minimum app version" below), so the shipped copy stays in use. The shipped copy is never checked: it was built with this app.

### Minimum app version
The marketplace serves only the latest copy of each plugin, and every installed app downloads it, so a plugin that needs a host feature an older app lacks (a new IPC surface, a native player) would otherwise reach that app and break there. A plugin can declare the oldest app it runs on, per platform, in its manifest:

```json
"minAppVersion": { "desktop": "0.9.12", "android": "1.4.0", "ios": "1.0.0" }
```

- **Per platform, because desktop and mobile version separately** and gain host features at different times. A platform with no entry, or a plugin with no field, has no floor. Values are plain `x.y.z`; an app's pre-release suffix is ignored, so `0.9.12-beta.1` meets a `0.9.12` floor.
- **An app below the floor keeps the copy it has.** Marketplace sync (`plugins-sync-marketplace`) checks the catalog entry before downloading and the downloaded `.axe` before saving, and reports the plugin under `skipped`. The loader skips a cached copy below the floor. Installing from Settings or from a file refuses with "needs Parachord X or later".
- **Rules live in `main-process/plugin-compat.js`** (`pluginCompatibility(manifest, appVersion, platform)`, `validateMinAppVersion`). The Android and iOS clients mirror them; keep the two in step.
- **`build-axes.js` validates the field and copies it to the marketplace entry**, so a client can skip a download without fetching the `.axe`; `--check` fails on drift.
- **Apps released before the field existed ignore it** (v0.9.11 and earlier on desktop). Until most people have updated past that, a plugin that depends on a new host feature still has to detect the feature and fall back, not only declare the floor.
- **Set the floor to the first release that has the feature.** During development `package.json` still carries the previous release, so a dev build skips the marketplace copy and runs its own bundled one, which is the copy you're working on.

### How Updates Reach Users (No New Build Required)
1. **Edit `plugins-src/<id>/implementation.js`** (or `manifest.json`) — and bump `manifest.version` in `plugins-src/<id>/manifest.json`
2. **Regenerate** — any lifecycle hook does it (`pretest`/`prestart`/…, build-axes first), or `node scripts/build-axes.js` by hand: regenerates `plugins/<id>.axe`, the fallback-resolvers module, and syncs the `marketplace-manifest.json` entry version (warns if content changed without a version bump — and the CI version-bump gate FAILS the PR on it)
3. **Commit the regenerated tracked output** — `marketplace-manifest.json` (the only tracked writer output left), or the drift gate fails
4. **Push to main** — the `sync-repos.yml` CI workflow generates the `.axe` files from `plugins-src/` and syncs them plus the manifest to `Parachord/parachord-plugins`
5. **User relaunches Parachord** — `syncPluginsWithMarketplace()` (src/renderer/app.js) compares cached version against marketplace manifest version; if different, downloads the new `.axe` and fires `parachord-plugins-updated` event for hot-reload

### Critical: Both Files Must Be Updated
This footgun is now generator-owned: `node scripts/build-axes.js` writes the `.axe` version and the `marketplace-manifest.json` entry version from the same source manifest. The only manual rule that remains: bump `manifest.version` in `plugins-src/<id>/manifest.json` when the implementation changes — the writer warns on content churn on an unchanged version, and the PR-only CI version-bump gate fails the build on it.

### Absorbing a Reverse-Sync Community Edit (automatic)
`reverse-sync.yml` PRs already carry `plugins-src/` diffs, not `.axe` files: the workflow generates our artifacts from `plugins-src/` first, compares each remote `.axe` against them (adoption only on strictly-greater semver or an unknown plugin — never downgrades/sidegrades, the #754 guard; equal-version-different-bytes is kept-ours and annotated as a workflow warning), and runs `build-axes.js --import` for anything adopted before opening the PR. So a community edit arrives pre-absorbed — review the `plugins-src` diff, never the `.axe`. Two failure behaviors to know: a failed import git-restores both paths so a PR never half-adopts (the daily run retries), and `plugins-src/<id>/build.json` (the es5 flag, which the `.axe` doesn't carry) is stashed/restored across the import. The manifest merge appends community-only entries (synthesizing a minimal one if the remote manifest lacks the adopted plugin) and runs BEFORE the import/regen, because build-axes' write mode hard-requires a marketplace entry per plugins-src id. Manual one-file re-absorb is still: delete the plugin's `plugins-src/<id>/` dir, then `node scripts/build-axes.js --import --plugin <id>`.

### Engine-Portable (ES5) Plugins
Plugins the mobile runtime also evaluates (subsonic, bandcamp) must keep ES5-level implementation text. Flag them via `{ "es5": true }` in `plugins-src/<id>/build.json` — the writer transpiles through esbuild `--target=es5` before serializing (requires esbuild installed). Unflagged plugins may use modern syntax in `implementation.js`.

### Marketplace Sync CI (.github/workflows/sync-repos.yml)
- Triggered on push to main when `plugins-src/**` or `marketplace-manifest.json` change
- Generates `.axe` artifacts in CI (`npm ci && node scripts/build-axes.js` — full npm ci with `ELECTRON_SKIP_BINARY_DOWNLOAD=1`; NOT `--ignore-scripts`, esbuild's postinstall binary is required by the es5 transpile path) and copies them to the `parachord-plugins` repo (does NOT delete community-contributed plugins)
- Merges manifest: updates monorepo entries, preserves community-only entries

### Reverse Sync (.github/workflows/reverse-sync.yml)
- Daily at 6 AM UTC or manual dispatch
- Pulls adopted plugins from `parachord-plugins` into `plugins-src/` via PR (see the auto-absorb section above). **Token hygiene is load-bearing:** this job executes imported plugin code (the writer `require()`s each `plugins-src` implementation — string-form values are evaluated as expressions at require time), so its checkout is `persist-credentials: false` (the push authenticates inline in the same command) and the read-only plugins-repo clone's token URL is dropped from git config immediately after cloning. Keep those two lines deleted-on-purpose when editing the job.

### Dynamic Model Selection
- AI plugins (Ollama, ChatGPT, Gemini, Custom LLM) use `type: "dynamic-select"` in their model setting
- Each plugin implements a `listModels(config)` function that fetches available models from the provider's API
- **Ollama**: `GET {endpoint}/api/tags` — returns locally installed models
- **ChatGPT**: `GET /v1/models` with blocklist filter (excludes `dall-e`, `whisper`, `tts`, `text-embedding`, `babbage`, `davinci`, `canary`, `moderation`, `embedding`, plus `realtime`/`audio`/`transcri`)
- **Gemini**: `GET /v1beta/models?key=` filtered by `supportedGenerationMethods.includes('generateContent')`
- **Claude**: No list endpoint — stays curated with static `type: "select"`
- **Custom LLM** (`customllm.axe`, parachord#997): dialect-aware — `GET {baseUrl}/models` (openai) or `GET {baseUrl}/v1/models` (anthropic). Sets `allowCustom: true` on its dynamic-select, so the settings UI renders a free-text input + `<datalist>` instead of a select — typing an arbitrary model id must always work because not every endpoint implements the list route. Model suggestions refresh when the `baseUrl` or `api` fields change (the generic extra-field renderer in the AI config block refetches dynamic models for those field keys).
- App-side: `dynamicModelOptions` state tracks loading/options/error per resolver; `fetchDynamicModels()` called on settings panel open and after API key/endpoint changes
- `fallbackOptions` in the plugin manifest shown when fetch fails or no API key configured yet
- Refresh button (↻) next to model label for manual re-fetch
- The AI config block renders extra `settings.configurable` fields generically (select/text/number) beyond the auth key + model pair — `customllm` uses it for `api` (dialect select), `baseUrl`, `maxTokens`; older AI plugins declare only apiKey + model so they render nothing extra. For `requiresAuth: false` AI services the block also renders an explicit **Enable toggle** (these services are enabled *solely* by `config.enabled === true` — see `isServiceEnabled` — so the flag must be visible and flippable, same as Ollama's own block), the modal footer's Enable button tracks `enabled !== true` (a set `apiKey` does NOT count as enabled for them), and the apiKey onBlur preserves the toggle (`state.enabled === true || !!value` — deliberately NOT `??`: nullish coalescing doesn't fall through on `false`, so an early empty-key blur would poison `enabled: false` and a later key entry could never re-enable — that exact sequence shipped customllm with a configured-but-disabled service).

## Authoring a plugin (.axe format)

An `.axe` file is JSON with up to five top-level keys: `manifest`, `capabilities`, `urlPatterns`, `settings` and `implementation`. For a bundled plugin you never write that JSON by hand. You write `plugins-src/<id>/manifest.json` (everything except `implementation`) and `plugins-src/<id>/implementation.js` (`module.exports = { search: async function (query, config) { ... }, ... }`), then run `node scripts/build-axes.js`, which serializes each exported function with `String(fn)` into the `.axe`. Because the source is a real module, modern syntax including template literals is fine, except in plugins flagged `es5` (see above). A community plugin installed from a file is the same JSON, however it was produced.

### Manifest

`resolver-loader.js` (`createResolverInstance`) reads `id` and `name` (both required; the file installer rejects a file without them), `version` (semver; the loader and marketplace sync compare it), `minAppVersion` (optional, per platform; see "Minimum app version" above), `author`, `description`, `icon` (an emoji; defaults to 🎵), `color` (hex; defaults to `#888888`), `homepage` and `email`. `type` is either absent (or `"resolver"`), meaning a content resolver that plays or finds tracks, or `"meta-service"`, meaning everything else: AI providers, concert sources, metadata and recommendation services, scrobbling services and the Achordion telemetry plugin. A `manifest.id` may contain only letters, digits, dots, dashes and underscores.

### Capabilities

A flat object of booleans. Content resolvers use `resolve`, `search`, `stream`, `browse`, `urlLookup`, `purchase` (shows a Buy button in the playbar) `albumSearch` (finds an album by name for the album-page catalog fallback; see "Album search" below) and `artistImage` (finds a photo of an artist by name; see "Artist images" below). Meta-services use, among others, `generate` (one-shot AI playlist), `chat` (Shuffleupagus), `concerts`, `playbackTelemetry` (self-registers with `window.scrobbleManager`), `recommendations`, `metadata`, `artistImages`, `biography`, `listeningHistory` and `scrobbling`. Several of these gate loading: the renderer loads a meta-service's implementation only when it declares `generate`, `chat`, `concerts` or `playbackTelemetry` alongside the matching function, or `urlLookup` with `urlPatterns`. `mobile: false` (declared by Ollama) marks a plugin the mobile client should not offer. Check the existing `plugins-src/*/manifest.json` files before inventing a new flag; nothing reads an unknown one.

### URL patterns and lookups

`urlPatterns` is a top-level array of glob-like strings, for example `"open.spotify.com/playlist/*"`, `"*.bandcamp.com/album/*"` or `"spotify:track:*"`. The protocol and a trailing slash are ignored, a leading `*.` matches any subdomain, a middle `*` matches one path segment, a trailing `*` matches the rest of the path, and the query string is ignored unless the pattern itself contains `?` (`matchUrlPattern`). `findResolverForUrl(url)` returns the first resolver whose pattern matches.

`lookupUrl(url, config)` returns a track, `lookupAlbum(url, config)` returns `{ name, artist, albumArt, tracks, ... }`, and `lookupPlaylist(url, config)` returns `{ name, tracks, trackCount, ... }`. Each may return `null`, and callers must handle that. Note that `getUrlType(url)` (which decides whether a matched URL is a track, album, playlist or artist) is a per-host switch inside `resolver-loader.js`, not plugin data, so a new service's URLs come back `'unknown'` until that function gets an arm for its host.

### Album search (`searchAlbums`, optional)

A content resolver that can find an album by name declares `capabilities.albumSearch: true` and implements two functions:

- `searchAlbums(query, config)`. `query` is `{ artist, title }` from an album page, or a free-text string from Search. Returns `[{ id, name, artist, albumArt, releaseDate, trackCount, url }]` (any field but `name` and `url` may be `null`), or `[]` on a miss. Never throws for a miss, and returns `[]` without a request when it lacks the credentials it needs (Spotify without a token, Subsonic without a server).
- `lookupAlbum(url, config)`, which must accept every `url` its own `searchAlbums` returns. The host calls it on the resolver that found the album (`ResolverLoader.lookupAlbumFrom`), not through `findResolverForUrl`, so a `url` may be private to the plugin and match no `urlPatterns` (`subsonic:album:<id>`, `localfiles:album:<artist>/<album>`). It returns the usual `{ name, artist, albumArt, releaseDate, trackCount, tracks, url }`, where each track has at least `title`, plus `duration` (seconds), `trackNumber` and `discNumber` when known.

`tests/resolver/album-search-capability.test.js` fails a plugin that declares the capability without both functions. Keep credentials out of anything returned: results and their urls are held in page state, and a Subsonic token in a cover or stream url replays until the password changes.

**Who uses it.** Every album page gets its track list from MusicBrainz through `fetchReleaseData` (Fresh Drops, Charts, Critic's Picks, Home, Search, Collection, the artist page, the playbar, `parachord://album` links). When MusicBrainz fails or doesn't have the album, `loadAlbumFromCatalogs` (src/renderer/app.js; the pure part is `src/renderer/lib/album-catalog.js`) asks the albumSearch resolvers in order (the one a release id came from, then the user's active services in their priority order, then every other installed one), keeps the first result whose artist and title match (`pickCatalogAlbum`: edition suffixes aside, one artist of a joint credit is enough), and loads it with `lookupAlbum`. It also runs when MusicBrainz is merely slow: a page still waiting for its track list after `MB_SLOW_FALLBACK_MS` (5s; every MusicBrainz request waits its turn in the 1 req/s queue) shows the catalogs' list meanwhile, and `fetchReleaseData`'s success replaces it when MusicBrainz answers (its own load leaves a catalog list on screen alone until then, and a MusicBrainz failure leaves it standing). That effect keys on the album (`sameAlbumIdentity`: artist and title), not the id, since a page moves from a release-group id to a release id while it loads, and concurrent lookups for one album share a single request. A release with a service's id (`spotify-…`, `applemusic-…`, `lastfm-…`, `discogs-…`, from a Search result or an artist-page card built from that service) skips MusicBrainz: these used to be sent to MusicBrainz and never open. Search asks every active albumSearch resolver at the same time as MusicBrainz (and the inactive ones too when MusicBrainz returns fewer than three, including when it is down), and a result carries `_catalog: { resolverId, url }` so the click loads it without searching again. See "Search" below.

MusicBrainz stays first for albums that have a MusicBrainz id. Its track titles are the ones track ids (`trackSlug` of artist, title, album) and the resolution cache are keyed on, and its recording ids feed scrobbles and Achordion; a service's titles differ by edition ("Song (Remastered 2011)"). For the same reason the converted release (`catalogAlbumToRelease`) keeps the requested artist and album title, drops the plugin's track ids and sources (the usual resolution pass finds each track on the user's services), and is not written to the MusicBrainz caches. The page says where the list came from ("Track list from Bandcamp").

Implemented by Apple Music (Apple's catalog through the host's `window.appleMusicSearchAlbumsWithMusicKit` when MusicKit is configured, else the public iTunes catalog, so no account is needed; a miss on artist + title retries with the artist alone. iTunes album search lags the catalog badly: "Mount Zero" by Swapmeet was missing for over three months after release. The hook returns the catalog's albums, `[]` for a real miss, or `null` when MusicKit can't answer, which sends the plugin to iTunes. The mobile hosts supply the same hook over their own catalog bridge), Spotify (signed in), Bandcamp (its public search API, albums only; covers are built from `art_id` as `img/a<art_id>_10.jpg`, since the API's own `img` field lacks the `a` prefix album art lives under and 404s at every size), Local Files (the user's own library, `localFiles:searchAlbums` / `localFiles:getAlbumTracks`), Subsonic (`search3`, `getAlbum`) and Amazon Music (the capture-and-replay gql flows — the albums tab of the same `SpecSearchSeeMorePage` the track search uses, and the album page's `AlbumDetailPage`; see [amazon-music.md](amazon-music.md), "Album search and lookup").

### Search

The Search page (`performSearch` in src/renderer/app.js; the pure part is `src/renderer/lib/search-catalog.js`) runs two sides at once. MusicBrainz answers artists, albums and tracks with three requests in the 1 req/s queue, so they land one to several seconds apart. The user's services answer in a few hundred milliseconds: every active resolver that declares `search` (and can `play`) for tracks, and every active `albumSearch` resolver for albums, in the user's priority order, each bounded at 8s (`withCatalogTimeout`). There is no artist-search capability; Search lists the artists those track and album results name when the name matches the query. Each answer re-publishes its category, and the page shows each category as soon as it has rows: the skeleton stands in only until the first rows land (it used to cover the whole list until the last request finished, so Search showed nothing until MusicBrainz's tracks came back, five seconds and more), and a new query with nothing cached clears the previous query's rows. MusicBrainz rows are canonical: a service hit with the same artist and title (normalized; not the scorer's containment test, which would fold "Creep (Acoustic)" into "Creep") and the same album, edition suffixes aside, or no album on either side, adds its source to the MusicBrainz row, at the confidence the scorer gives it and only above `MIN_CONFIDENCE_THRESHOLD`. The album condition is there because MusicBrainz returns several recordings of a song: without it, the studio "Roads" every service found joined a live recording's row and the studio version never showed. The same track from two services is one row, the higher-priority service's, carrying both sources. A row only a service found has that hit as its own source at confidence 1, and a service row that repeats a local file's row is dropped. Every list is re-ranked by `reRankResults`: fuzzy relevance (tracks against "artist title", `TRACK_RANK_KEY`, so "portishead roads" finds Portishead's "Roads" ahead of the covers titled "Portishead - Roads") blended with MusicBrainz's score or a service row's score, which is 100 less 5 per place down that service's list and 5 per service ahead of it in the priority order, plus 5 for each further service that returned the same track. Before 2026-11 MusicBrainz was the only source, with Spotify and Apple Music hard-wired in for artists and tracks only when it returned fewer than three results. Rows hold still as sources answer (`stabilizeRows`): a row that stands for one already on screen keeps its display key (`_rowKey`, which keys the card) and its position, and rows new to the list follow in ranked order. Merges record the ids a row stands for (`_aliases`), so a MusicBrainz row that absorbs a shown service row takes over its card without a remount; the real `id` still changes (MusicBrainz wins identity), and `data-track-id` stays on it for the resolution scheduler. Re-ranking the whole list on every answer used to move every card, and covers faded out and back in (2026-11-01: slots changed at 1.0s, 1.8s, 7.3s and 8.0s; now 22 sampled slots, 0 changes). Covers for the results go through `getAlbumArt` in the background lane (see [album-art.md](album-art.md)); a superseded query's queued MusicBrainz requests leave the queue without using a slot (`createLimiter`'s `signal` option). Tests: `tests/renderer/search-catalog.test.js`, `tests/renderer/search-speed.test.js`, `tests/resolver/limiter-abort.test.js`.

### Artist images (`searchArtistImage`, optional)

A content resolver that can find a photo of an artist declares `capabilities.artistImage: true` and implements `searchArtistImage(artistName, config)`, which returns an image URL or `null`. It never throws for a miss, and returns `null` without a request when it lacks what it needs (Subsonic without a server). The URL goes into the persisted artist-image cache, so it must not carry credentials: the host refuses any URL with a credential-shaped query parameter (`looksLikeCredentialBearingUrl` in `discord-presence-logic.js`), which rules out a Subsonic `getCoverArt` URL.

**Who uses it.** `getArtistImage` (src/renderer/app.js; the pure part is `src/renderer/lib/artist-image-chain.js`) serves every artist photo: Home's Shuffleupagus suggestions, recommendations, related artists, Search, top artists, friends, chat cards and the artist page. First photo wins: Spotify (signed in), Apple Music (MusicKit configured), the user's *active* artistImage resolvers in their priority order (inactive ones are not asked: this runs for every artist on a page), Deezer's public artist search (no account; through the main-process proxy, like the album-art chain), Wikipedia via Wikidata when the caller passes the artist's MusicBrainz id (`getArtistImage(name, { mbid })`; no MusicBrainz lookup is made just for a photo), and Discogs when the user has a Discogs token (its search needs one). Each step is bounded at 8s. A miss is remembered for 6 hours when every step answered, and forgotten when the Spotify token changes. It used to ask only Spotify and Apple Music, so a user signed in to neither saw only placeholders outside the artist page (2026-10-27).

Implemented by Subsonic (`search3` for the artist, then the OpenSubsonic `artistImageUrl` or `getArtistInfo2`'s image, credential-free URLs only; Navidrome's `/share/img/` links qualify) and Amazon Music (the artists tab of the same `SpecSearchSeeMorePage` the album search uses — the photo comes from an Artist node whose name matches exactly after normalization, and a lookup queued past the step budget skips its page load so a page asking for 5–20 photos cannot starve track resolution; see [amazon-music.md](amazon-music.md), "Artist images"). Bandcamp is deliberately not: its public search answers 429 under load, and the track resolver shares that budget.

### Settings

`settings.requiresAuth` (boolean), `settings.authType` (`none`, `apikey`, `oauth`, `token`, `username`, `userpass` or `musickit` in the shipped plugins) and `settings.configurable`, a map of field key to `{ type, label, description?, default?, options? }`. Field types in use: `text`, `password`, `select` and `dynamic-select`. A `dynamic-select` gets its options from the plugin's `listModels(config)`, shows `fallbackOptions` until that succeeds, and with `allowCustom: true` renders a free-text input with suggestions (see Dynamic Model Selection above).

### Implementation functions

Each entry in `implementation` is materialized with `new Function('return ' + src)()` in the renderer, then bound so `this` is the resolver object (a `resolve` can call `this.search(...)`). Consequences:

- **Plugins are not sandboxed.** The code runs in the renderer with the same privileges as the app's own renderer code: `fetch`, `window` (including `window.electron.*` bridges such as `proxyFetch`), the DOM, and globals the app sets up. Install only plugins you trust.
- **Each function is isolated from the others.** There is no shared module scope, so a helper used by two functions must be defined inside each.
- Implementation keys that collide with resolver fields (`id`, `name`, `capabilities`, `config`, `__proto__` and similar) are skipped with a warning.

Common signatures, taken from the shipped plugins: `search(query, config)` returns an array of tracks; `resolve(artist, track, album, config)` returns one track or `null`; `play(track, config)` returns a truthy value on success (falsy makes `handlePlay` try the next source); `init(config)` and `cleanup()` run on load and unload. A track carries `id`, `title`, `artist`, `album`, `duration` (seconds), `sources: ['<resolverId>']`, the resolver's own identifier (`spotifyId`, `bandcampUrl`, `youtubeId`, `soundcloudId`, `appleMusicId`, ...) and any cross-cutting metadata such as `isrc` (see "Resolver Result Shape" in [playback.md](playback.md)). Meta-services implement the functions their capability names: `generate(prompt, config, listeningContext)`, `chat(messages, tools, config)`, `listModels(config)`, `searchArtistEvents(artistName, config)` and `searchArtist(artistName, config)`.

Practical rules: return `[]` or `null` instead of throwing on a miss; check a service's minimum query length before calling it; respect the service's rate limits (content resolvers other than Apple Music, Spotify and local files are wrapped by the shared resolver limiter automatically); and log enough to debug a failure.

### Where plugins load from, and installing one

At startup the main process (`resolvers-load-builtin`) reads the app's own `plugins/` directory (inside the ASAR in a packaged build) and `~/.parachord/plugins/` (marketplace downloads and user installs), keeping the newer version of each id and preferring the shipped copy on a tie. The renderer also carries a `FALLBACK_RESOLVERS` copy of every bundled plugin (the generated `src/renderer/lib/fallback-resolvers.generated.js` module, required by `src/renderer/app.js` and bundled into it) for when that load fails or misses one. The "Add from file" button in Settings → Plug-Ins installs an `.axe` from a file (`resolvers-pick-file` then `resolvers-install`, which writes it into `~/.parachord/plugins/`) and hot-loads it without a restart; the marketplace installs and updates plugins the same way. To contribute a plugin to everyone, add it to [Parachord/parachord-plugins](https://github.com/Parachord/parachord-plugins).
