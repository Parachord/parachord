## Playback

### Resolver System
- Resolvers provide playback, search, and metadata (Spotify, Apple Music, Amazon Music, SoundCloud, YouTube, Bandcamp, local files)
- `CANONICAL_RESOLVER_ORDER` (L1266): `['spotify', 'applemusic', 'amazonmusic', 'bandcamp', 'soundcloud', 'localfiles', 'youtube']`
- Each track has a `sources` object keyed by resolver ID — playback picks the highest-priority available source above the confidence floor
- Resolvers loaded into `loadedResolversRef` (L7756) with `.play()`, `.search()`, `.capabilities`

### Resolver Result Shape

Resolver `.search()` and `.resolve()` results spread into `track.sources[resolverId]` via `{ ...result, confidence }`. The shape is conventional rather than typed — fields a resolver populates show up as `track.sources[id].<field>`. The required fields are obvious from the resolver implementations: `id`, `title`, `artist`, `album`, `duration`. The interesting set is the **optional cross-cutting metadata** that downstream consumers walk for, regardless of which resolver populated it:

- **`isrc?: string`** — recording ISRC, normalized to upper-case + trimmed, format `[A-Z]{2}[A-Z0-9]{3}\d{7}`. Capture from every API response that exposes it; leave undefined for the rest. Currently populated by: Spotify (`external_ids.isrc` on `/v1/search`, `/v1/tracks/{id}`, `/v1/playlists/{id}/tracks` — parachord#893), Apple Music native MusicKit (`song.isrc`), local files (ID3 TSRC / Vorbis ISRC / MP4 atom via music-metadata's `common.isrc` — parachord#895). Bandcamp / SoundCloud / YouTube / iTunes Search API don't expose ISRC; leave undefined. **Downstream consumers** walk `track.sources[*].isrc` (with top-level `track.isrc` as fallback) via `window.pickTrackIsrc(track)` — currently used by the ISRC→MBID fallback in `resolveMbidForLove` tier 3 + `enrichTrackWithMbid` (parachord#888 + #894) and the achordion submit ISRC-only fallback (parachord#892). New consumers should reuse `pickTrackIsrc` rather than reading `track.isrc` directly so a Spotify-resolved track with no top-level ISRC still works.

- **`limitedPlayback?: boolean`**: the plugin's own forecast that its player will probably refuse this source or play only a preview of it. `handlePlay` ranks such sources after every source that isn't flagged (then resolver priority, then confidence; `compareCandidateSources` in `src/renderer/lib/playback-helpers.js`, tests in `tests/renderer/source-selection-order.test.js`); an explicitly preferred resolver still goes first. It never drops a source: with nothing else, a limited source still plays, and a refusal takes the usual failure path. SoundCloud sets it when the API's `access` is `preview` or `blocked`, which its widget plays in full 0 of 7 and 1 of 14 times (2026-11-02 sample), so a SoundCloud match that won't play doesn't hold up a track another service could play at once. Generic on purpose: any resolver can set it; nothing reads a service's own fields.

- **`streamQuality?: object`** — technical parameters of the stream the resolver delivers: `{ tier?, codec, container, bitrate (kbps), sampleRate (Hz), bitDepth?, channels?, origin: 'measured' | 'claimed' }`, all fields optional. `tier` is the resolver's own quality vocabulary when it has one (Amazon: SD/HD/Ultra HD). **Presence of the record IS the capability** — a resolver that can't know (Spotify Connect, MusicKit JS) attaches nothing and surfaces render exactly as before. Unlike `isrc`, this describes the *playing stream*, not the track: consumers MUST key it off the resolver actually playing via `window.pickStreamQuality(track, playingResolverId)` (root `stream-quality.js`, loaded by index.html, also `require`-able) — never "any source on the track", because a Spotify-played track with a localfiles source attached is streaming through Spotify. Display via `window.formatStreamQuality(q)` → `"Ultra HD · FLAC · 48.0 kHz · 24-bit · 1478 kbps"`. Currently populated by: localfiles (play-time parse, see "Stream quality HUD" under Local Files Library), amazonmusic (see "Stream quality capture" under the Amazon Music resolver — measured median bitrate + captured DASH manifest/init params, nothing fabricated), subsonic and bandcamp (measured bitrate only — the shared players' decoded-byte meter: `src/renderer/lib/stream-bitrate-meter.js` samples Chromium's non-standard `HTMLMediaElement.webkitAudioDecodedByteCount` against media time and keeps a running median of 2s windows; the shared element's `timeupdate` listener feeds it for every html5Stream resolver, and Bandcamp's in-page `bcState()` reports the same property off the embed's own `<audio>` through the `onStreamQuality` handler. Host code only — a resolver implements nothing, and a resolver whose API tags file properties (Subsonic's `suffix`/`bitRate`/`sampleRate`) still attaches nothing, because the server may transcode and a claimed record would render as if measured). **Do NOT add scan-time DB columns for it** — play-time parsing was chosen deliberately (works for every file day one, no migration/backfill window; see that section). A track played straight from a search result (a link, a chat link, the AI's play tool) has an array of resolver ids in `sources` and no keyed entry, so its record sits on the flat track, which is the source record there: read through `pickStreamQuality` and write through `withStreamQualityFacts`, never by turning that array into an object.

The principle generalizes: any cross-cutting metadata (ISRC today; potentially BPM, key, release year, etc. later) belongs on the source record so downstream consumers can walk sources and pick from any resolver that captured it. Resolver-specific identifiers (`spotifyId`, `appleMusicId`, `bandcampUrl`) stay on the source record for the resolver that owns them.

### Match Confidence + Selection Floor

Source selection is a **two-stage gate**: validate, then sort. Without the floor, a higher-priority resolver's wrong-artist match silently outranks a correct lower-priority result, because confidence is otherwise only a within-priority tiebreaker.

**Stage 1 — Validation.** `validateResolvedTrack(result, targetArtist, targetTitle)` (`sync-providers/confidence-scoring.js`, exposed to the renderer as `window.ConfidenceScoring`) returns true only when BOTH the artist and the title match the target. Single-axis matches — same title, different artist; or same artist, different title — fail. Each axis first tries containment after `normalizeStr` (lowercase + strip non-alphanumeric), then one narrow fallback:

- **Artist: the credited names** (`_artistsMatch`). Services join one credit differently: "Erykah Badu and The Alchemist", "Erykah Badu & The Alchemist", "Erykah Badu, The Alchemist", and stripping punctuation leaves a stray "and" or "feat" that defeats containment. So a credit is also split on `,`, `&`, ` and `, ` x `, and ` feat. ` / ` ft. ` / ` featuring ` (with or without the dot, optionally opening a bracket), each piece normalized, and the two credits match when every name on one side is credited on the other, in any order. Names compare exactly, so sharing one name of two isn't enough ("Simon & Garfunkel" vs "Simon & Schuster") and neither is sharing a word ("Paul Simon" vs "Simon & Garfunkel"). The word joins need a space on both sides, so "Little Feat", "Malcolm X" and "X Ambassadors" stay whole. A one-name credit can't pass this way unless containment already passed, so this only adds matches between credits of two or more names.
- **Title: a trailing bracketed credit** (`_titlesMatch`). With a trailing `(feat. ...)` / `[ft. ...]` / `(featuring ...)` removed from both sides, the rest must be **equal**, which is how "Song (feat. A)" meets "Song (ft. A)". Equality, not containment: "Hello (feat. A)" must not reach "Hello Goodbye". The bracket is required, because a bare "ft" or "feat" can be part of the title.

Other separators ("+", "/", "vs", "with", "×") are deliberately not joins yet: the live evidence didn't call for them, and each one is a change on both platforms. Add one when a real rejection shows it.

**Stage 2 — Scoring.** `calculateConfidence(track, result)` (same module; `Parachord` aliases it) returns:
- `1.0`: **identity tier** (2026-10): the original and the result carry the same ISRC (`pickIsrc`: top-level `isrc`, else any `sources[*].isrc`; normalised and shape-validated as `[A-Z]{2}[A-Z0-9]{3}\d{7}`) or the same recording MBID (`mbid` / `recordingMbid`, case-insensitive). Checked before any name comparison, so a "Various Artists / Track 1" tag on a self-hosted rip still matches when the ids agree; Spotify and Apple Music results carry ISRCs too. A missing, malformed or different id falls through to the name gate unchanged. `handlePlay`'s `findBestMatch` uses the same order when it picks among a resolver's search results: MBID, then ISRC, then the exact normalised name, then the contains passes. **Cross-platform invariant** with mobile's `ResolverScoring.kt`; mobile parity ticket: Parachord/parachord-mobile#402.
- `0.95` — both axes pass `validateResolvedTrack`
- `0.50` — single-axis match, or no match
- `1.0` (or whatever the resolver supplied ≥ 0.95) — direct-ID match (cached `spotifyId`/`appleMusicId`/etc), preserved as-is

**Stage 3 — Selection floor.** `MIN_CONFIDENCE_THRESHOLD = 0.6` (same module). The source-selection sort in `handlePlay` drops sources below this floor BEFORE the priority sort runs. A 0.50 source never reaches selection.

**Stage 4 — Priority + confidence sort.** Sources passing the floor sort by user-configured resolver priority; confidence is the within-priority tiebreaker.

**What `handlePlay` actually does at selection time.** For each resolver with a non-`noMatch` source on the track it re-scores the source with `confidenceForSource` against the track's own artist and title (a cached source from an older code path may lack a `confidence` field). The one exception is a local-files row with a `filePath` but no artist or title: it keeps its stored score (1.0 when none), because re-scoring a nameless row would return 0.50 and drop a file that is on disk. Then, in order: keep only resolvers in `activeResolvers`; apply the floor; drop sources on the per-result blocklist (`resolverBlocklistRef`, matched on resolver, normalized artist and title, and source id); sort with `track.preferredResolver` first (if set), then priority ascending, then confidence descending. The first survivor plays.

Worked example. Resolver order `[spotify, bandcamp]`, track "Yesterday" by The Beatles. Spotify's top hit is a different artist's "Yesterday" (0.50), Bandcamp's is the right recording (0.95). Without the floor Spotify wins on priority and plays the wrong song; with it, Spotify is dropped before the sort and Bandcamp plays. If both sources score 0.50, nothing survives and `handlePlay` shows the "No Enabled Source" dialog (or auto-skips in auto-advance and spinoff contexts, see `autoSkipIfAdvancing` below), after logging a per-candidate scorecard (`Source selection scorecard`) that covers floor drops, inactive resolvers and blocklisted sources alike.

**Per-resolver play buttons are a preference, not a bypass.** The resolver badges in the list views call `handlePlay({ ...track, preferredResolver: resolverId })`. That only moves the resolver to the front of the sort; a source that is disabled, below the floor or blocklisted still cannot play.

**Tests.** `tests/resolver/confidence-scoring.test.js` covers `normalizeStr` (case folding, punctuation, Unicode), `validateResolvedTrack` (both-axes containment, missing and empty inputs), `calculateConfidence` (0.95 both-match, 0.50 single-axis, direct-ID 1.0 preserved, a wrong-artist result rejected even when the resolver claims 1.0) and the 0.6 threshold. It mirrors Android's `ConfidenceScoringTest`. Its `ARTIST_CREDIT_VECTORS` table (`tests/helpers/artist-credit-vectors.js`) is the shared artist-credit fixture, which `tests/resolver/plugin-credit-match.test.js` also runs through the plugins that filter their own results: mobile must return the same score for every row, in both directions.

**History.** Tightened on 2026-05-04 (`acb167d`). Before that, `calculateConfidence` ignored the artist (title and duration only), so a same-titled track by another artist could score 0.85, and with no floor it outranked a correct lower-priority source. The fix required both axes, added the 0.6 floor before the priority sort, and replaced three hardcoded `confidence: 0.9` stamps in background resolution with scoring plus a skip-on-reject. Android applied the same tightening to `scoreConfidence` in parachord-mobile. Credit-aware artist matching came on 2026-11-04, after the live console showed correct recordings scored 0.50 only because of how their credits were joined ("Breezy" by "Erykah Badu and The Alchemist" against Bandcamp's "&" and Spotify's ","). Because `pickConfidentMatch` runs on the same score, sync's `resolveTracks` can now mint an id across these join styles as well, and that is the same recording, so it is the correct id.

**All resolution paths gate on `MIN_CONFIDENCE_THRESHOLD`** and skip the attach entirely (with a warn log) when a result fails — three background paths (normal resolver pipeline, rate-limited iTunes, per-track flush) plus five `calculateConfidence`-using sites (search-page `resolveRecording`, validation pipeline, missing-resolver flush, bandcamp-shortcut path, scheduler flush). All eight follow the same pattern: `const confidence = calculateConfidence(track, result); if (confidence < MIN_CONFIDENCE_THRESHOLD) skip-and-warn; else attach`. This prevents wrong-artist results from ever entering `track.sources` (and so from rendering pale resolver badges) and from polluting `track.album` / `track.albumArt` fallback fields.

**Badge dim logic is absolute (≥ 0.95 = full opacity), not relative-to-best.** `getBestSourceConfidence(sources)` (src/renderer/components/track-lists.js — moved there with its pre-component consumers in Track 2b slice 2; the 10 in-component badge call sites bind it via the require-back destructure in app.js) returns the constant `0.95` regardless of input. Each badge renders dimmed (opacity 0.6) when its confidence is strictly less than 0.95, full otherwise — `(source.confidence || 0) < bestConf ? 0.6 : 1`. Since the upstream `MIN_CONFIDENCE_THRESHOLD = 0.6` floor drops sub-floor results before they reach `track.sources`, in normal operation the only values present are 0.95 (fuzzy validated) and 1.0 (direct-ID), so nothing dims unless a resolver explicitly returns a non-standard sub-0.95 value. The function signature is preserved (takes `sources`, returns a number) so the 11 badge call sites compile unchanged; the argument is ignored. **Historical note:** the prior relative-to-best model dimmed a 0.95 fuzzy match whenever a sibling resolver had 1.0, which users read as "wrong" when the match was actually correct — flipped to absolute on 2026-05-08. Applied at all 11 badge call sites (TrackRow + 10 list-view variants).

**Cross-platform invariant.** `sync-providers/confidence-scoring.js` is the **canonical desktop module** (`normalizeStr` / `validateResolvedTrack` / `calculateConfidence` / `MIN_CONFIDENCE_THRESHOLD` / `pickConfidentMatch`); `tests/helpers/confidence-scoring.js` is now a thin **re-export** of it (was a parallel byte-copy — collapsed to a re-export so the two can't drift). app.js now consumes the module directly (`window.ConfidenceScoring` aliases — the three inline copies, one of which had already drifted, are gone); the Kotlin equivalents (`parachord-mobile/shared/.../resolver/ResolverModels.kt#scoreConfidence`, `ResolverScoring.kt#MIN_CONFIDENCE_THRESHOLD`) remain the other byte-identical copies of the *function bodies*. All must agree byte-for-byte on the gate semantics — drift on any platform produces inconsistent source selection between desktop and Android for the same track. Test cases at `tests/resolver/confidence-scoring.test.js` mirror Android's `ConfidenceScoringTest`.

**Sync hydration (`resolveTracks`) gates on the same floor (parachord#911 D-Legacy-1).** `sync-providers/spotify.js` and `sync-providers/applemusic.js` `resolveTracks` mint a provider ID for an ID-less playlist track via search. The legacy code ended candidate selection in an unguarded `|| items[0]`, minting the top hit's URI with no confidence floor when no exact match existed — writing a wrong-song URI (e.g. local "Intro" by The xx → "Intro" by Alt-J) that then stuck fleet-wide via provider-ID equality. Both now route candidates through `pickConfidentMatch(track, candidates)` (best `calculateConfidence` ≥ `MIN_CONFIDENCE_THRESHOLD`, else `null` → drop to `unresolved`). Apple Music additionally (D-Legacy-2): tries an **ISRC-exact catalog lookup first** (`GET /catalog/{storefront}/songs?filter[isrc]=`, authoritative — recording identity, matches mobile's `getCatalogSongIdByIsrc`) and is **storefront-aware** (`getUserStorefront` via `/me/storefront`, falling back to `us`) instead of hardcoding `/catalog/us/` — so desktop and mobile mint the *same* catalog id for a given (ISRC, storefront) and don't create permanent AM duplicates. Fixtures: `tests/sync/resolve-tracks-identity.test.js`.

**A no-match answer does not outlive the rules that produced it.** A scoring change (#1253 made correct multi-artist matches pass) leaves old answers behind: a `{ noMatch: true }` sentinel, written when a resolver returned nothing or a missing-resolver fill was rejected, or a missing key, written when the main fan-out rejected a result. Two things clear them, so no version stamp or migration is needed. `validateCachedSources` re-asks every resolver when a cached entry at least 24h old is resolved again, and compares real sources only (`sourcesChangedOnRecheck`; comparing raw keys read `{ a: noMatch }` against a fresh `{ a: real }` as unchanged and refreshed the timestamp, so a track kept viewed never recovered, past the 30-day persisted TTL). And a click never trusts them: handlePlay counts only `playableSourceIds`, so a row with nothing playable, including one carrying the UI's `__noMatchAll` marker, resolves on demand under the current rules. The re-check updates `trackSourcesCache` and the row, not `track.sources`, so a persisted sentinel can seed a new cache entry after a 7-day gap, which the next re-check clears again; it ages out at 30 days.

**Picking one result for a named track (`pickTrackMatch`, `sync-providers/track-match.js`).** A path that plays a named track (play-time resolve in `use-playback-engine.js`, `parachord://play`, the DJ tools) picks among a search's results in this order: exact recording MBID, exact ISRC, exact normalized artist + title, a name match that isn't another version (`isOtherVersion`), then any name match; no match returns `null`. A resolver that declares `capabilities.resolvePicks` (SoundCloud) skips this at play time and is asked through its own `resolve` instead (see [plugins.md](plugins.md)). In the exact tier a trailing remaster label on the result ("- 2016 Remaster", "- Remastered 2009", "(Remastered)", "[2011 Remaster]", `REMASTER_LABEL`) doesn't count against it unless the request names one too (#1304). Spotify labels remastered studio tracks while a live album or an outtakes set carries the bare title, so comparing raw titles picked Ramones' live "Judy Is a Punk" over the studio "Judy Is a Punk - 2016 Remaster" ranked above it. Mobile's `selectBestMatch` (`ResolverModels.kt`) has the same tiers and the same pattern (parachord-mobile#581); keep the two the same.

### handlePlay (L13213)
- Central async playback function; manages `playbackGenerationRef` to supersede stale requests
- Stops all competing audio (Spotify, Apple Music, browser, local, SoundCloud, YouTube, Bandcamp) before starting new track
- Retry logic for Spotify: if `.play()` fails, retries after 2s with fresh token, then falls back to next resolver

**Shared HTML5 audio element.** Local files, Subsonic and the html5/Widevine stream resolvers play through one `audioRef` element (SoundCloud doesn't: see "SoundCloud" below). `ensureSharedAudioElement()` attaches every listener the first time any of those paths creates it. Resolver-specific listeners (local-file network-share seek retry, each path's error dialog) key off the element's `src` — `local-audio:` / `blob:` / `http(s)` — not off `track.sources`. A track can carry a Subsonic source while a local file is playing; if the first session play created the element, the other path's listeners must still run. A new HTML5 resolver adds its branch inside that function, it does not attach its own listeners on create. The element's `timeupdate` listener also feeds the shared measured-bitrate meter (`lib/stream-bitrate-meter.js`) for html5Stream owners — the stream-quality record's bitrate, with no resolver code.

**An unresolved row plays when clicked.** A track with no sources goes through `handlePlay`'s on-demand resolve, in the priority lane (see "Resolver queue lanes"). The album page's track row used to play only rows that had already resolved and opened a Search for any other, so an album track could only be played once its row finished resolving behind the rest of the page (2026-11-01). On *Dig Me Out*, a click 2.4s after the page opened, with 41 row searches queued, had its own 3 searches done by +1.2s while the backlog drained until +9.0s.

**Failure-path auto-skip in auto-advance contexts.** Near the top of `handlePlay` is `autoSkipIfAdvancing(reason)` which all 7 failure paths (No Source Found, No Enabled Source, Local Playback Error ×2, SoundCloud's widget refusing a track with no other source, Track Re-resolved ×2: `play()` returned falsy, and `play()` threw) call before showing a dialog. Both Track Re-resolved dialogs name the resolver (`resolver.name`) and the thrown one includes `error.message`; a bare "Playback failed" sent a resolver author looking for a Parachord bug while his own `play()` was returning false. The helper returns true when `isAdvancingTrackRef.current || spinoffModeRef.current` — i.e. handleNext is in flight, or we're inside a spinoff/radio session. In that case it logs `⏭️ Auto-skip "X" — <reason>`, marks the track's queue entry status: 'error' (no-op for spinoff-pool tracks since they aren't in the queue), schedules another `handleNext` via `setTimeout(... 600)` (after the 500ms re-entrancy lock releases), and returns true so the caller skips the dialog. User-initiated single-track plays from outside spinoff/auto-advance still surface the dialog as before. This makes radio/spinoff sessions resilient: a single unplayable track gets silently passed over instead of stopping playback with a modal.

**A failure that stops on the track leaves it for Play to load again (#1295).** When `autoSkipIfAdvancing` returns false, it first calls `holdFailedTrack`, which (if this play is still the current generation) hands the track to `holdTrackForPlay`: the track goes in the playbar, paused, progress 0, with `trackNeedsExplicitStart` set, the same state a restored queue's first track is in. `handlePlayPause` checks that mark before any engine arm (and not while another track is loading) and starts the track through `handlePlay`, so its source is chosen again; `trackToHoldAfterFailure` (`lib/playback-helpers.js`) drops `_activeResolver`, `_streamOwner`, the Spotify and Apple Music fallback flags and the placeholder `status` first, and a single-source pick keeps its source. The same hold covers the paths with no dialog: the Amazon sign-in window closed without signing in, the last source of a fallback chain failing, and a failure on a track with no artist or title. The shared element's `error` listener holds the track it was loaded with before its dialog, since resuming a dead element reports playing over silence. Before this, the playbar kept the previous track (its engine already stopped by `handlePlay`'s teardown) or the failed one with no engine, and Play fell through to a stale engine, a bare Spotify resume of Spotify's own last track, or `if (!audioContext) return` (reproduced: "No Source Found", OK, Play did nothing). Every success path clears the mark, and an effect clears it whenever `isPlaying` turns true, so a later pause and resume never restarts a track. A failed resume starts the track from the beginning; desktop has no start-position option for `handlePlay` yet, unlike mobile (parachord-mobile#569), which resumes a stream that failed mid-song where it stopped.

**The end of the queue clears the track; Previous restarts after 3 s (#1319).** These follow the mobile apps' shared rules (parachord-mobile `QueueAdvancePolicy`). When `handleNext` finds nothing left to play (an empty queue, or only tracks marked `error`, with any spinoff pool already exhausted), `endOfQueue` stops playback and clears the current track: it goes to `playHistoryRef` first, then `isPlaying`, progress and the playback context reset and `currentTrack` becomes null, the same state as a fresh launch. It used to stop with the track still in the playbar. A Listen Along session waiting for the friend's next track returns before this and keeps its track; that isn't the end of the queue. Previous decides with `previousAction` (`lib/playback-helpers.js`): more than `PREVIOUS_RESTART_AFTER_SECONDS` (3) into the track, or with nothing in the history, it restarts the track (through `handlePlay`, so every engine starts over the same way); otherwise it goes back to the last track in the history, as before. With no current track, Previous plays the last track from the history, so the track the end of the queue cleared comes back. The playbar's Previous button stays enabled in that state while there is history. Desktop has no repeat yet; mobile's repeat-all wraps at this point instead (#1319 item 1).

**Shuffle is refused during a spinoff or Listen Along (#1319).** Every way of turning shuffle on or off on the current queue goes through `requestShuffle` in app.js: the playbar button, the app menu, MPRIS, `parachord://shuffle/{on|off}` and the DJ `shuffle` tool (in-app chat and MCP). It checks `shuffleAllowed` (`lib/playback-helpers.js`) and refuses with mobile's wording, "Shuffle isn't available during a spinoff or Listen Along" (a toast; the DJ tool returns it as the error, and a refused MPRIS request re-publishes the real state to the desktop widget). A spinoff plays its own pool in order and Listen Along plays the friend's tracks, so there is no queue of ours to shuffle. A change goes through `toggleShuffle`, which shuffles the queue or restores its order; the menu, MPRIS and the link used to flip the flag alone. Starting new playback with shuffle on (Play All with shuffle, Collection Radio) isn't a toggle and doesn't go through it.

**Listen Along follows the mobile apps' session rules (#1319).** The friend poll (`refreshPinnedFriends`, every 15 s during a session) and `handleNext`'s Listen Along branch follow parachord-mobile's `ListenAlongSession`; the pure pieces are in `lib/playback-helpers.js`.
- **Failed polls:** a poll that can't answer (`fetchFriendRecentTrack` returns no track) isn't "the friend stopped". `listenAlongFailedPollsRef` counts them, and `LISTEN_ALONG_FAILED_POLLS_LIMIT` (4) in a row, about a minute, end the session as if the friend had gone off air. An answer resets the count, and a hidden Last.fm profile counts as stopped at once. Failures used to be ignored, so a session could sit on a dead connection forever.
- **Waiting for the next poll:** when our song ends with nothing held and the friend's position unknown, `handleNext` sets `listenAlongWaitingRef` to `'song-ended'`. The next poll decides with `listenAlongWaitDecision`, whether or not the cached track changed: another track plays; the same track ends the session with "X hasn't moved on - resuming your queue". "Where the friend is" is `listenAlongLastPollTrackRef`, the last poll since our song started. It used to be the friend object's `cachedRecentTrack`, a snapshot taken when the session began, so the session stalled until the friend changed track again.
- **A track that can't play:** a friend's track that can't play here plays the track they've since moved on to, if one is held. Otherwise it waits with the track on screen (`'unplayable'`): a change plays, the same track keeps waiting. It used to skip into the queue, which ended the session with "hasn't moved on". While the session waits, Play does nothing.
- **A friend who stops while you've paused:** the session ends and your queue comes back paused, its first playable track on screen for Play (`holdNextQueueTrack` in the engine). It used to start playing by itself. A song of theirs that's playing still finishes first.

`endListenAlongToQueue` (app.js) is the one way a session ends into the queue. It clears `listenAlongFriendRef` at once, because its sync effect runs only after the next render and `handleNext` would otherwise run its Listen Along branch again.

**Offline, a failure stops on its track instead of skipping (#1297).** Offline, the next track fails the same way, so the auto-skip only ran the queue to its end, marking every track `status: 'error'`. Now, when the device reports no network (`isDeviceOffline(navigator)` in `lib/playback-helpers.js`: `navigator.onLine === false`), `handlePlay`'s `stopIfOffline` holds the track for Play (`holdFailedTrack`, above), advancing or not, and shows a toast: "Couldn't start playing. Check your connection and try again." (`OFFLINE_PLAY_MESSAGE`, the same as mobile's). `autoSkipIfAdvancing` asks it first, so every failure path is covered. The refused-play (`!success`) and thrown-error branches ask it before the Spotify retry, the Apple Music fallback ("Track not available on Apple Music"), and the forced re-resolve: offline that re-resolve reaches nothing, and a plugin that answers `null` on a network error would have its miss stored as a no-match marker. An embedded player's failure asks it before falling back to another source, and the shared element's stream arm (Subsonic and other direct streams) asks it before its skip. A local file is exempt (`needsNetwork: false`, and the listener's local arm doesn't ask): being offline is no reason a file failed, and the next local file plays. When the network is back, Play loads the track again. A failed request is deliberately not the signal: one service being down also rejects with "Failed to fetch" (see `lib/musicbrainz-fetch.js`), and the queue should still move past a source that can't play a track while online. The cost is that `navigator.onLine` can say true behind a dead network (a captive portal, a router with no uplink), and then the old skip still runs. Mobile's rule (`failedPlayAwaitsLoad`, parachord-mobile#572/#573) holds every failure but an embed's refusal; desktop keeps the skip online.

### Cross-Resolver Enrichment (Eager Gate + Slow Trickle)

When a track has a persisted source from one resolver but is missing slots for other enabled resolvers, `resolveTrack` (app.js ~L23598) has two complementary code paths for filling those missing slots. The split exists because of a real performance regression — a user with 376 local FLACs and Bandcamp enabled saw ~1 minute of pinwheel + constant CPU on every library navigation, because library-page navigation tagged 374 tracks at page-priority and the scheduler walked them all firing Bandcamp searches that returned 0 every time.

**Eager gate (foreground, in-handler):** If the persisted sources include a `localfiles` source with no `noMatch` flag and confidence ≥ 1.0, the missing-resolver fill is skipped entirely. Localfiles confidence-1.0 means "this file exists on disk and plays" — cross-resolver enrichment for it is speculative (the user's obscure Japanese reggae rip is unlikely to also be on Bandcamp) and the burst pattern destroys UX. **Scoped specifically to `localfiles`**, not all confidence-1.0 sources: a confidence-1.0 Spotify match (cached spotifyId from sync) DOES carry cross-platform intent — those still fire the eager fill, because finding the matching Apple Music ID is useful.

**Slow trickle (background, separate useEffect):** A setInterval-driven loop walks `collectionTracksRef.current` looking for tracks with at least one real source but missing some enabled non-localfiles resolver. Fires `resolveTrack(..., { forceEnrichment: true })` on at most one candidate every 10 seconds, ONLY while the window is unfocused (mirroring the "do work while user is away" principle from background sync). The `forceEnrichment` option flips the gate inside resolveTrack so the same fill code path runs, just stretched over hours instead of seconds. Per-session `enrichmentAttemptedRef: Set<trackId>` prevents re-trying within a launch; cross-launch dedup is handled by the existing `noMatch` sentinel persistence in `cache_track_sources`.

This split preserves the Achordion contribution path: local-only listeners playing tracks that DO exist on streaming services eventually get those mappings resolved (during background time) and submitted to Achordion's match cache. See [parachord#791](https://github.com/Parachord/parachord/issues/791) for the polish backlog (negative cache per-(resolver, artist), telemetry, integration with ResolutionScheduler vs the parallel setInterval).

**Critical placement note:** the slow-trickle useEffect references `cacheLoaded` in its dep array, so it MUST live AFTER the `useState` line that declares `cacheLoaded` (~L9066). It's intentionally separated from its logical sibling (the background-sync useEffect around L6177) for this reason. See the placement comment in app.js and the React useEffect TDZ note in [Common Patterns](../../CLAUDE.md#renderer-patterns).

### SoundCloud (the widget)

SoundCloud plays through SoundCloud's own embeddable widget (`w.soundcloud.com/player`) in a hidden iframe in the main window, driven by `src/renderer/lib/soundcloud-widget-player.js`. It is the first embedded-player resolver: the plugin declares `capabilities.embedPlayer` and names the `soundcloud-widget` adapter (`src/renderer/lib/embed-players.js`; the capability is described in [plugins.md](plugins.md)), and the host routes by that, not by the resolver id. The general contract for embedded-player resolvers (what a plugin and an adapter provide, what the host does) is "Embedded-player resolvers (drop-in contract)" in [plugins.md](plugins.md). The API path it replaced could not play full tracks: on a signed-in account `/tracks/{id}/stream` redirects to a 30-second preview, the full streams exist only as AAC HLS, and every full-stream download answered 403 "An active Artist Pro subscription is required" (live-verified 2026-11-02, on a fully `playable` track too). So the old code fell back to opening the track in the browser for almost everything. The widget needs no sign-in (resolution still uses the API and the sign-in). A soundcloud.com link doesn't need it either: without a token, `lookupUrl` asks SoundCloud's public oEmbed endpoint for the title, uploader, artwork and the track id (from the embed's `api.soundcloud.com/tracks/<id>`; a set or a user page names `/playlists/` or `/users/` and is not a track), with no duration or `access` (#1217). `createTrackFromMeta` keeps that link as the track's SoundCloud source, with title and artist on it so rescoring keeps it; without a sign-in it is the only SoundCloud source the track gets.

- **Its own protocol, not api.js.** The module speaks the widget's postMessage protocol (JSON `{method, value}`) directly instead of loading SoundCloud's `api.js`, so no third-party script runs in the renderer beside `window.electron`. Only messages from `https://w.soundcloud.com` whose source is our iframe count.
- **The iframe delegates `encrypted-media`.** Some tracks SoundCloud serves only encrypted, and without this the widget has nothing it can play and never starts (#1244, Ed Sheeran "Shape of You": `policy: MONETIZE`, the full track, no subscription). The app's permission handlers don't lift a frame's permissions policy. The success rates in the next point predate this, and DRM tracks may have been among the refusals. Go+ tracks are still previews.
- **Started means the position moved.** A track the widget may not embed loads its title and art, shows "Play another track", and never starts; with the preview check below, the API's `access` field predicts it well (a re-run of the 56-track sample on 2026-11-02: `playable` 35/35 played in full, `blocked` 1/14, `preview` 0/7; by group, independent uploads 19/20, remixes and mixes 15/16, major-label hits 2/20, most of the rest being 30-second previews). A `blocked` track can still play in full (Flume's did), so the widget, not the field, decides. `load()` rejects with reason `unplayable` when nothing has moved after 10 seconds. Moving is not enough either: for some tracks SoundCloud lets the widget play only a 30-second preview, which starts, fades out and fires `finish` while `getDuration` still reports the full length (#1211: Taylor Swift "Shake It Off", `policy: SNIP`, `duration` 30000 of `full_duration` 219246). So once the position moves, the player asks `getCurrentSound` and rejects with reason `preview` when `policy` is `SNIP` or `full_duration` exceeds `duration` by more than a second (`isPreviewSound`); no reply within 2 seconds counts as the whole track. The first run of the 56-track sample predates this check and counted 7 such previews as full plays. The engine treats that as a failed source: another enabled source for the track plays (the Spotify-fallback shape), else auto-skip in auto-advance contexts, else a toast with an "Open in SoundCloud" action (worded for a preview when that was the reason).
- **Transport.** `mediaElementFor(resolverId)` (app.js) returns an embedded player's HTMLMediaElement-shaped facade (looked up through `embedPlayerKind`) and the shared element for every `usesSharedAudio` resolver; seek, volume, mute and the MCP seek go through it. `handlePlayPause` has an embedded-player arm ahead of the shared-element arm, and the wall-clock progress fallback skips embedded players. Progress, duration, pause/play from the widget and `finish` (→ `handleNext`) arrive as callbacks, generation-checked against the play that started them.
- **Leaving a SoundCloud track halts it.** `stopAllLocalAudio` calls `stopAllEmbedPlayers()`; the widget's `stop()` blanks the iframe.
- **What needs credentials.** "Credentials" here means the API client ID and secret (env or Settings → Advanced) plus the user's OAuth sign-in, whose redirect is the auth-server callback.

  | What | Needs credentials? |
  |---|---|
  | Playing a track through the widget | No: only the track's soundcloud.com link (`soundcloudUrl`). Neither the widget nor oEmbed is sent a client ID. |
  | `lookupUrl` for a track link (dropped, pasted, opened) | No: with no token it uses oEmbed (above). With a token it uses the API's `/resolve`. |
  | `search` / `resolve`: finding a track by artist and title, i.e. adding SoundCloud as a source to library, playlist, queue or search results | Yes. SoundCloud has no public search, so with no token these return nothing ("SoundCloud: No token, skipping search"). |
  | `lookupPlaylist` for a set link (`/sets/…`) | Yes. |

  So with no credentials, SoundCloud plays only tracks that arrive carrying their SoundCloud link: a link the user drops, pastes or opens, or a track whose SoundCloud source was found earlier. Credentials don't change what the widget will play: a track it plays only as a preview, or not at all (see "Started means the position moved"), does so either way. Live-verified 2026-11-03 with a fresh profile and no sign-in: a dropped link looked up and played in full through the widget.

### Bandcamp (the embed)

Bandcamp plays through Bandcamp's own embedded player (`bandcamp.com/EmbeddedPlayer`) in a hidden iframe in the main window, with no extra window. It uses the embedded-player contract ([plugins.md](plugins.md)), adapter `bandcamp-embed`, so transport, volume, scrobbling and auto-advance are the same host code SoundCloud uses.

- **Driven from main, because the embed has no protocol.** SoundCloud's widget takes postMessage commands. Bandcamp's takes none, and the renderer can't reach into a cross-origin iframe, but the main process can through `WebFrameMain`. `main-process/ipc/bandcamp-embed.js` runs `main-process/bandcamp-embed-control.js` in the frame, polls it every 500ms and sends changes to `src/renderer/lib/bandcamp-embed-player.js`, which owns the iframe. Polling lives in main because nothing there slows down with the window.
- **The page is third party.** Only the main window's top frame may send these messages. Only a frame showing exactly the URL asked for is driven, and that URL must pass `isBandcampEmbedUrl`. Only fixed scripts run: an action picks one, and a value reaches it only as a checked number. What the page answers goes through `sanitizeEmbedState`. The old mini window's `console-message` bridge is gone; anything on the page could write to it.
- **Always the single-track URL.** `album=…/track=…` is a player for the album: it runs on into the album's next track by itself (live-verified 2026-11). `track=…` stops at the end. So the URL is built from the track id alone, in `main-process/bandcamp-embed-url.js`. When a source has no id (older cached sources, `lookupUrl` results), main finds it through the search API and then the page, but only for a track page on a `bandcamp.com` subdomain. A custom-domain or album page with no id is refused as `unplayable`.
- **`#big_play_button`, not `.embeddedplaybutton`.** The second is a 0x0 element, and clicking it loads no stream.
- **`ended` is latched in the page**, and the element moving to another stream counts as the end too, so a poll can't miss it and the queue can't stall.
- **`decodedBytes` is the stream-quality feed.** `bcState()` also reports the page's own `webkitAudioDecodedByteCount` (compressed audio bytes decoded so far); the adapter samples it against the reported position through `lib/stream-bitrate-meter.js` and emits `onStreamQuality` — the track's Bandcamp source record gets the measured bitrate. A number off the element like `t`/`dur`, sanitized like the rest of the state; the codec stays absent (nothing verified to read it from the page), so the hover shows the bitrate alone.
- **`stream: false` stays.** SoundCloud's manifest says `stream: true`, but the `.axe` is shared, and the mobile apps send anything with `stream: false` to the browser. Flipping it would route Bandcamp to a player they don't have. The embedded-player branch in `handlePlay` runs ahead of the `!resolver.capabilities.stream` one, so desktop never reaches the external prompt with this plugin.
- **The Buy link is unchanged**: the playbar still offers it for any track with a Bandcamp match, whichever source is playing.
- **A track the embed won't start** is a failed source like any other. Never clear cookies or swap profiles to change how the embed behaves.

### Spotify Playback (Connect only)
- **Spotify Connect is the only mode.** The resolver's `play` (`plugins-src/spotify/implementation.js`) drives an external Spotify client (desktop app, phone, speaker) through the REST API (`/v1/me/player` endpoints). There is no in-app Spotify player: the Web Playback SDK is not loaded anywhere. In-app playback via the SDK on the castlabs Widevine build is tracked in parachord#1077.
- **A track starts inside its album (#1300).** The plugin's `play` sends `{ context_uri: "spotify:album:<id>", offset: { uri: <track> } }`, not a bare `{ uris: [<track>] }`: Spotify's Android app (9.2, Nov 2026) answers a bare-uris play with 204 and then plays nothing, with `/v1/me/player` showing its device active and `item: null`, while the album form plays at once there and on every other client. The album id is the source record's `spotifyAlbumId` (search, `lookupUrl`, album and playlist lookups all set it), else one `GET /v1/tracks/{id}`, remembered per track for the run (`window._spotifyTrackAlbums`, at most 500). That lookup sends no `market`, so no relinked id comes back: the offset is always the track's own uri, and the play confirmation and both pollers keep matching it (Spotify's own relinking still shows up under `item.linked_from`, as before). A failed lookup, a track with no album, a non-track uri, or an album play Spotify refuses goes out as the bare track.
- **The poller times a check for the track's end (#1300).** Started inside its album, Spotify carries on into the album's next track when ours ends, instead of stopping (or, with Spotify's autoplay on, starting a recommendation). The main-process poller polls every 20 s, so on its own it would let that track play for up to 20 s. When a poll finds our track playing and its end comes before the next regular poll, the poller sets one extra poll 1.5 s before the end (`endCheckDelayMs` in `spotify-startup-grace.js`), inside the 2 s near-end window, which advances to the queue's next track. Each poll replaces the check, so a pause clears it and a seek moves it at the next poll (a seek forward between polls can still let the album's next track start; the mismatch then advances). A first mismatch while `pollCount <= 2` is confirmed 2 s later rather than at the next regular poll. At the end of the queue, `handleNext` pauses Spotify before it finds the queue empty, so Spotify doesn't run on into the album. A poll that answers after the poller stopped or moved to another track does nothing, so overlapping polls don't advance twice. Every main-process Spotify request (the polls, recovery, and the pause on quit) has a timeout: 5 s for the polls (`SPOTIFY_API_TIMEOUT_MS`), 3 s for the pause on quit. A request on a dead connection would otherwise hang for minutes instead of failing, so a hung poll never counted toward recovery and a hung pause held the app open. A missed end check is still caught by the next regular poll, which sees the album's next track and advances.
- `streamingPlaybackActiveRef.current = true` is not a Spotify mode. It is set whenever any resolver with `capabilities.stream` starts playback, so browser-extension playback events are ignored while a streaming resolver owns playback.

- **Spotify needs Premium, through the app owner.** Every Parachord Spotify sign-in uses the person's own Development Mode app (BYOK), and since February 2026 Spotify runs a Development Mode app only while its **owner** has Premium (a lapse stops the whole app: search, sync and playback, not only play). The Settings setup text says so. So there is no "connected but Free" Spotify to handle, and Spotify has no entry in "Playback limits" below. A Free account added as a user on someone else's app is the one gap; Spotify's player endpoints refuse it with 403 `PREMIUM_REQUIRED`, which the plugin returns as a plain `false`. If Spotify ever comes back to playback limits (an extended-quota app that Free accounts can use), note that `/v1/me` no longer returns `product` to Development Mode apps, so the plan would have to be learned from that refusal.

### Playback limits (resolvers the account's plan can't play)

A resolver can be set up but unable to play on the account's plan: Amazon off Music Unlimited (#1220, details in [amazon-music.md](amazon-music.md) "Plan gate"), and any future service with a tier that can search but not play on demand. Such a resolver stays in `activeResolvers` for what it still does (search, album search, artist photos, links, playlist sync), but is left out of playback. One map decides it: `playbackLimits` in app.js, `{ [resolverId]: { blocked, planKey, label, message, searchesHeldBack } }`, built by per-service mappers in `src/renderer/lib/playback-limits.js` (`amazonPlaybackLimit(status)` today; a new service is one more mapper and one more map entry). From it: `planBlockedResolverIds` and `playbackResolvers` (`activeResolvers` minus the blocked ids), which feed the engine's `activeResolversRef` (selection, fallbacks), every source-icon filter (the app.js badge lists, the playbar picker, the Search/Artist/playlist/Collection pages) and the Settings grid (no priority number, shown after the numbered resolvers and before the inactive ones, not draggable; display only, `resolverOrder` keeps the slot); the tile's `statusLabel`/`statusTitle` (`tileStatus`) and each panel's explanation (`limitMessage`). **Upgrades:** an effect over the map remembers each resolver's last state in `localStorage` (`playback_limit_blocked:<id>`, across restarts) and, on blocked → playable, calls `clearResolverMisses(id)` when the limit says `searchesHeldBack` (Amazon: its searches answered not-ready while blocked, leaving fresh timestamps with no result; a service whose searches run on every plan needs none). **The play-time refusal** is shared: a resolver's play that fails with `reason: 'plan-ineligible'` (Amazon's widevine manifest, or any plugin's `play()`, see [plugins.md](plugins.md) "Plans that can't play on demand") goes through `handlePlanRefusal` in use-playback-engine.js, which reports it (`window.__parachordNotePlanRefusal(id, planKey)` records the plan and may return the wording; null means the refusal's own message is shown), plays another enabled source (a toast explains once per resolver per session) or shows the message, and drops a superseded play's refusal. A service whose plan can only be learned from playback would add a matching "a play started" report next to it.

### Apple Music

Apple Music has two playback backends, tried in this order by the resolver's `play` (`plugins-src/applemusic/implementation.js`):

1. **Native MusicKit (macOS).** A Swift helper app (`native/musickit-helper/`, driven from `musickit-bridge.js` over stdin/stdout JSON, macOS only) uses `ApplicationMusicPlayer` and the system's Apple Music sign-in, so it needs no developer token. Its own README lists the commands.
2. **MusicKit JS (every platform).** `musickit-web.js` loads Apple's MusicKit JS in the renderer and plays through the castlabs Widevine CDM (see [platform.md](platform.md)). It needs a developer token. Apple's licence server accepts only a production VMP-signed build, and the stream is 256 kbps AAC.

**Developer token.** `main.js` generates the MusicKit JWT at startup (ES256, signed with Node's `crypto`, 180-day expiry) from the `AuthKey_<keyId>.p8` key it finds in `resources/keys/` (packaged as `keys/`). The renderer reads it through the `config-get` IPC (`MUSICKIT_DEVELOPER_TOKEN`), which returns, in order, the `MUSICKIT_DEVELOPER_TOKEN` environment variable, the generated token, or a token the user saved in Settings (`applemusic_developer_token`), skipping any that has expired (`main-process/musickit-token.js`; it logs each skipped one once). An expired environment token also doesn't stop the startup generation. With none of these, MusicKit JS cannot be configured. Every renderer caller goes through `getMusicKitDeveloperToken()`. It uses the Settings copy in `localStorage` (`musickit_developer_token`) first while it hasn't expired, as callers always have (the user's Apple Music sign-in was made with it), and otherwise asks `config-get`. Callers used to use the saved copy even after it expired, while a fresh generated one went unused, and MusicKit refused it with "Initialized with an expired token": search, previews and the web player stopped, while native playback (no token) carried on. The renderer checks expiry with the same `main-process/musickit-token.js`, which esbuild bundles (it decodes with `atob` where there's no `Buffer`). The Settings token and an `.env` token expire within six months of being made; a generated one is made fresh at every launch.

**Search and lookups.** `window.appleMusicSearchWithMusicKit` tries native MusicKit, then MusicKit JS, then the unauthenticated iTunes Search API. The plugin implements `lookupUrl`, `lookupAlbum` and `lookupPlaylist`; playlist lookup goes through `window.appleMusicLookupPlaylist`, a MusicKit JS catalog call that returns nothing when MusicKit JS is not configured.

**Catalog throttle.** Every native catalog call goes through `window.nativeMusicKitLimiter` (`createLimiter` from `resolver-limiter.js`: 3 concurrent, 150 ms minimum gap, an 8-second cooldown after 3 consecutive throttle errors such as a 429 or `MusicDataRequest` failure). Apple's catalog throttle is per token and spills across endpoints, so an unthrottled search fan-out also breaks playback.

### Resolver queue lanes

Track resolution is what has to load fastest, and a play click most of all. The three queues resolver searches wait in, the shared `globalResolverLimiter` (Bandcamp, SoundCloud, YouTube, Amazon), `nativeMusicKitLimiter` and `iTunesRateLimiter` (Apple Music resolves through iTunes whenever MusicKit can't answer), have lanes:

- **priority**, the front of the foreground queue: the play path's on-demand resolve in `handlePlay` (both passes pass `config.__lane: 'priority'`);
- **foreground**: track resolution, i.e. rows on screen, the queue, and Search's own service searches;
- **background**: covers, which wait behind all of it (`getAlbumArtFromResolvers` passes `searchResolvers(..., { lane: 'background' })`, and the art pipeline's iTunes calls pass `{ background: true }`).

A caller picks the lane through the config it hands `resolver.search`: `laneRunOptions(config)` (`resolver-limiter.js`) maps `config.__lane` to the limiter's run options, and the wrap passes them, so `resolve()`'s internal `this.search()` calls inherit the lane. Apple Music's plugin passes its caller's lane on to the host hook (`appleMusicSearchWithMusicKit(..., { lane })`) and to its iTunes fallback; a host without lanes ignores the argument. Before 2026-11-01 nothing used the lanes: opening an album queued 42 searches at once, a request behind them waited 7.5s, and each cover lookup that reached iTunes held up Apple Music resolution by 1.2s. Tests: `tests/resolver/resolver-lanes.test.js`.

**Sync.** `sync-providers/applemusic.js` is the playlist and library sync provider (ISRC-first and storefront-aware track resolution, the PUT-then-POST degrade for playlist writes). See [sync.md](sync.md).

### Volume Management
- `volumeRef` (L6673): Current playback volume (0–100%). Always use the ref in async/event code to avoid stale closures
- `preMuteVolumeRef` (L4984): Stores pre-mute volume for unmute restore
- `resolverVolumeOffsets` (L5002): Per-resolver dB adjustments (Spotify 0dB, Bandcamp -3dB, YouTube -6dB)
- `trackVolumeAdjustments` (L5013): Per-track dB offset map
- `getEffectiveVolume()` (L7867): Combines base volume + resolver offset + track offset
- Spotify volume API calls are debounced via `spotifyVolumeTimeoutRef`

## Spotify Device Handling

All of this is the Spotify plugin's `play` (`plugins-src/spotify/implementation.js`); the renderer has no device code of its own.

### Device Discovery
- `GET /v1/me/player/devices`. No devices: `play` returns `false` (logged as "No Spotify devices found"), and the engine treats it like any refused play.
- Restricted devices (`is_restricted`, which can't be controlled remotely) are dropped, unless every device is restricted.

### Device Selection
The first match wins, in this order: a `Computer`, a `Smartphone`, a `Speaker`, the active device whose name doesn't contain "web", any device whose name doesn't contain "web", the first device. So an inactive computer is picked over an active phone or speaker. There is no device picker and no remembered device: an older renderer-side path (`playOnSpotifyConnect`, with a picker dialog and a `preferred_spotify_device_id` setting) had no caller after January 2026 and was removed in November 2026.

### Device Wake-up
- An inactive device gets `PUT /v1/me/player` with `{ device_ids: [id], play: true }`, then a 1000 ms wait, before the play request goes to `PUT /v1/me/player/play?device_id=`.
- The play is then confirmed by polling `/v1/me/player`; if the track hasn't started after 5 s, play is sent once more (parachord#985), and the main-process poller's startup grace covers a device that is slower still.
