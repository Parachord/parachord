## Now Playing broadcast: Discord, MPRIS, OS media session

Three feeds publish the current track outside the app, all fed from the same renderer effects (app.js, the cluster after the `handlePlay` region): **MPRIS** (`mpris-player.js`, Linux D-Bus — media keys + KDE/GNOME widgets, plus the inbound control channel back to the renderer), **`navigator.mediaSession`** (macOS Control Center / Windows SMTC — Chromium registers the OS session but publishes no `MediaMetadata` unless we set it, which is why the widget used to read "Parachord Desktop"), and **Discord Rich Presence**. Only Discord is opt-in (Settings → General → Discord Presence). On Linux, Chromium's OS media integration is disabled process-wide (the `disable-features` switch at the top of main.js — its MPRIS entry materialized next to the native player for ANY renderer audio, and the feature trio is the only thing that kills it), so the mediaSession feed is Linux-skipped and the native MPRIS player is the single surface; on macOS/Windows the mediaSession feed drives SMTC / Control Center.

### Discord Rich Presence

**The renderer never touches Discord.** It reports the toggle, the playing snapshot, and the seek position over ordinary `window.electron.discordPresence.*` IPC; the main process owns the socket, the Application id, and the reconnect schedule. Dependency is `@xhayper/discord-rpc` (a maintained fork of discordjs/RPC; its IPC transport probes `discord-ipc-0…9` on Windows pipes and the `XDG_RUNTIME_DIR`/`/tmp` unix sockets, snap paths included — chosen over `@xmcl/discord-rpc`, which nested-pinned undici 6.0.1 with open high-severity advisories). Its `connect()` resolves only when READY lands, and its `request()` **throws** when called while not connected — the manager never assumes otherwise.

**The Discord Application id is the whole feature.** The headline ("Listening to Parachord") and the fallback artwork come from the registered Discord application the id points at — they are not text we send. Shipped id: `1561699064683167862` (`DEFAULT_DISCORD_CLIENT_ID` in `discord-presence-logic.js`); resolution order is `DISCORD_CLIENT_ID` (`.env`, for a fork or dev build) → that constant. The id is **public, not a secret** — it is in the binary regardless, and local RPC needs no client secret, OAuth, redirect URI or interactions endpoint. There is deliberately **no in-app field** for it: the id names the *application*, not the user, and a text box only manufactures an otherwise-unreachable "Discord rejected the id" state for a user to shoot themselves in. A refused id (close code 4000) marks the connection `blocked` — retrying a bad id is pure waste — and only a toggle flip (or a restart) clears it, which is correct because the id can only change in a new build.

**The application's art assets: exactly one, key `parachord`** (the 1024×1024 logo, registered as a Rich Presence asset). `PRESENCE_ART_ASSET_KEY` sends it as `assets.large_image` whenever a track has no cover Discord is allowed to fetch, so the fallback is the logo and not whatever the client feels like drawing. **There are no small-image assets**, and nothing references one: `assets.small_image` must name a registered asset key (unlike `large_image`, which also takes a URL), so a reference to a missing key would be dead config — and there is no paused state left to mark anyway.

**Payload rules that are not obvious and are enforced in the logic module** (Discord rejects the whole `SET_ACTIVITY` otherwise, and a rejected payload looks like "the toggle does nothing"):
- `details`/`state` are 2–128 chars — sub-2-char lines are dropped, never padded; over-long is clamped code-point-wise with an ellipsis. **Three slots, one fact each:** `details` = title, `state` = artist, `assets.large_text` = album. Joining the album onto `state` printed it twice, because the client renders the image hover text as its own line under the card ("Clearwater / Sigur Rós — ( ) / ( )"). Nothing repeats: an empty artist slot falls back to the album and the hover text is then dropped, and an album equal to the title gets no hover text.
- `type` may only be Playing (0), Listening (2), Watching (3), Competing (5). We send Listening; if a client rejects it the manager retries once with the field omitted and remembers for the session.
- **The activity is public**: everyone who can see the user's Discord profile sees the payload. So a cover URL is only sent when it is https, has no userinfo, and has **no credential-shaped query parameter** (`isFetchablePresenceImageUrl` + `looksLikeCredentialBearingUrl`): Plex puts `X-Plex-Token` in the query and Subsonic/OpenSubsonic authenticates with the `u` + `t` (token) + `s` (salt) tuple plus `sig`, and handing one of those to Discord hands it to every viewer. Detection is by parameter *name* (substring matches on token/key/sig/auth/session/… plus the exact single letters Subsonic uses); a refused URL costs nothing but the `parachord` fallback. A token embedded in a path segment is not detected — documented, not solved.
- `file://`, `data:`, `blob:`, `local-audio://` and embedded-art cache paths are filtered out at build time too — sending them renders a broken image tile where the application artwork looked fine.
- **Only a playing track has a presence.** `buildDiscordActivity` returns null for a paused or stopped track and the caller clears the activity; resume rebuilds it from the current position. Freezing the clock instead (a paused payload carrying `timestamps: {}`, which a live client confirmed does replace a stored start) was more machinery than the feature is worth, and a paused card with a stopped counter was ambiguous to read. `timestamps.start` is unix **seconds** — Discord echoes it back in ms, which is the sanity check that we sent the right unit — and elapsed is computed client-side as `now - start`, which is why a seek must re-push the position or "listening for" keeps counting from before the drag. A known track duration becomes `timestamps.end` (only when it exceeds the position), which Discord renders as a progress bar instead of elapsed-only.
- **`SET_ACTIVITY` is sent as a raw `client.request`, not through the library's `user.setActivity` helper,** for the first attempt *and* the type-fallback retry (one `sendTo` path — mixing them would silently strip the nested objects on the retry). The helper rebuilds `timestamps`/`assets` from flat `startTimestamp`/`largeImageKey` inputs and feeds a `Date` through `getTime()`, which is ms where the protocol wants seconds, and it has no way to say "no activity", which the paused/stopped clear needs. The builder emits the RPC-shaped activity (nested `timestamps` / `assets`) and it goes through verbatim. Flat SDK keys handed to the IPC frame are ignored, which shows up as images and timestamps silently missing.
- **A clear is never sent when there is nothing to clear** (`payload` and `lastPayload` both null): a connection that comes up while paused, or a reconnect while paused, spends zero round trips. Discord accepts both clear forms (`{pid, activity: null}` and a bare `{pid}`), verified live.

**Renderer pushes one combined snapshot** (`updateState({ track, status, positionSeconds, durationSeconds })`) rather than three granular calls: granular pushes let main publish an activity built from the new title and the *old* position, i.e. a visibly wrong elapsed time for a frame. The effect keys on the **payload fields** (`discordNowPlayingKey`: title/artist/album/art/duration + isPlaying — duration in the key so a late duration (Amazon's play-time repair) updates the bar), not `currentTrack` identity. `currentTrack.duration` is **seconds** (same units as `progressRef` — the progress interpolation and the scrobbler's <30s floor compare them directly); `durationSeconds` is passed through undivided (a `/1000` here made a 251s track arrive as 0.251s, dropping `timestamps.end` at/below the start so the bar never showed) — the track object churns several times per play (art and stream-quality backfills) and each identity churn re-fires an effect whose computed start may round to a different second, re-sends the payload dedupe cannot see. Granular channels still exist for the seek path — where the re-anchor push lives in the 1s-after-drag settle callback, NOT per slider tick: the range input fires onChange continuously during a drag and every position computes a different activity start, so the payload dedupe never suppresses and a per-tick push is a burst of SET_ACTIVITYs (the push is also dropped if the track changed inside the 1s window — the change carried its own position). The manager sends at most one `SET_ACTIVITY` per distinct payload (equality guard), last-write-wins while one is in flight, and **rate-floors sends to one per 4s with a trailing send of the newest state**: Discord silently DROPS over-limit activity updates (a dropped update leaves the stale track showing), and a scripted run of quick track changes sent 7 in 14s — past the per-client limit. The type-fallback retry (one type-less resend when Discord rejects `type: 2`) keys on the payload-rejection error code (an ERROR reply's `data.code` 4000, INVALID_PAYLOAD) — any other send failure must NOT downgrade the session, or one transient socket error permanently turns "Listening to Parachord" into "Playing Parachord".

**Connection lifecycle** (`discord-presence.js`, unit-tested against a fake `Client` that models the library's real timing): **the library's `connect()` resolves when the socket opens, not on Discord's READY** — `user` only exists after READY, and a refused Application id produces no READY at all, it answers the handshake with a CLOSE frame carrying code 4000. So the manager waits for READY behind its own 8s deadline (`HANDSHAKE_TIMEOUT_MS`) and treats the opened socket as `connecting`, not connected. Believing the socket is what made a ticked checkbox do nothing: status said `connected` while every publish was dropped for want of a session, and an invalid id looked healthy forever. Drop detection watches `transport.on('close')` rather than the library's `disconnected` event, because the CLOSE frame is the only thing carrying a code (a refused or revoked id mid-session → `blocked`, no retry storm; an ordinary Discord quit arrives as the bare string `"Closed by Discord"`, which is why the handler accepts a non-object reason).

No auto-reconnect in the library, so the manager owns the rest: exponential backoff 5s→5min, deterministic (testable), reset on success; every publish is fire-and-forget with a catch because the library's `request()` only rejects pending calls when the socket closes, so a wedged socket must never stall playback or leak unhandled rejections; a fresh `Client` per attempt (its `connect()` stacks `once('connected')` listeners) and a failed attempt's transport is explicitly closed so retries cannot leak sockets; **`connect()` re-checks `enabled`/`disposed` after the handshake await before promoting the candidate** — the candidate is invisible to `teardown()` while connecting, so without the re-check a toggle-off during the handshake window would promote the connection afterwards and publish the track the user just turned off (the candidate is discarded instead; nothing was ever SET on it); after any reconnect the manager re-publishes **its own** current state, since the renderer will not re-push when Discord restarts. The presence never keeps the process alive (retry and handshake timers are `unref`d) and `will-quit` clears the activity.

**Persistence:** `discord_presence_enabled` is the only key this feature writes, and **main writes it** (like `media-key-handling`) — the renderer reads it back through `discordPresence.getStatus()`, so there is one source of truth for "is this on". It is in `ALLOWED_STORE_KEYS`; the Application id is not persisted at all (see above). The settings UI renders `statusOverride || status` from main with the `DISCORD_PRESENCE_STATUS_LABELS` map, and re-reads it every 3s **only while Settings → General is open** (the handshake resolves after the click returns, and Discord can start or close while the row is visible — one read at click time strands the label on "Connecting…"). A configuration problem always outranks "Discord is not running" in the copy — sending a user to start Discord when their id was refused wastes their time.

**Desktop-only: do not file a mobile parity ticket for this.** Discord Rich Presence is a local desktop IPC socket; parachord-mobile has no equivalent surface. The shared invariants (renderer-never-talks-to-Discord, public-https-only art, seconds timestamps) are single-platform by construction.
